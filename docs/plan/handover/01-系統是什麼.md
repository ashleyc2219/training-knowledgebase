# 01 系統是什麼

> 讀這篇不需要看程式。目的是讓你在腦中先有一張「它在幹嘛」的圖。

---

## 一句話

**Training Knowledge Base** 是一套「會自己長知識的教學庫」：它從產品的使用者回報和改版紀錄裡找出「哪裡缺教學、哪篇教學不好用」，用 AI 自動寫或改教學，再發布到一個公開網站給使用者看。

---

## 它解決什麼問題

想像一個產品的客服／支援團隊：

- 使用者一直開同樣的工單（「找不到匯出按鈕」開了五次）→ 代表缺一篇教學。
- 教學寫好了，但讀者評分很低，留言說「第三步講不清楚」→ 代表那一步要改。
- 產品改版把「匯出」改名成「下載」→ 所有提到「匯出」的教學步驟都過時了。
- 功能被移除了 → 教學該退役，讀者要被導去替代的教學。

以前這些都要人盯著做。這套系統把它變成三條**固定**的自動流程。

---

## 三條流程（整個系統的骨幹）

| 流程名稱 | 什麼時候跑 | 輸入 | 做什麼 | 產出 |
|---|---|---|---|---|
| **ticket-analysis**（工單分析） | 每收到一張工單 | 一張 GitHub Issue（或手動匯入的工單） | 把相似的工單分成一群；同一群在 14 天內累積到 **5 張**就判定是「知識缺口」，替它取名、寫一篇新教學 | 一篇**未發布**的教學第 1 版（或「已有教學，維持不動」） |
| **feedback-review**（回饋檢視） | 每天 UTC 00:30 自動跑 | 教學頁上讀者留下的評分與留言 | 找出「平均分低於 3.5、且至少 10 則回饋、同一類抱怨至少 5 則」的教學，**只改被抱怨的那幾步**；同時把重複出現的抱怨整理成「寫作規則」候選 | 改好的新版本（整批發布）＋ 候選規則 |
| **release-update**（改版更新） | 每收到一筆產品改版 | 一筆 Release（改名／變更／移除某功能） | 找出提到該功能的教學步驟，**只改那幾步**、其他字一個都不動；功能被移除就把教學退役並指向後繼 | 改好的新版本，或退役的教學 |

三條流程的共同原則：

- **只改該改的**：改寫永遠只動「命中」的步驟，其餘步驟逐字保留（有測試逐 byte 比對）。
- **同一件事只做一次**：同一個事件重送幾次都只處理一次（`operation_id` 永久去重）。
- **失敗就整個失敗，不留一半**：多篇教學一起發布時，有一篇失敗整批都不公開（設計決策 F49）。
- **AI 的輸出一定經過驗證**：模型回的 JSON 要符合 schema，引用的步驟要真的存在，不合就重來一次或失敗，絕不硬塞。

## 資料從哪來、到哪去

```
[來源]                     [接入層]                    [三條流程]              [儲存]              [公開]
GitHub Issue ──webhook──┐
GitHub PR ────webhook──┼─▶ 驗簽 → 正規化 → 去重 ──▶ ticket-analysis ──┐
Discord/Email/Changelog ┘   （Rote：先重放舊做法，        release-update ───┼─▶ DynamoDB（一張表）
                              沒有才問 AI）             feedback-review ──┘   S3 私有區（tutorials/ operations/）
教學頁的評分 widget ──下載檔──▶ import Lambda ─────────────────────────────▶ S3 公開區（site/）──▶ 靜態網站
```

- **接入層**負責把五花八門的來源整理成固定格式。它有個叫 **Rote** 的機制：同樣結構的事件第二次來，直接重放上次驗證過的處理步驟，不再問 AI（省錢、穩定）。
- **儲存**只有一張 DynamoDB 表 ＋ 一個 S3 bucket。十種資料（教學、版本、步驟、功能、工單、改版、回饋、瀏覽、規則、處理程序）全部放同一張表，靠主鍵前綴區分。
- **公開網站**是 S3 靜態網站：只有 `site/` 前綴是公開的，其他全部私有。

## 教學的一生

```
缺口出現 ──▶ 第 1 版（未發布）──▶ 發布（current_version 指向它）──▶ 讀者評分
                                                                      │
                     ┌────────── 低分 → feedback-review 改幾步 ◀───────┘
                     ▼
              第 2 版（未發布）──▶ 發布 ──▶ ... ──▶ 功能移除 → 退役（頁面留著、標示已退役、指向後繼）
```

- 每一版都是**新的**，舊版永遠不改（已發布的頁面是不可覆寫的）。
- 「發布」＝把 `current_version` 切到新版 ＋ 把新版的 HTML 寫進 `site/`。這兩件事沒辦法做成一個交易，所以多篇同時發布時理論上會有幾秒鐘「半新半舊」。Demo 不用在意，07 有紀錄。

## AI 在哪裡被用到

只有一個模組（`writing/`）可以呼叫 AWS Bedrock，兩種模型：

| 模型 | 用途 |
|---|---|
| Titan Embeddings（把文字變成 1024 個數字） | 工單分群、判斷改版提到的功能是哪一個 |
| Claude（寫字） | 替知識缺口取名、寫教學、改寫步驟、判斷回饋屬於哪一類、提出寫作規則 |

**現況：帳號還沒申請模型使用權**，所以上面這些步驟現在都會失敗——這是 05 的第 1 項，也是唯一真正卡住的事。不需要模型的路徑（例如「同一群工單還不到 5 張」、「功能被移除 → 退役」）已經在 AWS 上真的跑通。

---

## 現在還不能動的東西

只有一件：**AI 模型（Bedrock）還沒開通**。文件和程式碼裡會看到 `O5`、`BLOCKED` 這些字，指的就是它。

其他地方看到的 `O1`～`O7`、「gate」、「核定」是設計文件留下的檢查點代號；為了 Demo 都已經處理好（詳見 07 最後一節），你不用管。

## 名詞小抄

| 名詞 | 白話 |
|---|---|
| **Tutorial／TutorialVersion** | 一篇教學（用英文短名 `slug` 識別，例如 `prepare-meeting`）／它的某一個版本（`prepare-meeting@v2`） |
| **Feature（功能）** | 產品的一個功能，例如「準備會議」 |
| **Ticket（工單）／Release（改版）** | 使用者回報的問題／產品改版的一筆紀錄 |
| **Feedback／View** | 讀者在教學頁的評分留言／讀者看過教學的紀錄 |
| **CREATE／KEEP／UPDATE／REFINE／RETIRE** | 五種對教學的動作：新建／不動／因改版改幾步／因低分改幾步／退役 |
| **Rote** | 接入層的「重放舊做法」機制：先找完全一樣的、再找相似的，都沒有才問 AI |
| **PROC** | Rote 記住的一組「驗證過可重複用的處理步驟」 |
| **operation／ledger** | 一次可追溯的處理單位／記錄每個 operation 狀態的表 |
| **operation_id** | 同一個事件不管重送幾次都算出同一個 ID，靠它去重 |
| **pipeline／state machine** | 一條固定流程／AWS Step Functions 上跑它的那個東西 |
| **ASL** | Step Functions 的流程定義 JSON |
| **Retry／Catch** | 流程裡「暫時失敗就重試兩次」／「重試完還失敗就走到失敗終點」 |
| **TransientError／PermanentError** | 暫時故障（會重試）／資料不合法或設定錯（不重試，直接失敗） |
| **candidate／active／retired（規則）** | 剛提出還沒驗證／驗證有效、寫教學時會注入／驗證無效已停用 |
| **embedding／cosine** | 文字變成一串數字／兩串數字有多像（1 = 一模一樣） |
| **recurring／knowledge gap** | 同一群工單 14 天內累積到 5 張／它們指出的「缺的教學主題」 |
| **partial（半新半舊）** | 多篇一起發布時外面看到「A 已新版、B 還舊版」；本系統不允許 |
| **gate（關卡）／O1–O7／BLOCKED** | 設計文件留下的檢查點代號；Demo 只需要在意 O5（AI 模型沒開通 = BLOCKED） |
| **moto** | 測試用的假 AWS（本機模擬 DynamoDB／S3）；它綠燈不代表真 AWS 綠燈 |
| **00A** | `docs/plan/unfinish/00A-共用契約與名詞.md`，所有名稱、簽名、路徑的權威字典 |
