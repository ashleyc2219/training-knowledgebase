## 1. 這個系統在做什麼（一分鐘版）

它是一個**會自己長知識的教學庫**：

```
使用者回報問題（GitHub Issue）──┐
產品改版（PR / changelog）──────┼──→ 接入層（驗簽、正規化、去重）──→ 三條 Step Functions 流程
教學讀者的評分回饋 ───────────┘                                          │
                                                                          ▼
                                    DynamoDB（一張表）＋ S3（私有資料 + 公開 site/）
                                                                          │
                                                                          ▼
                                                      公開的靜態教學網站（S3 website）
```

三條流程各做一件事：


| 流程                | 什麼時候跑                    | 做什麼                            |
| ----------------- | ------------------------ | ------------------------------ |
| `ticket-analysis` | 每收到一張工單                  | 把相似的工單分群；同一群累積到 5 張就寫一篇新教學     |
| `feedback-review` | 每天 UTC 00:30 自動跑（也可手動觸發） | 找出評分低的教學，只改被抱怨的那幾步；順便提出新的寫作規則  |
| `release-update`  | 每收到一筆產品改版                | 找出提到該功能的教學步驟，只改那幾步；功能被移除就把教學退役 |


寫教學的 AI 模型是 AWS Bedrock（Titan 算向量、Claude 寫字）。**目前帳號還沒開通模型使用權**（見第 8 節），所以「需要模型」的步驟現在會停在 `PipelineFailed`——這是已知狀態，不是壞掉。

## 2. 電腦上要先有什麼


| 工具            | 用途                                                 | 怎麼確認                                                      |
| ------------- | -------------------------------------------------- | --------------------------------------------------------- |
| Python 3.12   | 程式語言                                               | `uv run python --version` → `3.12.x`                      |

- 如果你的終端機打 `node` 會出現 `Security: node blocked`，那是 shell 的保護設定；用 `command npx aws-cdk@2 ...` 就能繞過。

## 3. 環境變數（系統從哪裡讀設定）

所有設定都是 `TKB_` 開頭的環境變數。本機開發時把它們放進專案根目錄的 `.env`（範本在 `.env.example`；`.env` 已被 git 忽略，不會被提交）。


| 變數                           | 誰用                                                                    | 值                                                       |
| ---------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------- |
| `TKB_AWS_REGION`             | 所有會碰 AWS 的程式；**Demo 控制台沒設會直接拒絕**                                      | `us-east-1`                                             |
| `TKB_TABLE_NAME`             | DynamoDB 表名                                                           | 預設 `training_kb`，不用改                                    |
| `TKB_CONTENT_BUCKET`         | S3 bucket 名；**部署雲端與跑真實 AWS 測試時必填**                                    | `training-kb-content-example` |
| `TKB_PROJECT_ID`             | 資料屬於哪個專案                                                              | 預設 `demo`                                               |
| `TKB_BEDROCK_REGION`         | 模型所在 region                                                           | `us-east-1`（模型開通後才有意義）                                  |
| `TKB_EMBEDDING_MODEL_ID`     | 向量模型                                                                  | 預設 `amazon.titan-embed-text-v2:0`                       |
| `TKB_GENERATION_MODEL_ID`    | 生成模型                                                                  | **模型開通前留空，不要猜**                                         |
| `TKB_GITHUB_WEBHOOK_SECRET`  | GitHub webhook 驗簽的密鑰；**只在部署那一刻從你的 shell 讀進 Lambda**，不放 `.env`、不進 repo | 自己產生：`openssl rand -hex 32`                             |
| `TKB_ENV`                    | `prod` = 正式（故障注入永遠關閉）；`demo` = 演練用                                    | 平常**不要設**（預設 prod）                                      |
| `TKB_FAULT`、`TKB_FAULT_TASK` | 故障演練開關                                                                | 平常**不要設**                                               |
| `TKB_RUN_AWS_INTEGRATION`    | 設 `1` 才會跑需要真實 AWS 的測試                                                 | 平常不設（那些測試會自動略過）                                         |


最小可用的 `.env`（本機用）：

```bash
TKB_AWS_REGION=us-east-1
TKB_CONTENT_BUCKET=training-kb-content-example
TKB_BEDROCK_REGION=us-east-1
```

> `uv run` 不會自動讀 `.env`。要讓變數生效，在指令前面加 `export`，或用 `set -a; source .env; set +a` 一次載入。

```bash
uv run python -m infra.scripts.check_asl       # 檢查三條流程定義；要印三個「[通過]」
```

測試裡的 `skipped` 是需要真實 AWS 或模型的，本機不跑是正常的。

### 4.2 更新公開網站的外觀

公開站長這樣（2026-09-17 起依功能分資料夾）：

```
site/index.html                      首頁：一格一格的「功能資料夾」，每格列出裡面的教學
site/features/<功能>/index.html      一個資料夾：該功能底下所有教學的卡片
site/tutorials/<slug>/index.html     一篇教學：版本時間軸（目前版本有印章）
site/tutorials/<slug>/v<n>.html      一個版本：左欄版本資訊＋所屬功能，右欄內文與回饋 widget
```

「資料夾」= 產品功能（`Tutorial.feature_ids`）。一篇教學用到幾個功能就出現在幾個資料夾（像標籤）；沒有功能的教學放「未分類」。分組邏輯只有 `site.py` 的 `group_by_feature` 一份，pipeline 產生的新教學會自動歸入它用到的功能資料夾，不用手動分類。

公開站是發布流程的產物，**沒有「改一個 HTML 再上傳」這條路**：畫面在 `src/training_kb/site.py`，樣式在 `demo/site_assets/style.css`，真正寫進 `site/` 的只有 `Publisher`。改完外觀用一支腳本上線：

```bash
export TKB_AWS_REGION=us-east-1
export TKB_CONTENT_BUCKET=training-kb-content-example
demo/scripts/publish_site.sh            # 上傳 CSS／JS + 補缺的版本頁 + 重建所有索引頁
demo/scripts/publish_site.sh --assets   # 只改了 CSS／JS
demo/scripts/publish_site.sh --pages    # seed --apply 之後：替種子的版本補上公開頁（只補缺的）
demo/scripts/publish_site.sh --index    # 只改了索引頁版面（site.py）
```

| 你改的 | 改哪個檔 | 生效範圍 |
|---|---|---|
| 顏色、字型、間距、widget 樣式 | `demo/site_assets/style.css`、`widget.js` | 全站所有頁面（含已發布的舊版本頁） |
| 首頁、資料夾頁、版本紀錄頁的版面 | `site.py` 的 `render_site_index`、`render_folder_index`、`render_tutorial_index` | 跑 `--index` 後立刻生效（三種都是可重建的索引頁） |
| 版本頁的版面 | `site.py` 的 `render_version_page` | 只有**之後發布的新版本**會用新版面；已發布的 `v1.html` 不可覆寫，這是刻意的 |
| Demo 教學正文 | `demo/seed/*.json` → `uv run python -m demo.cli seed --apply` → `publish_site.sh` | 種子只寫資料庫；公開頁由 `--pages` 補（只補缺的，已有的版本頁不動） |
| 線上教學正文 | 走 pipeline（見第 6 節） | 發布成功才會寫 `site/` |

改 `site.py` 之前先跑 `uv run pytest tests/unit/test_site_pages.py tests/unit/test_site_renderer.py tests/unit/test_retired_page.py -q`，這三支測試釘住了機器可讀標記（`data-published`、相對連結、不得含 `http://`）。

| ---------------------------------------- | --------------------------- | --------------------------------------------------------------------------- |

| `metrics --version prepare-meeting@v1` | 看一個版本的評分／負面回饋／重開票 | 會（呼叫 `training-kb-analytics` Lambda） |


測試工單**不走** `demo/seed/tickets.json`（那是 Demo 種子，`seed` 仍讀它）。上傳步驟見 4.3.1。

#### 4.3.1 怎麼上傳測試工單

檔案放這裡，第一層是**主題類別**，底下再依**來源**分資料夾，每種來源三種格式各一份（欄位相同）：

```text
demo/test-tickets/
  prepare-meeting/            # 準備會議
    email/json/tickets.json   email/csv/tickets.csv   email/xlsx/tickets.xlsx
    discord/...               github_issue/...
  weekly-digest/              # 每週摘要
  share-summary/              # 分享摘要（空殼，可接著加票）
  notification-settings/      # 設定通知（空殼）
```

要加新主題：在 `demo/test-tickets/` 底下新建資料夾，名稱不要用 `email`／`discord`／`github_issue`，然後複製同一套來源 × 格式格子即可。`source` 仍必須等於來源資料夾名。

**json／csv／xlsx 都能上傳，不是另外兩種只能看。** 差別只在本機怎麼編：

| 你在本機做的事 | CLI 怎麼讀 | 真正送到雲端的東西 |
|---|---|---|
| 改 `tickets.json` | `--format json` 或 `--file …json` | 一律是 import Lambda 要的 JSON 事件（一張工單一包） |
| 用試算表改 `tickets.csv`／`tickets.xlsx` | `--format csv` 或 `xlsx`，或 `--file` 指到那個檔 | **一樣**先轉成 Ticket，再組成上述 JSON 後 `lambda.invoke` |

Lambda **從不**直接吃 xlsx 或 csv。轉換發生在你電腦上的 `demo.cli` → `demo/ticket_files.py`。三種檔同一組欄位：`id, source, text, author, ts, project_id, cluster_id, feature_ids, embedding`。`source` 必須等於所在資料夾名（email 資料夾裡不能寫 discord）。

```bash
export TKB_AWS_REGION=us-east-1

# 只送一張（依 ID 在目錄裡找）
uv run python -m demo.cli trigger-ticket --ticket-id t_3001

# 整格上傳：所有主題裡 email 的 csv 每一列各 invoke 一次
uv run python -m demo.cli upload-tickets --source email --format csv

# 只上傳一個主題
uv run python -m demo.cli upload-tickets --category prepare-meeting --source discord --format json

# 指定單一檔（json／csv／xlsx 都可以）
uv run python -m demo.cli upload-tickets --file demo/test-tickets/prepare-meeting/discord/json/tickets.json
uv run python -m demo.cli upload-tickets --file demo/test-tickets/weekly-digest/email/xlsx/tickets.xlsx
```

限制：

- `email`／`discord` 會呼叫 `training-kb-import`。`github_issue` 檔案讀得進去，但**不會送上雲端**（正式入口是 GitHub webhook，見 6.1）。
- 丟一張工單**不會**立刻改 S3 教學站。要同群 14 天內滿 5 張、模型開通、發布成功才會出新頁。
- Bedrock 未開通時，分析會停在 `PipelineFailed`。這是待辦 O5，不是指令寫錯。

從種子重新拆出三格式（不會改 `demo/seed/`）：

```bash
uv run python -m demo.scripts.export_test_tickets
```

## 5. 雲端啟動（部署到 AWS）

現況：**兩個 stack 都已經部署在** `us-east-1`（最後一次部署對應 commit `080cc2e`）。下面是「改了程式要重新部署」或「換一個帳號從零部署」的做法。

### 5.1 兩個 stack 是什麼


| Stack            | 裡面有什麼                                                 | 什麼時候要重新部署                             |
| ---------------- | ----------------------------------------------------- | ------------------------------------- |
| `TrainingKbData` | DynamoDB 表 `training_kb`、S3 bucket、資料存取角色、公開網站設定      | 幾乎不用（表和 bucket 設成刪不掉的 RETAIN）         |
| `TrainingKbApp`  | 4 支 Lambda、3 條 Step Functions、每日排程、log group、最小權限 IAM | **每次改了** `src/` **或** `infra/` **都要** |




### 5.2 部署 TrainingKbApp（改程式後最常做的事）

```bash
# (1) 先把 Lambda 需要、但 Lambda 執行環境沒有的套件打包成 layer
#     （每次部署前都跑；它會建 build/lambda-layer/，這個目錄不進 git）
uv run python -m infra.scripts.build_lambda_layer

# (2) 部署。三個變數缺一個，CDK 會「跳過」App stack 而不是報錯——看 stderr 有沒有「[infra] 跳過 TrainingKbApp」
AWS_REGION=us-east-1 AWS_DEFAULT_REGION=us-east-1 \
TKB_CONTENT_BUCKET=training-kb-content-example \
TKB_GITHUB_WEBHOOK_SECRET='你的密鑰' \
command npx aws-cdk@2 deploy TrainingKbApp --exclusively --require-approval never \
  --outputs-file /tmp/cdk-outputs-app.json

# (3) 看輸出：state machine ARN、webhook 的 Function URL、log group 名稱都在這個檔
cat /tmp/cdk-outputs-app.json
```

**密鑰怎麼管：** `TKB_GITHUB_WEBHOOK_SECRET` 的值要跟 GitHub 那邊設的一樣。第一次自己產生（`openssl rand -hex 32`），存在密碼管理器；之後每次部署都要用同一個值，否則 Lambda 會拒絕 GitHub 送來的所有事件。

**部署前四項檢查（每次都看）：**

1. 你的 shell **沒有** `TKB_ENV=demo`（否則故障注入開關會被烤進 Lambda）。
2. `TKB_FAULT` 和 `TKB_FAULT_TASK` **都沒設**。
3. 已跑過 `build_lambda_layer`（`build/lambda-layer/python/` 底下要有 `pydantic` 和 `jsonschema`）。
4. `uv run python -m infra.scripts.check_asl` 印三個「[通過]」。



### 5.3 部署 TrainingKbData（很少需要）

```bash
AWS_REGION=us-east-1 AWS_DEFAULT_REGION=us-east-1 \
command npx aws-cdk@2 deploy TrainingKbData --exclusively --require-approval never
```



### 5.4 從零開始（換新帳號時）

順序：`command npx aws-cdk@2 bootstrap aws://<帳號>/us-east-1` → 部署 `TrainingKbData` → 從它的輸出抄 bucket 名稱 → 用那個名稱部署 `TrainingKbApp`。

### 5.5 部署後驗證

```bash
# 三條 state machine 都在
aws stepfunctions list-state-machines --region us-east-1 --query 'stateMachines[].name'
# 四支 Lambda 都在
aws lambda list-functions --region us-east-1 --query 'Functions[?starts_with(FunctionName,`training-kb`)].FunctionName'
# 每日排程存在且是 ENABLED
aws scheduler get-schedule --region us-east-1 --name training-kb-feedback-review-daily --query '{state:State,cron:ScheduleExpression}'
# 跑三條流程的真實測試（會自己種資料、跑完自己清掉；約 2 分鐘）
TKB_RUN_AWS_INTEGRATION=1 TKB_CONTENT_BUCKET=training-kb-content-example \
uv run pytest tests/integration/test_ticket_state_machine.py \
               tests/integration/test_feedback_review_state_machine.py \
               tests/integration/test_release_update_state_machine.py -q
```

## 6. 怎麼讓事件進來（觸發流程）



### 6.1 接 GitHub（正式的入口）

1. 到 GitHub repo → Settings → Webhooks → Add webhook。
2. Payload URL 填 webhook 的 Function URL（部署輸出裡的 `WebhookFunctionUrl`；目前是 `https://examplewebhookurlid0000000000000.lambda-url.us-east-1.on.aws/`）。
3. Content type 選 `application/json`。
4. Secret 填 `TKB_GITHUB_WEBHOOK_SECRET` 的值。
5. 事件勾 **Issues**（Pull requests 也可以勾）。

之後每開一張 Issue，系統就會驗簽 → 正規化 → 去重 → 啟動 `ticket-analysis`。同一張 Issue 重送幾次都只會啟動一次。

### 6.2 手動送資料（不經 GitHub）

**工單**請用 4.3.1 的 `trigger-ticket`／`upload-tickets`（本機讀 json／csv／xlsx，再轉成 JSON 打 import Lambda）。不要把 `demo/test-tickets/` 的工單檔直接拿去 `aws lambda invoke`。

回饋與瀏覽紀錄才是下面這種 widget JSON：

```bash
cat > /tmp/feedback.json <<'EOF'
{"kind": "feedback", "source": "widget-download",
 "items": [{"id": "f_site-prepare-meeting-u_01-1789450000",
            "tutorial_version": "prepare-meeting@v1",
            "rating": 4, "category": "缺少資訊", "comment": "第三步沒說按鈕在哪",
            "user": "u_01", "ts": "2026-09-16T08:00:00Z"}]}
EOF
aws lambda invoke --region us-east-1 --function-name training-kb-import \
  --cli-binary-format raw-in-base64-out --payload file:///tmp/feedback.json /tmp/out.json && cat /tmp/out.json
```

或者更簡單，用教學網頁右下角的 widget 打分數 → 它會產生一個下載檔 → `uv run python -m demo.cli import --file 下載檔.json --kind feedback`。

### 6.3 直接啟動一條流程

```bash
# 每日回饋檢視（不用等到 00:30）
aws stepfunctions start-execution --region us-east-1 \
  --state-machine-arn arn:aws:states:us-east-1:123456789012:stateMachine:training-kb-feedback-review \
  --name manual-$(date +%s) --input '{"mode": "formal"}'
```

`ticket-analysis` 與 `release-update` 需要先有工單／改版資料在表裡，所以不建議手動 `start-execution`，請走 6.1 或 6.2。

看流程失敗時的小訣竅：失敗事件的欄位叫 `lambdaFunctionFailedEventDetails`，裡面的 `error` 就是 Python 例外的類別名。`TransientError` 表示暫時故障（系統已自動重試兩次）；`PermanentError` 表示資料不合法或模型還沒開通；`PublishError` 表示發布切點出問題。

### 7.1 監看 AWS log（三個指令就夠）

```bash
export AWS_DEFAULT_REGION=us-east-1

# (a) 即時追某條流程的 log（Ctrl+C 停）；換 release-update / feedback-review 看另外兩條
aws logs tail /aws/vendedlogs/states/training-kb-ticket-analysis --follow --since 10m --format short

# (b) 追某支 Lambda 的 log（webhook / import / pipeline-task / analytics 四支）
aws logs tail /aws/lambda/training-kb-pipeline-task --follow --since 10m --format short

# (c) 只看錯誤：加 --filter-pattern
aws logs tail /aws/lambda/training-kb-pipeline-task --since 1h --filter-pattern "?ERROR ?Error ?Traceback"
```

看一次執行到底停在哪一步：

```bash
# 最近 5 次執行與狀態
aws stepfunctions list-executions --state-machine-arn arn:aws:states:us-east-1:123456789012:stateMachine:training-kb-ticket-analysis --max-results 5 --query 'executions[].{name:name,status:status,start:startDate}'
# 某次執行的失敗事件（error 是例外類別名，cause 是訊息）
aws stepfunctions get-execution-history --execution-arn <ARN> --query "events[?type=='LambdaFunctionFailed'].lambdaFunctionFailedEventDetails"
# 走過哪些步驟
aws stepfunctions get-execution-history --execution-arn <ARN> --query "events[?type=='TaskStateEntered'].stateEnteredEventDetails.name" --output text
```

主控台路徑：CloudWatch → Log groups → 搜 `training-kb`；Step Functions → State machines → 點進去 → Executions → 點一次執行看圖（紅色節點就是停的地方）。三條流程的 log 保留 90 天。

## 9. 常見問題

**Q：**`cdk deploy` **說** `[infra] 跳過 TrainingKbApp`**。**
A：三個前提缺一個：`TKB_GITHUB_WEBHOOK_SECRET`、`TKB_CONTENT_BUCKET`、或還沒跑 `build_lambda_layer`。stderr 會寫缺哪一個。

**Q：Lambda 第一次呼叫就** `Runtime.ImportModuleError: No module named pydantic`**。**
A：layer 沒建好或建錯平台。重跑 `uv run python -m infra.scripts.build_lambda_layer`（它固定打 x86_64 Linux 的 wheel），再部署。

**Q：流程停在** `NameGap`**／**`EvaluateTargets`**／**`PrepareUpdate`**，錯誤是** `PermanentError: O5 尚未通過` **或** `ValidationException: Operation not allowed`**。**
A：模型還沒開通（O5）。這是預期狀態，不是程式錯。

**Q：**`demo.cli` **一啟動就說需要** `TKB_AWS_REGION`**。**
A：`export TKB_AWS_REGION=us-east-1` 再跑。控制台刻意不寫死區域。

**Q：測試出現** `需要真實 AWS 帳號；設 TKB_RUN_AWS_INTEGRATION=1 才執行` **的 skip。**
A：正常。想跑那些測試就設該變數並同時給 `TKB_CONTENT_BUCKET`。

**Q：GitHub webhook 回** `"ok": false, "message": "GitHub 簽名不符"`**。**
A：GitHub 上填的 Secret 和部署時的 `TKB_GITHUB_WEBHOOK_SECRET` 不一樣。兩邊改成一致後**重新部署** App stack。

**Q：我想做故障演練。**
A：看 `docs/plan/report/phases/2026-09-14-Phase59-REP.md`。重點：在本機 shell 設 `TKB_ENV=demo TKB_FAULT=<切點名>` 跑程式庫，**不要**用這個 shell 去部署。
