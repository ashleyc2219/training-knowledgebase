## 2. 實作邏輯（為什麼這樣排）

### 2.1 離線優先，AWS 最後

上一批留下兩個帳號層級的紅字：**O5 BLOCKED**（Bedrock model access 表單沒送，所有 runtime 呼叫回 `ValidationException: Operation not allowed`）與 **O3 FAIL**（DynamoDB 與 S3 是兩個 store，發布切點會出現 partial）。這兩件事都不是寫程式能解的，但 P21–P40 裡有一半的 Phase 的前置條件寫著「O3／O5 未 PASS 即停」。

裁決（00A **D-80**、**D-81**）：**這一批全部在 moto ＋ fake Writer 上完成，真實 AWS 接線整批延後到 P41**。具體口徑是：

- 程式照 Phase 文件與 00A 寫完，需要真實帳號的整合測試照文件寫好並標 `@pytest.mark.aws`（`TKB_RUN_AWS_INTEGRATION` 未設時自動 skip），本批不必實跑。
- 各 Phase 文件裡做不到的人工驗收（真實主控台、公開 website endpoint、真實 GitHub delivery、真實 Bedrock 呼叫）一律標「**延後至 P41／P59**」並在完成清單裡**維持未勾**，不得改寫成已完成。
- gate 一律保留紅字：**不得宣稱 O3 已過、不得放寬 F49、不得加未授權服務、不得填猜測的 model ID**。
- O6 未核定的來源用 **`xfail(strict=True)`** 站崗，不是 `skip`：斷言照跑、逐列印出「O6 尚未核定 `<domain>/<event_type>`」，而且一旦有人補臨時 mapping 讓它通過，strict 會把 XPASS 判成紅燈。

這個口徑的代價很明確：**moto 綠燈不是真實 AWS 的證據**。條件寫入（`IfNoneMatch`）、`ConsistentRead`、GSI 落後、`TransactWriteItems` 的取消原因、Step Functions 的錯誤碼，在 moto 上都只是模擬。這一點在每一份 Phase 報告的第 9 節都有記錄，也是第 8 節給維護者的待辦裡 P41 排最前面的原因。

### 2.3 只 review 高風險的 Phase

原本規劃四個獨立 review：**P23**（版本與關係完整寫入，後面四個 Phase 都疊在上面）、**P24**（發布提交，O3 的落點）、**P32**（接受去重與流程啟動，O2 的消費端）、**P37**（Rote 提交，三層接入的收斂點）。實際跑了**三個**（P23／P24／P32），P37 因為剛好是最後一個 Phase，它的 review 直接折進最終的兩份**分區** review：

- `review-final-A.md`：P21–P28（content／publishing／site／repository），2170 行。
- `review-final-B.md`：P29–P40（ingress／rote／adapters／pipelines／handlers），3532 行。

review 的**發現一律交給「當下持有那支檔案的人」修**，不回頭叫原作者改——這是多 agent 同一個 checkout 的必要規則：

| review | 發現 | 修的人 | 為什麼 |
|---|---|---|---|
| P23 | verify 只驗缺不驗多、重送沒有守門 | **P23 自己**（W4 沒有人碰 `content.py`） | 該檔當下閒置 |
| P24 | `record_version` 順序、N>1 半發布 | **P25**（它持有 `publishing.py`） | 避免兩人同時改同一支檔 |
| P24 | `Publisher._models` 整表 scan | 記進 ledger，等 **P27** 的 `list_versions_of_tutorial` | 不是 P24 的檔 |
| P32 | `BotoPipelineStarter` 沒分類暫時性錯誤 | **P32 自己**（`ingress.py` 到 P37 前閒置） | 該檔當下閒置 |

### 2.4 gate 不放水

沿用上一批的原則，而且這一批更常被挑戰，因為 O3／O5／O6 三個紅字直接壓在多數 Phase 上。實際做法：程式全綠、moto 全綠各自只證明自己的範圍；沒有真實帳號證據就在報告與 Phase 文件標 **FAIL／BLOCKED**，不填猜測值、不放寬設計、不加未授權服務。P25 甚至在 moto 上**又重現了一次切點 5 的 partial** 並寫進報告——FAIL 因此是有新證據的 FAIL，不是把上一批的結論抄過來。

## 4. 測試方式

### 4.1 三個離線門檻（不需要 AWS 憑證，任何人 checkout 後都能重現）

```bash
uv run pytest tests -q -W error     # -W error：任何 warning 都當失敗
uv run ruff check src tests infra
uv run mypy src infra
```

- 一律 `uv run ...`，不得用裸 `pytest` 或 `python -m pytest`。
- mypy 是 strict 模式，`src/` 與 `infra/` 內**沒有**任何 `# type: ignore` 或 `ignore_errors`。
- `[tool.mypy] files = ["src"]` 不涵蓋 `tests/` 與 `infra/`，所以要明寫 `mypy src infra`。

### 4.2 真實 AWS 測試的開關（這一批沒有實跑）

```bash
# 預設：aws 測試自動 skip（TKB_RUN_AWS_INTEGRATION 未設）
uv run pytest tests -q -W error

# 打開真實 AWS 測試 —— 本批刻意沒有執行，留給 P41
TKB_RUN_AWS_INTEGRATION=1 uv run pytest tests/integration -q -m aws
```

這一批新增的 17 支整合測試**都跑在 moto 上、都不標 `aws`**（依 00A §3.2 的分類），所以 CI 一定會跑到。23 個 skipped 全部來自前一批（10 個 `aws` marker ＋ 13 個需要隔離表名的 O2／O3 案例）。

## 5. 遇到的問題與解法

### 5.1 `verify_version_complete` 只驗「缺」不驗「多」，`create_version` 重送沒有守門（P23 review）→ 00A D-76

**問題**（review 兩個 Important）：(1) 核對只檢查「應有的東西在不在」，所以**多出來**的 STEP／`APPLIED_TO`／`SUPERSEDES` 邊一律放行；計畫明文要求兩邊都要擋。(2) `create_version` 對同一個 `version_id` 的重送沒有比對內容，帶著**不同的** `reason`／`rules_applied` 重送會被靜默接受，而 `APPLIED_TO` 邊還是照新的 `rules_applied` 寫——`rules_applied` 與實際的邊就此矛盾。

**解法**（簽名不變、只變嚴）：重送必須帶**同一份** `VersionPlan`（`allocate_version` 對同一個 `operation_id` 本來就回同一份），不同就丟 `ContentError`；`make_version_id(slug, number) != version_id` 的 plan 也拒絕；核對同時拒絕「缺」與「多」，並把損壞資料收斂成 `False`（不再丟 `ValueError`）。**連帶影響 P28**：重建 `APPLIED_TO` 邊時，刪舊邊與更新 `rules_applied` 必須一起做，否則核對會紅。

### 5.2 `record_version` 排在寫 `site/` 之後 ＋ N>1 的半發布（P24 review → P25 帶修）

**問題 1**：`commit` 先寫 `site/` 才 `record_version`。`a2` 切點（交易成功、寫 `site/` 之前失敗）因此會留下 `version_id=None` 的 ledger——**P59 單篇復原就完全沒有輸入**。
**問題 2**：整批時 `commit` 對每篇都呼叫 `record_version(父 operation_id, ...)`，但 `OperationRecord.version_id` 是單值且 write-once，**第二篇一定 `CoordinationError`**；更糟的是那個例外落在 S3 階段的例外轉換**之外**，留下「DynamoDB 兩篇都切、`site/` 只寫一篇、例外型別不是 `PublishError`」的半發布。

**解法**（由 P25 帶修，因為它當時持有 `publishing.py`）：`record_version` 移到交易成功之後、寫 `site/` 之前（`_after_transaction` 的第一步）；多篇依 **D-59 不寫父 operation**（版號在 per-slug 子 operation 上），交易後的整段收尾包進 `_after_transaction`，**任何例外一律轉 `PublishError` 並帶切點代號**。順帶補了兩個 Minor：`UNPUBLISHED_MARKER` 的 runtime 守門（`promote_site_objects` 是公開函式，可能不經 `commit` 被呼叫），以及讓 `test_transaction_bumps_revision_so_stale_writers_lose` 真的驗到舊 revision 寫入失敗。

### 5.3 交易的值**不能**用低階 `{"S": ...}` AttributeValue（P24）

Phase 24 §5 與 **00A §6.7 都寫「值用低階 `{"S": ...}` 形式」，與 boto3 的實際行為不符**。`boto3.resource("dynamodb")` 會在它自己的 client（也就是 `table.meta.client`，`Repository` 唯一拿得到的 client）上註冊 `dynamodb-attr-value-input`，把所有 AttributeValue 形狀的參數**再序列化一次**，所以送出 `{"S": "TUTORIAL#x"}` 會變成 `{"M": {"S": {"S": "TUTORIAL#x"}}}`，實測訊號是：

```
-> moto: TransactionCanceledException
   CancellationReasons=[{'Code': 'TypeError', 'Message': "unhashable type: 'dict'"}]
```

這是 **client 端**的轉換，真實 DynamoDB 一樣會收到雙層包裝而拒絕，**不是 moto 的問題**。裁決：`transact_write` 的 items 一律用**原生 Python 值**，與 `Repository` 其他方法一致（00A §6.3／§6.7 本次已更正）。P25 直接沿用 P24 的 `_update`，沒有再踩一次。

同一個 Task 還修正了兩件事：交易的 `Update` 要推進 `_revision`（沿用 P12 的 O3 spike 算式 `#rev = #rev + :one`，否則持舊 revision 的 `update_meta` 會靜默蓋掉 `current_version`），以及 `data-site-version` 這個機器可讀標記——沒有它，`a2` 切點只能證明「公開站什麼都沒有」，不是「公開站落後一個世代」。

### 5.4 `BotoPipelineStarter` 沒有分類暫時性錯誤 ＋ `_NAME_HEAD` 截斷（P32 review）→ 00A D-77

**問題**：`start()` 只攔 `ExecutionAlreadyExists`，其他 botocore 錯誤原樣冒出，所以 `_start_once` 的 `isinstance(error, TransientError)` 在**正式 adapter** 上永遠是 `False`——驗收表「StartExecution 暫時失敗 → `retryable=True`」那一列以前只在測試替身自己丟 `TransientError` 時才成立，是假的綠燈。

**解法**（與 `repository.py`「只翻已知碼」同一條慣例）：`TRANSIENT_START_CODES`（Throttling／ServiceUnavailable／InternalServerError／RequestTimeout 等）與 5xx 翻成 `TransientError`，三種 botocore timeout 也是；**不認得的碼原樣往外冒，不猜它可不可以重送**。兩個實作細節值得記下來：`ExecutionAlreadyExists` 的 `except` **必須排在 `ClientError` 之前**（它是子類，寫反會把「同名執行已存在」當成未知的永久錯誤）；`describe_execution` 走**同一套**分類（判斷「到底成功了沒」的那次查詢被節流時，不能被記成 `retryable=False`）。mutation 反證：把分類函式改成永遠回 `None`，7 個測試立刻紅。

同一回合的 minor：`_NAME_HEAD = 15` 會把 `op-feedback-review-`（19 字元）截成 `op-feedback-rev`。改成由型別導出 `len("op-") + max(len(kind) for kind in KINDS) + len("-") = 19`，雜湊長度 `80 - 19 - 1 = 60`——**算出來的，不是猜的**，之後多一種 `OperationKind` 也不會出現「超過 80 字被 AWS 拒絕」這種只在雲端才炸的錯。

### 5.5 GapNaming 到底走不走 correction（P39）→ 00A D-74

00A §6.5 的**通用列**寫「P39–P51 呼叫端一律只呼叫 `generate_validated_json` 一次」，但 00A §6.9 的 **P39 專屬列**寫「`generate_json` 在整個節點只呼叫一次」，而 Phase 39 文件又明文要求不存在的 `feature_id` 丟 `ContentError`。走 `generate_validated_json` 會多送一次修正請求、把失敗改成 `PermanentError`，`pytest.raises(ContentError)` 會直接紅燈。

**裁決：Phase 專屬契約優先**——`name_gap` 恰好呼叫一次 `generate_json`、不走 correction、未知 `feature_id` 直接 `ContentError`（模型指到不存在的 Feature 是**資料不一致**，再問一次也不會變對）。**P40 的教學寫作沒有專屬條款，所以回到通用規則走 `generate_validated_json`**，壞草稿因此是 `PermanentError`。同一支 `pipelines/ticket.py` 裡兩種呼叫方式並存是有意的，兩個 Phase 的報告都主動把它列成疑慮請主導者確認，本次以 D-74 定案並同步 00A §6.5／§6.9。

### 5.6 「重跑同版號」與「不是 CREATE 就失敗」互相矛盾（P40）

第一次跑完之後 `TUTORIAL#<slug>` 已經是 active，重送時 `decide_ticket_action` 會回 KEEP，而 `create_first_version` 的守衛「不是 CREATE 就 `PermanentError`」會把**合法的重試**擋掉。解法是把守衛改成「不是 CREATE **而且** `_own_retry_tutorial(...)` 是 `None`」，用 `Tutorial.cluster_id` 分辨**同群**（自己上一次留下的，沿用同版號補齊，F36／D26）與**別群**（含 Demo 種子教學，那是真正的 KEEP）。

這個判準**不是最緊的**（更緊的是問 `operations.load(operation_id).version_id` 指到哪裡），在「同群、不同 operation、各自 CREATE」時會替既有教學長出未發布的 v2。實際 state machine 走不到那條路（`DecideAction` 會先回 KEEP），所以先不加，列在第 8 節請維護者裁決。

另外 P40 因為 P27 還沒落地，`find_active_tutorial_for_feature` 當時不存在，用了一個 `@runtime_checkable` Protocol ＋ 同判準的基表 fallback；**P27 落地後這個 fallback 應該刪掉**（同一件事有兩份實作就是兩份），也列在第 8 節。

### 5.7 pydantic `ValidationError` 要不要收斂成 `IngressError`（P31）

Phase 文件沒寫，但 00A §4.1 說 `IngressError` 的拋出者就是 `validate_ticket`／`validate_release`，而 P30 的 handler 只接 `IngressError` 與 `PermanentError`。不收斂的話，`id="TICKET#t_881"` 這種輸入會讓 webhook 回 **500** 而不是 400。P31 自行加了 `try/except ValidationError` → `IngressError(fields=被拒欄位)` 並記在 Phase 文件 §13。本次把它寫進 00A §6.8，成為契約的一部分。

同一份報告帶出另一個不一致：00A §5.1 有一句「必填但值可以是 null 由入口檢查 key 有沒有出現」，但 §6.8 的 `RELEASE_REQUIRED` 明確不含 `source_event_id`／`old_name`／`new_name`，而且 `changed` 事件本來就可以完全沒有那兩個 key。**裁決：以 §6.8 的 `RELEASE_REQUIRED` 為準**，§5.1 加註記；**影響 P42**——`validate_feedback` 要用自己明列的 `FEEDBACK_FIELDS`，不要靠通則自行推論，否則兩個入口會長出兩套規則。

### 5.8 三個模組的循環 import（P36、P37、P28）

- **P36**：`adapters.py` 需要 `ingress.validate_ticket`／`validate_release`，但 P37 要把 `rote` 接進 `ingress`。模組層 import 會變成 `ingress → rote → adapters → ingress`（`ingress` 半初始化時 `validate_ticket` 還沒定義，會炸 `ImportError`）。解法：`validate()` **函式內** import `ingress`。
- **P37**：`rote` 需要 `assert_time_left`、`ingress` 需要 `Rote`，兩邊都放模組層就是循環。裁決：**`rote` 模組層 import `ingress`，`ingress` 用函式內 import 取 `rote` 與 `adapters`**——三層邏輯集中在 `rote.py`，那支檔的可讀性優先；`ingress.py` 模組層**完全沒有** `import adapters`（硬條件）。型別用 `TYPE_CHECKING`。
- **P28**：`repository` 不能在模組層 import `content`（相依方向是 `content` → `repository`），所以 `backfill_references` 在函式內 import `parse_markdown`。

三處都在 docstring 寫明理由。ruff 沒有選 `PLC0415`，mypy strict 也接受。

### 5.9 F14 在重放路徑會漏掉子 Release ＋ `normalize_then_accept` 的回傳形狀（P37）→ 00A D-73

Phase 文件的 F14（一個 PR 同時改到好幾個功能）段落只描述 Agent 路徑；但一筆改到 n 個功能的 PR **若走重放，只會回第 1 筆**。裁決：**兩條路都展開**——`_sub_releases` 把 `normalize_release` 那一步的 `index` 換成 `k` 並重用 parser 輸出，已記錄的 `k` 直接重用結果。展開是確定性後處理（不問模型），所以不算進 `AGENT_MAX_TOOL_CALLS`。

連帶把 P32 留下的未決問題結掉：`normalize_then_accept` 改回 **`list[Acceptance]`**，每筆子 Release 各自一個 operation（`op-release-…-1`、`…-2`，共用同一個 `source_event_id`），handler 回應同時給 `operation_id`（第一筆）與 `operation_ids`（全部）。單一 Ticket／單一 Release 就是長度 1，呼叫端取 `[0]` 等於原本行為。

P37 另外推翻了 P36 報告的一個說法：「canonical dict 已經是 `model_dump(mode="json")`，再驗一次會得到同一個物件（冪等）」**不成立**——dump 帶著 `cluster_id`／`feature_ids`／`embedding`，而 `validate_ticket` 第二道檢查就是「接入不得預填分析欄位」，實際紅燈逐字是 `IngressError: 接入不得預填分析欄位`。修法：`_validated_entity` 只做**還原**（`model_validate`），入口驗證交給序列最後一步的 `validate` 工具（`validate_recorded_steps` 保證最後一步一定是它）。

### 5.10 O3 的切點 5 在 moto 上又出現一次 partial（P25）→ 00A D-80

整批發布走協定 A，在「第 j 篇 promote 失敗」的切點 5 上，moto 觀察到 **DynamoDB 兩篇都是新的、公開站 A 回 200 / B 回 404**——對外同時看得到新舊混合。處置照 gate 規則：**判定維持 FAIL**、`pending-promote.json` ＋ 私有 staging 留給 P59 精確補齊、**不放寬 F49**、Phase 文件完成清單裡「真實 AWS 重跑五個切點與 website endpoint 人工驗收」**維持未勾**。三個決策出口仍在維護者手上（第 8 節第 5 項）。

### 5.11 「未核定來源要 gate failure」與「你的檔案要全綠」直接衝突（P31／P36／P37）→ 00A D-81

Phase 文件要求「測試必須以明確 gate failure 結束、不是 skip、不得補臨時 mapping」，但 COMMON 規則要求最後 `uv run pytest tests -q -W error` 自己的檔案全綠。採用 repo 既有前例 **`@pytest.mark.xfail(not APPROVED, strict=True, reason="O6 尚未核定 …")`**，它同時滿足三件事：報告逐列印出 `XFAIL … O6 尚未核定 <domain>/<event_type>`（不是 skip）、斷言真的執行並失敗、而且**一旦有人補臨時 mapping 讓它通過就會 XPASS 被 strict 判成紅燈**。

P31 還踩到一個細節：`validate_release` 本身是好的，所以測試會 XPASS ⇒ strict 失敗。解法是每個測試**第一行先 `assert (domain, event_type) in APPROVED`**——未核定時這行就失敗（XFAIL 成立），核定之後它自動通過、後面的斷言才真的跑。

最終全套的 **11 個 xfailed 全部來自這個機制**，分佈在 `test_adapter_fixtures.py`（3）、`test_o6_github_mapping.py`（3）、`test_release_extraction.py`（4）、`test_o6_stable_keys.py`（1）、`test_rote_commit.py`（1）。

### 5.12 `SyntaxWarning` 讓 `-W error` 整檔失敗（P22）

`escape_markdown` 的 docstring 裡逐字列出要轉義的字元（`` \ ` * _ `` …），Python 判成 `SyntaxWarning: invalid escape sequence '\ '`，在 `-W error` 下整支檔失敗。解法：docstring 改成 raw string（`r"""`），說明文字裡的反斜線改用中文「反斜線」描述。

同一支檔另外補掉一個真漏洞：Phase 文件的 `parse_markdown` 寫 `type=match[2]`，但 `StepType("scroll")` 丟的是**裸 `ValueError`**（不是 `ValidationError`），照文件原碼會直接外洩給呼叫端，違反「呼叫端只認得 Phase 02 的錯誤契約」。加了 `_step_type()` 轉成 `ContentError` 並補測試鎖住。

### 5.13 五維參考向量放不進 `Ticket`（P38）

Phase 文件的分群邊界案例用五維向量（`cosine([1,0,0,0,0], [17,7,6,5,1]) == 0.85` 精確成立），但 `models.py` 的 `Ticket.embedding` validator 要求**恰好 1024 個有限數值**。依「設計 > 00A > Phase 文件」，把五維改成「**種子**」再補零到 `TITAN_DIMENSIONS`：補零不動 dot、也不動任何一條 norm，所以兩個邊界等式**原封不動成立**；測試同時保留五維與 1024 維兩個斷言，讓「17 / 20」這條算式仍然可執行地被證明。`1024` 這個數字取自 `TITAN_DIMENSIONS`，測試裡沒有第二份。

### 5.14 假的要假在哪一層（P26、P27、P28、P35 共同的一課）

Phase 文件常寫「用假的 `Repository`」，但那樣一來「只補缺的邊」「不替換錯邊」「讀完所有分頁」「GSI 候選回基表核對」全部會變成**在測假物件**。四個 Phase 一致改成**只假掉儲存層**：`FakeTable`／`FakeBucket` 只實作 `Repository` 真的會呼叫的那幾個 boto3 操作，條件式用 boto3 的 `ConditionBase.get_expression()` 解讀且**只支援 `=`／`begins_with`／`AND`**（多送一種就 `AssertionError`，假表不會比真表寬鬆）。Phase 08 的原語一個都沒被覆寫，被測範圍反而更大。

同一類的小陷阱還有兩個：**排序**——`sorted()` 會把 `#10` 排到 `#3` 前面，`version_sort_key` 與 P28 的 `_sorted_step_pks` 都要用解析後的整數當鍵；**moto 的 GSI 是即時的**，做不出「GSI 落後」，只能用「候選來源關掉」與「邊少 `entity` 屬性」兩種**比真實更嚴格**的替身，真實證據仍然要等 P41。

### 5.15 退役提示永遠寫不到公開站（最終 review A）→ 00A D-83

**問題**：P26 讓 `render_version_page` 輸出 `RETIRED_NOTICE` 與後繼連結，測試也綠。但在協定 A 下，**已發布的版本頁是不可覆寫的**——`Publisher._version_problems` 會擋掉已發布版、`_put_public_object` 會比對 bytes。也就是說「退役之後讀者打開舊版本頁會看到提示並被導向後繼」這件事，用目前的結構**做不到**：提示掛在一個永遠寫不出去的頁面上。單元測試看不出來，因為它直接呼叫 renderer，沒有經過發布路徑。

**裁決（出口 c）**：退役提示與後繼連結改掛在**可覆寫**的教學索引頁 `tutorial_index_key(slug)`，由 `render_tutorial_index` 輸出退役區塊；**版本頁維持不變**（已發布版本的 bytes 仍是不可覆寫的歷史，這是對的）。P52 在 `retire_tutorial` 之後呼叫 `Publisher` **重寫該篇的教學索引頁**（只有索引頁，不重發版本頁）；`retire_tutorial` 自己仍然不寫任何 `site/` 物件。

**本批只改文件**（00A §6.6／§6.7／§8 與 Phase 26 文件）；`site.render_tutorial_index` 的退役區塊與 P52 的索引重寫**屬 P52／P57 的範圍，還沒寫**，列在第 8 節。

### 5.16 `version_sort_key` 丟的不是 `ValueError`（最終 review A）→ 00A D-82

00A §6.3 寫「不合格丟 `ValueError`」，但實作丟的是 `PermanentError`，兩者**沒有繼承關係**——照 00A 寫 `except ValueError` 的呼叫端會攔不到。裁決：**以程式為準**。理由是 §4.1「呼叫端只認得六個固定錯誤類別」，`version_id` 格式不合代表「這筆資料確定不合法」，不該讓 Python 內建例外外洩。注意這與 `keys.parse_step_pk`／`content.parse_version_id` 丟 `ValueError` 不同層：那兩個是解析原語，`version_sort_key` 是 `repository` 的查詢輔助。程式不改，改 00A。

### 5.17 多人同一個 checkout 的日常摩擦

七個波次、每波三到四個 agent 在同一份工作樹上跑，別人的檔案「暫時是紅的」是常態：P21 撞過 P29／P30 的 `ModuleNotFoundError`、P25 撞過 P26 尚未提交的 `retire_tutorial`、P27 撞過 P25 進行中的 `publishing.py`、P32 撞過 P36 編輯中的 `rote.py`、P33／P39 撞過 P31／P32 的 lint、P34／P40 撞過 P24／P36 的收集期錯誤。規則一律是：**只 `git add` 自己的檔**、提交一律 `git add <檔案...> && git commit -m "..." -- <同一批檔案...>`，絕不 `git add -A`／`stash`／`checkout`／`reset`／`clean`／`rebase`，不 push；別人的紅燈用 `--ignore` 跳過**並記錄**，不去修。每一次都在對方收尾後自行恢復，最後全套是零 failure。
