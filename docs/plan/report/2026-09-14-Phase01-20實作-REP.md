## 2. 實作邏輯（為什麼這樣排）

### 2.1 檔案 owner 決定能不能平行

計畫原本假設「一個實作者、嚴格照 Phase 編號一個一個做」。20 個 Phase 這樣跑會非常久，而 `00A §3.2 目錄與檔案路徑總表` 已經替每一支檔案指定了唯一的 owner 與允許的修改者——**這張表就是天然的平行度上限**：兩個 Phase 只要不碰同一支檔，就可以同時做；碰同一支檔的一律串行。

實作前先掃了一次「會共用檔案」的組合（下表就是掃描結果與處置），再據此排出 W0–W8 九個波次：

### 2.2 相依一次加齊

`pyproject.toml` 與 `uv.lock` 是全 repo 唯一的一份。若讓 P06（moto）、P07（moto[s3]）、P09（aws-cdk-lib）各自 `uv add`，三個人會同時改同一個鎖檔互相覆寫。所以 **Phase 01 一次把 Phase 01–20 會用到的相依全部加進去**：`boto3`、`moto[dynamodb,s3]`、`boto3-stubs`、`aws-cdk-lib`、`constructs`。這偏離了 Phase 01 文件原本寫的「依賴延後到使用它們的 Phase 增加」，理由與代價寫在 `01-Phase01-…md` 的「實作備註（2026-09-14）」。唯一的例外是 Phase 17 後來補的 `jsonschema` 與 `types-jsonschema`（當時只有它一個人在動這支檔，沒有競爭風險）。

### 2.3 TDD／BDD：每個 Task 都要有「因為正確理由而紅」的紅燈

每個 Task 的固定循環是：先寫測試 → `uv run pytest <檔>` 看到 **`ImportError`／`AttributeError`／`AssertionError`**（不是 `SyntaxError`）→ 最小實作 → 綠燈 → `uv run ruff check src tests` 與 `uv run mypy src` 全過 → 只 `git add` 自己的檔案後 commit。

行為的來源是 `docs/spec/features/*.feature` 的 147 條 Rule，經 `00B` 指派給各 Phase 的 primary Rule 轉成可執行斷言。有幾個 Phase 一開始不小心「先寫完實作才補測試」（P08 Task 2／3），處置是把實作移到暫存檔、照 Task 順序放回來，讓三個 Task 的紅燈都是真的；P07 另外做了**突變測試**（拿掉守門條件確認對應測試立刻紅）來證明事後補的測試有鑑別力。

### 2.4 只 review 重要的 Phase

使用者要求盡量減少 review 回合，所以只對**高風險**的 Phase 派獨立 reviewer：P05（鍵契約，一旦錯全庫要改名）、P06（Repository，後面四個 Phase 都疊在上面）、P10／P11（O2 操作紀錄，去重與版號的根）、P20（版號分配）。其餘 Phase 靠自我檢查（三門檻＋自己的驗收矩陣）＋最後整支 branch 的總 review。

review 的**發現一律交給「當下持有那支檔案的人」修**，不回頭叫原作者改：P06 review 的 `put_meta_item` 回傳值問題由 P07 修（commit `10fa581`），P10 review 的 `record_version` write-once 由 P11 修（commit `4897a6c`）。P20 的 review 則折進最終整支 branch 的總 review。

### 2.5 gate 不放水

O1–O7 需要的是真實證據，不是綠燈。程式全綠、moto 全綠、CDK synth 成功，各自只證明自己的範圍。沒有真實帳號證據就在報告與 Phase 文件標 **FAIL／BLOCKED**，不填猜測值、不放寬設計、不加未授權的服務去換綠燈。這是 O3 與 O5 留著紅字的原因。

## 4. 測試方式

### 4.1 三個離線門檻（不需要 AWS 憑證，任何人 checkout 後都能重現）

```bash
uv run pytest tests -q -W error     # -W error：任何 warning 都當失敗，確保輸出乾淨
uv run ruff check src tests infra
uv run mypy src
```

- 一律 `uv run ...`，不得用裸 `pytest` 或 `python -m pytest`。
- mypy 是 strict 模式，`src/` 內**沒有**任何 `# type: ignore` 或 `ignore_errors`。
- `[tool.mypy] files = ["src"]` 不涵蓋 `tests/` 與 `infra/`，所以需要時要明寫路徑，例如 `uv run mypy src infra/scripts/o2_report.py`。

## 5. 遇到的問題與解法

### 5.1 `StrictModel` 的 `strict=True` 與 `frozen=True` 衝突（P03）→ 00A D-69

**問題**：00A §6.2 寫 `StrictModel = ConfigDict(extra="forbid", strict=True)`，但 P03／P04／P06／P08／P42 五份 Phase 文件與 00A 自己的 §3.6、D-12、D-66 都假設 `frozen=True`、模型層**不**開 strict。
**調查**：實測 pydantic 2.13，開 `strict=True` 會讓 `StepDraft(type="click_ui")` 直接被拒（字串不能餵給 StrEnum 欄位），而全套文件到處都是這種寫法。
**裁決**：canonical 是 `ConfigDict(extra="forbid", frozen=True)`，不開 `strict=True`；`rating=True` 這類型別問題改由 P04 的 validator 擋。記成 **00A D-69**，並同步改 00A §2 名詞表與 §6.2。

### 5.2 zsh 不做未加引號變數的字詞切分（P13）

在 `bash` 裡 `$FILES` 會被切成多個引數，`zsh` 預設**不會**。照抄 bash 習慣的指令會把一整串檔名當成單一引數而找不到檔。解法：所有多檔指令改成逐檔明列，或用陣列展開。

### 5.3 這個 shell 的 `rm` 與 `node` 是會拒絕的 function（P01、P09）

要刪檔一律 `command rm <檔案>`（或 Python 的 `os.remove`），要跑 Node／CDK 一律 `command node`／`command npx`。P01 刪 ruff 樣本檔、P09 跑 `npx aws-cdk@2` 都踩過這一條。

### 5.4 Bedrock 帳號未開通 → O5 BLOCKED（P14）→ 00A D-72

**症狀**：所有 Bedrock runtime 呼叫都回 `ValidationException: Operation not allowed`。
**排除法**（每一項都實測）：換 body、換模型（Titan V1／Cohere／Nova／Claude Haiku 4.5／Sonnet 4.5）、換 API（`InvokeModel` 與 `Converse`）、換 Region（us-east-1／ap-northeast-1）——全部同一個錯；而 control plane（`ListFoundationModels` 等）與其他服務（`sts`、`s3`）全部成功，代表憑證與 IAM 沒問題。
**命中**：`bedrock:GetUseCaseForModelAccess` → `ResourceNotFoundException: You have not filled out the request form.`
**結論**：帳號 123456789012 **從未送出 Bedrock model access 的使用情境表單**，因此沒有任何模型被授權。
**裁決（D-72）**：O5 標 **BLOCKED**，不填任何猜測的 model ID；P15–P18 照常完成程式與單元測試（用假 Writer），真實 Bedrock 整合測試維持 FAIL／skip 並留下證據。後續 controller 曾嘗試 `create-foundation-model-agreement` 自動接受 Titan 的第一方條款，回應是「Agreement not supported for this model」——**帳號層級的開通只能在 console 做**，已透過推播通知使用者。

### 5.5 `parse_step_pk` 過寬（P05 review）→ 00A D-70

Phase 文件指定的實作只切字串，所以 `"STEP##3"`（空 version）、`"03"`（前導零）、全形數字 `"３"` 都會被接受，和 `step_pk` 產得出的字串不是同一個集合。收緊成：`isdecimal()` 且 `str(int(n)) == n`、version 段非空、頭尾不得有空白；`_bare` 同步擋掉含 `#` 與帶空白的輸入。（commit `b8f0fbe`）

### 5.6 `put_meta_item` 覆寫仍回 `True`（P06 review → P07 修）

契約寫的是「回傳值代表**這一筆是我建立的**」，但 `create_only=False` 走覆寫路徑時也回 `True`，呼叫端會誤判成首建。P06 交件時 reviewer 抓到，因為當時 `repository.py` 已經在 P07 手上，所以修正由 **P07** 帶（commit `10fa581`），避免兩個人同時改同一支檔。

### 5.7 `record_version` 沒有 write-once（P10 review → P11 修）

原實作允許同一個 `operation_id` 反覆寫入不同的 `version_id`，一旦重送拿到不同版號就會靜默分叉——那正是 O2 要擋的事。修正為：同值 **no-op**、不同值丟 **`CoordinationError`**（commit `4897a6c`），並在真實表的 `restart` 案例上驗過。00A §6.4 已補上這條備註。

### 5.8 O3 五個切點有四個是 partial → FAIL（P12）

在隔離表與隔離桶上跑了兩種協定順序（A：先交易後寫 `site/`；B：先寫 `site/` 後交易），五個切點的結果是 `a1` 正常、**`a2`／`a3`／`b1`／`c1` 都能觀察到 partial**（對外同時看得到新舊混合）。根因是 DynamoDB 與 S3 是兩個 store，沒有跨 store 的原子提交。順帶量到 `TransactWriteItems` 的上限 100 個動作／每篇 2 個 item = 一批最多 50 篇，與 P25 的假設一致。
**處置**：判定 **O3 FAIL**，阻擋 P24／P25／P41／P48／P52／P57；**不放寬 F49、不加 CloudFront**，改列三個未核定的決策出口交給維護者（見第 8 節）。

### 5.9 P19 的 fixture 只有一筆 evidence（P19）

P04 依 00A D-66 給 `AuthoringRule.evidence` 加了「至少 5 個不同 Feedback ID」的 validator，但 D-66 的影響欄只點名 P47／P55／P56，漏了 P19。P19 文件的 fixture 寫 `evidence=["f_12"]`，一跑就被 pydantic 擋下。解法：fixture 改成五個不同 ID；本次已把 **P19 補進 D-66 的影響欄**。

### 5.10 moto 的 `IfNoneMatch` 探針（P07）

`put_object(..., IfNoneMatch="*")` 是相對新的 S3 功能，不確定 moto 支不支援。先寫了一支最小探針確認 moto 5.2.3 **有**實作（撞鍵會回 412），才照設計寫條件寫入；moto 造不出的 409 則另外用假 bucket（`SimpleNamespace` + `ClientError`）補測試。

### 5.11 CDK bootstrap 與非互動部署（P09）

`us-east-1` 沒有 `CDKToolkit`，得先 bootstrap。另外三個坑：pytest 不會把專案根目錄放進 `sys.path`（`import infra` 失敗，解法是測試檔開頭插入 repo root，不改 `pyproject.toml`）；`mypy src infra` 因為缺 `infra/__init__.py` 報 `Source file found twice under different module names`（補空的 `__init__.py`，本次已補進 00A §3.2）；非互動環境不能用 `--require-approval any-change`（會停在 IAM 確認），改 `--require-approval never`，並靠單元測試鎖住「IAM 不得有萬用字元」。

### 5.12 `test/unit` 還是 `tests/unit`

dev prompt 裡寫的是 `test/unit`，但 00A §3.2 與既有 `AGENTS.md` 都是 **`tests/unit` 與 `tests/integration`**。裁決為 dev prompt 的筆誤，一律用 `tests/`。

### 5.13 多人同一個 checkout 的日常摩擦

工作樹裡同時有 200 多個舊專案的待刪除檔、很多未追蹤的 plan 文件，還有別人進行中的紅燈。規則是：**只 `git add` 自己的檔**、提交一律 `git add <檔案...> && git commit -m "..." -- <同一批檔案...>`，絕不 `git add -A`／`stash`／`checkout`／`reset`／`clean`／`rebase`，不 push。別人的測試暫時紅就用 `--ignore` 跳過並記錄，**不去修**。實際發生過好幾次（P02、P08、P12、P15、P16、P17、P18 都遇到），每份報告都有記錄，最後全部自行恢復。
