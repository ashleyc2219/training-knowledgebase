## 1. 實作邏輯

### 這個 phase 解決什麼

Phase 0 是所有 phase 的前置：把「空 repo ＋ 一疊規格」變成「可以 `uv run pytest` 且可以 `streamlit run` 的專案」。
它自己不產生任何 demo 價值，但後面四個 phase 全部靠它定下來的三件事平行開工：

1. **模組骨架**（`app/` 下八個子套件）— 讓 Phase 1～5 各自認領檔案而不互踩。
2. **資料存取介面**（`db.py` / `local_db.py` / `hotdata_client.py` 同一組方法名）— 讓「hotdata 當天連不上」變成換一行的事，不是改十個檔案。
3. **門檻純函式**（`app/agent/rules.py`）— 把 `CLAUDE.md` 訊號表裡那七條數字門檻集中在一支沒有 I/O 的模組，任何 phase 要判斷 CREATE／REFINE／KEEP 都呼叫同一份，不各自寫 `if`。

### 怎麼切

| 切法 | 內容 |
|---|---|
| 縱切（資料層） | `sql.py`（9 表 DDL ＋ 查詢常數）→ `local_db.py`（SQLite 實作）→ `db.py`（選擇器）→ `hotdata_client.py`（同介面的遠端版） |
| 縱切（決策層） | `rules.py` 純函式 ＋ `metrics.py` 三條學習指標 |
| 縱切（資料準備） | `bitext.py` 真實下載 Bitext CSV → `data/seed/` ＋ `data/script/` |
| 空殼 | `realtime` / `analysis` / `create_tutorial` / `feedback_review` / `release_update` / `rocketride_client` / `cognee_client` / `hydradb_client` / `rote_client` / Streamlit 只留簽名，交給後面 phase |

### 關鍵設計決定與理由

| 決定 | 理由 |
|---|---|
| SQLite（`.state/local.db`）與 hotdata 走**同一組方法名** | 黑客松當天網路／額度是最大風險。demo 時 `DB_BACKEND` 一換就能跑，不必臨時改業務程式碼。 |
| 門檻寫死在 `rules.py` 的純函式，不做設定檔 | 門檻在 `.clarify/resolved/` 已拍板（≥3 張票、avg<3.5、≥3 筆、同 category ≥2 筆），不會變。做成設定檔是為不存在的需求付費。 |
| `sql.py` 把查詢寫成**模組層常數**而非組字串 | 同一句 SQL 要同時餵 SQLite 與 hotdata，寫成常數才好比對方言差異（後來果然在 Phase 1 抓到 `GROUP BY` 差異）。 |
| Bitext 用**真實下載**而不是手刻假資料 | 評審會問資料從哪來。下載一次存進 `data/raw/`（git-ignored），之後跑離線的 `data/seed/*.json`，兩者兼顧。 |
| 種子 6 筆 Ticket、劇本 9 筆 | 6 筆剛好讓 `cancel_order` 過 ≥3 張的 CREATE 門檻、另兩個 intent 不過，demo 時「為什麼只有它產生 Tutorial」講得清楚。 |

## 2. 步驟（TDD 先紅後綠）

1. `uv init` ＋ 寫 `pyproject.toml`、`.python-version`（3.12 pin），補 `.gitignore`（`.venv/`、`.state/`、`data/raw/`、`__pycache__/`、`.env`）。
2. 建 `app/` 全部 `__init__.py` 與空殼模組，確認 `import app.xxx` 不炸。
3. **先紅**：寫 `tests/unit/test_rules.py`，照 `分析SupportTickets.feature`／`定期優化Tutorial.feature` 的門檻寫斷言 → 全紅（`rules.py` 還是空的）。
4. **後綠**：實作 `rules.py` 七個純函式 → 轉綠。
5. **先紅**：`tests/unit/test_metrics.py` 照 `展示學習指標.feature` 三條 Rule 寫 → 紅。
6. **後綠**：實作 `metrics.py` 三條指標（分母 0 回 `None`）→ 轉綠。
7. **先紅**：`tests/unit/test_local_db.py` 測建表、insert、query → 紅。
8. **後綠**：寫 `sql.py` 9 表 DDL ＋ 9 個查詢常數，`local_db.py` 實作 → 轉綠。
9. 寫 `hotdata_client.py` 初版（照 CLI help 寫，本 phase 未實跑）與 `db.py` 選擇器。
10. 寫 `app/ingest/bitext.py`，實際下載 Bitext CSV，產 `bitext_seed.json`（6 筆）與 `demo_tickets.json`（9 筆）。
11. 手寫 `feedback_seed.json`（10 筆，avg 2.9）、`feedback_v2_seed.json`（5 筆，avg 4.4）、`changelog.json`。
12. Streamlit 空殼 ＋ `scripts/reset_demo.py`；跑一次 bare mode 確認能起。
13. 全套 `uv run pytest -q` → 35 passed。

## 4. 測試方式

```bash
uv run pytest -q tests/unit/test_rules.py tests/unit/test_metrics.py tests/unit/test_local_db.py
```

對齊的 `.feature` Rule：

| 測試檔 | 對齊的 Feature / Rule |
|---|---|
| `test_rules.py` | `分析SupportTickets.feature`（同 `user_problem_id` ≥ 3 張且無 published Tutorial → CREATE）、`定期優化Tutorial.feature`（avg < 3.5、count ≥ 3、同 category ≥ 2、`is_possibly_outdated` 一律 KEEP）、`收集Feedback.feature`（rating 1–5 整數、六類＋其他） |
| `test_metrics.py` | `展示學習指標.feature` 三條 Rule：deflection rate = deflected/(deflected+escalated)、重放解決率 = Σ`replay_count`/deflected、圖譜覆蓋 = 有 published Tutorial 的 UserProblem / 全部 |
| `test_local_db.py` | `erm.dbml` 9 表結構（建表、insert、query 回 dict） |

## 5. 遇到的問題與解法

| 問題 | 原因 | 怎麼解 |
|---|---|---|
| 重放解決率案例湊不出計畫寫的數字 | 計畫文件裡的範例票數與 `展示學習指標.feature` Example 2/4 不一致 | 以 `.feature` 為準（來源優先序：規格 > 計畫），測試改用 4 張 deflected |
| `feedback_seed.json` 要剛好 avg 2.9 | rating 是 1–5 整數，不能填小數 | 用 10 筆整數湊總分 29（10 筆 → 2.9），順便讓筆數過 ≥3 門檻 |
| `HotdataClient` 寫完無法驗證 | 當時 hotdata database 尚未建立 | 照 CLI `--help` 先寫介面，標記為初版，Phase 1 實跑後補齊（`execute()` 不回 lastrowid、`reset()` 未實作） |
| Bitext CSV 下載慢且不該進 git | 27K 筆原始資料 | 下載到 `data/raw/`（已 git-ignore），只把抽樣後的 seed JSON 進 repo |
| Streamlit 在無瀏覽器環境測不了 | CI／終端機沒有 GUI | 用 bare mode 起一次確認不炸，UI 驗收留到 Phase 4／5 |
