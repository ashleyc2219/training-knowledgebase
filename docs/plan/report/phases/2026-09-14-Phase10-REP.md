## 1. 實作內容（含實作邏輯）

### 1.1 新增 `src/training_kb/operations.py`

最小的 operation ledger。檔案分三段：型別與三個 dataclass、item ↔ record codec、`OperationCoordinator`。

**型別（與 00A §6.4 逐字一致）**

```python
OperationKind = Literal["ticket", "release", "feedback", "view",
                        "ticket-analysis", "release-update", "feedback-review", "analytics"]
OperationStatus = Literal["accepted", "normalized", "started", "done", "failed"]
KINDS / STATUSES: frozenset[str]   # get_args(...) 得到的載入白名單
```

`KINDS`／`STATUSES` 存在的理由：表裡讀回來的是純字串，`_from_item` 先核對在白名單裡才 `cast` 成
Literal，寫錯的值在載入當下就明確失敗，而不是把髒資料帶進下游。沒有 `running`（用 `started`），
`Acceptance` 沒有 `is_duplicate`，`OperationRecord` 沒有 `result_ref`（D-08）。

**三個 frozen dataclass**：`AcceptOperation`（五欄）、`OperationRecord`（十四欄，`model_output_refs`
是 `tuple[str, ...]`）、`Acceptance`（`status`／`operation_id`／`record`）。`OperationRecord` 本
Phase **不含** `accept_seq`，Phase 11 會把它插在 `accepted_at` 之前；`_from_item` 只讀自己認得的屬性，
所以那時的既有 item 不需要資料遷移。

**codec**

- `_initial_record(request)`：四個請求欄位 ＋ `status="accepted"` ＋ `accepted_at = updated_at = request.now`，
  其餘一律 `None`／`()`。
- `_to_item(record)`：`datetime` → `to_iso`、`tuple` → `list`；**一個保留屬性都不寫**
  （`PK`／`SK`／`entity`／`_revision` 由 `put_meta_item` 補，`target` 不補，所以 `OPS#` 不進 `by_target` GSI）。
- `_from_item(item)`：`_to_item` 的反函式。`_text`／`_required_text`／`_refs`／`_flag`／`_revision`
  五個守門員把 `DynamoValue` 收斂成具體型別，形狀不對一律 `CoordinationError`（因此 mypy strict 全過，
  沒有任何 `# type: ignore`；只有兩處 `cast` 是**核對過白名單之後**才做的 Literal 收斂）。

**`OperationCoordinator`（十個公開方法，無多餘公開面）**

- `accept`：直接送 `put_meta_item(ops_pk(id), _to_item(record), create_only=True)`，
  也就是 DynamoDB 端的 `attribute_not_exists(PK)`；**沒有「先查再寫」**。
  回 `True` → `Acceptance("accepted", ...)`；回 `False` → `load()` → 讀得到就
  `Acceptance("duplicate", ..., 既有紀錄)`，讀不到就 `CoordinationError`（資料不一致，不得當新事件重做）。
- `load`：`get_meta_item` → `_from_item`；不存在回 `None`。
- `record_normalized`／`record_execution`／`record_version`：走 `_change`，**只改自己那個欄位**，
  不讀系統時鐘、不動 `updated_at`、不動 `status`。
- `record_model_output`：先讀既有清單，同 ref 直接返回（不重複附加）；否則附加一筆。
- `record_proc_sample`：`proc_sample_signature` 已有值回 `False`（Phase 35 不重複累加 `success_count` 的依據），
  否則寫入並回 `True`。
- `complete`／`fail`：有 `now` 參數，所以它們才寫 `status` 與 `updated_at`；`fail` 另寫 `error`／`retryable`
  （要不要重試由呼叫端依 `retryable` 決定，不是 ledger 決定）。
- 私有 `_existing`（item 不在就 `CoordinationError`）／`_write`（用**手上這一筆** item 的 `_revision`
  做 compare-and-swap，少一次讀取就少一個競態視窗，00A §3.6 的唯一例外）／`_change`。

### 1.2 修改 `src/training_kb/keys.py`（局部追加第 6 段，前五段一行未動）

## 5. 遇到的問題與解法

1. **「條件失敗卻讀不到既有 item」在真實表上做不出來。**
   Phase 文件 Task 1 Step 3 寫「把 item 直接從表刪掉再 `accept`」，但刪掉之後條件寫入就會成功，
   永遠走不到那個分支。解法：拆成兩條測試 —— 刪除後 `load` 回 `None` 且 `record_*` 丟 `CoordinationError`
   （這正是驗收矩陣的另一條 Failure 路徑），另一條用一個永遠讓 `get_meta_item` 回 `None` 的
   `Repository` 子類，把「條件失敗」與「讀不到」湊在同一次呼叫。Phase 文件已同步修正。

2. **`record_normalized` 到底改不改 `status`？**
   Phase 文件 §6 寫「其餘 `record_*` 沒有 `now` 參數就只改自己那個欄位」、§8 驗收矩陣寫「其餘欄位不動」，
   兩處都指向「不改」；但 `OperationStatus` 又有 `normalized`／`started` 兩個值，
   Phase 32 的測試替身裡也出現 `status="started"` 配 `execution_arn`。00A 與設計都沒有明文。
   依「設計 > 00A > Phase 文件」再加上最小實作原則，**裁決為不改 `status`**：本 Phase 只有 `accept` 寫
   `accepted`、`complete` 寫 `done`、`fail` 寫 `failed`，`normalized`／`started` 列為保留值留給接受路徑的
   owner（Phase 32）決定要不要推進。已在 Phase 文件 §6 明文寫下，避免後續 Phase 再猜一次。

3. **`operation_id_for`／`execution_name` 要不要放進 `keys.py`？**
   任務指示提到這兩個，但 00A §6.8 的介面 owner 表把它們指給 **P32**、模組是 `training_kb.ingress`，
   §6.2 的 `keys` 表只列 `ops_pk`／`operation_ref`（owner P10）。依文件優先序以 00A 為準，
   **本 Phase 不建立**這兩個函式；`keys.py` 只追加 `ops_pk`／`operation_ref`（外加私有守門員與 `OPERATIONS_PREFIX`）。

4. **mypy strict 下 `DynamoValue` 轉具體型別。**
   `get_meta_item` 回的是 `dict[str, DynamoValue]`，直接 `int(item["_revision"])` 或把 `list` 當
   `tuple[str, ...]` 都過不了 strict。解法是寫 `_text`／`_required_text`／`_refs`／`_flag`／`_revision`
   五個守門員：形狀不對就 `CoordinationError`，型別收斂與資料驗證一次做完，全檔零 `# type: ignore`。

5. **Task 2／3 沒有天然紅燈。** Task 1 的最小實作已含完整 §6.4 方法面（codec 本來就要寫齊全部欄位）。
   為了不讓 TDD 只剩形式，改用「暫時移除該功能 → 跑測試 → 還原」的 mutation check 取得紅燈訊號
   （第 3 節三段 RED 都是這樣來的），證明每條新測試都真的會咬。這是與 COMMON.md 流程的**偏差**，
   在此明確記錄。

6. **全套測試被別人的檔案擋住 collection。** Phase 12 的 `infra/scripts/o3_report.py` 正在被另一個 agent
   改到一半，`tests/unit/test_o3_observation.py` 與 `tests/integration/test_o3_cut_points.py` import 失敗。
   依 COMMON.md 用 `--ignore` 跳過並記錄，不去碰那些檔案。

## 7. Gate 狀態

### O2：**未通過（NOT PASSED）**

本 Phase 的全部證據來自 **moto 本機表**，只證明兩件事：

1. 同一個 `operation_id` 不會被建立第二次（條件寫入），重送拿到逐欄相同的既有紀錄；
2. 持久紀錄可以被**重新載入**（換一個 `OperationCoordinator` 物件仍讀得回）。

「換物件」不是「程序重啟」：資料自始至終都在同一個 moto 表、同一個行程裡。
00A §4.2 要求的五類案例 —— **重啟、重送、交錯事件、lease 過期、closed execution** —— 在真實 DynamoDB
留下 PASS 證據，以及 `accept_seq` 帶來的接受順序，全部是 **Phase 11** 的事。

因此本 Phase **不得**宣稱：FIFO、接受順序、同版號、O2 PASS。保留停止語：
「O2 尚未 PASS，不得宣稱永久去重或 FIFO；建版與接受路徑停止」、
「lease 不等於接受順序、TTL 不是準時解鎖」。

其餘 gate（O1、O3–O7）本 Phase 不涉及，狀態不變。
