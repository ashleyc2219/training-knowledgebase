## 1. 實作內容與邏輯（逐檔說明）

### 1.1 `src/training_kb/analytics/validation.py`（新增）

純判斷層，一個字也不寫回 DynamoDB／S3。

| 名稱 | 做什麼 |
|---|---|
| `Verdict` | `Literal["improved", "not_improved", "undecidable"]`。`undecidable` 是「資料不足」，**不是**「沒有改善」。 |
| `SeedBatch`（frozen dataclass，10 欄） | 一次比較所需的完整資料。`approved_by`／`approved_at` 是**批次**核定；`cluster_id` 只寫進證據檔供人工核對，不參與判斷。 |
| `RuleEvaluation`（frozen dataclass，13 欄） | 判定結果，含 `average_delta`／`rate_delta`（MET Rule 6）、`version_ids`（判斷兩批是否重疊）、`approved`、`decidable`。 |
| `_batch_problems` | 比較前的四道對照檢查 ＋ 一道核定檢查，回 reason tuple。 |
| `_delta` | 後版減前版，任一邊缺值回 `None`。**不四捨五入**。 |
| `_result` | 把 `VersionMetrics` 攤平成 `RuleEvaluation`；指標還沒取到時四個數字都是 `None`。 |
| `evaluate_batch(batch, *, approved, repository)` | 七關全過才做第八步比較。 |
| `_decisive`／`_two_unimproved` | 只留 `approved and decidable` 的批次；最後兩個都 `not_improved` **且 `version_ids` 不相交**才成立。 |
| `next_status(current, evaluations, conflict)` | 純函式狀態機，回 `RuleStatus`（StrEnum，所以測試的 `== "active"` 成立）。 |
| `_string_list`／`validated_conflict(judgement, candidate, *, repository)` | 採用衝突判定的唯一入口，五道檢查任一不過回 `None`。 |
| `curation_groups(rules)` | 依 `applies_when` 分群，排除 retired，單獨一條不成群；不寫任何資料。 |

**`evaluate_batch` 的判斷順序**（任何一關沒過就以括號內 reason 回 `undecidable`）：
前後 `TutorialVersion` 都讀得到（`missing_version`）→ 兩者 `slug` 都等於 `batch.slug`
（`cross_tutorial`）→ 兩者 `published_at` 都非 `None`（`unpublished_comparison`）→
before 版號 < after 版號（`wrong_order`，用 `parse_version_id(...)[1]`，不從字串排序猜）→
`approved_by` 與 `approved_at` 都有值（`batch_not_approved`）→ 兩版 `average` 都非 `None`
（`missing_average`）→ 兩版 `reopen.rate` 都非 `None`（`zero_denominator`）→
**`after.average > before.average` 且 `after.rate < before.rate`** 才 `improved`。

前四關寫成 `elif` 是刻意的：版本讀不到就不能再問 `slug`，而 `parse_version_id` 對不合格式的
字串丟 **`ValueError`**（不是 `PermanentError`），所以它一定排在「兩版都讀得到」之後。

`version_metrics` 用**模組層名稱綁定**（`from training_kb.analytics.version import version_metrics`），
測試才能 `monkeypatch.setattr(validation, "version_metrics", ...)` 換掉它。

**狀態機優先序（本計畫選擇，2026-09-14）：** 設計 §12.2 沒有規定三個判定誰先誰後，本 Phase
固定為「`retired` 終態 → 已驗證衝突 → 連續兩批未改善 → 最新一批 improved」，讓同一組輸入永遠
得到同一個結果。`evaluations` 由呼叫端依批次核定時間**升序**傳入。

  3. 非法轉移丟 `PermanentError`，寫入用 `expected_revision=revision_of(pk)` 的 compare-and-swap（D-27）；
  4. 併寫 `operations/rules/validated_at.json`；`clock.to_iso` 遇微秒**直接丟 `PermanentError`**
     （不靜默截斷），所以寫入前先 `now.replace(microsecond=0)`。

## 5. 遇到的問題與解法

### 5.1 Phase 54 的測試拿 `validate_rules` 當「未知 action」的例子

`tests/unit/test_reopen_metrics.py::test_handler_rejects_unknown_action_before_touching_aws`
原本斷言 `handler({"action": "validate_rules"}, None)` 會 `PermanentError`——本 Phase 讓它成為
第二個**已知**分支，那條測試必然轉紅（`_wiring` 被換成會爆炸的版本，於是變成 `AssertionError`）。

**裁決（本計畫選擇）：** 紅燈源自本 Phase 修改的共用檔（`handlers/analytics.py`），依 COMMON R3.5
「紅燈若來自你改的共用檔，就是你的責任」，由本 Phase 代改**一行 ＋ 一段 docstring 註記**：
action 名稱換成沒有任何 Phase 認領的 `"curation"`，其餘（`{}` 空事件、`_wiring` 會爆炸的守門、
測試名稱）一字未動。`validate_rules` 走新分支的斷言改放在
`tests/unit/test_rule_status_writer.py::test_handler_dispatches_validate_rules_and_still_rejects_unknown_actions`，
覆蓋率沒有變差。

### 5.2 `-0.49999999999999994 != -0.5`（文件 §7 Task 3 的已知 bug）

`0.2 - 0.7` 的浮點值是 `-0.49999999999999994`，JSON round-trip 之後 `== -0.5` 是 **False**
（`4.4 - 2.875 = 1.5250000000000004` 同理）。W0 已把文件改成 `pytest.approx(-0.5)`，本 Phase 照用，
**沒有**在 `_delta` 裡四捨五入——門檻比較一律吃未四捨五入的值（Phase 53 §7 第 1 條）。

### 5.3 `asdict` 遇到 `frozenset`

`RuleEvaluation.version_ids` 是 `frozenset[str]`，`json.dumps(asdict(...))` 會 `TypeError`。
`record_evaluation` 用 `asdict(evaluation) | {"version_ids": sorted(evaluation.version_ids)}` 覆寫，
證據檔裡就是排序後的清單（測試有斷言 `["prepare-meeting@v1", "prepare-meeting@v2"]`）。

### 5.4 RED 訊號不要波及別人的 collection

`tests/unit/conftest.py` 是整個 `tests/unit/` 樹共用的；如果一開始就在它的 import 區寫
`from training_kb.analytics.validation import SeedBatch`，RED 階段會讓**所有** unit 測試
collection error。作法是先建 docstring-only 的 `validation.py`、先寫測試檔跑出 RED，
確認訊號是 `cannot import name ...` 之後才動 conftest。

### 5.5 `RuleStatus(current)` 與 `is` 比較

`next_status` 的參數型別照 00A 寫成 `RuleStatus`，但測試傳字串 `"candidate"`。因為
`RuleStatus` 是 StrEnum，函式第一行 `status = RuleStatus(current)` 就把兩種形狀收斂成同一個
enum 成員，之後全部用 `is` 比較；回傳值也是 `RuleStatus`，可以直接丟給 `apply_rule_status`。
`fake_repo.update_meta` 用 `AuthoringRule(**{**rule.model_dump(), **changes})` 重新驗證，
所以寫回之後 `rule.status` 仍然是 enum 成員而不是裸字串，`is` 比較不會悄悄失效。

### 7.2 給 Phase 56（與 P58）的公開名稱與簽名

import 路徑一律走**子模組**（`analytics/__init__.py` 維持 docstring-only、不 re-export）。

```python
# src/training_kb/analytics/validation.py
Verdict = Literal["improved", "not_improved", "undecidable"]

@dataclass(frozen=True)
class SeedBatch:
    batch_id: str; rule_id: str; slug: str
    before_version_id: str; after_version_id: str
    cluster_id: str; project_id: str; synthetic: bool
    approved_by: str | None; approved_at: datetime | None

@dataclass(frozen=True)
class RuleEvaluation:
    batch_id: str; rule_id: str; verdict: Verdict; reasons: tuple[str, ...]
    before_average: float | None; after_average: float | None
    before_rate: float | None;    after_rate: float | None
    version_ids: frozenset[str]; approved: bool
    average_delta: float | None; rate_delta: float | None; decidable: bool

def evaluate_batch(batch: SeedBatch, *, approved: frozenset[str],
                   repository: Repository) -> RuleEvaluation: ...
def validated_conflict(judgement: Mapping[str, object], candidate: AuthoringRule, *,
                       repository: Repository) -> Mapping[str, object] | None: ...
def next_status(current: RuleStatus, evaluations: Sequence[RuleEvaluation],
                conflict: Mapping[str, object] | None) -> RuleStatus: ...
def curation_groups(rules: Sequence[AuthoringRule]) -> tuple[tuple[str, ...], ...]: ...

# src/training_kb/analytics/status_writer.py（Phase 40 的讀取端原封不動）
VALIDATED_AT_KEY = "operations/rules/validated_at.json"          # P40
def load_validated_at(repository: Repository) -> dict[str, datetime]: ...   # P40
LEGAL_TRANSITIONS: frozenset[tuple[RuleStatus, RuleStatus]]      # 三條合法轉移
def record_evaluation(evaluation: RuleEvaluation, *, repository: Repository) -> str: ...
def apply_rule_status(rule_id: str, status: RuleStatus, *, repository: Repository,
                      now: datetime) -> AuthoringRule: ...

# src/training_kb/handlers/analytics.py（Phase 54 的 handler／_wiring／_reset_wiring 未動）
def validate_rules_action(event: dict[str, Any], *, repository: Repository,
                          approved: frozenset[str]) -> dict[str, Any]: ...
def handler(event: dict[str, Any], context: object) -> dict[str, Any]: ...   # 多一個分支
```

**使用時的七條規則（Phase 56 請整條照抄）：**

1. **`approved` 這個關鍵字是 Phase 43 的「回饋類別」核定表**（`frozenset[str]`，例如
   `{"找不到按鈕", "缺少資訊"}`），與 `SeedBatch.approved_by` 的**批次核定**是兩回事。
   命名沿用 Phase 44／47／53，**不改名**。
2. **`undecidable` 不是 `not_improved`。** `decidable is False` 的批次不會進退役計數，
   也不會讓 candidate 升級。要判斷「這一批有沒有下結論」看 `decidable`，不要看 `verdict != "improved"`。
3. **`next_status` 的 `evaluations` 必須依批次核定時間升序傳入**，「最新一批」＝可判定清單的最後一個。
   `conflict` 只接受**已通過 `validated_conflict`** 的判定，把模型原始輸出直接餵進去是錯誤用法。
4. **退役要兩個不重疊的已核定 `not_improved`**；共用任何一個 `version_id` 就算重疊、只能算一批。
5. **`apply_rule_status` 是唯一寫 `RULE.status` 的入口。** 不要自己 `update_meta(rule_pk(...),
   {"status": ...})`，也不要在別處補一份 `validated_at`。`AuthoringRule` 沒有 `validated_at` 欄位（D-40）。
6. **`now` 必須是整秒的 aware datetime**（函式內部會 `replace(microsecond=0)`，但呼叫端自己先
   `clock.now_utc()` 最保險）；非法轉移與規則不存在都丟 `PermanentError`。
7. **證據檔不是驗證時間的來源。** `record_evaluation` 寫的
   `operations/analytics/rule-validation/<rule_id>/<batch_id>.json` 是給人看的佐證；
   Phase 19 的 `validated_at_by_rule` 一律從 `load_validated_at(repository)` 讀單一檔（D-28）。

**Lambda event 形狀**（`action: "validate_rules"`）：

              "before_version_id": "prepare-meeting@v1",
              "after_version_id": "prepare-meeting@v2",
