## 1. 實作內容（含實作邏輯）

建立 `src/training_kb/models.py`，內容分成三層，順序刻意安排成「不依賴實體的 primitive 先、草稿模型後」，讓 Phase 04 可以直接在檔尾追加十個邏輯實體，不必改動本 Phase 的任何名稱或位置：

1. **七個 StrEnum**（`TicketSource`、`ReleaseSource`、`ReleaseKind`、`StepType`、`TutorialStatus`、`RuleStatus`、`ProcStatus`）。成員名大寫、值小寫，逐字照 00A 第 5.3 節。使用 `enum.StrEnum` 而非 `Literal`，所以 `StepType.CLICK_UI is StepType.CLICK_UI` 與 `StepType.CLICK_UI == "click_ui"` 兩種比較同時成立（00A 裁決 D-32：消費端一律 import StrEnum）。
2. **`StrictModel`**：`model_config = ConfigDict(extra="forbid", frozen=True)`，只設這兩項。
   - `extra="forbid"`：模型輸出或 DynamoDB raw item 多塞一個欄位會直接 `ValidationError`，不會被靜默丟掉（Phase 06 的 `get_meta` 過濾、Phase 08 的 `item_to_model` 都建立在這個行為上）。
   - `frozen=True`：建立後不可改，避免同一份資料在不同 Phase 被偷改。
   - **沒有** `strict=True`（理由見第 6、9 節）。
3. **`bare_id(value) -> str`**：共用的裸 ID 檢查。拒絕空字串、前後有空白、含 `#`、含控制字元（`any(char < " " for char in value)`）；**保留 `@`**，因為 `prepare-meeting@v2` 本身就是合法的裸 version ID。`#` 只屬於 Phase 05 的物理 PK／SK，所以在裸 ID 這層就擋掉。
4. **`filled(value) -> str`**：共用的「顯示文字非空白」檢查，被 `StepDraft.text` 與 `TutorialContent` 的三個文字區塊共用。維持 Phase 文件的公開名稱（不加底線），因為 Phase 04 的實體文字欄位可以直接重用同一份判斷。
5. **三個草稿 value object**：
   - `ProcStep(tool: str, args: dict[str, str])` — `args` 的值是 JSONPath 字串，本 Phase **不驗語法**（白名單工具名與 JSONPath 合法形式是 Phase 36 的責任）。
   - `StepDraft(number: int, type: StepType, text: str, feature_id: str)` — 三個 `field_validator`：`number >= 1`、`text` 非空白、`feature_id` 走 `bare_id`。步驟編號欄位名一律是 `number`（00A 第 3.3 節），不叫 `index`／`step_number`。
   - `TutorialContent(title, problem, prerequisites, steps, expected_outcome)` — 三個文字區塊走 `filled`；`model_validator(mode="after")` 的 `contiguous_steps` 要求 `steps` 的編號恰好是 `1..n` 連續且**非空**，不自動重排也不補號。`prerequisites` 允許空清單（設計 §7.6 只要求五個區塊齊全，沒要求前置條件非空），`steps` 不允許空清單（五段 Markdown 的 Steps 區塊不能是空的）。

**本 Phase 刻意不做的事（已驗證）：** 不 import `ContentError`（那是 Phase 21／22 才丟）、不 import Phase 02 的 `parse_iso`（本 Phase 沒有時間欄位）、不檢查 `feature_id` 指到的 Feature 是否存在（Phase 21）、不加 `PipelineName`（Phase 29）與 `ALL_STEP_TYPES`（Phase 40）。最後一項以 `hasattr` 實測確認為 `False`。

**與 Phase 02 的相依：** 本 Phase 的固定介面雖然列了 Phase 02，但實際**零 import**，所以沒有遇到「Phase 02 檔案不存在」的問題。（實測時 `errors.py`／`clock.py`／`config.py` 已由另一個 agent 完成，我全程沒有讀寫那三支檔。）

## 5. 遇到的問題與解法

### 5.1 00A 第 6.2 節說 `strict=True`，Phase 文件說 `frozen=True`

**問題：** 00A 第 604 行（§6.2 `models` 介面表）`StrictModel` 那列的備註寫「`extra="forbid"`（多一個欄位就拒絕）＋ `strict=True`」，而 Phase 03 文件（以及 Phase 04、06、08、42）一律寫 `extra="forbid"` ＋ `frozen=True`。COMMON.md 的文件優先序是「設計 > 00A > Phase 文件」，照字面應該以 00A 為準。

**調查：**
1. 設計文件 `docs/design/training-kb.md` 對 `StrictModel` **完全沒有敘述**（`grep -n "StrictModel\|frozen\|strict=True"` 零命中），所以最高優先的來源沒有裁決。
2. 實測 pydantic 2.13.5：設了 `strict=True` 之後，`StepDraft(type="click_ui")` 會被拒 —— `ValidationError: Input should be an instance of ST [type=is_instance_of, input_value='click_ui', input_type=str]`。這會直接打掉 Phase 文件 Task 2 的驗收案例與「完成後看得到什麼」整段。
3. 00A 第 3.6 節（嚴格模型規則，專門講這件事的章節）**完全沒提** `strict`，只講 `extra="forbid"` 與 `RESERVED_ATTRS`。
4. **決定性證據是 00A 自己的裁決：** D-12 與 D-66 明講 `Feedback.rating` 收到 `rating=True`（bool）在模型層會通過，所以 P04 必須自己加 `rating_is_strict_int` validator。若 `StrictModel` 真的開了 `strict=True`，pydantic 轉換表本來就會擋掉 `bool → int`，這兩條裁決會變成多餘。Phase 42 文件第 132 行更是逐字寫「Phase 03 的 `StrictModel` 只設 `extra="forbid"`、`frozen=True`，入口必須自己擋」。

**裁決（自行判斷，不停下等人）：** 00A §6.2 該列的「＋ `strict=True`」是 **00A 內部的筆誤**，不是真正的 00A 對 Phase 文件的覆寫；它同時和 00A 的專章（§3.6）、00A 的裁決（D-12／D-66）以及五份 Phase 文件衝突。實作採 `ConfigDict(extra="forbid", frozen=True)`。

**為什麼不直接改 00A：** 00A 是所有 agent 共讀的契約檔、不在我的「預計新增／修改的檔案」清單裡，同一個 checkout 還有別的 agent 在跑，逕自改共用契約風險大於效益。改法記在 Phase 03 文件裡並在第 9 節列為待辦，交給 00A 的 owner 修正一個字。
