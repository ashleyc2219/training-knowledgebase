實作者：Phase 30 agent；完成時間 2026-09-14；branch `backend`。

## 1. 實作內容（含實作邏輯）

本 Phase 建立公開 webhook 的接入點，讓 `training-kb-webhook` 這支 Lambda 在**解析 JSON 之前**
先用原始 request bytes 驗 `X-Hub-Signature-256`，並讓整個 handler 在八秒內給出明確成功或失敗。

### 1.1 `src/training_kb/ingress.py`（新增，owner P30）

模組 docstring 寫明分節順序與追加位置，讓 P31／P32／P37 有明確落點：

1. **驗簽（P30）** —— `SIGNATURE_HEADER`、`SIGNATURE_PREFIX`、`HEX_DIGEST_LENGTH`、`verify_github_signature`。
2. **整體期限（P30）** —— `time_left`、`assert_time_left`。
3. **接線點（P30 stub → P32 接受端 → P37 完整三層）** —— `normalize_then_accept`。
4. **正規化（P31 追加於「接線點」之前）** —— 本 Phase 留空。

`verify_github_signature(raw_body, signature_header, secret)` 的判斷順序是刻意的：

- `secret` 為空 → `PermanentError`。這是**環境設定錯誤**，不是使用者輸入錯誤，所以不能報成
  `IngressError`，也不能放行。
- header 缺少或沒有 `sha256=` 前綴 → `IngressError(fields=("X-Hub-Signature-256",))`。
- 去掉前綴、`.lower()` 之後，先擋掉長度不是 64 或含非 hex 字元的值。先擋格式有兩個好處：
  一是不把任意長度字串丟進比較，二是讓「格式錯」與「簽名不符」都收斂到同一個 `fields`。
  先 `.lower()` 也順帶讓大寫十六進位的合法簽名可以通過（`hexdigest()` 是小寫）。
- 真正的比對一律 `hmac.compare_digest(expected, supplied)`，不得寫成 `==`；錯誤訊息只說
  「不符」，不回報期望值。

`assert_time_left(deadline, *, step)` 在剩餘時間 `<= 0` 時丟 Python 內建的 `TimeoutError`
（不是 `TransientError`：這不是服務故障而是來不及）。`deadline` 一律是 `time.monotonic()` 的
**絕對時刻**，由 handler 進入時算好往下傳，下游不重新計時、也不自己呼叫 `monotonic()`。

`normalize_then_accept` 是 00A D-60 的六個 keyword 參數（`domain`／`adapter`／`event_type`／
`headers`／`payload`／`deadline`），`payload` 逐字是 `Mapping[str, JSONValue]`，`JSONValue`
從 P29 的 `pipelines/common.py` import（D-31，全套只有那一份定義）。本 Phase 只放一個明確丟
`PermanentError("Phase 31／32 尚未接線；本 Phase 不得先回成功再背景處理")` 的 stub —— 刻意不回假的
成功，因為設計 §14.1 要求「先驗證，再承認處理成功」，不得「先回 202、之後再背景正規化」。

### 1.2 `src/training_kb/handlers/__init__.py`、`handlers/github_webhook.py`（新增，owner P30）

`handlers/` 只放三支非 pipeline 的 Lambda 入口（webhook、import、analytics；00A §3.2、D-56、D-62），
`__init__.py` 的 docstring 已寫明這條界線，避免後面的 Phase 把 pipeline handler 搬進來。

`handler(event, context)` 的固定次序與失敗出口：

```text
deadline = monotonic() + 8.0   # 先算期限，之後一路往下傳
delivery = header(event, "X-GitHub-Delivery")
secret   = load_secret()       # 設定錯誤（PermanentError）直接往外丟，不轉成使用者錯誤
  |
  v
decode_body(event)                 isBase64Encoded=true -> 嚴格 base64；false -> UTF-8 編碼一次
  |
  v
verify_github_signature(...)       <-- 這一步之前沒有任何 json.loads
  |  合法                           | 不合法
  v                                 v
parse_json(raw)                {"ok": false, "fields": ["X-Hub-Signature-256"], "operation_id": null}
  |
  v
lower_headers -> X-GitHub-Event -> GITHUB_ADAPTERS 對應 adapter（沒有對應就 IngressError）
  |
  v
normalize_then_accept(domain="github.com", adapter=..., event_type=..., headers=..., payload=..., deadline=...)
  |  八秒內完成              | TimeoutError
  v                          v
{"ok": true, "operation_id": ...}   {"ok": false, "operation_id": null}
```

幾個實作決定：

- **`load_secret()` 在 `try` 之外**。`PermanentError` 因此不會被 `except IngressError` 接住，
  也不會變成 `{"ok": false}` 的使用者錯誤回應，而是讓 Lambda 整支失敗 —— 這正是「設定錯誤」
  該有的行為（維護者要看到它，不是讓 GitHub 以為自己送錯）。
- **`header()` 大小寫不分、同名兩次視為沒有簽名**。Function URL 的 header 鍵大小寫不保證，
  所以逐一 `.lower()` 比對；找到超過一個就回 `None`（走「缺簽名」的拒絕路徑），不挑第一個。
- **`_raw_headers()` 私有 helper**。`lower_headers` 與 `header` 共用，且 `headers` 不是對照表時
  當作沒有 header，避免公開入口因為畸形輸入直接 `AttributeError`。
- **`decode_body` 不做 JSON round-trip**。`isBase64Encoded=false` 時只 `raw.encode("utf-8")` 一次；
  `true` 時 `base64.b64decode(raw, validate=True)`（嚴格模式），失敗回 `IngressError(fields=("body",))`。
- **`parse_json` 另外擋「合法 JSON 但不是物件」**。`[1,2]` 也是合法 JSON，但宣告的回傳型別是
  `dict[str, Any]`（下游是 `Mapping[str, JSONValue]`），所以一併回 `IngressError(fields=("body",))`。
- **`_record(delivery, outcome, operation_id)`** 只印 delivery ID、operation ID 與結果類型
  （`accepted`／`rejected`／`timeout`）。原始 body、簽名、secret 一律不進 log（00A §3.8）。

回應形狀固定 `{"ok": bool, "operation_id": str | None}`，失敗時另有 `message` 與 `fields`；
本 Phase 不新增 HTTP 錯誤碼契約（設計 §7.1）。

## 5. 遇到的問題與解法

| 問題 | 解法 |
|---|---|
| 計畫要求 `payload` 的型別逐字是 `Mapping[str, JSONValue]`，而 `JSONValue` 的唯一定義在 P29 的 `pipelines/common.py`（D-31）—— 開工時那支檔還不存在（同一個 checkout 有別的 agent 在做 P29）。 | 先做不需要它的 Task 1（驗簽），再在 Task 2 前確認 P29 已經把 `pipelines/common.py` 提交進來，然後直接 import，不自己另寫一份 `JSONValue`。沒有為了趕進度而違反 D-31。 |
| `mypy --strict` 的 `disallow_any_generics` 不接受 00A §6.8 逐字寫的 bare `dict`（`event: dict`、`parse_json(...) -> dict`）。 | 補上型別參數寫成 `dict[str, Any]`，執行期形狀與契約完全相同；`handler` 回傳仍是 `dict[str, object]`。這是 mypy gate 與文件字面的衝突，已在 Phase 文件第 6 節與第 15 節記錄，00A 不動。 |
| strict 的 `warn_return_any` 不准 `return json.loads(raw)` 直接當 `dict[str, Any]`。 | `parse_json` 加一個 `isinstance(payload, dict)` 檢查，順帶把「合法 JSON 但不是物件」（例如 `[1,2]`）也收斂成 `IngressError(fields=("body",))`，讓宣告的型別是真的。 |
| `test_uppercase_hex_signature_is_accepted` 紅燈。 | 判定是測試誤讀「大寫十六進位」：大寫的是 digest，prefix 仍是 GitHub 送的小寫 `sha256=`。修測試、不放寬實作，並把這句澄清寫回 Phase 文件。 |
| 計畫的最小實作完全沒有 log，但 Task 3 Step 4 要求「log 只記 delivery ID、operation ID 與結果類型」。 | 加 `_log`／`_record` 與 `DELIVERY_HEADER`，三個出口各記一次，並補一個斷言 log 不含 body／簽名／secret 的測試。 |
| 收尾時 `uv run ruff check src tests infra` 一度因為 P29 的 `tests/unit/pipelines/test_common.py` 匯入未排序而失敗。 | 依 COMMON.md 的 git 規則**不去修別人的檔案**，只確認自己的四支檔案 `All checks passed!`；P29 稍後自行修好，最終全樹 ruff 也是綠的。 |

**給 P31（正規化）**

- 在 `ingress.py` 的「3. 接線點」**之前**加你的第 4 段（`TICKET_REQUIRED`、`RELEASE_REQUIRED`、
  `missing_nonempty_strings`、`validate_ticket`、`validate_release`），`normalize_then_accept`
  留在檔案最後，讓「入口 → 正規化 → 接受」由上往下讀得通。
- 每一步開始前呼叫 `assert_time_left(deadline, step="normalize")`，**不重新計一次八秒、
  也不自己呼叫 `monotonic()`**；逾時是 `TimeoutError`，handler 已經會把它轉成
  `{"ok": false, "operation_id": null}`。
- `IngressError.fields` 是 `tuple[str, ...]`（D-06）。`missing_nonempty_strings` 的回傳值可以
  直接當 `fields`。handler 會把它 `list(...)` 之後放進回應的 `fields`。

**給 P32（接受去重與啟動）**

- 把 `normalize_then_accept` 的函式**內容**換掉，**簽名一個字都不要改**（六個 keyword，D-60）；
  它現在丟的 `PermanentError("Phase 31／32 尚未接線…")` 是刻意的佔位，不得改成回假的成功。
- `deadline` 直接往下傳給 `accept_ticket`／`accept_release`／`accept_normalized`
  （`def accept_ticket(ticket: Ticket, *, deadline: float) -> Acceptance`），每一步開始前
  `assert_time_left(deadline, step="put-input")`／`step="start-execution"`。
- 回傳型別是 `training_kb.operations.Acceptance`（`status`／`operation_id`／`record`），
  handler 只讀 `acceptance.operation_id`。
