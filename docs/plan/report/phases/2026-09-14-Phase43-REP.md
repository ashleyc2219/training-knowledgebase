### 1.1 `src/training_kb/ingress.py`（`# ---- Phase 43 ----` 區段）

controller 原本在這裡只預宣告了 `DEFAULT_FEEDBACK_CATEGORIES`（讓 W1／W2 併行的
P44／P53／P54／P57 可以先 import）。本 Phase 把區段補完，**常數的值一個字都沒有改**，只是搬進
區段內並補上 docstring。

| 名稱 | 內容 |
|---|---|
| `PENDING_CATEGORY` | `"待分類"`。收斂用的保留值，**不是**核定類別（設計 §12.1 的負面回饋數不算它） |
| `DEFAULT_FEEDBACK_CATEGORIES` | `frozenset({"找不到按鈕", "缺少資訊"})`（controller 預宣告，值不變） |
| `FEEDBACK_CATEGORIES_PK` | `"CONFIG#feedback_categories"` |
| `CLASSIFY_NODE` | `"classify_comment"` |
| `approved_categories(repository)` | 用 `get_meta_item` 讀設定 item 的 `categories`；**只讀** |
| `_settle(value, approved)` | module-private。核定值原樣／未核定降級 `待分類`／空值回 `None` |
| `classify_feedback_category(...)` | 決策表四條分支，只有第 4 列送一次 request |
| `_resolve_category(...)` | module-private。`import_feedback` 的接線點，回一個新的 `Feedback` |

四條互斥分支（由上往下第一個命中者決定）：

```text
1  勾選值在核定表內        -> 原值            0 次模型呼叫
2  勾選值非空但未核定      -> 待分類          0 次
3  沒勾選且留言去頭尾後為空 -> None（只有評分） 0 次
4  沒勾選且留言非空        -> 模型值收斂      恰好 1 次
```

三個刻意的設計點：

1. **`_settle` 的空值語意是 `None` 而不是 `待分類`。** 只給評分的回饋不該憑空長出一個問題類別
   （決策表第 3 列、設計 §19.1 的 `D12`）。
2. **模型回「答了等於沒答」時才是 `待分類`。** 空字串／全空白／非字串／缺 `category` 欄位四種，
   `_settle` 會回 `None`，`classify_feedback_category` 再收斂成 `PENDING_CATEGORY`——留言非空卻
   判不出類別是「待分類」，不是「這筆沒有類別」。
3. **不走 correction。** Phase 18 第 5 節的對照表把 `CommentClassification` 列為「否」，所以直接
   `Writer.generate_json`，未核定的回答由 `_settle` 降級，**全程只有一次 request**，不重問第二次。

`approved_categories` 的降級是硬需求：`categories` 缺欄位／非 list／空 list／元素全是空白，四種
都退回 `DEFAULT_FEEDBACK_CATEGORIES`，**不得回空集合**（回空集合會讓 Phase 44 的同類計數整批歸零，
一個壞掉的設定就等於「永遠沒有弱教學」）。

`import_feedback` 只加一個**有預設值**的尾巴 keyword `writer: Writer | None = None`，並在
`_dedupe` 之後、`repository.put_meta` 之前呼叫 `_resolve_category`：

```text
欄位驗證 -> 版本／退役 -> _dedupe ──duplicated? 是──> return duplicate（完全不分類）
                                   └────── 否 ─────> _resolve_category -> put_meta -> put_edge
```

放在 `accept` 之前的話每次重送都會多一次 Bedrock 呼叫（`COL` Rule 6 的停止點）。**續跑補寫**分支
（`accept` 回 duplicate 但物件其實不存在，00A D-45）走的是「否」那一條，所以會分類一次——模型輸出
從未保存過，重算符合設計 §14.2「已保存的輸出才重用」。

`Feedback` 是 frozen，所以用 `model_copy(update={"category": ...})`。Pydantic v2 的 `model_copy`
**不重跑 validator**，把 `category` 設成 `None` 因此不會踩到 `carries_signal`；沒有改成
`Feedback(**{...})` 重建。

### 5.2 「只限核定生成模型 ARN」在 O5 BLOCKED 期間是什麼

Phase 文件與 brief 都寫「只限核定的生成模型 ARN，與 P41 給 `task_fn` 的寫法相同」。實際讀 P41 的
程式，它給 `task_function`／`webhook_function` 的那一條資源是
`arn:aws:bedrock:<region>::foundation-model/amazon.titan-embed-text-v2:0`，並在註解寫明「O5 BLOCKED
期間只列已核定用途的 embedding 模型；生成模型的 ARN 等 `TKB_GENERATION_MODEL_ID` 有實測值之後再加」。
全案**沒有**已核定的生成模型 ID（`config.py` 的 `generation_model_id` 預設就是 `None`）。

**本計畫選擇（2026-09-14）：** 照抄 P41 的那一條，資源同樣只放已核定的 embedding 模型 ARN。理由是
「不得填猜測值」（00A §3.5）優先於「湊一個看起來對的 ARN」；等 O5 解除、生成模型 ID 有實測值之後，
把那個 ARN 加進 P41 與本區段兩處即可。所以本 Phase 的 `Template` 斷言守的是「**有**一條
`bedrock:InvokeModel`、資源是具名 `foundation-model/` ARN、**沒有**萬用字元」，**不是**「生成模型
已核定」——已寫進測試 docstring，避免之後被誤讀成 O5 證據。
