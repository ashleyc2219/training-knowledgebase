### 1.1 `Repository.__init__` 與 `_paged`

- `__init__(self, table, bucket=None, *, page_size: int | None = None)`：多存一個 `self._page_size`。
  `page_size` 是**測試鉤子**，正式程式不設定它（讓 DynamoDB 用預設的 1 MB 分頁）。
- `_paged(operation, **arguments)`：Phase 07 已經只以 `LastEvaluatedKey` 判斷結束；本 Phase 只加
  「`page_size` 有值就對每個請求（含續查那幾次）加 `Limit`」，並把註解裡「Phase 08 會擴充」改寫成
  現況。結束條件仍然只有一個：回應沒有 `LastEvaluatedKey`。空頁（`Items` 是空的但游標還在）
  不得提前停止——`FilterExpression` 是在 1 MB／`Limit` 之後才套用的，一頁零筆是正常現象。

### 1.2 三個公開查詢

| 方法 | 走哪裡 | 一致性責任 |
|---|---|---|
| `query_pk(pk, *, sk_prefix=None, consistent=True)` | 基表 Query，`Key("PK").eq()`（＋`begins_with`） | `ConsistentRead`，可直接當判斷依據 |
| `query_by_target(target_pk)` | `by_target` GSI Query，`Key("target").eq()` | **沒有** `ConsistentRead`（GSI 只有最終一致），只回候選 |
| `scan_entity(entity, *, consistent=True, meta_only=True)` | 基表 Scan ＋ `Attr("entity").eq()` | `ConsistentRead`；預設只回 `SK == META` |

- `meta_only` 的過濾放在**讀完所有分頁之後**，不寫進 `FilterExpression`：一個請求只送一條 filter，
  空頁不早停這件事只由 `_paged` 負責，兩件事不互相干擾。
- `entity` 的值等於 PK 前綴（00A §3.6），所以 `scan_entity("RULE")` 會連 `APPLIED_TO#` 邊一起掃到；
  邊沒有模型欄位，直接 `item_to_model` 會整筆 `ValidationError`。`meta_only=True` 當預設，五個
  `list_*` 因此自動乾淨，唯一傳 `meta_only=False` 的是 `get_steps`（STEP 沒有 `META` item）。
- `IndexName` 直接寫字面值 `"by_target"`：它與 Phase 09 CDK 的 `TARGET_INDEX` 同值，但 `src/` 不得
  import `infra/`（會把 aws-cdk-lib 拉進執行期），所以兩邊各自宣告、由測試對齊。

### 1.3 六個固定讀取

- `get_steps(version_id)`：`scan_entity("STEP", meta_only=False)` → 用 `parse_step_pk(PK)` 還原
  `(tutorial_version, number)` 並依 `version_id` 過濾 → `feature_id` 由邊的 `target` 經 `parse_pk`
  還原 → `item_to_model(payload, TutorialStep)` → 依 `number` 升序。鍵是權威：`payload` 用
  `{**item, ...}` 覆寫同名屬性，所以就算 Phase 23 之後把 `number` 也寫成屬性也不會分岔。
  不新增 `step_count`（00A §3.6：應有步驟數的權威是 S3 全文）。
- `list_feedback_of_version(version_id)`：`query_by_target(version_pk(...))` 拿候選 → 三重過濾
  （`relation == "REFERS_TO"`、起點前綴是 `FEEDBACK`、`parse_edge_sk` 的終點等於這一版）→ 逐筆
  `get_meta(pk, Feedback)`（一致讀取整筆重讀，因為候選只有鍵）→ 讀不到就 `PermanentError`
  （GSI 只會落後基表、不會多出資料，所以「候選沒有本體」代表資料不完整）→ 依 `id` 升序。
- `_scan_models(entity, model, key, **equals)`（私有）：`scan_entity` 預設值 → 用 `equals` 對 raw item
  的屬性字串做等值過濾（不先建物件）→ `item_to_model` → 穩定排序。寫成 PEP 695 泛型
  `def _scan_models[M: StrictModel]`，mypy strict 才過得了。
- `list_views_of_version`（依 `(ts, user)`）、`list_tickets`（依 `id`）、`list_rules`（依 `rule_id`，
  `status` 有值時再篩）、`list_procs`（`domain` 與 `adapter` 都要相等，依 `signature`）。

2. **Task 2／3 一開始沒有紅燈**：我第一次就把六個讀取一起寫進去了。為了維持 TDD，先把
   `get_steps` 之後的區塊移到暫存檔（連帶暫時移除 `parse_step_pk`／`RuleStatus` 兩個 import 讓 ruff
   乾淨），再照 Task 順序放回來，所以三個 Task 的 RED 都是真的。
3. **`list_procs` 的排除條件寫錯**：第一版斷言 `list_procs("discord", "rest") == []`，但那筆資料
   本來就該命中（只有 `domain` 換掉）。改成驗兩個方向：`github/graphql` 只回 `c`、`discord/rest`
   只回 `d`、`discord/graphql` 回空，這樣「只比對其中一個欄位」的實作錯誤才會被抓到。
4. **`_scan_models` 的泛型**：mypy strict 下 `key: Callable[[M], Any]` 需要方法自己帶型別參數；
   沿用檔案裡 `item_to_model[T: StrictModel]` 的 PEP 695 寫法（ruff UP047 也要求）。
5. **GSI 名稱來源**：`TARGET_INDEX` 目前只宣告在 `infra/training_kb_data_stack.py`（P09 owner）。
   `src/` 不能 import `infra/`（會把 aws-cdk-lib 變成執行期相依），所以 `query_by_target` 直接寫
   字面值，並由單元測試 `table.requests[0]["IndexName"] == "by_target"` 與 conftest 的 GSI 宣告
   雙邊鎖住。已寫進 docstring 與 Phase 文件。
