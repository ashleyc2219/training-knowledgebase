# Phase 36 報告：JSONPath 與白名單 Adapter

## 1. 實作內容（含實作邏輯）

新建 `src/training_kb/adapters.py`（三段），並在 `src/training_kb/rote.py` 的**第 5 段**
（`# --- 5. 記錄步驟的驗證與執行（Phase 36 追加）---`）追加兩個函式。`rote.py` 的 1–4 段
完全沒有重排、沒有改既有簽名，只在 import 區多一組 `from training_kb.adapters import ...`
與 `ProcStep`。

### `adapters.py` 第 1 段：安全 JSONPath

| 名稱 | 形狀 | 邏輯 |
|---|---|---|
| `PATH_ROOTS` | `("$event", "$steps")` | 只有兩個根節點。 |
| `_TOKEN`（私有） | `\.([A-Za-z_][A-Za-z0-9_]*)\|\[(0\|[1-9][0-9]*)\]` | 唯一合法的兩種 token：欄位名、非負 index。 |
| `resolve_jsonpath` | `(root: JSONValue, path: str) -> JSONValue` | 逐 token 前進，任何一步不合就 `PermanentError`。 |

四個關鍵決定：

1. **不用通用 JSONPath 函式庫**。那些函式庫支援 `..`、`[*]`、filter 與函式呼叫，一個沒擋住的
   運算式就能把整包事件（含 secret）撈出來當工具參數。本 Phase 是一個 30 行的白名單 parser，
   支援的語法窮舉得完。
2. **根節點後至少要有一個 token**。`position == len(path)` 就拒絕：光是 `$event` 等於把整包事件
   當參數，`$steps[0]` 才是合法的最短形式。
3. **缺欄位丟 `PermanentError`，不回 `None`**。回 `None` 會讓「欄位不存在」與「值就是 null」
   變成同一件事，重放時悄悄換掉語意（設計 §7.2、§9 常見錯誤第三列）。
4. **只讀不寫**。回傳的是 `root` 裡的同一個物件，不複製也不修改 `root`。

### `adapters.py` 第 2 段：工具白名單

`TOOL_NAMES`（八個名稱的 `frozenset`）、`FINAL_TOOL = "validate"`、`SUB_RELEASE_INDEX = "index"`、
`PARSER_KIND`、`AdapterTool`、`is_index_literal`、`ToolRegistry`。

- `ToolRegistry` 是 `frozen=True` 的 dataclass，**建構時**（`__post_init__` 比對
  `set(self.tools) - TOOL_NAMES`）與 **`run()` 時**各擋一次，兩處訊息都含「白名單」三個字。
  沒有執行期註冊 API，模型或 payload 給的名字進不來。
- `is_index_literal` 是「唯一允許的字面值」這條例外的**唯一**判斷處（00A §6.8）：
  `tool == "normalize_release"`、`name == SUB_RELEASE_INDEX`、`value` 符合 `[1-9][0-9]*`
  三個條件同時成立。`rote.py` 的兩個函式都 import 它，不各自再寫一次條件。

### `adapters.py` 第 3 段：八個工具

五個 parser（`parse_github_issue`／`parse_discord_message`／`parse_support_email`／
`parse_pr_diff`／`parse_changelog`）、兩個 normalizer、`validate`，加上 `default_registry()`。
共用的私有取值器 `_arg`／`_pick`／`_mapping`／`_sequence`／`_text`／`_whole`：缺欄位或型別不對
一律 `PermanentError`，**沒有一處回 `None` 假裝欄位存在**。

原稿未指定、由本 Phase 裁決的四件事（已寫回 Phase 文件 §5）：

1. **parser 多帶一個 `encoding`**（`"github"`／`"file"`），對應 O6 核定紀錄的 `id_encoder` 欄
   （`github_ticket_id`／`github_release_id` vs「檔案提供」）。normalizer 靠它決定 ID 與穩定 user
   是用 Phase 13 的編碼函式算，還是檔案自己帶；parser 本身**不產生 ID 或 user**，只把算 ID 需要的
   來源事實（`owner`／`repo`／`number`）原樣往下傳。
2. **`validate` 用 `source` 分派，不是用 `kind`**。canonical `Release` 的 `kind` 已經是
   `renamed`／`changed`／`removed`（Phase 31 的必填欄位），不能同時兼任「ticket 還是 release」的
   判別欄位；`TicketSource` 與 `ReleaseSource` 的值互斥，所以讀 `candidate["source"]` 就夠。
   **`kind` 仍是 parser 輸出的判別欄位**（`PARSER_KIND` 契約不變），`_require_kind` 照原稿在
   `validate` **之前**擋掉「PR diff 拿去做 Ticket」。
3. **`parse_pr_diff` 的 `changes` 依 `feature` 升序**。Phase 13 的 `sub_release_ids` 是「依 Feature
   名稱升序配 `k`」；若照 body 條列順序回傳，同一個 PR 換個條列順序就會得到不同的 `r_` ID。
   排序後 `changes[k-1]` 與 `github_release_id(..., k)` 與 Phase 13 完全對齊
   （PR fixture：`k=1` 是 `Legacy Export`、`k=2` 是 `Prepare`）。
4. **`validate` 對 `ingress` 用函式內 import**。`adapters.py` 需要 Phase 31 的
   `validate_ticket`／`validate_release`，但 Phase 37 很可能讓 `ingress._normalize` 反向 import
   `rote`，那會形成 `ingress → rote → adapters → ingress` 的循環。延後到呼叫時才載入，
   `rote.py → adapters.py` 的單向相依（00A §6.8）在兩個方向都成立。

### `rote.py` 第 5 段：記錄步驟的驗證與執行

| 名稱 | 形狀 | 邏輯 |
|---|---|---|
| `validate_recorded_steps` | `(steps: Sequence[ProcStep]) -> None` | 三件事：至少一步且 `steps[-1].tool == FINAL_TOOL`；每個工具名在 `TOOL_NAMES` 且 `validate` 只能在最後一步；每個參數值是 JSONPath（唯一例外走 `is_index_literal`）。只看形狀，不解析 path 也不碰事件。 |
| `execute_recorded_steps` | `(event, steps, registry) -> JSONValue` | **先驗證再跑**，所以不合法時工具呼叫數是 0（F07）。`root = {"steps": outputs, "event": {...}}`，`root["steps"]` 與 `outputs` 是同一個 list 物件，append 之後上一步的輸出立刻能被 `$steps[k]` 引用。值只在執行當下解析，`ProcStep.args` 進來是什麼 path、出去還是同一個 path。 |

`event.headers`／`event.payload` 在組 `root` 時各包一次 `dict(...)`：`RawEvent` 宣告的是
`Mapping`，`JSONValue` 要的是 `dict`，不轉會過不了 mypy strict，而且順手保證工具改不到原事件。

## 5. 遇到的問題與解法

1. **「未核定來源要 gate failure」與 COMMON.md「你的檔案全綠」直接衝突**：Phase 文件要求
   「測試必須以明確 gate failure 結束、不是 skip、不得補臨時 mapping」，COMMON.md 要求最後
   `uv run pytest tests -q -W error` 我的檔案全綠。採用 repo 既有前例
   （`tests/integration/test_o6_github_mapping.py` 的 `@pytest.mark.xfail(not PR_APPROVED,
   strict=True, reason="O6 尚未核定 …")`）：`pytest.param(..., marks=pytest.mark.xfail(strict=True))`
   同時滿足三件事——報告逐列印出 `XFAIL … O6 尚未核定 <domain>/<event_type>`（不是 skip）、
   斷言真的執行並失敗、而且**一旦有人補臨時 mapping 讓它通過就會 XPASS 被 strict 判成紅燈**。
   裁決依據：設計 > 00A > Phase 文件，且與 P31 同一份 gate 用同一種表達。已寫進文件（第 6 節第 3 點）。
2. **`kind` 一名二用**：Phase 文件要 parser 輸出帶 `kind`（ticket／release）給 normalizer 配對檢查，
   但 Phase 31 的 canonical `Release` 也有必填的 `kind`（`renamed`／`changed`／`removed`）。
   若 normalizer 輸出把 `kind` 寫成 `"release"`，`validate_release` 會當場丟
   `IngressError("Release kind 不合法")`。解法是把兩者分層：`kind` 只出現在 **parser 輸出**
   （配對檢查照原稿在 `validate` 之前擋），`validate` 改用互斥的 `source` 值分派。
3. **`normalize_release` 的 `k` 與 Phase 13 的 `sub_release_ids` 可能對不上**：P13 依 Feature 名稱
   升序配 `k`，Phase 36 原稿是 `changes[k-1]` 的位置式。讓 `parse_pr_diff` 在回傳前依 `feature`
   升序排序，兩邊就完全一致，同一個 PR 條列順序不同也得到相同的 `r_` ID。
4. **潛在的循環 import**：`adapters.py` 需要 `ingress.validate_ticket`／`validate_release`，
   但 Phase 37 要把 `rote` 接進 `ingress._normalize`。模組層 import 會變成
   `ingress → rote → adapters → ingress`（`ingress` 半初始化時 `validate_ticket` 還沒定義，
   會炸 `ImportError`）。改成 `validate()` 內部 import，並在 docstring 與報告第 7 節提醒 P37。
5. **mypy strict 的 `Mapping` vs `dict`**：`JSONValue` 的 union 成員是 `dict[str, JSONValue]`，
   所以私有取值器一律回 `dict[str, JSONValue]`（不是 `Mapping`），`execute_recorded_steps` 組
   `root` 時也要 `dict(event.headers)`／`dict(event.payload)`。一開始寫成 `Mapping` 產生 33 個
   `arg-type` 錯誤，改回 `dict` 後 0 錯，全程沒有用 `# type: ignore`。
6. **Phase 文件 Task 3 的 `FIXTURES = Path("tests/fixtures")` 是相對路徑**：CWD 不在 repo 根目錄時
   讀不到 fixture。改成 `REPO_ROOT = Path(__file__).resolve().parents[2]`，與 repo 既有寫法一致
   （與 phase35-report 第 5 節第 1 點同一個坑）。已修文件。
7. **手動匯入來源是「批次」而不是單筆**：`manual/*.json` 的形狀是
   `{"source", "domain", "adapter", "batch_id", "items": [...]}`，而 Phase 文件固定的
   `steps_for()` 只給 parser 一個 `payload`。`_batch_item` 的規則是：`payload` 有 `items` 就取
   **第一筆**，沒有就把 `payload` 本身當一筆（Agent 想指定第幾筆時記 `$event.payload.items[k]`，
   index 仍在 path 裡、不是字面值）。多筆批次的逐筆展開是 Phase 42 固定匯入的事，本 Phase 的工具
   只處理「一次一筆」。三個手動來源都在 gate 中，這條路徑目前沒有被當成已驗收。

  也沒有被加列。**不得宣稱 PR／Discord／email／changelog 的 adapter 已驗收。**
- **O2／O3／O5／O1 與本 Phase 無關**：零 DynamoDB 寫入、零 S3、零發布切點、零模型呼叫。

給 P37 的介面（`src/training_kb/adapters.py`）：

| 名稱 | 簽名／值 | 備註 |
|---|---|---|
| `TOOL_NAMES` | `frozenset[str]`，八個名稱 | **固定八個**，不得動態擴充。 |
| `FINAL_TOOL` | `= "validate"` | 最後一步的工具名。 |
| `PATH_ROOTS` | `= ("$event", "$steps")` | 也可直接餵給 `str.startswith`。 |
| `SUB_RELEASE_INDEX` | `= "index"` | F14 子 Release 序號的參數名。 |
| `PARSER_KIND` | `Mapping[str, str]`，五個 parser → `"ticket"`／`"release"` | P37 要「對每一筆 change 重跑」時用它挑 normalizer。 |
| `AdapterTool` | `Callable[[Mapping[str, JSONValue]], JSONValue]` | 工具**拿不到 `Settings`**，所以 `project_id` 一律 `DEFAULT_PROJECT_ID`。 |
| `ToolRegistry` | `@dataclass(frozen=True)`；`tools: Mapping[str, AdapterTool]`；`run(name, arguments) -> JSONValue` | 建構與 `run()` 都比對白名單。**沒有註冊 API**，要換工具就建新的 registry。 |

給 P37 的介面（`src/training_kb/rote.py` 第 5 段）：

| 名稱 | 簽名 | 備註 |
|---|---|---|
| `validate_recorded_steps` | `(steps: Sequence[ProcStep]) -> None` | 保存 PROC **之前**一定要過這關（ING Rule 12／13）。合法回 `None`，不合法丟 `PermanentError`。 |
| `execute_recorded_steps` | `(event: RawEvent, steps: Sequence[ProcStep], registry: ToolRegistry) -> JSONValue` | 回**最後一步的輸出**，也就是 `validate` 回的 `model_dump(mode="json")` dict。內部會先呼叫 `validate_recorded_steps`，P37 不必再驗一次。 |

P37 一定要知道的七件事：

1. **`execute_recorded_steps` 回的是 dict，不是 `Ticket`／`Release` 物件**。要物件請用同一組
   Phase 31 validator（`validate_ticket(canonical)`／`validate_release(canonical)`）再轉一次；
   canonical dict 已經是 `model_dump(mode="json")`，再驗一次會得到同一個物件（冪等）。
   判斷是哪一種用 `canonical["source"]`（`TicketSource` vs `ReleaseSource` 互斥），或看你挑的
   parser 在 `PARSER_KIND` 裡是 `"ticket"` 還是 `"release"`。
2. **F14 多筆子 Release 是 P37 的迴圈**。本 Phase 只提供單筆：`parse_pr_diff` 回
   `{"kind": "release", "changes": [...]}`（依 `feature` 升序），P37 要對 `k = 1..len(changes)`
   各跑一次 `normalize_release → validate`，每筆各自接受、共用同一個 `source_event_id`。
   序列裡的 `index` 要記成**字面值字串**（`"1"`、`"2"`），`execute_recorded_steps` 會在執行時
   `int()` 回來；`k` 超出長度丟 `PermanentError`，不會回猜出來的空 Release。
3. **`adapters.validate` 內部是函式內 import `ingress`**，所以 `ingress` 可以安全地反向 import
   `rote`。**但請不要把 `from training_kb.adapters import ...` 加到 `ingress.py` 的模組層**，
   那會直接把循環變回來。
4. **失敗一律是 `PermanentError`（或它的子類 `IngressError`）**。JSONPath 違規、工具不在白名單、
   parser／normalizer 配對錯、`index` 超界都是 `PermanentError`；欄位缺漏由 Phase 31 丟
   `IngressError`（帶 `fields`）。整條接入要照 F07 回失敗，**不得**寫入半成品或成功 PROC。
5. **記錄 PROC 之前先 `validate_recorded_steps`**。Agent 產的序列如果把事件真值寫進 `args`
   （例如 `{"text": "找不到按鈕"}`），這裡就會擋下來——這是 Rule 12 的最後一道防線，
   不要用「反正等一下 validate 會過」跳過它。
6. **`ToolRegistry` 沒有註冊 API**。要在測試裡放 fake 工具，請用 `ToolRegistry(tools={...})`
   自己建一個（名稱仍只能是那八個），不要去改 `default_registry()` 回來的物件（它是 frozen）。
7. **`root` 的形狀是契約的一部分**：`{"event": {"domain", "adapter", "event_type", "headers",
   "payload"}, "steps": [...]}`。Agent 產 path 時 `$event.payload.…` 指原始 payload、
   `$event.headers.…` 指小寫 header、`$steps[k]` 指第 k 步（從 0）的輸出。

## 9. 未完成／疑慮

1. **四個來源的 adapter 已實作但未驗收**：`parse_pr_diff`／`parse_discord_message`／
   `parse_support_email`／`parse_changelog` 的程式碼都能跑通（第 4 節的人工驗收），但 O6 的
   `approved_by` 是空的，所以測試維持 XFAIL。**這不等於它們對**——核定紀錄一旦補上，
   strict xfail 會變成 XPASS 紅燈，那時要有人真的核對欄位對應（尤其手動匯入的
   `stable_user_source` 是「檔案 author」，目前只做 `stable_user_from_import` 的格式檢查）。
2. **手動匯入只取第一筆 `items`**：`_batch_item` 的「有 `items` 就取 `[0]`」是本 Phase 的裁決
   （第 5 節第 7 點），Phase 文件與 00A 都沒有規定批次怎麼展開。多筆批次的正解可能是 Phase 42 的
   固定匯入，或是 Agent 記 `$event.payload.items[k]`（這條 path 完全合法）。目前的 fixture 每個
   批次只有一筆，所以看不出差別。
3. **PR body 的抽取只認三種 `kind` 前綴的條列**：`- <renamed|changed|removed>: …`。fixture 就是
   這個格式，但真實 PR body 不會這麼規矩。ING Rule 14／REL Rule 1（從 PR diff 或 changelog 抽出
   四欄）的 primary 在 Phase 37，那裡可能要用 Agent 而不是這個正則；本 Phase 的 `parse_pr_diff`
   是「可重放的確定性版本」，不是唯一的抽取路徑。
4. **`changes` 排序與 `sub_release_ids` 的一致性沒有被測試鎖定**：兩邊都依 `feature` 升序，但目前
   沒有一條測試同時呼叫兩者比對（那條測試會落在 gate 中的 PR 列）。如果之後有人改掉任一邊的排序，
   同一個 PR 會長出兩組不同的 `r_` ID 而不會被現有測試發現。建議 P37 在
   `test_release_extraction.py` 加一條交叉比對。
5. **`resolve_jsonpath` 的「不改動 root」只由回傳值相等間接證明**：測試比的是值不是 identity，
   實作上回傳的確實是同一個物件（沒有複製）。如果 P37 想倚賴「工具拿到的是同一份記憶體」，
   那是目前的實際行為但沒有測試鎖定。
6. **`validate` 的函式內 import 是防禦性的**：目前 `ingress` 並沒有 import `rote`，所以就算寫在
   模組層也還不會壞。這是為 P37 預留的，如果 P37 決定改用別的接線方式（例如把 `Rote` 注入
   `ingress`），可以把它移回模組層——但請連同 docstring 一起改，不要只搬 import。
