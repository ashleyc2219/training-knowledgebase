### 1.1 `src/training_kb/pipelines/release.py`（修改，只用 Edit 追加 `# ---- Phase 52 ----` 區段）

Phase 49／50／51 的區段**一行都沒有動**。本 Phase 在檔尾追加兩段。

**（a）RETIRE 與共用小工具**

| 名稱 | 做什麼 |
|---|---|
| `RETIRE_RECORD_NAME = "retire"`、`SUCCESSORS_NAME = "successors"`、`HIT_REF_SEPARATOR = "#"` | 三個檔名／格式常數，不在別處重打。 |
| `retire_for_release(release, hits, *, repository, successor_by_slug, now) -> tuple[str, ...]` | 入口只接受 `removed`（其他 `kind` 丟 `PermanentError`）。先對 `hit.slug` **去重再排序**，所以呼叫次數等於篇數不是命中步驟數；每篇呼叫 Phase 26 的 `retire_tutorial`，`successor` 只從 `successor_by_slug.get(slug)` 取。 |
| `_text(state, field)` | 取一個必填非空字串，缺了就說出缺哪一個欄位。 |
| `_load_release(state, repository)` | 用 `input_ref` 把 canonical 輸入讀回成 `Release`；`ValidationError`／`ValueError` 一律轉 `PermanentError`（ASL 的 `ErrorEquals` 比對的是類別名）。 |
| `_load_successors(repository, operation_id)` | 讀 `operations/<op>/successors.json`；檔案不存在就是空 dict（F19／F54）。 |
| `_hit_ref(hit)`／`_hits(state)` | `StepHit` ↔ `"<version_id>#<number>"`；slug 用 Phase 20 的 `parse_version_id` 還原，不再查表。 |
| `task_retire(state, deps)` | RETIRE 分支。順序固定是**先退役、再重寫索引頁、最後寫紀錄**。 |

**`task_retire` 的三步與 D-83**

```text
action != "RETIRE" -------------------------> 原樣回傳（本機序列會叫到它，雲端由 ChooseAction 跳過）
retire_for_release(...) --------------------> 每篇 status=retired、successor 只來自維護者
Publisher(repo, SiteRenderer(), ops)
    ._write_tutorial_index(slug) 逐篇 -------> D-83：只重寫教學索引頁
operations/<op>/retire.json 不存在才寫 ------> 同 operation_id 重送不重寫（retired_at 不被改掉）
```

順序不可顛倒：索引頁的內容取自 `repository.get_tutorial(slug)`，`status` 還沒變成 `retired` 之前寫出去的頁面不會有退役區塊。`_write_tutorial_index` 走 `_put_index` → `_put_public_object(..., if_none_match=False)`，索引是可重建的投影所以允許覆寫；**已發布版本頁一個 byte 都不動**（協定 A 下 `_version_problems` 會擋、`_put_public_object` 會比對 bytes），也不呼叫 `prepare`／`inspect`／`commit`、不建立任何新版本。

**（b）七個 Task、固定 state 與 handler**

`RELEASE_STATE_FIELDS` 是 00A §7 的十一個欄位。七個 Task 的形狀一致：先檢查前置條件，不適用就 `return dict(state)`，適用才呼叫 Phase 49–51 或 Phase 25，再把**小型結果**併回 state。

| Task | 前置條件 | 呼叫 | 寫回 state |
|---|---|---|---|
| `task_locate_feature` | 無（第一個節點） | P49 `locate_feature` | `release_id`、`feature_id`（可為 `None`）、`hit_refs=[]`、`prepared_version_ids=[]` |
| `task_find_steps` | `feature_id` 非空 | P50 `find_release_hits` | `hit_refs` |
| `task_safety_net` | 無 | P50 `needs_safety_net`／`safety_net` | `hit_refs`（聯集）、`action` |
| `task_prepare_update` | `action == "UPDATE"` | P51 `prepare_update` | `prepared_version_ids` |
| `task_publish_batch` | `action == "UPDATE"` 且有版本 | P24／P25 `Publisher` | `publish_request_ref` |
| `task_update_aliases` | `action == "UPDATE"` 且 `kind == renamed` | P49 `update_feature_aliases` | `alias_update` |
| `task_retire` | `action == "RETIRE"` | 見上 | `result_ref` |

三個設計決定寫在程式的 docstring 裡，也列在 Phase 文件的「實作後修正」：

1. **聯集在 `task_safety_net` 這一層做**（`set(direct) | set(net)`）：P50 的 `safety_net` 只回補漏證據，補漏永遠只會新增，不可能抹掉明確命中。觸發條件是「直接反查為零」**或** `needs_safety_net(...)` 成立（F16）。
2. **`_release_action`**：`removed` → `RETIRE`（即使零命中）；有命中且 `renamed`／`changed` → `UPDATE`；其餘 → `KEEP`（F18）。
3. **`task_locate_feature` 順手把 `hit_refs`／`prepared_version_ids` 設成空值**：雲端的 KEEP 與 RETIRE 兩條分支都跳過 `PrepareUpdate`，在第一個節點給定初值，三條分支的輸出形狀才一致（文件 §2 要求成功輸出列得出這幾個欄位）。

`task_publish_batch` 把整組 `version_id` 包成**一個** `PublishRequest`（F49），`commit` 的 `PublishResult.failed` 有值時丟 `PublishError` 而不是正常回傳——形狀與 `ticket.task_publish_version` 相同，理由也相同：回一個正常 state 會讓執行走到 `Succeeded`，從外面看不出這次其實沒發布。

`run_release_update` 是本機序列版，`release_update_handler` 依 `event["task"]` **只跑一個 Task**（D-24／D-25），兩者共用 `_TASK_BY_NAME`，相依用模組層 `_DEPS` 快取。**handler 不寫 try／except**：`TransientError` 要讓 Retry 抓、`PermanentError` 要讓 Catch 抓。

### 1.2 `infra/stepfunctions/release-update/v1.json`（新增）

七個 Task state 全部由 Phase 29 的 `task_state(ARN, next)` 產生，再補上 `Parameters`，所以 `Retry`（D-53 的兩條 retrier）／`Catch`（單一 `States.ALL` → `PipelineFailed`）／`TimeoutSeconds`（120）逐字來自 `pipelines/asl.py`，本檔不抄字面值。`Resource` 一律 `${PipelineTaskFunctionArn}`（直接函式 ARN，**沒有** `Payload` 外層，D-49）。`ChooseAction` 是 Choice（`Default="RecordKeep"`、沒有 `Retry`／`Catch`／`End`），`RecordKeep` 是 `Pass`（`Result="KEEP"`、`ResultPath="$.action"`），唯一成功終點 `Succeeded`，唯一失敗終點 `PipelineFailed`。`RetireTutorials.Next == "Succeeded"`——**不經 `PublishBatch`**。檔案本身就是 `canonical_json(...)` 的輸出（7724 bytes），與 S3 快照同一份 bytes。

### Minor 3：`retire.json` 的 check-then-write

`if repository.get_object(ref) is None: put_object(...)` 改成
`try: put_object(..., if_none_match=True) except ObjectAlreadyExists: pass`（比照
`asl.save_asl_snapshot`）。同一個 operation 兩個 execution 並發時，先查再寫會留下空窗，而且
輸家會被 `ObjectAlreadyExists` 打進 `PipelineFailed`——但「別人已經寫好同一份紀錄」不是失敗。
既有的重送冪等測試照樣綠（`retire.json` 的 bytes 與寫入次數都沒變）。

### Minor 4：放寬過頭的 log group 斷言

`tests/unit/infra/test_ticket_asl.py::test_state_machine_logs_to_its_own_group` 我上一輪只是把
`resource_count_is(..., 1)` 拿掉，變成「三台 machine 任一命中就過」。改成**用邏輯 ID 把兩邊接
起來**：先依 `LogGroupName` 找出 ticket 的 group，再依 `StateMachineName` 找出 ticket 的
machine，斷言它的 `LoggingConfiguration.Destinations` 真的指向那一個 group、`Level == "ALL"`。
這樣「ticket 記到別人的 group」會轉紅。

### Minor 6：`retire_for_release` 的非原子性

docstring 補一段：第 k 篇失敗時前面 k-1 篇已經是 `retired`、`retire.json` 不會寫、整次走
Catch → `PipelineFailed`；重跑同一個 `operation_id` 時已退役的那幾篇是零次 `update_meta`
（`retire_tutorial` 冪等），所以會走到同一個失敗點再失敗一次。刻意不做補償的理由也寫進去了。

### Minor 7：延後項（controller 記 ledger）

pipeline 共通的（`ticket_analysis_handler`／`feedback_review_handler` 也一樣），依 controller
裁決由 final 修正波統一在 `pipeline_task_handler` 處理，本回合**不改**。
