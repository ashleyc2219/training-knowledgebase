本 Phase 產出的**公開名稱與簽名**（給 Phase 48、55 用，逐字照 00A §6.9）：

```python
MIN_CANDIDATE_FEEDBACK = 5
PROPOSE_NODE = "propose_rule"

@dataclass(frozen=True)
class CandidateGroup:
    version_id: str
    category: str
    feedback_ids: tuple[str, ...]

def candidate_groups(feedback: Iterable[Feedback],
                     approved: frozenset[str]) -> tuple[CandidateGroup, ...]: ...
def candidate_rule_id(group: CandidateGroup) -> str: ...
def propose_candidate(group: CandidateGroup, *, writer: Writer, repo: Repository,
                      operation_id: str, rule_id: str) -> AuthoringRule: ...
```

module-private（不是跨模組 API，Phase 48 不要 import）：`_require_rule_text(value) -> str`、
`_require_step_type(value) -> StepType`、`_evidence_comments(group, *, repo) -> tuple[str, ...]`。

邏輯：

- **`candidate_groups`** 是純函式，完全不呼叫模型、不碰 `Repository`。分桶 key 是
  `(tutorial_version, category)` **兩欄**，所以「v1 三筆 + v2 兩筆」總數雖然是五也不成組
  （設計 F25）；同桶內先用 `set` 去重再數，同一筆回饋被讀兩次撐不起門檻。`category` 是
  `None` 或 `待分類` 時都不在核定類別表裡，直接跳過。輸出依 `(version_id, category)` 升序、
  每組 ID 升序，這個順序是 `candidate_rule_id` 能決定性的前提。全程沒有讀 `rating`，也沒有
  呼叫 `is_weak`：能提規則不代表這一版是弱教學（設計 F26）。
  `approved` 是**參數**不是查詢——要不要去讀 `CONFIG#feedback_categories` 是 Phase 48
  呼叫端的事，本 Phase 對 Phase 43 沒有任何程式相依。
- **`candidate_rule_id`** 把 `[version_id, category, list(feedback_ids)]` 用
  `json.dumps(..., ensure_ascii=False, separators=(",", ":"))` 編成 UTF-8 bytes，取
  SHA-256 前 8 個十六進位字元，前綴 `R-`。**編碼方式是契約的一部分**：換掉
  `ensure_ascii`、`separators` 或排序方式，既有 item 的 ID 就對不上。三個期望值已在測試裡
  釘死：`R-f6c7a0d2`（v1、找不到按鈕、`f_1..f_5`）、`R-7e16d4f3`（同組換成 v2）、
  `R-ad0afde8`（設計 §11.2 的八筆證據，與 00A §6.9 的範例一致）。
- **`propose_candidate`** 的順序固定（Phase 文件 §6）：
  1. `len(set(group.feedback_ids)) < 5` → `ContentError`，**連模型都不打**。模型層
     `AuthoringRule.evidence_has_five_distinct_ids`（D-66）是第二道防線，不是唯一防線。
  2. `repo.get_meta(rule_pk(rule_id), AuthoringRule)` 命中 → 原樣回傳既有規則，不覆寫、
     不再打模型。因為這一步先擋，流程上不會走到 `put_meta(create_only=True)` 的撞鍵。
  3. `prompt_propose_rule(...)` → `writer.generate_json(..., RuleProposal, node=PROPOSE_NODE)`，
     **每組最多一次**。
  4. `_require_rule_text` 與 `_require_step_type` 驗證模型只該決定的兩個欄位；不合法一律
     `ContentError`（`PermanentError` 的子類，ASL 的 Catch 會導向失敗終點）。
  5. 組 `AuthoringRule`：`rule_id`／`evidence`／`derived_from`／`status`／`applied_to`
     **一律由程式依已驗證的 group 填**，模型回傳的 `evidence` 與 `derived_from` 讀完就丟
     （它們留在 schema 裡只是為了在 trace 中比對）。`status` 永遠是 `RuleStatus.CANDIDATE`、
     `applied_to` 永遠是 `[]`。
  6. `repo.put_meta(candidate)`（`create_only=True` 是預設值）。
  keyword 是 `repo=` 不是 `repository=`（00A §6.9，Phase 48 已照這個名稱呼叫）。
  判斷類參數 `max_tokens 512`、`temperature 0.1` 由 Phase 15／18 的 `inference_config`
  依 schema 的 `$id` 決定（`RuleProposal` 不在 `WRITING_MAX_TOKENS` 表裡，所以是 512），
  本 Phase **不重設**。

## 5. 遇到的問題與解法

1. **同檔併行的 import 區塊競態。** `pipelines/feedback.py` 在同一波次由 P44／P45／P47
   同時追加，`E402` 又不允許把 import 放在模組中段，所以四個人的 import 必須併進同一個
   已排序的區塊。前兩次 Edit 都因為「檔案在讀取後被改過」而被擋下（正是 Edit 該擋的情況），
   第三次重讀後把自己的四行併進去成功。**沒有**用 Write、沒有 `git stash`／`checkout --`。
2. **`mypy --strict` 看不出分桶 key 的第二欄是 `str`。** `Feedback.category` 是
   `str | None`，Phase 文件 §7 的片段 `if item.category in approved:` 不會讓 mypy 窄化，
   `buckets[(item.tutorial_version, item.category)]` 會型別錯誤。改成
   `category = item.category` ＋ `if category is None or category not in approved: continue`，
   語意完全相同（`None` 本來就不可能在核定類別表裡）。P44 的 `_top_category` 後來也採同一寫法。
3. **文件片段的 `bool` 檢查其實永遠不會執行。** `if not isinstance(value, str) or isinstance(value, bool)`
   的第二段只在 `value` 已經是 `str` 時才求值，`str` 不可能是 `bool`。把兩段對調成
   `if isinstance(value, bool) or not isinstance(value, str)`，「`True` 不是合法值」這句話
   才是真的在擋。行為不變（`True` 本來就會被第一段擋掉），但意圖與註解一致了。
4. **`REV` Rule 9 的靜態斷言不能用整份字串比對。** `"propose_candidate" not in source` 會被
   將來某支檔的註解（例如「本模組不呼叫 `propose_candidate`」）誤判成違規。改成用 `ast`
   取程式碼中真正引用／定義到的名稱，註解與 docstring 自然被排除。第一版漏收 `FunctionDef`
   導致正向斷言失敗（§3 Task 3 的中間紅燈），補上後正反兩面都成立。
5. **整套 pytest 有別的 Phase 進行中的紅燈（不是我的）。** 依 COMMON.md R3.5 處理：
   - 第一次跑：`tests/unit/pipelines/test_ticket_flow.py` 收集失敗
     （`cannot import name 'TICKET_ANALYSIS_TASKS' from 'training_kb.pipelines.ticket'`），
     用 `--ignore=tests/unit/pipelines/test_ticket_flow.py` 排除後得到
     **`1 failed, 1038 passed, 23 skipped, 11 xfailed, 8 errors`**。那個 1 failed 是
     `tests/unit/test_site_pages.py::test_site_index_links_each_tutorial_index`、8 errors 是
     `tests/integration/test_batch_publish_cutpoints.py` 的 fixture
     （`PermanentError: prepare-meeting@v2 缺少 supersedes`，來自 `src/training_kb/site.py:154`）。
     兩者都來自同時進行中的 site／publishing Phase（commit `bd00704 feat(site): 退役頁與索引只列已發布版本`），
     與 `pipelines/feedback.py`、`writing/prompts.py` 沒有任何相依，**我沒有去修別人的測試**。
   - 收尾重跑（`040ffbb` 之後、不需要 `--ignore`）：**`1 failed, 1105 passed, 23 skipped,
     11 xfailed, 8 errors`**。此時 `test_ticket_flow.py` 與 `test_site_pages.py` 都已由對應

### 7.2 給 Phase 48（W3）的介面清單

`from training_kb.pipelines.feedback import ...`：

```python
MIN_CANDIDATE_FEEDBACK: int = 5
PROPOSE_NODE: str = "propose_rule"          # generate_json 的 node=，也是 ASL 狀態名

@dataclass(frozen=True)
class CandidateGroup:
    version_id: str
    category: str
    feedback_ids: tuple[str, ...]

def candidate_groups(feedback: Iterable[Feedback],
                     approved: frozenset[str]) -> tuple[CandidateGroup, ...]
def candidate_rule_id(group: CandidateGroup) -> str
def propose_candidate(group: CandidateGroup, *, writer: Writer, repo: Repository,
                      operation_id: str, rule_id: str) -> AuthoringRule
```

呼叫端要知道的五件事：

1. **keyword 是 `repo=`**，不是 `repository=`（00A §6.9）。`writer`／`repo`／`operation_id`／
   `rule_id` 四個都是 keyword-only。
2. **`rule_id` 一律傳 `candidate_rule_id(group)`**。傳別的值（例如時間戳或隨機值）會讓
   同一組證據每次都產生新規則，去重就失效。設計 §11.4 的 `R-007` 是 Phase 56 的種子直接
   指定的既有 ID，**不經** `candidate_rule_id`。
3. **`approved` 由呼叫端準備**。Phase 43 在 `ingress.py` 追加的
   `approved_categories(repository)` 是 Phase 48 要呼叫的，`candidate_groups` 只收
   `frozenset[str]`；本 Phase 沒有 import 它（也不該 import）。
4. **`propose_candidate` 每組最多打一次模型**，而且只有在 `RULE#<rule_id>` 不存在時才打。
   失敗型別一律是 `ContentError`（`PermanentError` 子類）→ ASL 用 Catch 導向失敗終點，
   不要放進 Retry。
5. **candidate 分支與弱教學分支互不依賴**：`candidate_groups` 不讀 `rating`、不呼叫
   `is_weak`、不需要 `WeakTarget`；兩條分支在 Phase 48 各自跑，其中一條沒命中不影響另一條。

`from training_kb.writing.prompts import prompt_propose_rule`（`(version_id, category,
feedback_ids, comments) -> (system, user)`）——只有 `propose_candidate` 會用它，Phase 48
不需要直接呼叫。
