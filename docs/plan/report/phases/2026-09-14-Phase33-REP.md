# Phase 33：Rote 結構簽名與 STABLE_KEYS — 實作報告

## 1. 實作內容（含實作邏輯）

新建 `src/training_kb/rote.py`（owner = P33），只做「原始事件 → 16 字元結構簽名」的純函式轉換：
不連 AWS、不呼叫模型、不讀 `tests/` 路徑、不碰 `PROC#` item。

- **`RawEvent`**（`@dataclass(frozen=True)`）：`domain`、`adapter`、`event_type`、
  `headers: Mapping[str, str]`、`payload: Mapping[str, JSONValue]`。`JSONValue` 從 P29 的
  `training_kb.pipelines.common` import（D-31：全專案只有一份定義）。
- **`HEADER_PREFIXES = ("x-github-", "x-discord-", "x-zendesk-")`**：「哪些 header **名稱**有資格
  進簽名」的前綴白名單；只取名稱，永遠不取值。
- **`STABLE_KEYS`**：逐條抄寫 Phase 13 核定紀錄中 `approved_by` 非空的列，目前只有
  `("github.com", "issues") -> {action, issue, repository, sender}`。`pull_request` 與三個 manual
  來源以註解保留位置，核定前不加。
- **`event_stable_keys(event)`**：兩道 gate 後回「核定清單 ∩ payload 實際出現的最上層 key」。
  1. `domain` 或 `adapter` 為空 → `PermanentError("RawEvent 缺少可信入口設定的 domain 或 adapter")`；
  2. `(domain, event_type)` 不在 `STABLE_KEYS` → `PermanentError(... 尚無核定 STABLE_KEYS；O6 未核對前為 blocked)`。
  兩條路徑都**沒有 fallback 分支**，不會回一個猜出來的簽名（O6 gate）。
  取交集而非整份核定清單是刻意的：缺一個核定 key 屬於「結構不同」必須換簽名，
  P34 的 Jaccard 也才有比較對象（Phase 文件 §7、§10 第二列）。
- **`signature_shape(event) -> dict[str, object]`**：
  `{"domain": ..., "headers": [小寫去重排序且只留三個前綴的 header 名稱], "keys": sorted(交集)}`。
  `adapter` **刻意不進 shape**（D-09／D19，範圍欄位存在 `ProvenWorkflow.domain`／`adapter`）。
- **`structure_signature(event) -> str`**：
  `hashlib.sha1(json.dumps(shape, sort_keys=True).encode()).hexdigest()[:16]`，逐字照設計 §7.2；
  **不加 `separators`**（預設 `", "`／`": "`，改了 bytes 就不同）。docstring 明寫 SHA-1 只是結構索引、
  不是驗簽，安全邊界在 P30 的 HMAC。

檔案分成六段並標好後續追加位置：1 來源脈絡與白名單（P33）、2 結構簽名（P33）、
3 兩層命中與候選排序（P34）、4 PROC 生命週期（P35）、5 記錄步驟的驗證與執行（P36）、
6 三層 normalize 與成功提交（P37）。3–6 目前只有段落註解。

測試兩支：`tests/unit/rote/test_signature.py`（7 個案例）與
`tests/integration/test_o6_stable_keys.py`（3 passed + 1 xfailed；不需要真實 AWS 故不標 `aws`）。
`tests/unit/rote/` 是新目錄，比照 `tests/unit/pipelines/` 不放 `__init__.py`。

## 5. 遇到的問題與解法

1. **Task 3 拿不到 Phase 文件寫的紅燈訊號**（P13 已交付、Task 1 的 literal 已是最終值）。
   解法：不偽造紅燈，改以「暫時改壞 `STABLE_KEYS` → 觀察兩個 FAIL → 還原」證明測試有偵測力，
   並把這段寫進 Phase 文件的 Step 2（見第 6 節）。
2. **fixture 路徑用相對路徑或 `__file__` 推導**。Phase 文件寫 `Path("tests/fixtures")`，但
   `tests/integration/` 既有檔案（含 P13 的 `test_o6_fixture_contract.py`）一律用
   `Path(__file__).resolve().parents[2]`，且 repo 內沒有任何測試使用相對路徑。依「與既有程式一致」
   採用 `REPO_ROOT` 推導，並修 Phase 文件。行為與斷言內容不變。
3. **`mypy --strict` 下 `dict[str, object]` 的 invariance**：`signature_shape` 直接 `return {...}`
   會被推成 `dict[str, str | list[str]]`。因為有回傳型別註記，mypy 以型別脈絡推導字面值，實測通過，
   不需要額外 `cast`。
4. **spec 與 Phase 文件對空 `domain` 的落差**：`docs/spec/features/接入來源事件.feature` 的註解寫
   「domain 缺省為空字串」，但 00A §6.8／Phase 文件要求「`domain`／`adapter` 只能來自可信入口設定」，
   空值屬於缺可信脈絡。依「設計 > 00A > Phase 文件」與 O6 gate，採「空值一律 `PermanentError`」，
   不回可重放簽名。spec 檔屬維護者的規格來源，未修改（見第 9 節）。
5. **同 checkout 多 agent**：全程只 `git add <自己的檔案>` + `git commit -- <同一批檔案>`，
   期間其他 agent 的 commit（`feat(ingress): 固定事件與執行名稱`、`feat(ticket): 判斷同群 recurring`）
   穿插在 log 中，未造成衝突；沒有動 `ingress.py`／`source_ids.py`／`content.py`／`pipelines/`／`models.py`／
   `pyproject.toml`／`uv.lock`。
