### 寫入順序（固定，每個中斷點都有明確的對外可見狀態）

```text
get_version      -> 已存在且 published_at 非 None ------> ContentError「已發布」
scan_entity(FEATURE) + item_to_model -> known_feature_ids
validate_content -> 不合格一次丟出全部問題（ContentError）
_previous_markdown（supersedes 有值才讀前一版全文）
put_private_artifact  tutorials/<slug>/v<n>.md   --- 中斷 -> 產物留著，重送沿用（F36）
put_private_artifact  tutorials/<slug>/v<n>.diff --- 中斷 -> 同上
put_meta(TutorialVersion, published_at=None)     --- 中斷 -> 有產物沒 VERSION：verify False
_write_edges  REFERENCES x n -> SUPERSEDES -> APPLIED_TO x m --- 中斷 -> verify False
_verified -> _missing_parts 為空才回傳 VERSION item，否則 ContentError（不刪任何產物）
```

### 幾個關鍵決定

- **`published_at` 一律不寫、`Tutorial.current_version` 一律不碰**（D25、F37）。實測 `create_version`
  之後 `get_tutorial(slug).current_version` 仍是 `None`（Task 1 測試直接斷言）。
- **重送冪等**：先 `get_version`，已存在且未發布就跳過 `put_meta`（Phase 06 的 `create_only=True`
  會拒絕重複建立），只補寫產物與邊。S3 冪等由 Phase 22 的條件寫入保證（同 bytes 靜靜通過、
  不同 bytes 丟 `ContentError` 且保留既有物件）；邊的內容完全由 `plan`／`content` 決定，
  重寫同一筆是安全的，所以用無條件 `put_edge`。實測同 plan 第二次呼叫回傳值完全相同、
  `VERSION#…@v2` 的 `_revision` 仍是 1、VERSION item 只有兩筆（v1、v2）。
- **STEP 邊只帶 `type` 與 `text`**：`entity` 由 `put_edge` 自己從 PK 前綴算；`tutorial_version`／
  `number` 由 `STEP#<version_id>#<n>` 還原、`feature_id` 由 `target` 還原（00A §3.6）。
  實測 item 的屬性集合恰好是 `{PK, SK, target, entity, type, text}`，而 Phase 08 的
  `get_steps("prepare-meeting@v2")` 能把四步完整還原成 `TutorialStep`。
- **`APPLIED_TO` 只依 `plan.rules_applied` 產生**，不從前一版繼承（F29、D17）。
- **核對只用基表**：`_missing_parts`／`_has_edge`／`_step_edge_problems` 全部走完整 PK 的
  `query_pk(..., consistent=True)` 與具名 getter，沒有任何一處呼叫 `query_by_target`。
  應有步驟一律以 S3 全文 `parse_markdown().steps` 為權威，VERSION item 上沒有 `step_count`。
- **取既有 Feature 走 `item_to_model(item, Feature).feature_id`**，不直接 `Feature.model_validate(item)`
  （strict 模型不收 `PK`／`SK`／`entity`／`_revision`）。

### `_missing_parts` 檢查的七件事

1. VERSION item 存在（不存在就立刻返回，不再讀 S3）
2. TUTORIAL item 存在
3. `version.s3_key == markdown_key(slug, number)`
4. S3 全文存在（讀不到就返回，後面的核對沒有意義）
5. S3 差異檔存在
6. 每一步恰好一條 `REFERENCES` 邊、`target` 等於 SK 終點、該 Feature 真的存在
7. `supersedes` 有值時有 `SUPERSEDES` 邊；每個 `rules_applied` 都有 `APPLIED_TO` 邊

## 5. 遇到的問題與解法

1. **fixture 放哪裡。** 需求書 §7 說三個 Task 的 fixture 寫在 `tests/integration/conftest.py`，
   但 00A §3.2 的 conftest owner 是 Phase 06、修改者只有 Phase 07 與 Phase 08，本 Phase 不在其中，
   而且同一個 checkout 還有別的 agent 在跑。依「設計 > 00A > Phase 文件」裁決：共用器材寫在
   `test_create_version.py`，由 `test_version_complete.py` import；moto 的 `repository`／`table`／
   `bucket` 三個 fixture 仍然沿用 conftest。`tests/` 沒有 `__init__.py`，pytest 預設的 prepend
   import mode 會把 `tests/integration` 放進 `sys.path`，所以 `from test_create_version import ...`
   在整包跑與單檔跑都成立（兩種都實測過）。Phase 文件已改。
2. **`fail_next_put_meta()`／`fail_next_put_edge()` 兩個鉤子。** 原設計要掛在 conftest 的
   `repository` fixture 上；改成同檔的 `fail_next(repository, name)`：覆寫 instance 屬性讓下一次
   呼叫丟 `TransientError`，失敗那一次自己把原本的 bound method 放回去，所以「重送」走的是真實路徑。
3. **mypy strict 的 `str-bytes-safe`。** 需求書 Task 3 Step 3 的
   `f"...{rows[0].get('SK')}"` 過不了 strict（raw item 的值型別含 `bytes`），而本專案不用
   `# type: ignore`；改成先 `sort_key = str(rows[0].get("SK", ""))` 再比較與組訊息。Phase 文件已改。
4. **需求書 §7 程式片段的 `repo` 與 `repository` 混用。** 00A §3.2 明定 integration fixture 名稱
   一律是 `repository`；全部改成 `repository`，並讓 `seeded_feature`／`published_v1` 直接回傳
   同一個 `Repository`，測試簽名少一個重複參數。Phase 文件已改。
5. **Task 1 的 RED 訊號與文件預期略有差異。** 文件寫 `cannot import name 'create_version'`，

### 寫入順序（P24 的發布提交、P40 的 CREATE 都建立在這個順序上）

```text
1 S3  tutorials/<slug>/v<n>.md      （條件寫入，同 bytes 冪等）
2 S3  tutorials/<slug>/v<n>.diff    （v1 是 0 位元組）
3 DDB VERSION#<version_id> / META   （published_at = None，create_only）
4 DDB STEP#<version_id>#<i> / REFERENCES#FEATURE#<id>   每一步一筆，attrs 只有 type、text
5 DDB VERSION#<version_id> / SUPERSEDES#VERSION#<前一版>（supersedes 有值才寫）
6 DDB RULE#<rule_id> / APPLIED_TO#VERSION#<version_id>  每條 rules_applied 一筆
7 verify_version_complete == True 才回傳，否則 ContentError 且不刪任何產物
```

### 呼叫端要知道的七件事

1. **`plan` 必須先經 `allocate_version` 取號**：`create_version` 不配號、不讀 operation 紀錄。
   `VersionPlan.slug`／`number` 與 `version_id` 必須自洽（key helper 會用它們組 S3 key）。
2. **前置資料要先在**：`TUTORIAL#<slug>` item、每個 `step.feature_id` 對應的 `FEATURE#<id>` item；
   `plan.supersedes` 有值時，那一版的 VERSION item **與它的 S3 全文**都要讀得到，否則丟
   `ContentError`（「找不到前一版…」／「前一版…缺少 S3 全文…」）。
3. **錯誤型別**：全部是 `ContentError`（`PermanentError` 子類，不進 ASL Task Retry）——
   已發布不可覆寫、內容驗證失敗、前一版缺失、核對失敗；底層的 `TransientError`
   （S3 409、DynamoDB 暫時故障）原樣往上拋，交給 ASL Retry。
4. **重送安全**：同一份 plan 重複呼叫不會新增版本、不會重建 VERSION item、不會改 `_revision`，
   回傳值完全相同。中斷後重送會沿用同版號與同產物（F36）。
5. **P24 發布前一定要先問 `verify_version_complete`**：它回 `False` 的版本一律不可發布。
   核對只用基表一致讀取，不查 `by_target`（GSI 最終一致，剛寫入的邊可能還讀不到）。
6. **P24 不得把 `published_at`／`current_version` 交給本 Phase 寫**：`create_version` 永遠寫
   `published_at=None`，也不碰 `Tutorial.current_version`；發布是另一筆交易（設計 §8.2）。
7. **P40 的 CREATE**：Tutorial 與 Feature 要先建立好（本 Phase 不建），`reason` 用 `gap:<cluster_id>`；
   v1 的 `supersedes=None`，`v1.diff` 會是 0 位元組物件但一定存在。

## 1. 改了什麼

### Important 1（plan-mandated）：核對只驗「不缺」不驗「不多」

reviewer 用 moto 實測出三個假陽性：四步的 v1 多塞 `STEP#prepare-meeting@v1#5` 仍回 `True`；
`rules_applied=[]` 卻多一條 `RULE#R-999 APPLIED_TO#VERSION#…@v1` 仍回 `True`；多一條
`SUPERSEDES` 同理。

- 刪掉 `_has_edge`（只問「有沒有」），換成 **`_exact_edge_problems`**：某個起點上的某種邊
  必須**恰好**等於期望集合，缺的與多的都進問題清單。`SUPERSEDES` 的期望集合是
  `[] if version.supersedes is None else [version_pk(version.supersedes)]`，所以「v1 多一條」
  與「v2 有兩條」都會被抓到。
- 新增 **`_extra_step_problems`**：`{step.number for step in parse_markdown(全文).steps}` 與
  `{item.number for item in repository.get_steps(version_id)}` 比集合，多出來的每一步一條問題。
  缺的步驟仍由 `_step_edge_problems`（該步 0 條邊）抓。
- 新增 **`_applied_to_problems`**：`APPLIED_TO` 邊的起點是 `RULE#<rule_id>`、散在不同 PK 上，
  只查 `rules_applied` 那幾個起點驗得出「不缺」、驗不出「不多」，所以改用基表一致的
  `scan_entity("RULE", meta_only=False)`（`entity` 等於 PK 前綴，邊會跟著本體一起被掃出來，
  00A §3.6）挑出 SK 恰為 `APPLIED_TO#VERSION#<id>` 的列，rule id 集合必須恰等於
  `rules_applied`。**仍然沒有任何一處查 `by_target`**（GSI 最終一致）。
- `_missing_parts` 的 docstring 補上「『不缺』與『不多』都要驗」的理由。

### Important 2：VERSION item 重送沒有內容守門

原本 `existing is not None` 就直接沿用既有 item、不比對 plan，導致同 `version_id` 換
`reason="release:r_42", rules_applied=("R-007",)` 重送會靜默成功、回傳舊的 `rules_applied=[]`，
卻照新 plan 寫出 `RULE#R-007 APPLIED_TO` 邊，讓權威欄位與邊矛盾而 `verify` 仍 `True`。

- 新增 **`_planned_version(plan)`**：先確認 plan 自洽（`make_version_id(slug, number) == version_id`，
  `ValueError` 轉 `ContentError`），再組出這次應該寫的 `TutorialVersion`（`published_at=None`、
  `s3_key=markdown_key(slug, number)`）。不自洽會寫出「item 說自己是 v1、全文卻放在 `v2.md`」
  的版本——RED 階段的實測輸出正是這個。
- 新增 **`_reject_changed_version(existing, planned)`**：逐欄比對
  `_VERSION_FIELDS = ("version_id", "slug", "supersedes", "reason", "rules_applied", "s3_key")`
  （不比 `published_at`：本模組永遠不寫它，「已發布不可覆寫」在更前面就擋掉了），
  不同就丟 `ContentError("…已存在且內容不同，不覆寫：…")`。與 `put_private_artifact` 比對
  bytes 是同一個作法。
- 兩道關卡都放在 `get_version` 之後、**任何寫入之前**，所以被拒的重送不留下半筆產物或邊。
- `create_version` 內部改用 `planned`（`md_key = planned.s3_key`、`put_meta(planned)`），
  同一份 item 只由一個地方組出來。

### Minor 3：`pytest.raises(Exception, match="應恰好一條")` → `ContentError`（並 import 它）。

### Minor 4：損壞資料不得變成例外

- 新增 **`_expected_sk(relation, target)`**：`edge_sk` 的安全版，`target` 不是合法 PK
  （例如手改出來的 `FEATURE#`）時回 `None` 而不是丟 `ValueError`；`_step_edge_problems` 與
  `_exact_edge_problems` 都改用它。
- `_missing_parts` 的關係核對整段包 `except ValueError`（涵蓋 `parse_step_pk`／`parse_pk`
