### 1.2 `src/training_kb/pipelines/ticket.py`（新建）

模組常數只有一個：`CLUSTER_COSINE_THRESHOLD = Thresholds().cosine_match`（00A §5.4、D-35 的
欄位別名）。整支檔案裡沒有第二份字面值 `0.85`，也沒有自創 `Thresholds.cosine_cluster`。

**`ensure_embedding(ticket, *, writer, repository, operation_id) -> Ticket`**

固定順序：`get_meta(ticket_pk(id), Ticket, consistent=True)` 一致讀取 → 既有 `embedding`
有值就直接回傳（模型 0 次）→ 否則 `writer.embed(text, operation_id=..., node="ticket-embedding")`
→ `model_copy(update={"embedding": vector})` → `put_meta(create_only=False)` 寫回。

- 「先讀再決定」是重送不重算的關鍵：只看傳入物件會讓每次重送都多一次 Bedrock 呼叫。
- 維度／NaN／`bool` 的判斷完全交給 Phase 16 的 `Writer.embed`；本函式不重做檢查。
- `PermanentError`／`TransientError`／`CoordinationError` 一律**原樣往上拋**，函式內不重試、
  例外時不寫回半筆（寫回是流程的最後一步，例外發生在它之前）。
- 寫回只動 `embedding` 一個模型欄位（D-40：item 屬性 = 模型欄位 + `RESERVED_ATTRS`）。

**`assign_cluster(ticket, *, repository) -> str`**

固定順序：已有 `cluster_id` 就原樣回傳（設計 §14.2 的重試沿用）→ 沒有 `embedding` 丟
`PermanentError` → `list_tickets(ticket.project_id)` 讀同專案全部工單 → 依 `cluster_id` 分組
（`known` 收集**所有**既有編號，`groups` 只收集「不是自己且有向量」的成員）→ 每組
`centroid(...)` 再 `cosine(...)` → 篩掉 `< CLUSTER_COSINE_THRESHOLD` → 依 `(-分數, cluster_id)`
排序取第一個 → 沒有候選就 `new_cluster_id(known)`。

三個刻意的細節：一律走 `centroid` 即使群裡只有一筆（F10，不拿第一筆當代表）；排序鍵的
第二層是 `cluster_id` 升序，所以重送不會因為掃描順序改變而換群；自己不當自己的群中心，
但自己的群編號仍算既有編號（避免新群撞到自己那一號）。本函式**只判斷、不寫資料庫**，
寫回 TICKET 是 Phase 41 `assign_cluster` Task 的責任。

**`new_cluster_id(existing) -> str`**

只認得 `c<數字>`：取最大數字加一，完全沒有既有群回 `c1`；撞號丟 `PermanentError`（不靜默換號）。
MVP 不合群、不重編號，既有 `cluster_id` 永遠保留（設計 §7.3、D29）。

## 5. 遇到的問題與解法

1. **Phase 文件的五維參考向量放不進 `Ticket`。** `models.py` 的 `Ticket.embedding` 有
   `field_validator`：不是 1024 個有限數值就 `ValidationError`。依「設計 > 00A > Phase 文件」，
   以 00A §5.1 的模型欄位為準，把五維改成「種子」再 `vector(seed)` 補零到 `TITAN_DIMENSIONS`。
   補零不動 dot 也不動任何一條 norm，所以 `cosine(AXIS, ON) == 0.85` 與
   `cosine(AXIS, BELOW) < 0.85` 原封不動成立；測試同時保留五維與 1024 維兩個斷言，
   讓「17 / 20」這條算式仍然可執行地被證明。`1024` 這個數字取自 `TITAN_DIMENSIONS`，測試裡沒有第二份。
2. **conftest 的三個工廠照原文寫會 `NameError`。** conftest.py 的模組層級函式不會自動進入
   測試模組的命名空間。改用 pytest 官方的 factory-as-fixture（測試函式參數多寫工廠名字，
   測試**內容**逐字不變）；沒有採用「把 conftest 當模組 import」那種 sys.path 作法，
   因為 `tests/unit/conftest.py` 與 `tests/unit/pipelines/conftest.py` 同名，容易撞 module 名。
3. **`new_cluster_id` 的撞號分支不可能被觸發。** `max + 1` 在結構上一定大於所有解析得出的
   既有編號（`f"c{n}"` 一定解析得回 `n`）。它是防守用的，沒有為了覆蓋率去偽造無法發生的
   輸入；改成斷言「回傳值永遠不在既有集合裡」（含 `c1`／`c01`／`c10` 這種容易誤判的輸入）。
4. **跑 mypy 時撞到別人的檔案。** 中途 `uv run mypy src infra` 有 6 個 `src/training_kb/ingress.py`
   的錯（Phase 30／31 的 agent 正在改、當時未提交）。依 COMMON.md 不去修；最後一次驗證時
   對方已修好，全域 mypy 乾淨。
5. **`node="ticket-embedding"` 要不要做成常數。** 00A §6.9 沒有把這個名字列進 P38 的公開介面
   （對比 P45／P46／P47／P51 的 `*_NODE` 都有列）。為了不讓 P39／P41 有機會各寫一份不同的
   字串，照 Phase 文件的 sketch 內嵌字面值並加註解說明理由。

### 給 Phase 39（以及 P40／P41）的介面

`from training_kb.pipelines.ticket import ...`

```python

                     operation_id: str) -> Ticket: ...

```

`from training_kb.pipelines.common import Deps`

```python
@dataclass(frozen=True)
class Deps:
    operations: OperationCoordinator
    now: Callable[[], datetime]
    repository: Repository | None = None
    writer: Writer | None = None
    settings: Settings | None = None

    def need_repository(self) -> Repository: ...   # 缺相依時 PermanentError("pipeline deps 缺少 repository")
    def need_writer(self) -> Writer: ...
    def need_settings(self) -> Settings: ...
```

行為契約（P39／P41 可以直接依賴）：

- `ensure_embedding` 對同一筆 Ticket 重複呼叫，`writer.embed` 只會發生一次；回傳的 `Ticket`
  一定帶 1024 維 `embedding`，而且 TICKET item 已經同步。它**不**寫 `cluster_id`。
- `assign_cluster` **只判斷不寫入**。把 `cluster_id` 寫回 TICKET 是 Phase 41 `assign_cluster`
  Task 的責任，該 Task 必須先一致讀取 TICKET 再呼叫。
- `assign_cluster` 對已有 `cluster_id` 的 Ticket 直接回原值（連 `list_tickets` 都不會呼叫）；
  對沒有 `embedding` 的 Ticket 丟 `PermanentError`，所以 Phase 41 的 Task 順序必須是
  `EnsureEmbedding` → `AssignCluster`（00A §7 已如此定義）。
- 群編號唯一性只在同一個 `project_id` 內成立；`assign_cluster` 讀的是 `ticket.project_id`，
  不是 `Settings.project_id`。`need_settings()` 留給 Phase 41 的 Task 包裝決定要掃哪個專案。

   建議在 `tests/integration/` 補一個用真 `Repository`（moto）的案例，而不是把假 repo 做複雜。
