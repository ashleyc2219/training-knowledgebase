## 1. 逐 finding：改了什麼、覆蓋測試、指令與輸出

### 1.1 A#4／B#3（Important，跨三條 pipeline）：雲端逐 Task 失敗從不進 ledger

**問題。** 雲端不走 `run_sequence`——Step Functions 每個 Task 各 invoke 一次 Lambda，由
`common.pipeline_task_handler` 分派。那一層原本一個 `except` 都沒有，所以
`OperationCoordinator.fail(...)` **從來沒有在雲端被呼叫過**：同一次失敗在本機看得到 `OPS#`
轉 `failed`，在雲端卻永遠停在 `accepted`。

**改了什麼**（`src/training_kb/pipelines/common.py`）：

| 位置 | 改動 |
|---|---|
| `_DEPS_BY_PIPELINE` ＋ `deps_for(pipeline)` | 接手三個 pipeline 模組各自的 `global _DEPS`；分派層與三個 `*_handler` 因此共用**同一份** `Deps`。三條 pipeline 的 `load_settings(os.environ)` 一併統一（原本 feedback 帶 `os.environ`、ticket／release 不帶） |
| `_state_operation_id(event)` | 從 `event["state"]["operation_id"]` 取；缺了或型別不對回 `None`（代表不記帳） |
| `_record_task_failure(...)` | 只用**已經組好**的相依。`operations.fail(operation_id, str(error), isinstance(error, TransientError), now=deps.now())`；記帳自己失敗時只留一行 `logging.warning`，**不改寫往外丟的 errorType** |
| `pipeline_task_handler` | `maybe_fail_task` ＋ 模組解析 ＋ handler 呼叫包進同一個 `try`，`except Exception` 記帳後 `raise`（無引數，往外丟的是原例外） |
| `ticket.py`／`release.py`／`feedback.py` | 刪掉模組層 `_DEPS`，handler 改呼叫 `deps_for(...)` |

**三個 soundness caveat 都照做：**
`build_deps` 自己失敗時不去補組一份（沒有 coordinator 就沒有 ledger 可寫，硬組只會把原例外
換成「缺 TKB_AWS_REGION」）；`operation_id` 缺席就不記、例外原樣往外丟；`maybe_fail_task`
移進被包住的區域，注入的故障與真實故障在 ledger 上同形狀。

**為什麼記帳失敗要吞掉：** ASL 的 `Retry`／`Catch` 比對 Lambda runtime 回報的**類別名字串**。
把 `TransientError` 換成記帳時冒出來的 `CoordinationError`，第一條 retrier 就比不中——
等於用記帳改壞了重試語意。

**覆蓋測試**：`tests/unit/pipelines/test_task_failure_ledger.py`（新增，19 條）
——三條 pipeline 各六項（transient 記 retryable、permanent 記 not retryable、注入故障也記、
缺 `operation_id` 不記、記帳失敗不改寫 errorType、`build_deps` 失敗不被掩蓋），
加一條「記過 `failed` 之後重試成功仍然 `complete` 得了」（`operations._change` 沒有轉移守門）。

```text
$ uv run pytest tests/unit/pipelines/test_task_failure_ledger.py -q
（RED）19 errors in 0.18s     # common._DEPS_BY_PIPELINE 還不存在
（GREEN）19 passed in 0.05s
```

**測試接線點同步改了兩處**（R3 moot，但逐字寫明）：
`tests/unit/pipelines/test_ticket_flow.py` 的 `wired` fixture 與
`tests/unit/test_feedback_review_flow.py::test_handler_runs_exactly_one_task`，
從 `monkeypatch.setattr(<module>, "_DEPS", ...)` 改成
`monkeypatch.setitem(common._DEPS_BY_PIPELINE, "<pipeline>", ...)`。

### 1.3 A#1（**Critical**）：`task_commit_batch` 的跳過分支會把「半發布」宣稱成成功

**問題。** `Publisher._after_transaction` 先切 `published_at` 再寫 `site/`，所以「每一版都有
`published_at`」與「公開站已經寫好」不是同一件事——切點 4（`a2_after_transact_before_site`）
與切點 5（`a3_after_first_site_before_second`）留下的正是「全部已發布、`site/` 半寫」。
原本的跳過分支只看 `published_at`，於是重跑會寫出 `review-result.json`、`complete` 這筆
operation、整條流程 `Succeeded`——對外宣稱整批發布成功，公開頁卻缺一半。

**改了什麼**（`pipelines/feedback.py::_assert_finished_here`，在跳過交易之前呼叫）：

```text
1 公開物件齊不齊   public_site_keys(version_ids) 每一個都要 object_exists
2 是不是本 operation 發的
    多篇  operations/<op>/pending-promote.json 存在（Publisher._record_pending_promote）
    單篇  ledger 的 OPS#<op>.version_id 等於那一版（Publisher._record_versions）
任一道不過 -> PermanentError，訊息指名 publishing.resume_publish
```

> **與裁決 2 的差異（本計畫選擇 2026-09-15，已在程式 docstring 寫明）：** 裁決 2 只點名
> `operations/<op>/pending-promote.json`。但依 00A §6.7，**單篇批次本來就不寫那個檔**
> （`_record_pending_promote` 的 `len(version_ids) < 2` 直接 return），證據在
> `OPS#<op>.version_id`。照字面實作會讓「單篇批次的合法續跑」變成永久失敗。所以第 2 道
> 用與 `publishing._resume_targets` **完全同一套**的兩種互補輸入。裁決要守的兩件事沒有放寬：
> 公開物件一定要齊，而且一定要有「本 operation 發布過」的證據。

**覆蓋測試**（`tests/unit/test_feedback_review_flow.py`，裁決要求的三種情況都有）：

- `test_commit_batch_refuses_when_the_public_objects_are_missing`（site/ 缺頁 → `PermanentError`，訊息含 `resume_publish`）
- `test_commit_batch_refuses_when_this_operation_never_published_the_batch`（刪掉 `pending-promote.json`）
- `test_commit_batch_still_resumes_a_genuine_batch`（合法續跑不受影響）
- `test_commit_batch_resumes_a_single_version_batch_from_the_ledger`（單篇走 ledger 那一半）

### 1.7 A#6（Important）：匯入 handler 的逐筆界線與 docstring 不符

### 1.12 B#4（Important）：`validate_rules` 的退役判定可能永遠不會觸發

**裁決 10 我選了後備做法（document + test），理由寫進 `validate_rules_action` 的 docstring：**

```text
1 沒有前綴列舉  Repository 只有 get_object／put_object／object_exists，沒有 list_objects；
```

`test_validate_rules_only_sees_the_batches_in_this_event`——兩份證據檔都寫出來了，

（原本漏 `KeyError`／`TypeError`／`ValueError`）。覆蓋測試兩組 parametrize。
