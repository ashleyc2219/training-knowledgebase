### 1.2 `src/training_kb/pipelines/release.py`（共用檔，只 `Edit` 加 `# ---- Phase 51 ----`）

新增 `REWRITE_NODE`、`assert_unchanged`、`prepare_update`，與五個 module-private helper
（`_apply_rewrite`／`_rules_for_hits`／`_sub_operation`／`_rewrite_once`／`_prepare_one`）
和一個 `_log`。`LEASE_TTL_SECONDS` 從 `training_kb.pipelines.feedback` **import**（owner P46），
本檔沒有第二份宣告。

每篇教學的固定順序（`_prepare_one`）：

```text
子 operation(accept) -> 基底全文(parse_markdown) -> 選規則 -> allocate_version
   -> 模型一次(_rewrite_once) -> _apply_rewrite -> assert_unchanged
   -> validate_content -> create_version -> verify_version_complete
```

- **`_apply_rewrite`**：先擋「改寫集合有重複編號」，再擋「改寫集合 ≠ 命中集合」（多回是越界、
  漏回是沒做完，兩種都不放行）；未命中步驟**整個物件原樣帶過**；命中步驟只允許改 `text` 與
  `type`，`feature_id` 一變就是 `ContentError`（改名不搬移 Feature 主鍵，D06）。
  `model_copy(update=...)` 在 pydantic v2 不驗證，所以 `type` 先經 `StepType(...)` 轉換，
  不合法的值收斂成 `ContentError`（裸 `ValueError` 不在 00A §4.1 的錯誤契約裡）。
- **`assert_unchanged`**：四個段落、步驟數量、每個未命中步驟的 `model_dump()` 三道比對。
- **`_rules_for_hits`**：`step_types` **只取命中步驟的 `type`**（F29：沿用原文不算本次套用），
  丟給 Phase 19 的 `rules_for_content`，再依 `step_types` 出現順序用 `seen` 去重，注入順序與
  `applied_rule_ids` 完全一致。驗證時間一律走
  `analytics/status_writer.load_validated_at(repository)`（D-28），本檔沒有第二份
  `_load_validated_at`；`list_rules(RuleStatus.ACTIVE)` 讓 candidate／retired 進不了門。
- **`_sub_operation`**：`operation_id_for("release-update", f"{release.id}--{slug}")`，
  先 `accept` 再交給 `allocate_version`（D-59）。`project_id` 沿用**父** operation 紀錄；
  父 operation 讀不到就 `CoordinationError`。
- **`_rewrite_once`**：整個流程唯一呼叫模型的地方。模型輸出 ref 是 **per-slug** 的
  `operations/<父 operation_id>/rewrite-<slug>.json`（不是 `model_output_refs[-1]`），
  重送先 `get_object` 讀回來；寫入用 `put_object(..., if_none_match=True)`，
  `record_model_output` 記在父 operation 上。業務驗證用 Phase 18 的 `step_rewrite_validator`。
- **`prepare_update`**：`kind` 不是 `renamed`／`changed` 就 `PermanentError`；命中依 slug 分組，
  逐篇取 `TUTORIAL#<slug>` 租約（`LEASE#` 由 Phase 11 自己補）、`try/finally` 歸還；
  拿不到租約就 `TransientError` 交 ASL 有限重試。**退役教學跳過**（見 §5.1）。

## 5. 遇到的問題與解法

### 5.1 退役教學會被 `find_release_hits` 命中（controller 2026-09-14 裁決）

Phase 27 的 `_is_current_published` **不看 `Tutorial.status`**，而 D-38 又禁止 Phase 50 的包裝層
自己再篩一次，所以退役教學的步驟**會**出現在 `hits` 裡。設計 §8.1 說退役的教學不再維護，
UPDATE 不得替它建新版。

**處置**：過濾放在 `prepare_update` 這一層——讀 `get_tutorial(slug)`，`status` 不是 `active`
就跳過並用 `logging.INFO` 記 `slug`／`status`／`release_id`，**不丟例外**（那是別篇教學的正常
結果，不該讓整次改版失敗）。教學根本不存在則仍是 `ContentError`（資料不一致，不可當成跳過）。
測試：`test_retired_tutorial_is_skipped_with_a_reason`、`test_unknown_tutorial_is_a_content_error`。

### 5.2 Phase 文件 §7 的 `match="改寫集合"` 只涵蓋一半

`step_rewrite_validator`（Phase 18）依 00A §6.5 的接入點排在 `_apply_rewrite` **之前**，所以
模型「多改未命中步驟」會先撞到它的固定錯誤碼 `step_number_not_in_hit_set`，而不是
`_apply_rewrite` 的「改寫集合…」。兩者都是 `ContentError`、都不建立版本，驗收矩陣不受影響。

**處置**（R5：以既有程式為準，差異寫進文件）：測試分兩支——越界改寫斷言
`step_number_not_in_hit_set`、漏回與重複回斷言 `改寫集合`；Phase 文件 §10.1 加了現況核對。
順帶補強：文件片段的 `changed = {int(item["number"]): item …}` 會讓模型回兩份同一步時後者
靜靜覆蓋前者，`_apply_rewrite` 因此多比一次 `len(changed) != len(reply["steps"])`。

### 5.3 「模型把第 3 步改指別的 Feature」原本測不到 D06

`allowed_features` 是基底**全部步驟**引用的 Feature；當四步都指 `Prepare` 時，模型回 `Share`
會先被 validator 的 `feature_id_not_found` 擋掉，走不到 `_apply_rewrite` 的 D06 檢查。

**處置**：把基底第 4 步改成引用另一個既有 Feature（`Share`），白名單因此有兩個值，
`ContentError("步驟 3 不可改變引用的 Feature")` 才真的被觸發。

### 5.4 假 Writer 分不清兩篇教學的 prompt

`prompt_release_rewrite` 依設計**不放 slug 也不放 version_id**（分區名稱不得自創，簽名也沒有
這兩個參數），所以「兩篇教學各給一份回覆」不能用 slug 當 key。改用「只出現在該篇 prompt 的
步驟原文」當標記（`FakeWriter.replies_by_marker`）。

### 5.5 `StepRewrite` 的 `maxTokens`

00A §3.7 把 P46／P51 列在「教學寫作模型 `max_tokens` 2048、`temperature` 0.1」那一列，但
P17 原本的 `WRITING_MAX_TOKENS` 只有 `{"TutorialDraft": 2048}`，而
`tests/unit/test_writing_validation.py::test_every_schema_gets_max_tokens_and_low_temperature`
斷言「其餘七個都是 512」。本 Phase **沒有**動 `writing/client.py`：W2 期間 P46 已用 controller
核准的 R3.6 例外在 commit `4d8d3c4` 補上 `"StepRewrite": 2048` 並同步改了那支測試。
本 Phase 只消費 `inference_config(StepRewrite)`，截斷（`stopReason == "max_tokens"`）仍由
Phase 15 判成 `PermanentError`、不發布。

### 5.6 `ruff format`

依 COMMON.md §1，gate **不含** `ruff format`；本專案既有程式是手寫對齊的續行風格，
`ruff format --check` 對新檔一樣會要求重排成 Black 風格，與周邊檔案不一致。三個新測試檔因此
維持與 `test_release_safety_net.py`／`test_retire_tutorial.py` 相同的排版，只跑 `ruff check`。

### 5.7 `prompts.py` 的 commit 歸屬

W2 期間 P46 與本 Phase 同時在改 `writing/prompts.py`。P46 的 commit `4d8d3c4`
（`feat(feedback): REFINE 只改命中步驟並記錄注入規則`）在 `git add` 時把工作區裡本 Phase 的
`# ---- Phase 51 ----` 區段一起帶進去了——這正是 COMMON.md R3.3 明訂的行為（共用檔含別人的
未提交修改照樣提交，不 stash／不 reset）。`prompt_release_rewrite` 因此不在本 Phase 的
commit 清單裡，但內容與歸屬不變。
