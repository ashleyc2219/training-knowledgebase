## 1. 實作內容與邏輯（逐檔）

### `src/training_kb/pipelines/common.py`（Edit，加 `# ---- Phase 41 ----` 區段）

| 名稱 | 做什麼 | 為什麼這樣寫 |
|---|---|---|
| `task_name(task)` | 函式名去掉 `task_` | ASL 的 `Parameters.task` 由函式本身導出，兩邊不可能各打一份字串而分岔 |
| `maybe_fail_task(pipeline, task, env=None)` | 讀 `TKB_FAULT_TASK="<pipeline>:<task>"`，命中就 **`raise TransientError`** | ASL 的 `ErrorEquals` 比對**類別名字串**、不認繼承。丟 `faults.InjectedFault`（`TransientError` 的子類）在雲端不會命中第一條 retrier，證出來的是假陰性 |
| `build_deps(settings)` | boto3 resource → `Repository` → `OperationCoordinator` ＋ `BedrockWriter` | 形狀照 `ingress._build_wiring`，只是不需要 `PipelineStarter`；client 在函式裡才建立，模組 import 不碰網路 |
| `pipeline_task_handler(event, context)` | 依 `event["pipeline"]` 分派到三條 pipeline 的直接入口 | 共用 Lambda `training-kb-pipeline-task` 的唯一入口（00A D-24） |

`pipeline_task_handler` **一次只跑一個 Task**（controller 裁決）：分派前先呼叫
`maybe_fail_task`（每次 invoke 重讀環境變數，**不**跟 `_DEPS` 一起做模組層快取），
再 `import_module` 目標模組。三種接不起來的情況全部轉 `PermanentError`：pipeline 不在
白名單、`ModuleNotFoundError`、**模組在但 handler 屬性不存在**（controller 預建的
`feedback.py`／`release.py` 空殼就是這一種，不轉的話 `errorType` 會變成看不出原因的
`AttributeError`）。兩層 handler 都不 try／except，`TransientError` 要讓 Retry 抓到、
`PermanentError` 要讓 Catch 抓到。

### `src/training_kb/pipelines/ticket.py`（Edit，加第 8 段）

七個 Task 包裝 Phase 38–40 的業務函式，形狀一致「前置條件不成立就 `return dict(state)`」，
所以本機序列與雲端 Choice 分支不會產生兩套語意：

| Task | 行為 |
|---|---|
| `task_ensure_embedding` | 從 `input_ref` 讀回 canonical `Ticket` → `ensure_embedding` → 把 `ticket_id` 放進 state |
| `task_assign_cluster` | 一致讀表 → `assign_cluster`（只判斷）→ **自己 `put_meta(create_only=False)` 寫回 `cluster_id`** |
| `task_evaluate_recurring` | 一致讀表（群號以 state 為準）→ `is_recurring` → `is_recurring` 欄位 |
| `task_name_gap` | 非 recurring 原樣回傳；否則 `name_gap` 後只放 `gap_ref`（`gap`／`feature_id` 不進 state） |
| `task_decide_action` | `_gap_of` 讀回 `gap-naming.json` 組 `TicketGap` → `decide_ticket_action`；KEEP／NO_FEATURE 就地 `record_decision` |
| `task_create_first_version` | `action != "CREATE"` 原樣回傳；否則 `create_first_version` → `version_id` |
| `task_publish_version` | `Publisher.prepare` → `commit`（`commit` 第一件事就是 `inspect`，不重複呼叫）→ `published` |

另外新增 `TICKET_STATE_FIELDS`（十個欄位的 tuple，用途同 P52 的 `RELEASE_STATE_FIELDS`）、
`TICKET_ANALYSIS_TASKS`、`run_ticket_analysis`（本機序列，測試與 Demo 用）、
`_TASK_BY_NAME`／`_DEPS`／`ticket_analysis_handler`（雲端一次一個 Task 的入口）。

## 5. 遇到的問題與解法

1. **`taskFailedEventDetails` 永遠是空的。** 直接函式 ARN（D-49）的失敗事件是
   `LambdaFunctionFailed`／`lambdaFunctionFailedEventDetails`，只有
   `arn:aws:states:::lambda:invoke` 最佳化整合才會出現 `TaskFailed`。文件與 00A §3.7 的
   停止條件照字面讀會誤判成「重試沒生效」。**解法**：改查
   `lambdaFunctionFailedEventDetails.[error,cause]`，實測 `error` 逐字是 `TransientError`
   且恰好三次，語意上的停止條件並未觸發。已在 Phase 文件 Task 3 Step 6 補「現況核對」，
   00A §3.7／§8 證據表建議由 controller 改字。
2. **不做跨 stack 參照。** brief 原本要 `TrainingKbStack(..., data: TrainingKbDataStack)`，
   但同一波次 Phase 57 正在改 data stack；CDK 的 `Export` 一旦建立就會卡住對方之後的修改，
   而且 `--exclusively` 也擋不住跨 stack 相依。**解法**（controller 裁決）：用
   `Table.from_table_attributes` ＋ `Bucket.from_bucket_name` 以純字串名稱接進來，
   樣板裡沒有任何 `Fn::ImportValue`（有測試守住），實際部署用
   `deploy TrainingKbApp --exclusively` 完成、完全沒有碰 `TrainingKbData`。
3. **webhook 第一次打回 502。** log 顯示 `rote.normalize_all` 找不到可重放的 PROC →
   走 Agent → `converse_with_tools` → `PermanentError: O5 尚未通過`。這是 O5 BLOCKED 的
   牆，不是 bug。**解法**：種一筆 active PROC（與 `tests/conftest.py` 的 `active_proc`
   同一組步驟），接入層就走重放層、0 次模型，於是拿到 `ok: true` 與啟動證據。
   **代價**：A1 的「八秒夠不夠」只量到不含模型的那一段。
4. **`grant_read_write_data()` 會把 `DeleteItem` 混進同一條敘述**，D-79 要的「只有一條
   `DeleteItem`」就守不住。**解法**：DynamoDB 的授權改成手寫（形狀照 P09 的資料角色，
   不含 `DeleteItem`），`DeleteItem` 單獨一條、資源只有表本體。
5. **D-79 做不到逐字。** DynamoDB 的 IAM 條件鍵只有 `dynamodb:LeadingKeys`（比 PK）、
   `dynamodb:Attributes` 等，**沒有**比 SK 的條件鍵，「`SK begins_with APPLIED_TO#`」在
   IAM 層無法表達。**解法**：授權收到「單表、單動作、不給索引」，範圍由程式層
   `DELETABLE_RELATIONS` 守住（§4 有真實表上的實證），`Template` 斷言固定成「恰好一條
   `DeleteItem`、資源只有這張表、沒有 `dynamodb:*`」。
6. **`cdk` 每個子命令都會合成整個 app**，所以 `os.environ[SECRET_ENV]` 會讓沒帶 secret 的
   人連 `TrainingKbData` 都部署不了。**解法**：`infra/app.py` 在三個前提任一缺席時只跳過
   `TrainingKbApp` 並把原因印到 stderr；`TrainingKbStack` 本身仍然硬性要求 secret。
7. **同波次紅燈**：`tests/integration/test_release_hits_consistency.py`（P50）一度有兩個
   `E501`，本 Phase 沒有動它；提交前重跑時對方已修好，最終 `ruff check src tests infra`
   全綠，**沒有用到 `--ignore`**。
