### 1.1 公開介面（簽名逐字照 00A §6.8）

```python
TICKET_REQUIRED  = ("id", "source", "text", "author", "ts", "project_id")
RELEASE_REQUIRED = ("id", "source", "feature", "kind", "evidence", "ts")
RENAMED_REQUIRED = ("old_name", "new_name")
ANALYSIS_FIELDS  = ("cluster_id", "feature_ids", "embedding")

def missing_nonempty_strings(payload: Mapping[str, object],
                             keys: Sequence[str]) -> tuple[str, ...]: ...
def validate_ticket(payload: Mapping[str, object]) -> Ticket: ...
def validate_release(payload: Mapping[str, object]) -> Release: ...
```

內部 helper（底線開頭，其他 Phase 不得 import）：`_parsed_ts`、`_optional_string`、`_invalid_fields`。

### 1.2 實作邏輯

兩個函式都是**純函式**：不收 `deadline`、不呼叫 `monotonic()`、不 import `boto3`／`Repository`／`Writer`，
也不寫任何 DynamoDB item 或 S3 物件（已用 `grep` 驗證，見 §4）。期限由呼叫端管——P32 的
`normalize_then_accept` 會先 `assert_time_left(deadline, step="normalize")`，本 Phase 不重新計八秒。

驗證順序固定（Phase 文件 §5 的流程圖），每一關把不合法欄位名收進 `IngressError.fields`：

1. **必填非空字串**：`missing_nonempty_strings` 是「一次回報所有缺欄位」的**唯一**實作。
   `not isinstance(value, str) or not value.strip()` ⇒ 缺值，所以 `author="   "` 歸到缺必填
   （D23 覆寫 D09）。它只判斷合不合法，**不 strip 之後改寫來源給的值**。
2. **分析欄位不得預填**：`tuple(key for key in ANALYSIS_FIELDS if key in payload)`，
   判斷的是 key 有沒有出現（`feature_ids: []` 也算預填）。
3. **`kind == renamed` 時 `old_name`／`new_name` 也必須非空**：用同一個 `missing_nonempty_strings`
   累加到同一份 `fields`，所以兩個都缺時一次回報 `("new_name", "old_name")`
   （`IngressError` constructor 已排序去重）。
4. **enum 合法**：`payload["source"] not in set(TicketSource)`／`set(ReleaseSource)`／`set(ReleaseKind)`。
   StrEnum 成員本身就是字串，不另外維護字面值清單（D-32：不得改寫成 `Literal[...]`）。
5. **`ts` 是 aware 的 UTC ISO-8601 整秒**：`parse_iso` 的 `ValueError` 轉 `IngressError(("ts",))`；
   另外擋掉微秒（00A §3.5：靜默截斷會讓以時間入鍵的計算悄悄改變答案）。
6. **模型層的拒絕也收斂成 `IngressError`**（本 Phase 補強）：`Ticket`／`Release` 建構包在
   `try/except ValidationError`，`_invalid_fields` 把 pydantic 的 `loc[0]` 取成欄位名。
   理由：00A §4.1 把 `IngressError` 的拋出者寫成 `validate_ticket`／`validate_release`，而 P30 的
   `handlers/github_webhook.handler` 只 `except IngressError` 與 `except TimeoutError`——
   `ValidationError` 漏出去會變成 Lambda 500，而不是 `{"ok": false, "fields": [...]}`。
   例：`id="TICKET#t_881"` ⇒ `IngressError(fields=("id",))`。

`source_event_id`／`old_name`／`new_name` 是「必填但值可為 null」，一律 `payload.get(...)`（包成
`_optional_string`）：`payload["old_name"]` 在 `changed`／`removed` 會 `KeyError`，那是程式錯誤不該
變成接入錯誤。這三個欄位**不檢查 key 是否出現**——00A §6.8 的 `RELEASE_REQUIRED` 不含它們，
`changelog` 來源也本來就沒有上游事件識別碼。

**ID 一律由 Phase 13 的編碼函式產生**，本 Phase 只驗證「抽取之後」的 canonical 結果：
不呼叫模型、不猜 user、不把 PR number 當 `Release.id`。多 Feature 的 PR（F14）由 adapter 先拆成
多個候選，`validate_release` **逐筆**驗證；兩筆共用同一個 `source_event_id`。

## 5. 遇到的問題與解法

1. **Phase 文件的範例程式過不了 mypy strict。** `TicketSource(payload["source"])`、
   `payload.get("old_name")` 把 `object` 餵給 `str`／`str | None`，`uv run mypy src infra` 報 6 個
   `arg-type`。→ 改成 `TicketSource(str(payload["source"]))` 與 `_optional_string(payload, key)`；
   此處已通過必填檢查，`str(...)` 只收斂型別不改值。行為與文件描述完全相同。
2. **`xfail(strict=True)` 與「測試本體會過」互相矛盾。** `("github.com", "pull_request")` 未核定時
   必須是 XFAIL，但 `validate_release` 本身是好的，測試會 XPASS ⇒ strict 失敗。
   → 每個測試第一行先 `assert (domain, event_type) in APPROVED`：未核定時這行就失敗（XFAIL 成立），
   核定之後它自動通過、後面的斷言才真的跑。
3. **Task 3 的紅燈已被 Task 1 消化。** → 改用 mutation（暫時拿掉 `TICKET_REQUIRED` 的 `author`）
   證明整合測試不是假綠，還原後再提交。
4. **Task 2 沒有真紅燈的風險。** 實作 Task 1 時整段都寫完了。→ 提交 Task 1 前把 Release 相關程式
   暫存出檔案、從 `ingress.py` 移除，Task 2 寫完測試看到真的 `ImportError` 再還原。
5. **`ingress.py` 模組 docstring 的區塊清單自相矛盾**（把正規化列為第 4 點，卻要求放在第 3 點之上）。
   → 依「放在接線點之上」為準，正規化改成第 3 節、接線點改成第 4 節（只動兩行註解與 docstring 兩行）。
6. **Phase 文件相對路徑 fixture。** `Path("tests/fixtures/github")` 會隨 pytest 的 cwd 飄掉。
   → 改用 `Path(__file__).resolve().parents[2]`，與 Phase 13 的 `test_o6_fixture_contract.py` 同款。
7. **`Release` 沒有 author 欄位**，但 Phase 文件 §8 Step 3 要求斷言 "stable author"。
   → 改成斷言 `github_user_id(sender.id)` 的編碼可追溯到核定紀錄的 `stable_user_source`。

給 P32 的接線注意事項：

1. **兩個函式都不收 `deadline`**。P32 的 `normalize_then_accept` 要在呼叫它們**之前**先
   `assert_time_left(deadline, step="normalize")`（P30 的 helper），用 handler 進入時算好的同一個
   `deadline`，**不重新計八秒、不在正規化裡呼叫 `monotonic()`**。
2. 失敗一律是 `IngressError`（`PermanentError` 子類），`fields` 是**排序去重後的 `tuple[str, ...]`**
   （D-06）。P30 的 handler 已經會把它轉成 `{"ok": false, "fields": [...]}`；P32 不需要再包一層。
   模型層的 `ValidationError` 不會漏出來。
3. 正規化階段**零寫入**：沒有 operation、沒有 item、沒有 S3 物件。`OperationStatus.normalized`／
   `started` 怎麼寫由 P32 決定，本 Phase 沒有預設任何值。
4. 一個 PR 可能產生多筆子 Release（F14）：adapter 先拆候選，`validate_release` 逐筆驗；
   多筆共用同一個 `source_event_id`，但 `accept_release` 要各自開一個 operation
   （`op-release-r_gh-…-pr42-1`、`…-2`）。
5. `ingress.py` 目前的區塊順序是 1 驗簽 → 2 整體期限 → **3 正規化** → 4 接線點；
   P32 的 accept 端請接在第 4 節，不要插進第 3 節。
6. 第 3 節新增的 module import：`pydantic.ValidationError`、`training_kb.clock.parse_iso`、
   `training_kb.models.{Release,ReleaseKind,ReleaseSource,Ticket,TicketSource}`、
   `collections.abc.Sequence`、`datetime.datetime`。

給 P36 的注意事項：`normalize_ticket`／`normalize_release` 產出的候選欄位，欄位名要與
`TICKET_REQUIRED`／`RELEASE_REQUIRED` 逐字相同，`project_id` 用 `DEFAULT_PROJECT_ID`；
`validate` 這一步就是呼叫本 Phase 的兩個函式。
