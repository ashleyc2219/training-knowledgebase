# Phase 19：Active 規則選取與注入 — 實作報告

## 1 實作內容（含實作邏輯）

新增 `src/training_kb/rules.py`，Phase 19 是這支檔案的 owner。裡面只有四個純函式，
不碰 `Repository`、`Writer` 或任何 AWS API（00A §6.5）：

| 函式 | 邏輯 |
|---|---|
| `select_active_rules(rules, step_type, validated_at_by_rule)` | 先 `status == RuleStatus.ACTIVE`，再 `applies_when == step_type`（單一等值比較，不寫條件字串 parser）；接著檢查每條 matching 規則都有驗證時間，缺任何一條就丟 `PermanentError` 並把缺的 `rule_id` 排序後列進訊息；最後兩次穩定排序取第一條，同一 `step_type` 最多回一條。 |
| `render_rules_block(rules)` | 每條輸出 `[<rule_id>] applies_when=<value>\n<rule>`，以 `\n` 串接；**不自己轉義**。 |
| `applied_rule_ids(rules)` | `dict.fromkeys` 去重且保留注入順序，直接餵 Phase 20 的 `allocate_version(..., rules_applied=...)`。 |
| `rules_for_content(rules, step_types, validated_at_by_rule)` | `dict.fromkeys(step_types)` 去掉重複型態又保留順序，逐型態呼叫 `select_active_rules`，回 `dict[StepType, list[AuthoringRule]]`（D-03：以 P19 為準，不是 tuple）。 |

三個關鍵設計決定：

1. **status 先於時間。** retired 規則即使驗證時間比較新也不入選——測試刻意讓 R-006（retired）
   的時間比 R-007（active）新，只看時間的實作會紅燈。
2. **兩次穩定排序，不用複合 key。** 先 `key=rule_id` 升序，再 `key=validated_at, reverse=True`。
   若寫成 `key=(時間, rule_id)` 再 `reverse=True`，`rule_id` 會被一起反轉成降序，平手時反而選到
   較大的 R-007；測試 `test_same_timestamp_falls_back_to_smallest_rule_id` 就是釘這件事。
3. **轉義只做一次。** `render_rules_block` 輸出原文，轉義由 Phase 17 `writing/prompts.py` 的
   `_as_data` 在 `<active_rules>` 分區統一做（00A D-67：不得各自複製一份 `_as_data`）。
   `prompt_write_tutorial` 已經寫成 `<active_rules>{_as_data(rules_block)}</active_rules>`，
   所以本模組再轉一次會變成雙重轉義。整合測試同時釘住「block 不轉義」與「prompt 有轉義」。

**最近驗證時間**維持 00A D-28 的裁決：`AuthoringRule` 沒有 `validated_at` 欄位，權威來源是私有
S3 檔 `operations/rules/validated_at.json`（`VALIDATED_AT_KEY`／`load_validated_at` 由 P40 首建、
P55 寫入）。本 Phase **沒有**提前建立 `analytics/` 套件，`validated_at_by_rule` 全部由參數傳入。
