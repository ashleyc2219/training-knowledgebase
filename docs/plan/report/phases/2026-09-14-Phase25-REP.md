### 1.1 新的公開介面（`training_kb.publishing`）

```python
MAX_BATCH_VERSIONS = 50                      # 100 個 action ÷ 每篇 2 個
PENDING_PROMOTE_NAME = "pending-promote"     # operation_ref(op, 這個值) -> operations/<op>/pending-promote.json
PENDING_PROMOTE_CONTENT_TYPE = "application/json"
UNPUBLISHED_MARKER = b'data-published="false"'

def assert_batch_publishable(prepared: PreparedPublish) -> None: ...
def build_commit_transaction(prepared: PreparedPublish, *, repository: Repository,
                             now: datetime) -> list[dict[str, object]]: ...
def promote_site_objects(prepared: PreparedPublish, *,
                         repository: Repository) -> tuple[str, ...]: ...
def public_site_keys(version_ids: tuple[str, ...]) -> tuple[str, ...]: ...
```

四個 dataclass 與 `prepare`／`inspect`／`commit` 三個簽名**一個字都沒改**（00A §6.7）。

### 1.2 整批的四個邊界（`assert_batch_publishable`）

| 拒絕 | 訊息關鍵字 | 理由 |
|---|---|---|
| 空清單 | 至少要有一個版本 | 「成功但沒事做」會讓上游以為已發布。 |
| > 50 篇 | 最多 50 篇 | 交易上限；拆兩次交易就不再是全有或全無。 |
| 重複 `version_id` | 重複的 version_id | **不自動去重**，去重會遮蔽上游錯誤。 |
| 同 slug 兩版 | 同一篇教學 | 兩個 action 指到同一筆 `TUTORIAL#<slug>`，AWS 判 validation error；屬 O2 接受順序問題。 |

`prepare` 的**第一件事**就是用一個 `staged_keys=()` 的暫時 `PreparedPublish` 問它一次，
所以任何拒絕都發生在寫第一個 staging 物件之前。slug 用 `parse_version_id`（D-19），
不自己 `split("@")`。

### 1.3 一次交易（`build_commit_transaction`）

Phase 24 的私有 `Publisher._transact_items` 搬成模組函式 `_version_and_tutorial_actions`
（兩個 `Update` 與條件式逐字不變，含 `#rev = #rev + :one`），**單篇因此成為 N=1 特例，
全套只有一份條件式**。`build_commit_transaction` 先重跑 `assert_batch_publishable`
（它是 P48／P52／P59 也會直接呼叫的公開入口），再逐篇產出 2 個 action：

```text
items[0] VERSION#prepare-meeting@v3   SET published_at = :now   條件：還沒發布過
items[1] TUTORIAL#prepare-meeting     SET current_version = :v  條件：current_version = :base
items[2] VERSION#share-summary@v2     …
items[3] TUTORIAL#share-summary       …
```

`transact_write` 回 index → 第 `index // ACTIONS_PER_VERSION` 篇、
`CANCEL_REASONS[index % ACTIONS_PER_VERSION]` 的原因。版本或教學讀不到一律 `PublishError`
（不是讓 `None` 帶到 `AttributeError`）。

### 1.4 `commit` 的新順序

```text
inspect（不過 -> PublishError，交易次數 0）
  v
build_commit_transaction -> 一次 transact_write
  |                              |
  回 index -> PublishResult(published=(), failed=version_ids[index//2])   零公開產物
  v 回 None
_after_transaction：任何例外一律轉 PublishError（訊息帶切點代號）
   (1) record_version         單篇才寫（D-59），排在 S3 之前（Phase 24 review Important 1）
   (2) _restage 每篇           用已切換的欄位重新渲染 staging（00A §3.8／§6.7）
   (3) pending-promote.json   多篇才寫（00A §6.7：單篇不寫）
   (4) 逐篇 _promote           版本頁 -> 公開 diff 副本
   (5) 每個 slug 的教學索引     依 version_ids 首次出現順序
   (6) 站台索引                整批只寫一次
```

`site_writes` 的實際順序（兩篇）：

```text
site/tutorials/prepare-meeting/v3.html      site/tutorials/prepare-meeting/v3.diff.txt
site/tutorials/share-summary/v2.html        site/tutorials/share-summary/v2.diff.txt
site/tutorials/prepare-meeting/index.html   site/tutorials/share-summary/index.html
site/index.html
```

「版本頁 → 教學索引 → 站台索引」讓中斷時公開站最多是「新頁已存在但索引還沒指過去」，
不會是「索引指向不存在的頁」。

### 1.5 D-59：父 operation 不持有版號

`OperationRecord.version_id` 是**單值**。Phase 24 的 `commit` 對每篇呼叫
`record_version(parent_op, ...)`，第二篇必定 `CoordinationError`。本 Phase 的
`_record_versions` 因此是：

- **N == 1**：照 Phase 24 記在這一筆 operation 上（行為完全不變）。
- **N > 1**：**不寫**。版號已由上游（P48 `refine_operation_id`／P52
  `operation_id_for("release-update", …)`）在每篇自己的 per-slug 子 operation 上
  `allocate_version` 時記好；父 operation 只負責整批追溯。

兩種復原輸入互補、不重複：

```text
單篇  OPS#<op>.version_id + site_key            <- _record_versions
多篇  operations/<op>/pending-promote.json      <- _record_pending_promote
```

### 1.6 `promote_site_objects` 與 runtime 守門

`promote_site_objects(prepared, *, repository)` 依 `version_ids` 順序逐篇搬
（版本頁先、`v<n>.diff.txt` 後，D-54），回傳實際寫出的公開 key（含 `site/`），
**已存在且 bytes 相同的 key 仍然回傳**（同樣代表「這個公開物件已就緒」）。
`Publisher._promote` 與它共用 `_promote_version`，所以 `commit` 走私有方法（保留 Phase 12
／24 的切點注入點）而寫出的東西完全相同。

`_put_public_object` 三道關卡：`UNPUBLISHED_MARKER` 守門（00A §3.8）→
`put_object(if_none_match=True)` → 撞鍵才比對 bytes（不「先查再寫」，避免空窗）。

## 5. 遇到的問題與解法

### 5.1 整批 `record_version` 會撞 `CoordinationError`（D-59）

Phase 24 的 `commit` 對每篇呼叫 `record_version(prepared.request.operation_id, …)`。
`OperationRecord.version_id` 是單值、write-once，第二篇一定 `CoordinationError`，而且那個
例外原本落在 S3 階段的例外轉換**之外**——會留下「DynamoDB 兩篇都切、`site/` 只寫一篇、
例外型別不是 `PublishError`」的半發布。

**裁決**（00A §8 D-59 ＋ controller 轉來的 review Important 2）：多篇不寫父 operation；
單篇維持 Phase 24 行為。並把整個交易後收尾包進 `_after_transaction`，**任何例外一律轉
`PublishError`**，訊息帶切點代號。測試：`test_batch_commit_does_not_touch_the_parent_operation_ledger`
（父 operation 先持有別的版號，整批照樣成功）與
`test_single_commit_turns_a_ledger_conflict_into_publish_error`（單篇衝突 → `PublishError`、
`site/` 零物件）。

### 5.2 單篇不該寫 `pending-promote.json`

第一版對所有 N 都寫，Phase 24 的 `test_cut_point_a2_after_transact_before_site` 立刻紅：
它斷言 `operations/op-pub-2/` 底下的物件就是 `prepared.staged_keys`，多一個
`pending-promote.json` 就不相等。回頭查 00A §6.7：「**單篇發布不寫這個檔**，P59 用 operation
紀錄的 `version_id` + `site_key` 重算」。

**裁決**：`_record_pending_promote` 在 `len(version_ids) < 2` 時直接 return。這也讓兩種復原
輸入剛好互補（單篇靠 ledger、多篇靠清單），而且解釋了 review Important 1 為什麼非做不可：
單篇的 ledger 若在 a2 時是 `None`，P59 就完全沒有輸入。

### 5.3 `commit` 要不要直接呼叫 `promote_site_objects`

Phase 文件 §6 的收尾第 (2) 步寫 `promote_site_objects(...)`，但 Phase 12／24 的切點注入點是
`Publisher._promote(version_id, operation_id)`（`tests/integration/test_publish_cutpoints.py`
用 `monkeypatch` 換掉它），本 Phase 的切點 5（只讓**第 j 篇**失敗）也需要它。

**裁決**：兩者共用 module-private 的 `_promote_version`，`commit` 走 `self._promote`、
`promote_site_objects` 是給 P48／P52／P59 的 repository-only 入口。寫出的 key、順序與條件
寫入語意完全相同，`promote_site_objects` 自己有五條測試。已寫進 Phase 文件 §6。

### 5.4 `_write_indexes(slug)` 一次寫兩個索引，多篇會亂序

Phase 24 的 `_write_indexes` 同時寫教學索引與站台索引，逐篇呼叫的話兩篇會變成
「A 版本頁 → A 教學索引 → 站台索引 → B 版本頁 → …」，違反「版本頁 → 教學索引 → 站台索引」。

**裁決**：拆成 `_write_tutorial_index(slug)` 與 `_write_site_index()`，站台索引整批只寫一次。
N=1 的寫入順序完全沒變，Phase 24 的測試不受影響。

### 5.5 `data-published="false"` 只靠呼叫順序把關太脆

review Minor 3。`promote_site_objects` 是公開函式，P48／P52／P59 可以不經
`Publisher.commit` 直接呼叫，那樣就沒有 `_restage` 幫忙。

**裁決**：`_put_public_object` 在寫出去之前驗 `UNPUBLISHED_MARKER`（00A §3.8）。
連帶讓四條直接呼叫 `promote_site_objects` 的測試要先 `restage_as_published`——這件事本身
就是守門有效的證據（見第 3 節的中途紅燈）。

### 5.6 `transact_write` 的值形狀

00A §6.7 寫「值用低階 `{"S": ...}` 形式」與 boto3 實際行為不符（phase24-report §5.1）。
本 Phase 直接沿用 Phase 24 的 `_update`（原生 Python 值），**沒有踩到同一個坑**。
00A §6.7 那一句仍待 controller 同步（見第 9 節）。

#### P48（Feedback Review）／P52（Release）要知道的六件事

1. **一次 `PublishRequest` 最多 50 篇**，而且同一批不得有重複 `version_id` 或同 slug 兩版；
   超過或違反就是 `PublishError`。**分批決策在你們那邊**，而且每一批各自遵守 F49——
   `Publisher` 不會、也不得幫你把 60 篇拆成兩次交易。
2. **每篇各開一筆 per-slug 子 operation 取版號**（D-59）；`PublishRequest.operation_id` 是
   **父** operation，`commit` 在 N>1 時**不會**在它上面 `record_version`。父 operation 只
   負責整批追溯（它的 `version_id` 若已有值也不會被動到）。
3. **`commit` 的回傳值要看兩個欄位**：`failed is None` 才是成功；`failed` 有值代表整批
   被 DynamoDB 條件擋下（`published` 一定是空 tuple、`site/` 一定沒有新檔），
   **重讀基底再決定**，不要只重送失敗那一篇。
4. **`commit` 丟 `PublishError` 分兩種**：訊息含「發布前檢查未通過」＝交易次數 0、什麼都
   沒發生；訊息含切點代號（`a2_…`／`a3_…`）＝**DynamoDB 已切、公開站落後**，要走 P59 的
   補償重送，**不可以**當成可重試的暫時故障丟回 ASL Retry。
5. **`published` 的順序與 `PublishRequest.version_ids` 相同**，`promote_site_objects` 回傳的
   公開 key 也是（每篇兩個：`v<n>.html`、`v<n>.diff.txt`）。
6. 整批的 `prepare` 一失敗就整次停；已寫出的私有 staging **保留不刪**（設計 §8.2 F36），
   同 `operation_id` 重送會覆寫同一份 bytes。

#### P59（失敗復原與重送）要知道的七件事

1. **復原輸入分兩種，不要混**：
   - 單篇：`OPS#<operation_id>.version_id` ＋ `site_key(version_id)`／`_diff_copy_key(...)`
     重算（00A §6.7）。`record_version` **已經排在交易成功之後、寫 `site/` 之前**，所以
     切點 a2 發生時 ledger 一定有值（Phase 24 review Important 1，本 Phase 代修）。
   - 多篇：`operations/<operation_id>/pending-promote.json`，內容
     `{"version_ids": [...], "site_keys": [...]}`，`site_keys` **含 `site/` 前綴**、順序與
     `version_ids` 相同、每篇兩個。用 `operation_ref(operation_id, PENDING_PROMOTE_NAME)` 組 key。
2. **補齊可以直接呼叫 `promote_site_objects(prepared, repository=...)`**：已存在且 bytes 相同
   的公開 key 會靜靜略過（`ObjectAlreadyExists` → 比對 bytes → 相同就通過）並**仍然回傳**，
   bytes 不同則 `PublishError` 且保留既有物件。本 Phase 的
   `test_resending_the_same_operation_only_fills_the_missing_public_objects` 就是這個流程的
   最小版本；正式的 `resume_publish` 歸你們。
3. **補齊之後索引還沒重建**（教學索引與站台索引仍指舊世代）。它們是可重建投影，
   `Publisher._write_tutorial_index(slug)`／`_write_site_index()` 各自獨立、可重複呼叫，
   `resume_publish` 要記得補這一段。順序仍是「版本頁 → 教學索引 → 站台索引」。
4. **`maybe_fail` 的插入點**：`Repository.transact_write`（a1）、`Publisher._stage_one`
   （prepare 第 k 篇）、`Publisher.inspect`、`Publisher._promote`（a2／a3，**逐篇**，
   所以能只讓第 j 篇失敗）。本 Phase 用 `monkeypatch`，沒有提前建 `TKB_FAULT`。
5. **`Publisher._promote` 與 `promote_site_objects` 共用 `_promote_version`**，改一邊要改另一邊；
   `_promote` 之所以還在，就是為了留住第 4 點的注入點。
6. **交易後的任何例外一律是 `PublishError`**，訊息帶切點代號（`_cut_point(prepared)`：
   N<2 → `a2_after_transact_before_site`，N≥2 → `a3_after_first_site_before_second`）。
7. **`UNPUBLISHED_MARKER` 守門在 `_put_public_object`**：任何補齊路徑若搬到還沒重新渲染的
   staging，會直接 `PublishError` 而不是把未發布標記推上線。要先
   `Publisher._restage(version, tutorial, operation_id, now=...)`。
