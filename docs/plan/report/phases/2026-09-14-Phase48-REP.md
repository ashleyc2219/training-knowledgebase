## 1. 實作內容與邏輯（逐檔說明）

### 1.1 `src/training_kb/pipelines/feedback.py`（追加 `# ---- Phase 48 ----` 區段）

這支檔的 owner 是 Phase 44，P45／P46／P47 各自有區段。本 Phase **只追加自己的區段**，
一個字都沒有改別人的程式（只在檔頭的 import 區加了三行：`os`、`load_settings`、
`pipelines.common` 與 `publishing`／`site` 的匯入）。

| 名稱 | 做什麼 |
|---|---|
| `FEEDBACK_REVIEW_PIPELINE` | `"feedback-review"`，`run_sequence` 與 ASL 的 `Parameters.pipeline` 都用它 |
| `REVIEW_MODES` | `("formal", "demo")`，ASL input 唯一合法的兩個值 |
| `_review_mode(state)` | 讀 `mode`；未知值丟 `PermanentError`（**不默默退回 formal**）。回傳值逐一比對 `REVIEW_MODES`，型別收斂靠比對本身，不用 `cast` |
| `_ids` / `_listed` | `list[str]` 與 `list[JSONValue]` 的互轉。list 在型別上是不變的，`list[str]` 不是 `list[JSONValue]` 的子型別，直接塞進 state 過不了 `mypy --strict`；只在這裡轉一次，不在每個 Task 各寫一份 `cast` |
| `_review_targets(repository)` | active Tutorial 的 current 且已發布的版本 ID，升序 |
| `review_operation_id(state, deps)` | `op-feedback-review-<project>-<UTC 日期>`；canonical id 用**連字號**（D-61），`execution_name` 才不必走 SHA-256 截取 |
| `task_list_targets` | 先驗 `mode`（未知就連表都不掃）→ `accept` 當日 operation → 列目標 |
| `task_evaluate_targets` | 同一個 Task 裡兩條**獨立**分支；每個弱教學 target 先 `accept` 一筆 `refine_operation_id` 子 operation（D-59）再交給 `refine_target`（**修正波 2026-09-15**：先 `_guard` 再決定要不要打模型，診斷存進 `operations/<op>/diagnose-weak.json` 並在重送時沿用）；逐篇「沒有改動」的理由寫私有 `review-no-change.json`，**不進 state** |
| `_publisher` / `_prepare_batch` / `_restored` | `Publisher(repository, SiteRenderer(), operations)`；**只有 `PrepareBatch` 真的跑一次 `Publisher.prepare`**，`InspectBatch`／`CommitBatch` 從 `publish-request.json` 重建（`_restored`），超過 `MAX_BATCH_VERSIONS` 在寫第一個 staging 之前就擋下來。（**現況核對 2026-09-15**：本列原文寫的 `_prepared` 每個 Task 重算一次，是 review 修正回合 1 之前的舊形狀，函式早就不存在了） |
| `task_prepare_batch` | 只寫私有 staging ＋ `operations/<op>/publish-request.json`；結束時**一個公開物件都還沒寫** |
| `task_inspect_batch` | 整批只讀不寫；任一篇不過丟 `PermanentError` |
| `task_commit_batch` | 一次交易切完整批；`PublishResult.failed` 有值就丟 `PermanentError`（**不回一個看起來正常的結果**，比照 P41 review 必修 3）。整批已發布時要先過 `_assert_finished_here`（**修正波 2026-09-15**：公開物件要齊、而且要有「本 operation 發布過」的證據，否則 `PermanentError` 指名 `publishing.resume_publish`）才續寫結果。最後寫 `review-result.json`（把 `review-no-change.json` 併進來）並 `operations.complete(...)` ——這是整條流程的停止點 |
| `FEEDBACK_REVIEW_TASKS` / `_TASK_BY_NAME` | 五個 Task 的固定順序；名稱由 `task_name` 導出，不另打字串表。（**現況核對 2026-09-15**：模組層的 `_DEPS` 快取已搬進 `common.deps_for`，見修正波報告） |
| `run_feedback_review` | 本機整條序列：先補 `operation_id` 再交給 `run_sequence`（D-07 的第一個參數是 pipeline 名） |
| `feedback_review_handler` | 共用 Lambda 的直接入口，**只跑 `event["task"]` 那一個 Task**，不 try／except |

**為什麼是三個 Task 而不是一個。** `prepare`／`inspect`／`commit` 本來就是 P24／P25 的三段式；
本 Phase 唯一多做的事是把它們**拆成三個 ASL Task**，這樣「第二篇檢查失敗」一定發生在任何
公開前綴寫入**之前**。拆進 `Map` 逐篇處理會讓「第一篇已 publish、第二篇失敗」變成可能，
那正是 F49 禁止的形狀（§3 有實驗證據）。

### 1.2 `infra/stepfunctions/feedback-review/v1.json`（新檔）

五個 Task 一條直線 `ListTargets → EvaluateTargets → PrepareBatch → InspectBatch →
CommitBatch → Succeeded`，**沒有 Choice、沒有 Map**，加上 `Succeeded`（Succeed）與
`PipelineFailed`（Fail）兩個終點。每個 Task 的 `Retry`／`Catch`／`TimeoutSeconds` 都是
`task_state(ARN, next)` 的輸出（Phase 29 的 `RETRY`／`CATCH`），本 Phase 沒有抄任何字面值；
`Parameters` 封套只有 `pipeline`／`task`／`state.$`，**沒有** `Payload` 外層（D-24、D-49）。

檔案是用 `canonical_json(definition)` 的 bytes 落檔（`indent=2, sort_keys=True`），所以
`DefinitionBody.from_file` 讀到的 bytes 與 `save_asl_snapshot` 存進 S3 的**逐 byte 相同**。

### 1.3 `infra/training_kb_stack.py`（追加 `# ---- Phase 48 ----` 區段）

模組層加 `REVIEW_MACHINE`／`REVIEW_ASL_PATH`／`REVIEW_SCHEDULE_NAME`／
`REVIEW_SCHEDULE_EXPRESSION`／`REVIEW_SCHEDULE_TIMEZONE`／`REVIEW_SCHEDULE_INPUT`；
建構子加五個 construct：

1. `FeedbackReviewLogs`（`/aws/vendedlogs/states/training-kb-feedback-review`，90 天）

**本 Phase 不新增任何 Lambda**（D-23：三條 pipeline 共用 `training-kb-pipeline-task`），
相依 layer 沿用 P41 的 `self.deps_layer`（R2）。也**沒有**給 webhook
`grant_start_execution`／`DescribeExecution`：`feedback-review` 沒有外部事件入口。

## 5. 遇到的問題與解法

1. **單元測試的器材：手寫假 `Repository` 行不通。** 整條流程會走到 `create_version`／
   `verify_version_complete`／`Publisher.prepare|inspect|commit`／`transact_write`／
   lease／`record_version`，手寫替身等於複製一份會漂移的 `Repository` 副本。改成比照
   `tests/unit/test_feedback_refine.py`（P46）與 `tests/unit/test_publisher_single.py`（P24）
   已在用的做法：moto 表＋bucket 上的**真** `Repository`，只加一個記錄 `accept` 順序的
   `OperationCoordinator` 子類。
   種子資料也走真的 `create_version`（含 `.md`／`.diff`／STEP 邊）再 `update_meta` 補
   `published_at`／`current_version`，`Publisher.inspect` 的「已保存步驟 vs 公開內容」
   才比對得出來。順序是 **TUTORIAL item 先建**：`create_version` 最後的
   `verify_version_complete` 會查它（第一次跑就踩到 `找不到 TUTORIAL item a`）。
2. **`mypy --strict` 擋下 `list[str]` 進 state。** `JSONValue` 的 list 分支是
   `list[JSONValue]`，而 list 是不變的，所以 `list[str]` 不是它的子型別。加了
   `_ids`／`_listed` 兩個小函式集中轉換，沒有在各個 Task 灑 `cast`。
3. **「第二篇檢查失敗」要挑對切點。** 一開始改 STEP 邊的文字，結果 `prepare` 自己就先丟
