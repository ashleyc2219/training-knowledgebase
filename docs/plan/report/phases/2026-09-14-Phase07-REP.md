**S3 條件寫入的邏輯**固定是「先送出、再依 AWS 回應分類」，不先查再寫（先查再寫會在兩個請求
之間留空窗，兩個 Lambda 可能同時判斷為不存在）：

```text
put_object(..., if_none_match=True) -> PutObject + IfNoneMatch="*"
  200 -> 完成
  412 PreconditionFailed        -> ObjectAlreadyExists（PermanentError 子類）
  409 ConditionalRequestConflict-> TransientError（交 ASL Retry，這裡不自己迴圈）
  其他 ClientError               -> 原樣往外丟（不吞錯）
```

送出的參數白名單只有 `Key`／`Body`／`ContentType`（＋`IfNoneMatch`）：**沒有 `ACL`**，公開與否
一律由 bucket policy 的 `site/*` 決定（00A §3.8）。`MISSING_CODES = {"NoSuchKey", "404"}` 是
「key 不存在」的唯一判斷（`GetObject` 回 `NoSuchKey`、`HeadObject` 沒有 body 只回 `404`），
其餘 `ClientError` 一律往外丟。`object_exists` 用 `Object(key).load()`（HeadObject），不下載 body。

**關係邊的一致性有兩個檢查點**：

- 寫入端：`target` **只**由 `target_pk` 導出（`edge_sk(relation, target_pk)` → `SK`，`target=target_pk`），
  `attrs` 命中 `RESERVED_ATTRS` 任何一個就 `PermanentError`；再做一次 `parse_edge_sk(sk) == (relation, target_pk)`
  的 round-trip 自檢。`entity = parse_pk(pk)[0]`（等於 PK 前綴，Phase 08 的 `scan_entity` 靠它篩選）。
- 讀取端：`list_edges` 逐筆比對 `parse_edge_sk(SK)[1] == item["target"]`，不符就 `PermanentError`
  且 **不自動修正**；`SK == META` 跳過。之所以讀取端也要檢查，是因為 backfill（Phase 28）與維護
  腳本也會寫邊，只在寫入端檢查發現不了已經寫壞的資料。

`_paged(operation, **arguments)` 是私有的最小分頁迴圈：反覆呼叫同一個 boto3 操作直到回應沒有
`LastEvaluatedKey`，**空頁不早停**（DynamoDB 可能回一頁沒有 `Items` 卻仍帶 cursor）。本 Phase 只有
`list_edges` 用它，Phase 08 會擴充（加 `Limit`）再給三個公開查詢共用。

`_require_bucket()` 把「建 `Repository` 時沒給 bucket」變成看得懂的 `PermanentError`，而不是
`AttributeError: 'NoneType' object has no attribute 'put_object'`；三個 S3 方法都經過它。
`bucket` 預設 `None`，所以 Phase 06 既有的 `Repository(table)` 呼叫完全不受影響
（`tests/integration/test_repository_meta_smoke.py` 就是這樣用的，沒有改）。

## 10. 代修 Phase 06 review 項目

controller 轉來的 `review-p06.md` 結論是 Approved ＋ 1 項 Important；因為 `repository.py` 現在由
Phase 07 持有，以下由本 Phase 一併修掉，放在獨立 commit `10fa581`。

### 10.1 Important 1：`put_meta_item` 受控覆寫的回傳值（已修）

**問題**：`_put_item` 走完 revision CAS 覆寫成功後仍 `return True`，但 docstring 與 00A §6.3 說回傳值是
「本次是否由我建立」。回 `True` 會讓 `OPS#`／`SEQ#`／`LEASE#` 的呼叫端誤以為自己是第一個建立者，
永久去重的判斷點失效。

**RED**（先寫測試）：

```text
>       assert repository.put_meta_item("OPS#op-9", {"status": "done"}, create_only=False) is False
E       AssertionError: assert True is False
```

**修法**：`_put_item` 最後一行由 `return True` 改成 `return current is None`（新建才 `True`，
受控覆寫成功回 `False`）。**連帶必須處理兩個地方，否則會產生新的 bug**：

1. `put_meta(entity, create_only=False)` 原本是「`_put_item` 回 `False` 就丟 `CoordinationError`」，
   改完之後受控覆寫成功也會回 `False`。因此 `put_meta` 改成：

   ```python
   created = self._put_item(pk, payload, create_only=create_only)
   if create_only and not created:
       raise CoordinationError(f"metadata already exists or changed since read: {pk}")
   ```

2. 上一點會讓「`create_only=False` 但 item 在讀取後才被別人建立」（`attribute_not_exists` 條件失敗、
   **什麼都沒寫**）變成靜默成功。所以 `_put_item` 在那條路徑改成明確丟
   `CoordinationError("metadata created by someone else since read: …")`——呼叫端要的是受控覆寫，
   結果一個 byte 都沒寫，這就是協調失敗。`create_only=True` 撞鍵仍然回 `False`（語意不變，
   `put_meta_item` 靠它判斷「別人先建立了」）。

**GREEN**：新測試 `test_controlled_overwrite_reports_that_it_did_not_create` 釘住「第一次 `True`、
第二次覆寫 `False`、`_revision` 變 2、內容是新的」；既有的
`test_controlled_overwrite_keeps_revision_monotonic` 與 `test_meta_item_primitives_serve_non_model_prefixes`
都仍然綠（後者驗的是 `create_only=True` 撞鍵回 `False`，語意沒變）。

### 10.2 Minor 2：`_encode` 只認 `list`（已修）

**RED**：`put_meta_item("OPS#op-10", {"scores": (0.5, 1)})` →
`TypeError: Float types are not supported. Use Decimal types instead.`（reviewer 預測的錯誤逐字重現）。

**修法**：`isinstance(value, list | tuple)`（PEP 604 寫法，ruff UP 規則友善），tuple 一樣遞迴編碼成 list。
測試 `test_tuple_values_survive_the_decimal_codec` 釘住 `("a","b")` → `["a","b"]`、`(0.5, 1)` → `[0.5, 1]`。
Phase 10 的 `OperationRecord.model_output_refs`（`tuple[str, ...]`）之後就不會撞到這個坑。

### 10.3 Minor 3：壞 PK 的 `ValueError` 逃出錯誤分類（已修）
