## 1. 實作內容（含實作邏輯）

在 `src/training_kb/repository.py` 追加設計 §10 的固定關係查詢：一個模組函式 `version_sort_key`、
兩個私有輔助（`_meta_models`、`_is_current_published`）與五個具名方法，和 Phase 08 的
`list_feedback_of_version` 合為 00A §6.3 說的六種固定圖譜查詢。**全部只讀、不接 `Writer`，
所以正常關係遍歷不可能呼叫模型**；沒有任何寫入路徑。既有簽名一行都沒有改動，只在檔案尾端追加
（模組 docstring 補上第 6 段的說明，並把已經過期的「檔案分成四段」改成六段）。

### 1.1 `version_sort_key(version_id) -> tuple[str, int]`（模組函式）

`<slug>@v<n>` → `(slug, n)`。字典序會把 `@v10` 排在 `@v2` 前面，所以只要牽涉版本排序就一律經過它。
它與 `content.parse_version_id` 回傳同一種東西，但**不能** import：相依方向是 `content` 呼叫
`repository`（設計 §5），反向 import 會循環，所以自帶一份最小解析。驗證寫法與 `content.parse_version_id`、
`keys.parse_step_pk` 對齊——`isdecimal()`（不是 Phase 文件原本寫的 `isdigit()`）擋掉 `²` 這種
`int()` 會丟自己的 `ValueError` 的字元，再用 `f"{slug}@v{number}" != version_id` 的 round-trip 比較
擋掉 `a@v01` 的前導零與 `a@v１` 的全形數字（它們 `int()` 得到同一個值卻是不同字串，排序就不再是全序）。
格式不合丟 `PermanentError`（不是 `ValueError`）：呼叫端拿到的是「這筆資料確定不合法」。

### 1.2 `_meta_models(entity, model)`（私有）

`scan_entity(entity)` → 自己再濾一次 `SK == META` → `item_to_model`（D29），**不排序**，
順序留給各查詢自己決定。與既有的 `_scan_models` 的差別只有兩點：不接 `equals` 等值過濾、不排序。
`scan_entity` 的預設 `meta_only=True` 已經濾過一次，這裡仍然自己再濾一次的理由寫在 docstring：
`entity` 等於 PK 前綴（00A §3.6），所以 `scan_entity("VERSION")` 同時涵蓋 VERSION 本體與它的
`SUPERSEDES` 邊，預設值一旦改變、或有人改傳 `meta_only=False`，邊就會被當成版本餵進 `item_to_model`
而整筆 `ValidationError`。

### 1.3 `find_feature_by_name_or_alias(name) -> Feature | None`

設計 §7.4：先比 `name` 再比 `aliases`。掃描結果先依 `feature_id` 升序排好再比對，讓 name 撞名時的
回傳可重現。`name` 命中時直接採用（所以「某個 Feature 的舊名是另一個 Feature 的現名」不會誤判）；
alias 必須唯一（D07），同一字串命中兩個 Feature 的 alias 丟 `PermanentError`，不自行挑一個；
找不到回 `None`，**不做語意搜尋、不建立 Feature**（那是 Phase 49）。

### 1.4 `list_versions_of_tutorial(slug) -> list[TutorialVersion]`

回**全部**版本（含歷史版與 `published_at=None` 的未發布版），依 `version_sort_key` 升序。
`VERSION#<slug>@v` 不是合法的 Query 鍵（PK 是完整值，不是前綴），所以照設計 §10 走基表分頁 Scan
再依 `slug` 篩選。篩已發布是呼叫端的責任（索引頁屬 Phase 24）。

### 1.5 `find_current_published_steps_referencing(feature_id) -> list[TutorialStep]`

本 Phase 唯一有兩條資料來源的查詢，順序是「先基表、後 GSI」：

- **B（基表，決定結果集合）**：`scan_entity("TUTORIAL")` 一致讀取每篇教學 → `current_version`
  非空且 `_is_current_published` 成立 → `get_steps(current)` 篩 `step.feature_id == feature_id`，
  收進 `dict[(version_id, number)]`。
- **A（GSI，只補候選）**：`query_by_target(feature_pk(feature_id))` 的候選三重過濾（關係是
  `REFERENCES`、起點是 `STEP#`、終點確實是這個 Feature），排除 TICKET 的 `ASKS_ABOUT`；
  不是目前已發布版就跳過；**是目前已發布版卻不在 B 的結果裡 → `PermanentError`**。

B 已經用一致讀取列出每個目前已發布版的全部步驟，所以走到 `raise` 就代表那筆候選的 STEP item 在基表
缺失或缺 `entity` 屬性。不靜默跳過、也不在查詢裡補寫（補寫是 Phase 28）。結果依
`(version_sort_key(version_id), number)` 升序。

`_is_current_published(version_id)`：`Tutorial.current_version == version_id` **且**
`TutorialVersion.published_at is not None`，兩個條件同時成立才算，兩者都走基表一致讀取。

步驟 PK 的解析改用 `keys.parse_step_pk`（`step_pk` 的反函式，`get_steps` 也用它），不自己
`rpartition` 再 `int()`：那樣 `STEP#a@v1#03` 這種組不回原鍵的字串會被靜默接受，兩個不同字串就會
對應到同一步。

### 1.6 `list_versions_applying_rule(rule_id) -> list[str]`

從 `RULE#<id>` 的 `APPLIED_TO#` 邊取候選，但**以 `VERSION.rules_applied` 為唯一權威**（D17）：
邊存在而該版的 `rules_applied` 不含這條規則時不回傳（多餘邊會讓「規則套用次數」多計）。
邊指向已不存在的版本只跳過——本 Phase 只讀，清理與投影重建是 Phase 28。回 version_id 字串集合，
依 `version_sort_key` 升序並去重。

### 1.7 `find_active_tutorial_for_feature(feature_id) -> Tutorial | None`

只看 `status == "active"` 且 `feature_id in feature_ids`：即使 `current_version` 還是 `None`
（尚待首次發布）也算已有教學（F12），`retired` 不算，所以不會阻擋 CREATE。走基表 Scan 而不是
`ASKS_ABOUT` 邊（D-52 明載本方法不改）。多篇時回 slug 升序第一筆，讓結果可重現。

## 5. 遇到的問題與解法

1. **Phase 文件的 `repo` fixture 說「覆寫 Phase 08 的四個原語」。** 那樣一來「空頁不早停」與
   「GSI 候選回基表核對」就變成在測假物件。改成只假掉儲存層（`FakeTable` 實作四個 boto3 操作），
   Phase 08 的原語一個都不覆寫，被測範圍反而更大。已改文件。
2. **`version_sort_key` 用 `isdigit()` 太寬。** 會放行 `²`（`int()` 丟自己的 `ValueError`）、
   `a@v01`、`a@v１`。改成 `isdecimal()` + round-trip 比較，與 `content.parse_version_id`、
   `keys.parse_step_pk` 同一套。已改文件。
3. **moto 的 GSI 是即時的，做不出「GSI 落後」。** 整合測試改用兩種更嚴格的替身：(a) 把
   `query_by_target` 換成永遠回空清單（結果必須完全由基表一致讀取決定）；(b) 直接對 moto 的表寫一筆
   **沒有 `entity` 屬性**的 `REFERENCES` 邊——`by_target` 看得到（它有 `target`），`scan_entity`
   的 `entity` 過濾卻掃不到，正是 §6 描述的「基表資料不完整」。已改文件。
4. **Phase 文件的前置寫 Phase 26，與實際波次相反。** controller 的依賴鏈是 P24→P27→P28，
   P26 與 P28 同一波（在本 Phase 之後）。本 Phase 只讀 `Tutorial.status`（Phase 04 的模型欄位），
   不依賴 P26 的退役流程。已改文件並保留原連結。
5. **`_meta_models` 與既有 `_scan_models` 看起來重複。** 不動既有程式（COMMON 規則），
   新增的 `_meta_models` 差別是「不接 `equals`、不排序、自己再濾一次 `SK == META`」，
   三個 Scan 型查詢因此能各套自己的順序（`version_sort_key`／`feature_id`／`slug`）。
   已在 docstring 與文件註明差異。
6. **`ruff` 曾因別人的檔案整批紅。** 期間 `tests/unit/test_publisher_batch.py`（未追蹤）有語法錯誤、
   `publishing.py` 有 F401／E501；那是 Phase 25 agent 的進行中檔案，改用縮小範圍的
   `ruff check <自己的檔案> infra` 驗證自己的部分，最後那位 agent 修好後全域 `ruff` 已 `All checks passed!`。
