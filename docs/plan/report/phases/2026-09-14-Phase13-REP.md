### 1.1 新增的程式檔

`src/training_kb/source_ids.py`（209 行，owner P13，00A §3.2）。整支只做「來源事實 → canonical
字串」的純函式轉換：不連 GitHub、不呼叫模型、不讀寫 AWS、不建立 User 實體或身分對照表。

**確定性 ID 編碼（Task 1）**

```text
github_ticket_id("Acme","Copilot",128)      -> t_gh-acme-copilot-128
github_release_id("acme","copilot",42,1)    -> r_gh-acme-copilot-pr42-1
github_source_event_id("acme","copilot",42) -> gh-acme-copilot-pr42
github_user_id(90210)                       -> u_gh-90210
```

- `_part()`：`owner`／`repo` 先 `strip().lower()`，再用 `SLUG_PATTERN = ^[a-z0-9._-]+$` 全字比對。
  不合法字元**一律拒絕而不是取代**（`acme/evil` → `IngressError(fields=("owner",))`），避免兩個不同
  repo 被「清洗」成同一個 ID。
- `_positive()`：`number`／`pr_number`／`k` 必須是大於 0 的整數，且先擋 `bool`（Python 的 `True`
  是 `int` 子類，不擋會讓 `github_ticket_id(o, r, True)` 編出 `-1`）。
- `github_source_event_id` 刻意**不帶** `t_`／`r_`／`f_` 前綴（00A §6.8）：它是來源事件識別碼，
  不是實體 ID。
- `sub_release_ids(owner, repo, pr_number, features)`：本 Phase 另建，是「同一個 PR 的子變更依
  Feature 名稱升序配 `k`（從 1 起算）」的唯一實作處，回 `(feature, release_id)` 序對。空清單、
  空白字串與重複 Feature 名稱一律 `IngressError(fields=("feature",))`。因為排序只看 Feature 名稱，
  同一份 PR 無論以什麼順序重送，都得到完全相同的一組 `r_` ID。

**穩定使用者（Task 2）**

- `github_user_id(numeric_id)`：只吃 `sender["id"]` 這種數字，改名（`login`）不改人；非正整數或
  `bool` → `IngressError(fields=("user",))`。純函式、不查表。
- `stable_user_from_import(value)`：只做格式檢查（`USER_PATTERN = ^[a-z0-9_-]{2,64}$`），缺值、
  只有空白、含大寫或標點一律拒絕，**不補值、不從顯示名稱猜、不隨機產生**。`u_03`（Demo 形狀）與
  `u_gh-90210`（真實 GitHub 形狀）都合法，兩種形狀共存但不互換，系統不建立兩者的對照表。

**核定紀錄（Task 3）**

- `SourceApproval`：`@dataclass(frozen=True)`，九個欄位順序逐字照 00A §6.8
  （`domain, event_type, adapter, stable_keys, fixture, id_encoder, stable_user_source,
  approved_by, approved_at`）。`fixture` 存的是相對 `tests/fixtures/` 的路徑。
  另加一個 `approved` property：`approved_by` 與 `approved_at` 都非空白才算核定。
- `load_source_approvals(path)`：讀 JSON 陣列，逐列檢查九個欄位齊全、型別正確、`stable_keys` 是
  非空字串清單；任何一項不合就 `IngressError`，**不補預設值**。刻意不用 `SourceApproval(**row)`，
  以免 `json.loads` 的 `Any` 讓錯誤的 JSON 靜悄悄通過。
- `approved_stable_keys(rows)`：只回 `row.approved` 為真的 `(domain, event_type)`；未核定的來源
  不會出現在結果裡，下游 Phase 因此拿不到清單可用，自然 blocked。
- `render_mapping_table(rows)`：把核定紀錄渲染成 mapping 表的九欄；未核定的列的 `STABLE_KEYS`
  自動標「候選：」、核定者與核定日期自動標「待維護者核定」。讓
  `docs/plan/report/o6-mapping.md` 由紀錄產生而不是手抄，整合測試會斷言報告裡的表格與紀錄一致。

## 5. 遇到的問題與解法

**5.1 Phase 文件自相矛盾：renamed 到底是 `k=1` 還是 `k=2`**

§6.2 規定「`k` 的順序由子變更的 Feature 名稱升序決定」，但 §2 與 §6.2 的圖同時把 renamed
（Feature 名稱 `Prepare`）畫成 `k=1`、removed（`Legacy Export`）畫成 `k=2`。`Legacy Export` 的
字典序在 `Prepare` 之前，兩者不可能同時成立。

**裁決：** 升序規則是載重條件（它才是「同一個 PR 重送得到相同 ID」的機制），示意表只是說明，
所以保留規則、改示意表：`Legacy Export` → `r_gh-acme-copilot-pr42-1`、`Prepare` →
`r_gh-acme-copilot-pr42-2`，並在 §6.2 加一句寫明原因。驗收矩陣要求的「兩個不同 `r_` ID 共用
`gh-acme-copilot-pr42`」不受影響。

**5.2 `("github.com","issues")` 的核定者要填什麼**

Phase 文件 §6.3 把五列的核定者都寫成「待填」，但 Task 3 的測試要求
`approved_stable_keys()[("github.com","issues")]` 必須存在——而該函式只收核定過的列。00A §4.2
與設計 §7.2 都明寫「只有 `("github.com","issues")` 的 `action, issue, repository, sender`
已核定」。

**裁決：** 以 00A 為準。這一列的 `approved_by` 填**文件出處**
`docs/design/training-kb.md §7.2`、`approved_at` 填設計文件日期 `2026-09-13`，並在 Phase 文件與
報告都寫明「這一欄記的是文件出處，不是個人簽收」。**沒有虛構任何維護者姓名**；其餘四列留空、
維持 blocked。

**5.3 Task 2 Step 4 要求斷言 Feedback／View 的 `user`，但那兩份匯入檔不屬於本 Phase**

00A §3.2 把 Feedback／View 匯入檔 fixture 指派給 Phase 42，本 Phase 只有三份手動 fixture，且
changelog 那份是 Release 形狀、沒有使用者。

**裁決：** 從 Discord 與 email 兩份匯入檔取出同一位 `u_03`，另外斷言 changelog 的 items **沒有**
`author`／`user`（對應 mapping 表的「不適用」），再用同一個字串建 `Ticket`、`Feedback`、
`TutorialView` 三個實體，斷言 `ticket.author == feedback.user == view.user == "u_03"`。契約
（設計 §7.1「三者必須是同一字串」）完整被驗，也沒有越界建別的 Phase 的檔案。

**5.4 `load_source_approvals` 用 `SourceApproval(**row)` 會讓壞掉的 JSON 靜悄悄通過**

`json.loads` 回 `Any`，mypy strict 不會擋，執行期也只在欄位名完全對不上時才報 `TypeError`。
改成逐欄取值＋型別檢查，缺欄位回 `IngressError(fields=(缺的欄位名...))`，與全套「一次回報所有
缺欄位」的慣例一致。

**5.5 `zsh` 不做未加引號變數的字詞切分**

`FILES="a b c"; git add $FILES` 在 zsh 會被當成單一路徑。改成把檔名逐個列出。

## 9. 未完成／疑慮

1. **O6 本身未 PASS（預期內）。** 四列來源等維護者簽收；這是人工 gate，不是程式缺陷。
2. **`("github.com","issues")` 的核定者是文件出處而不是人。** 依 00A §4.2 該列已核定，但簽收的
   是設計文件而非具名維護者。如果維護者希望所有五列都有具名簽收，把第一列的 `approved_by` 換成
   人名即可，測試不受影響。
3. **PR fixture 的兩個子變更放在 `pull_request.body`。** 真實 GitHub payload 不帶「哪些 Feature
   被改」的結構化欄位，本 fixture 用 `- renamed: A -> B` / `- removed: C` 的 body 行表達。
   [Phase 36] 的 `parse_pr_diff` 要能從這個形狀抽出 `{"changes": [...]}`；本 Phase 的單元測試用
   一個 3 行的測試內建正則讀同一格式，**沒有**在 `src/` 放第二份 parser。若 Phase 36 決定改用
   diff 或別的來源抽取，請同步更新這份 fixture 的 body。
4. **`sub_release_ids` 的排序用 Python 預設的 codepoint 升序**（不是 locale collation）。
   Feature 名稱若含 CJK，順序仍然確定但不是「中文筆畫／注音」直覺順序。確定性是本 Phase 要的
   性質，這不影響正確性。
5. **`render_mapping_table` 與 `sub_release_ids` 不在 00A §6.8 的介面列裡。** 兩者都在
   `source_ids.py`（owner P13）內，屬本檔延伸；已在 Phase 文件 §5 Produces 補上簽名與說明。若
   [Phase 33]／[Phase 36] 要引用，建議先把它們補進 00A §6.8。

   `114 passed, 3 skipped`、零 warning、ruff 全過。收尾期間 Phase 06 的 agent 短暫推上一個
