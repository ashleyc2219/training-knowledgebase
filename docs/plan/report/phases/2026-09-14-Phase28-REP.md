## 1. 實作內容（含實作邏輯）

在 `src/training_kb/repository.py` 追加第 7 段「維護批次」：兩個模組級名稱、一個模組級私有
函式、三個 `Repository` 方法。**只追加、不重排、不改任何既有簽名**；既有程式一行都沒有改動
（唯二的既有行改動是模組 docstring 的「六段 → 七段」與 import 清單加 `dataclass`／`step_pk`）。
兩個修復函式都**不接 `Writer`、不呼叫模型**（D-46），完全不寫 `VERSION` item、不寫
`RULE.status`、不碰 S3、不產生新版本。

### 1.1 `DELETABLE_RELATIONS`（模組級）

`frozenset({"APPLIED_TO"})`。`keys.RELATIONS` 是 `keys.py` 的內部白名單、外部模組一律不
import（00A §6.3），所以這裡自帶一份，而且刻意只有一個值：`REFERENCES`／`SUPERSEDES`
是已發布版本的歷史事實，錯了也不能由程式片面改寫（F40），這道白名單就是「不替換錯邊」的
**程式保險絲**——backfill 就算寫錯也刪不掉引用邊。

### 1.2 `BackfillReport`（模組級 frozen dataclass）

`added`／`conflicts`／`unresolved` 三個 `tuple[str, ...]`，值都是**步驟 PK 字串**。

`DELETABLE_RELATIONS` 與 `BackfillReport` 放在段 3 之後、`Repository` **之前**：沒有
`from __future__ import annotations` 時，方法的回傳註解在 class body 求值時就要看得到名稱，
放在 class 之後只能寫成字串註解，那比插在前面更難讀。

### 1.3 `_sorted_step_pks(values)`（模組級私有）

`tuple(sorted(set(values), key=parse_step_pk))`。排序鍵用 `parse_step_pk`（回
`(version_id, number)`）而不是字串本身：字典序會把 `STEP#a@v2#10` 排到 `#3` 前面，
與 `version_sort_key` 擋掉的是同一個坑。需求書原文寫 `tuple(sorted(added))`，已依專案一貫
立場改成數值序並在文件記錄（`test_backfill_report_fields_are_sorted_step_pks` 用十步的版本
直接鎖住這件事）。去重是防禦性的——`TutorialContent` 已保證步驟編號從 1 連號且唯一。

### 1.4 `Repository.delete_edge(pk, relation, target_pk)`

`put_edge` 的反向操作，`relation not in DELETABLE_RELATIONS` 一律 `PermanentError`。
本 Phase 只在 `rebuild_rule_projection` 內用它。刪不存在的邊是 no-op（`DeleteItem` 本來就
冪等），所以重跑安全；`edge_sk` 順便把不合法的 `target_pk` 擋成 `ValueError`。

### 1.5 `Repository.backfill_references(version_id) -> BackfillReport`

```text
get_version -> None 或 published_at is None -> PermanentError（不補半成品）
get_object(version.s3_key) -> None -> PermanentError（沒有權威可比對）
for draft in parse_markdown(全文).steps:
    existing = [edge["target"] for edge in list_edges(step_pk(...), "REFERENCES")]
      target in existing  -> 什麼都不做（冪等，連 item 都不重寫）
      existing 非空       -> conflicts（不替換、不追加第二條；D05、F40）
      get_feature is None -> unresolved（不建立 Feature）
      否則                 -> put_edge(pk, "REFERENCES", target, {"type", "text"}) -> added
```

幾個關鍵決定：

- **判斷缺邊只用 `list_edges(step_pk(...), "REFERENCES")`**（完整 PK、一致讀取、讀完分頁），
  不查最終一致的 `by_target`，也**不先用 `get_steps` 問「有沒有 STEP item」**——設計 §9.1 把
  步驟與引用放在同一筆 item，先問 STEP item 會讓缺邊案例在第一關就被吃成 `unresolved`
  （需求書 §9 明列的失敗模式）。
- **補出來的 item 與 Phase 23 `_write_edges` 寫的完全一樣**：`attrs` 只有 `type` 與 `text`，
  屬性集合恰好是 `{PK, SK, target, entity, type, text}`。需求書原本要求 `attrs` 還帶
  `tutorial_version`／`number`，與 00A §3.6（「模型欄位可以由鍵導出時不落成 item 屬性」）
  及 Phase 23 的實際寫法衝突，依「設計 > 00A > Phase 文件」改成兩個屬性並修文件。
- **`parse_markdown` 在函式內 import**：相依方向是 `content` 呼叫 `repository`（設計 §5），
  module 層反向 import 會循環。`src/training_kb/adapters.py:398` 對 `ingress` 已有同樣前例。
- 「版本不存在」「未發布」「沒有全文」三者都是 `PermanentError`：它們都是「確定不該補」，
  不是暫時性故障，不該進 ASL Task Retry。

### 1.6 `Repository.rebuild_rule_projection(rule_id) -> list[str]`

```text
scan_entity("VERSION") -> 再濾一次 SK == META -> item_to_model(TutorialVersion)（D29）
expected = 去重 {v.version_id | rule_id in v.rules_applied}，依 version_sort_key 升序
get_meta(RULE#<id>) is None -> PermanentError（先確認規則在，才動任何一筆邊）
wanted - current -> put_edge（補缺邊）
current - wanted -> delete_edge（刪多餘邊）
rule.applied_to != expected -> update_meta(..., expected_revision=revision_of(pk))
return expected
```

- **`rules_applied` 是唯一權威**（D17）：`applied_to` 與 `APPLIED_TO` 邊都是投影，不是三個
  獨立權威，所以這裡是真正的重建（補、刪、改寫），與只補不刪的 backfill 相反。
- **先確認規則存在再動邊**（與需求書順序不同）：規則不存在時（基表只剩孤兒邊）原本的順序
  會先刪掉幾條邊才丟 `PermanentError`，留下「邊改了一半、欄位沒改」的中間狀態。
- **`published_at` 不參與判斷**：`rules_applied` 含該規則的未發布版照樣算，與 Phase 27 的
  `list_versions_applying_rule` 同一套判準（測試直接斷言兩者重建後完全一致）。
- **`CoordinationError` 往外拋**：不攔截、不重試、不靜默覆蓋，由維護批次記錄後下一輪重跑。
- **完全不寫 `VERSION` item、不寫 `RULE.status`**（設計 §7.6、§12.2），單元與整合測試各有
  一條直接斷言。
- mypy 細節：`update_meta` 的 `changes` 值要先宣告成 `list[DynamoValue]`（`list` 在型別系統裡
  不變，直接傳 `list[str]` 過不了 strict）。

### 1.7 與 Phase 23 修正後 `verify_version_complete` 的對接

Phase 23「修正回合 1」之後，核對也會把**多出來的** STEP／`APPLIED_TO`／`SUPERSEDES` 邊當成
問題。整合測試因此把每個情境都做成「弄壞 → `verify` 是 `False` → 跑本 Phase 的函式 →
`verify` 回 `True`」，涵蓋缺 STEP 邊、缺 `APPLIED_TO` 邊、多一條 `APPLIED_TO` 邊三種，
以及兩者各跑一輪之後仍然 `True` 且兩次都冪等。

### 測試設計

**單元測試（`tests/unit/`）假的不是 `Repository` 而是它底下的儲存層。** `MaintenanceRepository`
是真的 `Repository` 子類別，只把 `table` 換成 `FakeTable`、`bucket` 換成 `FakeBucket`；
`backfill_references`／`rebuild_rule_projection`／`delete_edge` 與它們用到的
`list_edges`／`put_edge`／`scan_entity`／`get_meta`／`update_meta`／`revision_of`／`_paged`
全部跑真的程式。`FakeTable` 只實作 `Repository` 真的會呼叫的六個 boto3 操作
（`put_item`／`get_item`／`update_item`／`delete_item`／`query`／`scan`），條件式用 boto3 的
`ConditionBase.get_expression()` 解讀且只支援 `=`／`begins_with`／`AND`（多送一種就
`AssertionError`），`update_item` 只支援 `update_meta` 真的送得出的運算式與
`#revision = :expected` 條件，不符就丟真的 `ConditionalCheckFailedException`，
所以 `CoordinationError` 是走真的路徑產生的。

`FakeTable.written_pks`／`FakeBucket.written_s3_keys` 記下每一次寫入；`snapshot()` 取完會把
紀錄清空，所以「`before = snapshot()` → 動作 → `after = snapshot()`」之後
`after.written_pks` 恰好是那個動作寫過的 PK——一旦出現 `VERSION#`／`TUTORIAL#`／`RULE#`
或任何 S3 key，測試就紅。

**整合測試（moto）改的是 Phase 23 真的寫出來的資料**：直接沿用 `test_create_version.py` 的
`build_ready_v2`／`four_step_content`／`version_plan`，不自己拼 item，所以「補回來的那筆與
`create_version` 寫的一模一樣」是拿真貨比對，而不是兩份測試各寫一種形狀。

## 5. 遇到的問題與解法

1. **需求書的 `attrs` 與 00A §3.6 衝突。** 需求書要 `attrs` 帶
   `tutorial_version`／`number`／`type`／`text`，00A §3.6 與 Phase 23 `_write_edges` 都只寫
   `type`／`text`（其餘由鍵與 `target` 還原）。依「設計 > 00A > Phase 文件」採用兩個屬性，
   並在測試直接鎖 `set(item) == {"PK","SK","target","entity","type","text"}`；已修文件。
2. **`repository` 不能在 module 層 import `content`。** 相依方向是 `content` 呼叫
   `repository`（設計 §5），module 層反向 import 會循環。改成在 `backfill_references` 函式內
   import `parse_markdown`，與 `adapters.py:398` 對 `ingress` 的既有前例一致；ruff 沒有選
   `PLC0415`，mypy strict 也接受。已在文件與 docstring 記錄理由。
3. **`tuple(sorted(pk_strings))` 會把 `#10` 排到 `#3` 前面。** 改成
   `sorted(set(...), key=parse_step_pk)`，與 `version_sort_key` 擋掉的是同一個坑；
   加了一條十步的測試把它鎖住。已改文件。
4. **需求書要把 fixture 放 `tests/unit/conftest.py`，但那支檔的 owner 是 P15、修改者只有
   P55**（00A §3.2），本 Phase 不是它的修改者。改成把器材放在
   `tests/unit/test_backfill_references.py`，`test_rule_projection.py` 直接 import
   （Phase 23 的 `test_version_complete.py` import `test_create_version.py` 是同一個作法）。
   已改文件。
5. **需求書說 `repo` 是「假 `Repository`」。** 那樣一來「只補缺的邊」「不替換錯邊」

## 7. Gate 狀態／給下一個 Phase 的介面清單

### Gate

- **本 Phase 不依賴也不宣稱 O2／O3。** O3 仍是 FAIL、O5 仍 BLOCKED（本 Phase 不碰模型）。
  修復動作只在維護批次執行，不在發布路徑上；它**不能**用來補救 Phase 24／25 的 partial
  publish，也**不是** O3 的替代方案。
- **moto 全綠只證明資料形狀與分頁邏輯。** `DeleteItem` 的真實行為、GSI 落後、`ConsistentRead`
  都是模擬；真實驗證留給 P41 起的接線（controller「離線開發優先」裁決）。
- **O1 未核定**（`META`）；本 Phase 透過 `keys.META` 使用它，沒有另外假設。

### 已知相依：IAM 尚未授權 `DeleteItem`

Phase 09 的真實資料角色刻意排除 `dynamodb:DeleteItem`，所以 `delete_edge`（以及用到它的

Phase 28 文件的全域限制與 `delete_edge` 的 docstring 裡。

### 給 P55（規則驗證與狀態轉移）的介面

| 介面 | 簽名 | 語意 |
|---|---|---|
| `Repository.rebuild_rule_projection` | `(self, rule_id: str) -> list[str]` | 以 `VERSION.rules_applied` 為唯一權威重建；回去重、依 `version_sort_key` 升序的 version_id 清單，與重建後的 `AuthoringRule.applied_to`、`APPLIED_TO` 邊、Phase 27 的 `list_versions_applying_rule` 四者完全一致。**不寫 `RULE.status`**（那是 P55 經 `analytics/status_writer` 的唯一寫入路徑）、不寫任何 `VERSION` item。規則不存在丟 `PermanentError`；`update_meta` 衝突時 `CoordinationError` 往外拋，不重試。 |
| `Repository.delete_edge` | `(self, pk: str, relation: str, target_pk: str) -> None` | 只允許 `DELETABLE_RELATIONS`（`{"APPLIED_TO"}`），其餘一律 `PermanentError`。刪不存在的邊是 no-op。**雲端要等 P41／P57 補 IAM。** |
| `DELETABLE_RELATIONS` | `frozenset[str]` | 模組級常數；要加第二種可刪關係必須先改 00A §3.3／§6.3，不可在呼叫端繞過。 |

**P55 要注意的兩件事：** (1) 驗證流程若改了 `RULE.applied_to` 以外的欄位，`_revision` 會變，
同一輪裡先跑 `rebuild_rule_projection` 再寫 status 比較安全（反過來會撞
`CoordinationError`，而本 Phase 刻意不重試）。(2) `applied_to` 是投影，P55 **不要**把它當歷史
紀錄累加；要「曾經套用過」的事實請看 `VERSION.rules_applied`。

### 給 P59（失敗復原與重送驗收）的介面

| 介面 | 簽名 | 語意 |
|---|---|---|
| `Repository.backfill_references` | `(self, version_id: str) -> BackfillReport` | 只吃**已發布**版本；未發布、不存在、缺 S3 全文三者都丟 `PermanentError`（`PermanentError`，不進 ASL Task Retry）。只加不改：不替換錯邊、不刪邊、不改既有步驟文字、不碰 S3、不產生新版本、不動 `published_at`／`current_version`、不呼叫模型。重跑冪等（第二次 `added == ()`，其餘欄位相同）。 |
| `BackfillReport` | `(added, conflicts, unresolved)` | 三個 `tuple[str, ...]`，值是**步驟 PK**，去重且依 `(version_id, number)` 升序，所以兩次執行結果可直接比對。`conflicts`／`unresolved` 是給維護者的待處理清單，**不是**程式要自己補齊的清單。 |

半成品補成「看起來完整」，正是本 Phase 拒絕未發布版的理由。
