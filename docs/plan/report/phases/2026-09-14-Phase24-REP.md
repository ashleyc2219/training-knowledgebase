## 1. 實作內容（含實作邏輯）

### 1.1 `src/training_kb/site.py`（新建，125 行）

最小公開頁 renderer，只吃領域物件、吐字串，**不知道 key、不知道 bucket、不知道交易**。

| 成員 | 行為 |
|---|---|
| `SiteRenderer.__init__(*, notice="", batch="", categories=(), asset_prefix="/site/assets")` | 四個參數全部有預設值，存起來備用（P57 才用），`SiteRenderer()` 永遠成立。 |
| `render_version_page(tutorial, version, steps, content)` | 先核對「已保存步驟（DynamoDB `STEP` 邊）」與「公開內容（S3 全文解析）」的 `(number, text)` 逐字相同，不同就丟 `PublishError`；再輸出 `<h1>` 標題 + `<p class="version">` 版號 + 四個 `<h2>`（Problem／Prerequisites／Steps／Expected Outcome），退役教學再加 `<p class="retired">`。最外層是 `<article data-published=… data-slug=… data-version-id=…>`。 |
| `render_tutorial_index(tutorial, versions)` | **只列 `published_at` 非空的版本**，`current_version` 那一筆加「（目前版本）」；根元素帶 `data-site-version="v<n>"`。 |
| `render_site_index(tutorials)` | **只列 `current_version` 非空的 Tutorial**。 |

- 所有使用者可見文字一律 `html.escape`（含 `"`／`'`）。與 P22 的 `escape_markdown` 不同層，不互換。
- 版號一律 `parse_version_id(version_id)[1]`，不自訂 `version_number`（D-19）。
- 退役提示是固定佔位 `RETIRED_PLACEHOLDER`，不顯示退役原因（沒有 `retired_reason` 欄位）。
- **`site` 不 import `publishing`**（`publishing` 單向 import `site`），避免兩支檔互相 import。

### 1.2 `src/training_kb/publishing.py`（新建，約 450 行）

四個 frozen dataclass（`PublishRequest`／`PreparedPublish`／`PublishInspection`／`PublishResult`）、
三個公開 key helper、`Publisher` 三段式提交。

**三個 key helper（D-54，回傳都不含 `site/` 前綴）**

```python
site_key("prepare-meeting@v2")     -> "tutorials/prepare-meeting/v2.html"
tutorial_index_key("prepare-meeting") -> "tutorials/prepare-meeting/index.html"
site_index_key()                   -> "index.html"
_diff_copy_key("prepare-meeting@v2")  -> "tutorials/prepare-meeting/v2.diff.txt"   # module-private，P57 的 site_diff_key 回同一字串
_public_key(rel)  -> "site/" + rel            # PUBLIC_SITE_PREFIX 由 content.py 提供
_staging_key(op, rel) -> f"operations/{op}/site/{rel}"
```

**`prepare`**：對每個 `version_id` 走 `_stage_one`

```
verify_version_complete   False -> PublishError「內容或關係不完整」，零 staging 對外可見
  v
_load: get_version / get_tutorial / get_object(s3_key) -> parse_markdown
  v
render_version_page（此時 published_at 必然是 None -> data-published="false"）
  v
put_object(operations/<op>/site/tutorials/<slug>/v<n>.html,  if_none_match=False)
put_object(operations/<op>/site/tutorials/<slug>/v<n>.diff.txt, 逐字複製私有 v<n>.diff)
```

`staged_keys` 是**排序後**的 tuple；staging 用 `if_none_match=False`（渲染是決定性的，同 operation 重送覆寫同一份 bytes 是安全的）。

**`inspect`**（只讀不寫，所以 `commit` 可以再呼叫一次）三類問題：

1. `staged_keys` 任一個 `get_object` 回 `None` → 「私有 staging 讀不回來：`<key>`」
2. `published_at` 已有值 → 「…已經有值，不可再發布」
3. `tutorial.current_version != version.supersedes` → 「基底已位移：current_version 不等於 supersedes（… != …）」
4. `get_steps(version_id)` 與 `parse_markdown(全文).steps` 的 `(number, text)` 不同 → 「已保存步驟與公開內容不同步」

**`commit`**

```
inspect 不過 -> PublishError（problems 併進訊息），transact_write 呼叫次數 = 0
   v 過
transact_write([VERSION.published_at, TUTORIAL.current_version])    # 每篇固定 2 個 action
   +-- 回 index != None -> PublishResult(published=(), failed=version_ids[index//2],
   |                                     reasons=(CANCEL_REASONS[index%2],))   不丟例外
   v 回 None
_publish_site：重新渲染（published_at/current_version 已切）-> 覆寫同一 staging key
             -> promote 版本頁 + v<n>.diff.txt（if_none_match=True，撞鍵比對 bytes）
             -> 重寫 tutorial_index_key / site_index_key（可重建投影，允許重寫）
             任一步失敗 -> PublishError（切點 a2_after_transact_before_site）
   v
operations.record_version(operation_id, version_id)
```

`CANCEL_REASONS = ("published_at 已經有值", "current_version 不等於 supersedes")`，順序與
`_transact_items` 的 VERSION、TUTORIAL 完全一致，P25 靠它把 index 換算回「第幾篇、哪個欄位」。

**交易 action**（`_update`）

- `VERSION#<version_id>`：`SET published_at = :now, #rev = #rev + :one`，
  條件 `attribute_not_exists(published_at) OR attribute_type(published_at, :null)`
- `TUTORIAL#<slug>`：`SET current_version = :version, #rev = #rev + :one`，
  條件 `current_version = :base`（`supersedes` 非空）或
  `attribute_not_exists(current_version) OR attribute_type(current_version, :null)`（v1）

## 5. 遇到的問題與解法

### 5.1（最重要）交易的值**不能**用低階 `{"S": ...}` AttributeValue

Phase 24 §5 與 **00A §6.7 都寫「值用低階 `{"S": ...}` 形式」，與 boto3 的實際行為不符。**

`boto3.resource("dynamodb")` 會在**它自己的 client**（也就是 `table.meta.client`，`Repository`
唯一拿得到的 client）上註冊 `dynamodb-attr-value-input`（`boto3/dynamodb/transform.py`
`DynamoDBHighLevelResource.__init__`），把所有 `AttributeValue` 形狀的參數**再序列化一次**。
所以送出 `{"S": "TUTORIAL#x"}` 會變成 `{"M": {"S": {"S": "TUTORIAL#x"}}}`：

```
TRANSACT ITEMS: [{'Update': {'Key': {'PK': {'M': {'S': {'S': 'V#a'}}}, ...}}}]
-> moto: TransactionCanceledException
   CancellationReasons=[{'Code': 'TypeError', 'Message': "unhashable type: 'dict'"}]
```

（`moto/dynamodb/models/dynamo_type.py:79` 的 `DynamoType.__hash__` 撞到 dict 型 `cast_value`。）
這是 **client 端**的轉換，真實 DynamoDB 一樣會收到雙層包裝而拒絕，不是 moto 的問題。

**裁決**：`transact_write` 的 `items` 一律用**原生 Python 值**（`{"PK": pk, "SK": META}`、
`{":now": "2026-09-14T00:30:00Z", ":one": 1}`），與 `Repository` 其他方法一致。
`repository.py` 與 `publishing.py` 的 docstring 都寫明理由與實測訊號，Phase 24 §5 已更正。
**00A §6.7 那一句尚待 controller 同步**（見第 9 節）。

驗證過的四個情境（scratchpad 探針＋整合測試）：happy／already-published（index 0 失敗）／
base-moved（index 1 失敗）／v1 首發（`current_version` 是 NULL），四個都符合預期，
且交易取消時 DynamoDB 完整回滾。

### 5.2 `data-published` 與「交易後重新渲染」的歸屬衝突

Phase 24 §6 說「本 Phase 的最小 renderer 不輸出 `data-published`……這一點在 Phase 57 有實作前
不得視為已處理」，但 **00A §3.8** 要求未發布頁一律帶 `data-published="false"`、**00A §6.7**
把「重新渲染的責任」明確歸給 **P24 的 `commit`**（P57 doc 自己也寫「重新渲染的責任不在本 Phase」）。

依 COMMON.md 的文件優先序（設計 > 00A > Phase 文件），**以 00A 為準**：

- `SiteRenderer.render_version_page` 就輸出 `data-published`；
- `Publisher.commit` 在交易成功後、寫 `site/` 之前，用已切換的兩個欄位**重新渲染並覆寫同一個
  staging key**，promote 仍然只是「複製 staging 的同一份 bytes」（P25 的 `promote_site_objects` 不必改）。

`test_commit_never_exposes_unpublished_pages` 與切點測試的 happy 案例都掃描 `site/`，
出現 `data-published="false"` 即失敗。Phase 24 §6 已改寫。

### 5.3 交易要不要推進 `_revision`

Phase 文件的 `_update` 片段沒有推進 `_revision`，但 Phase 12 的 O3 spike
（`infra/scripts/o3_report.py::publish_transaction`）有 `#rev = #rev + :one`。
不推進的話，發布之後仍持有舊 `_revision` 的寫入者會用 `update_meta` 靜默蓋掉
`current_version`。**採 O3 spike 的算式**（也讓 P41／P59 能在真實 AWS 重跑同一組切點），
並補一條測試 `test_transaction_bumps_revision_so_stale_writers_lose`。

### 5.4 conftest 的 owner 不是 P24

Phase 文件 §7 說「共用 fixture 寫在對應的 `conftest.py`」，但 00A §3.2 明列
`tests/unit/conftest.py` 的 owner 是 P15、`tests/integration/conftest.py` 的 owner 是 P06，
P24 都不是它們的修改者（而且此刻有其他 agent 在同一個 checkout 工作）。
**器材一律留在自己的測試檔裡**（與 Phase 23 相同做法）；整合測試用既有的 `repository`／`bucket`
fixture（00A：integration fixture 名一律是 `repository`，不是 `repo`）。

### 5.5 切點表的「公開 site/：舊版」需要真的有舊世代

第一版寫法裡 `site/` 是空的，`a2` 只能證明「公開站什麼都沒有」，不是「公開站落後一個世代」。
改成先用同一個 `SiteRenderer` 把 v1 的三個公開物件寫出去（模擬上一次成功發布），
`a2` 的證據才真的是 `data-site-version="v1"` 對上 DynamoDB 的 `v2`。

### 5.6 `site` 與 `publishing` 的 import 方向

P57 會讓 `site.py` 用到 `site_key`／`tutorial_index_key`（都在 `publishing.py`），
而 `publishing.py` 需要 `SiteRenderer` 的型別。本 Phase 固定成**單向**：
`publishing` → `site`，`site` 不反向 import（在兩支檔的 docstring 都寫明）。
**留給 P57 的注意事項見第 7 節。**
