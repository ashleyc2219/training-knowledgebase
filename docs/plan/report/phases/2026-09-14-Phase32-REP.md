### 1.1 `training_kb.ingress` 第 4 節（新增）

```python
SAFE_EXECUTION_NAME: re.Pattern[str]                   # [A-Za-z0-9_-]{1,80}
PIPELINE_FOR_KIND: dict[OperationKind, PipelineName]   # ticket→ticket-analysis、release→release-update
INPUT_NAME = "input"

@dataclass(frozen=True)
class Wiring: operations, starter, repository, settings

def operation_id_for(kind: OperationKind, canonical_id: str) -> str
def execution_name(operation_id: str) -> str
def accept_ticket(ticket: Ticket, *, deadline: float) -> Acceptance
def accept_release(release: Release, *, deadline: float) -> Acceptance
def accept_normalized(obj: Ticket | Release, *, deadline: float) -> Acceptance
def normalize_then_accept(*, domain, adapter, event_type, headers, payload, deadline) -> Acceptance
```

**名稱（Task 1）。** `operation_id_for` 固定回 `op-<kind>-<canonical_id>`（00A §3.3），`kind` 用
Phase 10 的 `OperationKind`，所以 P42 的 `feedback`／`view` 可以直接沿用。`execution_name` 先比
`[A-Za-z0-9_-]{1,80}`，合規就原樣回；不合規（超長或含非 ASCII）才取固定的 UTF-8 SHA-256 全長
64 個十六進位字元，前面保留最多 15 個可讀字元當前綴——`15 + 1 + 64 = 80` 剛好填滿上限，而且雜湊
不截短到沒有測試根據的長度。名稱只由 kind 與已核定的 canonical ID 組成，**不含 user、留言或標題**。

**接受路徑（Task 2）。** `_accept` 的次序是固定的，不能換：

```text
operations.accept(AcceptOperation(...))        # 先永久接受：OPS# 一寫下去，去重就成立
   ├─ duplicate 且 execution_arn 有值 ──────> 直接回既有 Acceptance（不寫物件、不啟動）
   └─ 其餘（accepted，或 duplicate 但還沒啟動＝續跑，00A D-45）
        assert_time_left(deadline, step="put-input")
        put_object(operations/<op>/input.json, if_none_match=True)   # 撞 key 就沿用，不覆寫
        record_normalized(...)（只有 input_ref 還沒記時才寫）
        assert_time_left(deadline, step="start-execution")
        starter.start(pipeline, execution_name(op), 三鍵 input)
        record_execution(...) → load(...) → Acceptance(status=原本那個, ...)
```

- **續跑判斷用事實欄位，不用 `status`。** 分支只看 `input_ref` 與 `execution_arn` 有沒有值；
  `accept` 已寫 `OPS#` 但物件或 execution 還沒建立時，本次補完即可，不建立第二筆 operation、
  **不換名字重跑**（00A D-45）。
- **ASL input 固定三個鍵**（`operation_id`、`project_id`、`input_ref`，00A §7）。`Release` 模型沒有
  `project_id`，由 `Settings.project_id` 取得後寫進 operation 紀錄與 ASL input。工單全文、
  Release evidence 與向量都留在私有 S3，不進 execution history。
- **`ObjectAlreadyExists` 用型別判斷**，不比對訊息字串；其他 S3 錯誤照常往上拋。
  `json.dumps(..., ensure_ascii=False, sort_keys=True)` 讓同一份 canonical 物件每次都是同一串 bytes。
- **`_start_once`**：`starter.start(...)` 失敗時先 `operations.fail(operation_id, str(error),
  isinstance(error, TransientError), now=now_utc())` 留下可追溯紀錄，再把**原例外**往外丟
  （判準與 `pipelines/common.run_sequence` 一致）。失敗後 `input_ref` 仍在，重送會走續跑分支、
  沿用同一個 execution name。本模組**不自己重試**（只有一層重試，00A §3.7）。
- **期限一律走 Phase 30 的 `assert_time_left(deadline, step=...)`**，模組裡沒有第二份
  `monotonic()` 比較（`grep -c "monotonic()" ingress.py` 只命中 P30 的 `time_left`）。

**接線點（第 5 節）。** `normalize_then_accept` 維持 00A D-60 的六個 keyword 參數，先
`assert_time_left(deadline, step="normalize")`，再呼叫 `_normalize(...)`，最後
`accept_normalized(normalized, deadline=deadline)` 依型別分派。`_normalize` 是留給 Phase 37 的接縫，
在它接上之前刻意丟 `PermanentError("Phase 37 尚未接線：...")`——**不得先回一個假的成功**（設計 §14.1）。

**`_wiring()`（本計畫選擇，00A §6.8）。** 模組層可覆寫的工廠，回 frozen dataclass `Wiring`，
讓 `accept_ticket(x, *, deadline)` 維持 00A 的兩個參數。預設值由 `_build_wiring(load_settings())`
建立（boto3 resource／client 在函式內才建、帳號由 STS 現查、Region 由 client 自報，
所以不新增 `TKB_` 以外的環境變數）並快取一次；測試 `monkeypatch.setattr(ingress, "_wiring", ...)` 注入 fake。

### 1.2 `training_kb.pipeline_starter`（新建）

```python
STATE_MACHINE_NAMES: dict[PipelineName, str]                       # 00A §3.5 的三個名稱
def state_machine_arns(*, region: str, account_id: str) -> dict[PipelineName, str]
class PipelineStarter(Protocol):
    def start(self, pipeline: PipelineName, execution_name: str,
              input: dict[str, JSONValue]) -> str                  # 回 execution ARN
class BotoPipelineStarter:
    def __init__(self, client: object, arns: dict[PipelineName, str],
                 operations: OperationCoordinator) -> None
```

`start` 送 `stateMachineArn`／`name`／`input=json.dumps(input, sort_keys=True)`。
`sort_keys` 不是裝飾：StartExecution 的冪等條件是「同名**且同 input**」，鍵順序飄動會讓本來該冪等
的重送變成錯誤。

`ExecutionAlreadyExists` 之後的 `_reuse` 有三個出口（設計 §14.2）：

| ledger | `describe_execution` | 結果 |
|---|---|---|
| 有／沒有 `execution_arn`（沒有就由 state machine ARN 推導） | `RUNNING` | 沿用原 ARN；ledger 缺 ARN 時補寫 `record_execution` |
| `status == "done"` | 已結束 | 沿用原 ARN |
| 其他（含 `status != "done"`、ledger 根本不存在） | 已結束 | `CoordinationError("... 同名執行已結束但 ledger 沒有原結果，需人工確認")` |

**`ExecutionAlreadyExists` 一律當成功會讓「已經失敗的那次」被報成成功；換名字重跑會讓同一個事件
跑出第二條版本鏈。兩個都不行。** ledger 沒有 `execution_arn` 時由 state machine ARN 推導執行 ARN
是**本計畫選擇**，必須由 Phase 41 的雲端驗收實證後才可信賴。

### 1.3 保留狀態 `normalized`／`started` 的裁決（00A §6.4 指定由 P32 決定）

**裁決：本 Phase 不寫入這兩個保留值，`operations.py` 一行都沒有改。** 續跑一律看
`input_ref`／`execution_arn` 兩個事實欄位。三個理由：

2. **O2 gate（P11，真實 DynamoDB PASS）是用現在這份 `operations.py` 取得的**；改寫它的寫入行為
   等於讓 gate 證據與程式脫鉤。
3. 每推進一次狀態就多一次 CAS 往返與一個競態視窗，在八秒期限內沒有收益。

## 5. 遇到的問題與解法

1. **`WEBHOOK_DEADLINE_SECONDS` 不在 00A 說的地方。** 00A §6.8 把它列在 `ingress.py`，
   Phase 30 實際放在 `handlers/github_webhook.py`。→ 不動別人的檔案，測試依實際落點 import，
   並在 Phase 文件 §13 第 10 條記錄，建議主導者在 00A 更正落點或請 P30 搬家。
2. **Task 2 需要 `PipelineStarter` 的型別，但 adapter 是 Task 3。** → Task 2 先建
   `pipeline_starter.py` 的 Protocol 與 `STATE_MACHINE_NAMES`／`state_machine_arns`，
   `_build_wiring` 暫時丟 `PermanentError`；Task 3 的紅燈因此仍然是真的
   （`cannot import name 'BotoPipelineStarter'`），綠燈後才把 `_build_wiring` 接上真 adapter。
3. **Phase 文件 §8 的 `harness.operations.put(ledger_record(...))` 不存在。** Phase 10 的寫入入口
   只有 `accept`／`record_*`／`complete`／`fail`。→ 改成 `harness.seed(status=..., execution_arn=...)`
   走公開方法，`done`／`failed` 用 `complete`／`fail`；不繞過 Phase 10 的契約。
4. **`normalized`／`started` 兩個 ledger 狀態沒有任何公開方法寫得出來。** → 見 §1.3 的裁決；
   單元測試的 `seed(...)` 把欄位走公開方法寫完之後，只把 `status` 屬性直接擺成目標值，
   並在測試 docstring 與 Phase 文件裡寫明「這是測試自己擺的狀態」。
5. **`_normalize` 的四個參數在 stub 裡沒被使用，`ruff`／可讀性都不理想。** → 把它們收進
   `PermanentError` 的訊息（`domain/event_type`、`adapter`、headers 與 payload 的鍵數），
   既證明「原樣轉交、不解讀」，逾時／失敗訊息也看得出卡在哪個來源。
6. **全套測試一度無法收集**：另一位 agent 的 `src/training_kb/rote.py` 在編輯中（`NameError:
   name 'ProvenWorkflow' is not defined`）。→ 當下用 `--ignore=tests/unit/rote
   --ignore=tests/integration/test_o6_stable_keys.py` 跑完（627 passed），不去修別人的檔案；
   對方完成後重跑全套已是 655 passed。

### 1（必修）adapter 自己分類暫時性失敗 — commit `f0c13e0`

**問題（同意）：** `BotoPipelineStarter.start` 只攔 `ExecutionAlreadyExists`，其他 botocore 錯誤
原樣冒出，所以 `_start_once` 的 `isinstance(error, TransientError)` 在**正式 adapter** 上永遠是
`False`——§9 驗收表「StartExecution 暫時失敗 → `retryable=True`」那一列以前只在測試替身自己丟
`TransientError` 時才成立，是假的綠燈。

**修法**（`pipeline_starter.py`，與 `repository.py`「只翻已知碼」同一條慣例）：

```python
TRANSIENT_START_CODES = frozenset({
    "ThrottlingException", "ThrottledException", "TooManyRequestsException",
    "ServiceUnavailable", "ServiceUnavailableException",
    "InternalServerError", "InternalError", "InternalFailure",
    "RequestTimeout", "RequestTimeoutException"})
TIMEOUT_ERRORS = (ConnectTimeoutError, ReadTimeoutError, EndpointConnectionError)
SERVER_ERROR_STATUS = 500

def _transient(error: ClientError) -> TransientError | None:   # 已知碼或 5xx 才翻
    ...
# start()／_describe() 共用：
except self._client.exceptions.ExecutionAlreadyExists:   # 排在 ClientError 之前（它是子類）
    return self._reuse(...)
except TIMEOUT_ERRORS as error:
    raise TransientError(f"Step Functions 連線逾時：{type(error).__name__}") from error
except ClientError as error:
    transient = _transient(error)
    if transient is not None:
        raise transient from error
    raise                                 # 不認得的碼原樣往外冒，不猜它可不可以重送
```

三個實作決定：

- **`ExecutionAlreadyExists` 的 except 一定要排在 `ClientError` 之前**：boto3 那個例外就是
  `ClientError` 的子類，順序寫反會讓「同名執行已存在」被當成未知的永久錯誤。
- **`describe_execution` 走同一套分類**（新的私有 `_describe`）。判斷「這次到底成功了沒」的那次
  查詢被節流時，如果原樣冒出 `ClientError`，一次純粹的暫時性失敗會被記成 `retryable=False`。
- **訊息只留錯誤碼與 HTTP 狀態**，不回填 input（00A §3.8）。

**新增 11 個測試**（`tests/integration/test_start_execution_idempotency.py`）：六種會被翻成
`TransientError` 的失敗（`ThrottlingException`／`ServiceUnavailableException` 503／
`InternalServerError` 500／`RequestTimeout`／不認得的碼但 5xx／`ConnectTimeoutError`）、
三種原樣冒出的碼（`ValidationException`／`StateMachineDoesNotExist`／`AccessDeniedException`）、
節流的 `describe_execution`，以及**正式 adapter ＋ moto 上的真 ledger** 兩個端到端案例：
`ThrottlingException` → `TransientError` 且 ledger `("failed", True)` 且 `input_ref` 留著；

### 2（minor）`execution_name` 保住完整 kind 前綴 — commit `fd14986`

`_NAME_HEAD = 15` 會把 `op-feedback-review-`（19 字元）截成 `op-feedback-rev`。改成由型別導出：

```python
MAX_EXECUTION_NAME = 80
_NAME_HEAD = len("op-") + max(len(kind) for kind in KINDS) + len("-")   # 19
_DIGEST_LENGTH = MAX_EXECUTION_NAME - _NAME_HEAD - 1                    # 60 個十六進位字元
head = "".join(ch for ch in operation_id if ch in _ALLOWED)[:_NAME_HEAD].rstrip("-")
return f"{head}-{digest[:_DIGEST_LENGTH]}"
```

`19 + 1 + 60 = 80`。雜湊從 64 縮到 60 個十六進位字元（240 bits）是**算出來的**，不是猜的：
前綴長度由 `OperationKind` 決定，之後多一種 kind 也不會出現「超過 80 字被 AWS 拒絕」這種只在
雲端才炸的錯。實際輸出：

```
op-feedback-review-e2367be6f32dab3d0a40c2d110f76b50cbd8a694de567513b2d2fdcdad21   (79 字)
```

新增兩個測試：四種 kind（含 `feedback-review`／`ticket-analysis`）配超長 Unicode ID，斷言前綴完整、
長度 ≤ 80、符合 `[A-Za-z0-9_-]{1,80}`；同 kind 的兩個長 ID 仍可分辨且同輸入同輸出。
