## 1. 實作內容（含實作邏輯）

`src/training_kb/content.py` 是 00A §6.6 的 `content` 模組第一段（Phase 21–23 會在同一支檔案
追加內容驗證、Markdown／diff 與建版）。本 Phase 交付四個公開名稱，簽名逐字取自 00A §6.6
（D-04 裁決：以 P20 為準）：

```python
@dataclass(frozen=True)
class VersionPlan:
    version_id: str; slug: str; number: int; supersedes: str | None
    reason: str; rules_applied: tuple[str, ...]; operation_id: str

def make_version_id(slug: str, number: int) -> str: ...
def parse_version_id(value: str) -> tuple[str, int]: ...
def allocate_version(tutorial_id: str, operation_id: str, operations: OperationCoordinator,
                     *, repository: Repository, reason: str,
                     rules_applied: Sequence[str]) -> VersionPlan: ...
```

### 1.1 版本 ID 編碼（`make_version_id` / `parse_version_id`）

`<slug>@v<n>`（00A §3.3）。`parse_version_id` 只接受 `make_version_id` 產得出來的字串，
也就是 `make_version_id(*parse_version_id(v)) == v` 必須成立——最後那個 round-trip 比較
同時擋掉 `a@v01`（前導零）與 `a@v１`（全形數字）這類「`int()` 得到同一個值、組回去卻不是
原字串」的寫法，否則兩個字串會對應同一版。

### 1.2 決策順序（`allocate_version`）

```text
reason 空白 -----------------------------> ContentError（不寫任何紀錄）
operations.load(operation_id) is None ----> CoordinationError（尚未被 O2 接受）
record.version_id 有值 -------------------> _replay_plan：重用原版號
   |  slug 不符 ---------------------------> CoordinationError（訊息含兩個 slug）
   |  VERSION item 已存在 -----------------> supersedes / reason / rules_applied 一律用表裡那筆
   |  VERSION item 還沒寫 -----------------> supersedes 由基底重推，其餘用參數
record.version_id is None ----------------> _base_version -> _next_free_number
   -> record_version(...) 先落地 -> 回傳 VersionPlan
```

三個關鍵取捨：

1. **基底與號碼是兩件事。** `supersedes` 只取 `Tutorial.current_version`（F37：publish 成功
   才切換它，所以它就是「最近已發布版本」）；號碼則由 `_next_free_number` 從基底往上探，
   跳過已有 VERSION item 的號碼。只做 `base + 1` 會覆寫上一次永久失敗留下的未發布 v2——
   D26 允許缺口、不允許覆寫。
2. **重送重用，不重新配號。** 有紀錄就走 `_replay_plan`；已寫出的 VERSION item 的
   `supersedes`／`reason`／`rules_applied` 一律以表裡那筆為準，第二次傳進來的參數不得改寫
   已保存的內容（設計 §14.2）。已發布版本**不**在這裡擋，那是 Phase 23 `create_version`
   的關卡。
3. **失敗不留半筆紀錄。** 四條失敗路徑都在 `record_version` 之前丟出，單元測試以
   `assert fake_ops.writes == []` 把關。

### 1.3 與 Phase 11 `record_version` write-once 的相依（controller 中途指示）

Phase 10 review 要求 `OperationCoordinator.record_version` 改成 write-once（同 operation
重送同值 → no-op；換值 → `CoordinationError`），Phase 11 正在改。本 Phase 的流程是
「先 `load`、有 `version_id` 就直接重用、沒有才配號並 `record_version`」，**重送根本走不到
第二次寫入**，所以完全相容；併發探到不同空號時，輸的那一邊會拿到 `CoordinationError`
而不是靜默覆寫。實作與測試**都不依賴**「第二次 `record_version` 可以換值」：

- `tests/unit/test_allocate_version.py::test_replay_reuses_recorded_version_and_base`
  斷言 `len(fake_ops.writes) == 1`；
- `test_allocate_version_rejects_bad_input` 的第四個案例只在 **setup** 呼叫一次
  `record_version` 播種，之後斷言 `writes == []`；
- 整合測試用真的 `OperationCoordinator`，斷言 `OPS#` item 的 `_revision` 在重送後**不變**。

`FakeOperations` 刻意維持單純記錄器、不複製 write-once 語意（Phase 11 還在改，替身不該
先押一個猜測的介面），理由已寫進替身的 docstring；權威驗證在整合測試。程式與測試的
相依說明分別寫進 `content.py` 模組 docstring 與 Phase 文件 §6。

### 1.4 沒有做的事

不驗證內容、不產生 Markdown／diff、不寫 VERSION／STEP item、不切 `current_version`、
不建立 Tutorial 身分、不決定 `reason` 的三種格式內容（只擋空白、原樣帶走）。
沒有在 `TutorialVersion` 或 `Tutorial` 上加任何模型以外的欄位（00A §3.6）：版號探測結果與
基底推導過程只存在於回傳的 `VersionPlan` 與 operation 紀錄裡。

## 5. 遇到的問題與解法

1. **Phase 文件 Task 2 Step 4 的「預期全部 PASS」不成立。** 第四個失敗案例需要
   `_replay_plan` 的 slug 守門員，而它在文件裡排在 Task 3。解法：Task 2 只補守門員
   （`existing` 分支留給 Task 3 當紅燈），並修正文件的預期輸出；Task 3 的紅燈因此落在
   欄位覆寫而不是「函式不存在」，文件的 Step 2 預期也一併改成實際訊息。
2. **`CoordinationError` 不是 `PermanentError` 家族。** 需求書 §5 Consumes 寫「兩者都是
   PermanentError 家族」，但 `src/training_kb/errors.py`（Phase 02）裡
   `CoordinationError(Exception)`、只有 `ContentError(PermanentError)`。以程式為準修文件。
3. **`isdigit()` 會放行 `²`。** 文件的 `parse_version_id` 用 `suffix.isdigit()`，遇到
   `a@v²` 會讓 `int()` 丟自己的 `ValueError`（訊息不是我們的）。改用 `isdecimal()`，與
   `keys.parse_step_pk` 同一套寫法；同時在 `make_version_id` 補 `isinstance(number, bool)`
   （`bool` 是 `int` 的子型別，mypy 擋不住，`True` 會組出 `a@vTrue`）與
   `slug != slug.strip()`（不然 `parse_version_id` 會接受 `make_version_id` 產不出來的
   ` a@v1`，round-trip 不變式破洞）。三個守門員都不影響需求書指定的任何測試案例。
4. **整合測試怎麼算「換程序」。** `tests/integration/conftest.py` 的 fixture 在
   `mock_aws()` 區塊裡 yield，所以測試中途可以另外 `boto3.resource(...)` 取得**全新的**
   Table handle。第一次呼叫之後連 handle 一起換掉（`_restarted()`），只有表裡的資料還在，
   比單純換一個 `Repository` 物件更接近「換 Lambda 執行環境重試」。表名與 region 由
   `table.meta.client.meta.region_name` 與 `table.name` 取得，不從 conftest import 常數。
5. **「`version_id` 只被寫入一次」怎麼斷言。** 用 `OPS#` item 的 `_revision`：先記下
   `accept` 之後的值，第一次 `record_version` 讓它 +1，重送之後必須維持不變。寫成
   「基準值 + 1」而不是寫死 `2`，這樣 Phase 11 若改變 `accept` 的寫入次數也不會誤紅。
6. **`operations.py` 在我工作期間被 Phase 11 改了兩次**（`accept_seq`、lease）。我只消費
   `load` 與 `record_version`，兩者簽名未變，全套測試持續綠燈，未做任何調整。
7. **一度出現別人檔案的 ruff E501**（`src/training_kb/operations.py:268`，105 > 100）。
   沒有動它；Phase 11 隨後自己修掉了，最終 `ruff check src tests` 全綠。

## 7. Gate 狀態

### O2（操作紀錄與接受順序）：**未通過（NOT PASSED）**，本 Phase 不改變它

本 Phase 的全部證據來自 **fake 替身與 moto 本機表**，兩者都**不是** O2 證據。可以宣稱的
只有一句：

> **給定同一份操作紀錄時，版號是確定的。**

具體來說，moto 上證明了：同一個 `operation_id` 在丟棄整組 Python 物件（含 boto3 Table
handle）之後重送，仍拿到同一個 `version_id`，而且 `OPS#<operation_id>` 的 `version_id`
只被寫入一次（`_revision` 不再增加）。

**不得宣稱**（依需求書 §全域限制、§9 與 `phase10-report.md` §7 的口徑）：

- 併發建版安全：O2 未 PASS 前，兩個併發操作仍可能探到同一個空號。`_next_free_number`
  是「讀了再寫」，本身沒有條件寫入保護；真正的序列化靠 F35 的接受順序串行，而那正是
  Phase 11 要在真實 DynamoDB 上證明的事。
- 跨程序重啟已驗收：換 boto3 handle 不是換程序，資料自始至終在同一個 moto 表、同一個
  行程裡。
- FIFO／接受順序：`accept_seq` 與 lease 都是 Phase 11 的範圍，本 Phase 一個都沒有消費。

停止語（沿用 Phase 10）：**「O2 尚未 PASS，不得宣稱永久去重或 FIFO；雲端併發建版路徑停止」。**
需求書 §9 的對應停止條件「併發操作拿到同一個空號 → 停止雲端併發建版，保留 FAIL 給
Phase 11」在本 Phase 結束時仍然有效。

其餘 gate（O1、O3–O7）本 Phase 不涉及，狀態不變。
