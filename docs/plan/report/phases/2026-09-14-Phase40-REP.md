### 1.1 `pipelines/ticket.py` §5：CREATE／KEEP 決策

| 產出 | 內容 |
|---|---|
| `TicketAction = Literal["CREATE", "KEEP", "NO_FEATURE"]` | 三種結果。 |
| `TicketGap`（frozen dataclass） | `cluster_id`／`gap`／`feature_id: str \| None`／`ticket_ids: tuple[str, ...]`。 |
| `_ActiveTutorialFinder`（私有 `@runtime_checkable` Protocol）、`_active_tutorial` | Phase 27 `find_active_tutorial_for_feature` 的委派＋同判準 fallback（見 §5 第 2 點）。 |
| `decide_ticket_action(gap, *, repository) -> TicketAction` | 純判斷，**一個字都不寫**。 |
| `record_decision(action, gap, *, repository, operation_id, now) -> str` | 寫 `ticket-decision.json`；CREATE／KEEP 另外連工單（D-52）。 |
| `_link_tickets(gap, *, repository)`（私有） | `Ticket.feature_ids` 與 `ASKS_ABOUT` 邊的唯一寫入者。 |

實作邏輯：

- **判斷順序固定，而且「有沒有教學」看 `status` 不看 `current_version`**（F12）：
  `feature_id is None` → `NO_FEATURE`（保留 gap，Ticket Analysis 永不建 Feature）→
  `get_feature` 找不到 → `ContentError`（資料不一致，不猜也不補建；Phase 39 已經擋掉
  不存在的 ID，走到這裡代表資料被改過）→ 有 `status=active` 的教學 → `KEEP`（即使
  `current_version` 還是 `None`）→ 否則 `CREATE`（只有 `retired` 不算已有教學）。
- **`record_decision` 三種結果都寫**，這就是 `分析工單` Rule 8 的「只記錄 log」：
  KEEP 一個字都不寫進教學內容，但「為什麼不改」留得下來。物件用
  `put_object(..., if_none_match=False)` 覆寫，所以同一個 `operation_id` 重跑安全；
  ref 一律由 `operation_ref(operation_id, "ticket-decision")` 產生，不手拼字串。
  JSON 是 `sort_keys=True, ensure_ascii=False`，六個鍵：`action`／`cluster_id`／`gap`／
  `feature_id`／`ticket_ids`／`decided_at`。
- **`_link_tickets` 的冪等**：先一致讀回 `TICKET#<id>`，`feature_ids` 已等於
  `[feature_id]` 就跳過寫入，否則 `put_meta(create_only=False)` 覆寫成**單一元素**
  （不是 append，D04）；邊的 SK 固定是 `ASKS_ABOUT#FEATURE#<id>`，重寫同一條不會多出
  item，所以 Phase 41 的 `DecideAction` Task 與 `create_first_version` 各呼叫一次也安全。
  工單不存在丟 `ContentError`，不安靜跳過。

| 產出 | 內容 |
|---|---|

固定順序（不可調換）：

```text
1 decide_ticket_action != CREATE 且不是自己的重試 -> PermanentError
2 list_rules(ACTIVE) + load_validated_at -> rules_for_content(ALL_STEP_TYPES) -> 去重 injected
3 render_rules_block(injected) 進 prompt -> generate_validated_json(TutorialDraft) 一次
4 （驗證在 3 裡面：model_validate + validate_content，最多一次修正）
5 tutorial_slug 產生並驗證 kebab-case 與唯一
6 create_tutorial_identity（create_only=True、feature_ids=[feature_id]；重試沿用同一篇）
7 allocate_version(reason="gap:<cluster_id>", rules_applied=applied_rule_ids(injected))
8 create_version -> published_at 仍是 null、current_version 不變
9 record_decision("CREATE", ...) -> 寫決策紀錄並連工單到 Feature
```

- **先驗內容再建身分**：模型輸出不合法時不留下一個空的 `TUTORIAL#` item（測試直接斷言）。
- **`rules_applied` 只放本次實際注入 prompt 的 ID**（F29）：`injected` 是 `rules_for_content`
  回的 dict 依 `ALL_STEP_TYPES` 展平後**以 `rule_id` 去重**（同一條規則同時適用兩種型別時
  不會出現兩次），`render_rules_block` 與 `applied_rule_ids` 吃**同一份 list**，prompt 與
  版本紀錄因此不會分叉。
- **`load_validated_at` 是唯一的驗證時間來源**：`pipelines/ticket.py` 裡沒有
  `_validated_at`／`_load_validated_at` 私有副本（D-28）。缺驗證時間的 active 規則由
  Phase 19 丟 `PermanentError`，而且擋在模型呼叫**之前**（測試斷言 `calls == []`）。
- **模型呼叫走 `generate_validated_json` 一次**（00A §6.5：schema 後業務驗證＋最多一次修正
  的唯一合法入口），本函式自己不重試、不另組修正 prompt。`node` 固定 `"create_v1"`。

## 5. 遇到的問題與解法

1. **`generate_json` vs `generate_validated_json`。** 需求書 §5 Consumes 與 §7 Task 3 Step 3
   的片段是「`writer.generate_json(...)` 之後呼叫端自己 `model_validate` ＋ `validate_content`」；
   00A §6.5 與 COMMON.md 都寫「`generate_validated_json` 是唯一合法的『schema 後業務驗證＋
   最多一次修正』入口，呼叫端不得自己重試」，`writing/validators.py` 的表格也把
   `TutorialDraft` 的 correction 記成「是」。**依 COMMON.md 的優先序採 00A**：包一個
   `_tutorial_draft_validator`（內容仍只是 Phase 21 的 `validate_content`，一份都沒重寫），
   呼叫 `generate_validated_json` 一次。副作用是壞草稿的失敗型別從 `ContentError` 變成
   `PermanentError`（前者是後者的子類，測試一律 `pytest.raises(PermanentError)`）。
   Phase 39 當時因為 00A §6.9 有 **P39 專屬**的「`generate_json` 只呼叫一次」而走相反裁決；
   00A §6.9 的 P40 段**沒有**同樣的專屬條款，所以這裡回到通用規則。
2. **Phase 27 還沒落地。** 需求書 §5 Consumes 列的
   `Repository.find_active_tutorial_for_feature` 不存在（`repository.py` 的 owner 是 P06／P27，
   而且同一個 checkout 有別的 agent 在改它，本 Phase 不得碰）。解法是模組私有的
   `_active_tutorial`：`repository` 滿足 `_ActiveTutorialFinder`（`@runtime_checkable` Protocol）
   就直接委派，否則走**同一份判準**的基表查法（`scan_entity("TUTORIAL")` ＋ `SK == META` ＋
   `status == active` ＋ `feature_id in feature_ids`，多篇取 slug 升序第一筆，與 Phase 27 §6
   逐字相同）。測試的 `fake_repo` 有這個方法，所以**委派路徑是被跑到的**；P27 落地後把
   Protocol 與 fallback 一起刪掉即可，判準不變。
3. **「重跑同版號」與「不是 CREATE 就 `PermanentError`」互相矛盾。** 第一次跑完之後
   `TUTORIAL#<slug>` 已經 active，重送時 `decide_ticket_action` 會回 KEEP，守衛會把合法的
   重試擋掉（實際紅燈見第 3 節）。改成「不是 CREATE **而且** `_own_retry_tutorial(...)` 是
   `None`」才失敗：用 `Tutorial.cluster_id` 分辨**同群**（自己上一次留下的，沿用同版號補齊，

### 給 Phase 41 的七個 Task 與 state 契約（00A §7）

ASL state 名稱（括號是 `Parameters.task` 的值，也就是 `task_name(...)` 的回傳值）：

```text
EnsureEmbedding(ensure_embedding) -> AssignCluster(assign_cluster)
-> EvaluateRecurring(evaluate_recurring) -> [IsRecurring? Choice]
-> NameGap(name_gap) -> DecideAction(decide_action) -> [ChooseAction? Choice]
-> CreateFirstVersion(create_first_version) -> PublishVersion(publish_version)
終點：Published / Kept / GapRetained / NotRecurring（Succeed）、PipelineFailed（Fail）
state: operation_id, project_id, input_ref, ticket_id, cluster_id, is_recurring,
       gap_ref, action, version_id, published
```

七個 Task 函式名（P41 自己定，`TICKET_ANALYSIS_TASKS` 的順序就是上面那條）：
`task_ensure_embedding`、`task_assign_cluster`、`task_evaluate_recurring`、`task_name_gap`、
`task_decide_action`、`task_create_first_version`、`task_publish_version`。

P41 要知道的十件事：

1. **`TicketGap` 由 `DecideAction` Task 自己組**：`cluster_id` ＋ Phase 39 `name_gap` 回的
   dict（`naming["gap"]`、`naming["feature_id"]`）＋ 同群 `Ticket.id`。`ticket_ids` 本 Phase
   **不提供**查法；群成員請用 `scan_entity("TICKET")` ＋ `SK == META` 過濾後依 `cluster_id`
   取（`_meta_rows` 是私有 helper，要共用請與主導者協調升格，不要兩邊各寫一份）。
   `ticket_ids` 請**排序後**傳進來，`ticket-decision.json` 才可重現。
2. **`decide_action` Task 一定要呼叫 `record_decision`**：三種結果都要寫
   `operations/<op>/ticket-decision.json`，`GapRetained`（NO_FEATURE）與 `Kept`（KEEP）
   兩個終點就靠它留紀錄。ref 放進 state（或用 `operation_ref(op, "ticket-decision")` 重算，
   兩者一定相同）。
3. **`create_first_version` 內部會再判一次並再呼叫一次 `record_decision`**，兩者都冪等，
   所以 `DecideAction` 與 `CreateFirstVersion` 各呼叫一次是安全的，不會多出第二條
   `ASKS_ABOUT` 邊或第二個 `feature_ids` 元素。
4. **`action` 的三個值就是 `TicketAction`**：`CREATE`／`KEEP`／`NO_FEATURE`，直接放進 state
   給 `ChooseAction` Choice 用；不要另外發明字串。
5. **`create_first_version` 回 `VersionPlan`**，把 `plan.version_id` 放進 state 給
   `PublishVersion` 用；**本 Phase 不發布**（`published_at=None`、`current_version` 不變），
   `published` 欄位一律由 P41 的 `publish_version` Task 依 Phase 24 的結果填。
6. **`now` 由 Task 傳入**（`Deps.now()`），業務函式不讀系統時鐘；`now` 必須是 UTC 整秒
   （`clock.now_utc()`），帶微秒會被 `to_iso` 擋。
7. **失敗型別**：`ContentError`／`PermanentError` 不進 ASL Task Retry；`CoordinationError`
   （`record_version` write-once、`put_meta(create_only=True)` 撞鍵）也不是 `PermanentError`
   的子類，`run_sequence` 的 `except Exception` 已經涵蓋，`Catch States.ALL` 導向
   `PipelineFailed`。`TransientError` 原樣往上拋交給 ASL 的兩條 Retry。
8. **Phase 27 落地前**，`decide_ticket_action` 走的是 `pipelines/ticket.py` 裡的基表 fallback
   （`scan_entity("TUTORIAL")`）。真實 `Repository` 一旦有了
   `find_active_tutorial_for_feature`，同一段程式會自動改走委派，**不需要改 P41**。
9. **`prepare-meeting` 這個 slug 在 Demo 種子裡是直接寫入的**（00A §6.9 P40 那列），
   它的 `cluster_id` 若不是本群，`create_first_version` 會正確地丟 `PermanentError`；
   Demo 腳本要讓它走 CREATE 的話，種子的 `cluster_id` 必須與 gap 同群。
