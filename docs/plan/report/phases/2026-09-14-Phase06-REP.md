### 1.2 關鍵實作邏輯

**保留屬性只有一份定義。** `RESERVED_ATTRS = frozenset({"PK", "SK", "target", "entity", "_revision"})`
在本檔宣告（00A §6.3 owner P06）。`target` 本 Phase 用不到（Phase 07 的關係邊才用），仍一起列進來，
讓 Phase 07 沿用同一個常數而不是再宣告一次。

**實體 → PK 沒有 fallback 猜鍵。** `_entity_pk` 用十個 `isinstance` 分派；`TutorialStep` 放在第一個並直接
`raise PermanentError("TutorialStep 沒有 metadata item，請用 Phase 07 的 put_edge")`——設計 §9.1 讓同一筆
edge item 同時表達「第幾步」與「引用哪個 Feature」，所以它不能有 `SK=META` 的假步驟。最後一行是
`PermanentError(f"unknown entity type: ...")`：未來漏掉哪個實體會直接撞上它，不會悄悄寫出一把錯的鍵。

**Decimal codec 只有一個入口，而且是遞迴的。** 寫入路徑固定 `model_dump(mode="json")` →
`_encode`（`float` → `Decimal(str(value))`）；讀取路徑 `_decode`（`Decimal` → 整數值回 `int`、否則回 `float`）。
用 `Decimal(str(value))` 而不是 `Decimal(value)`，否則 `0.1` 會把二進位浮點誤差一起寫進表，讀回來相等斷言會失敗。
codec 寫成遞迴是因為 list 與 map 都可能帶數字（`Ticket.embedding` 是 1024 個值、`ProvenWorkflow.steps` 是 list of map）。

**建立與覆寫共用同一條條件寫入。** 私有 `_put_item(pk, payload, *, create_only) -> bool`：
- `create_only=True` → `ConditionExpression="attribute_not_exists(PK)"`，`_revision = 1`。
- `create_only=False` → 先 `_revision_or_none(pk)`，有值就 `revision = current + 1` 且
  `ConditionExpression="#revision = :current"`。**覆寫不把 `_revision` 重設成 1**，否則拿著舊 revision 的人
  還能成功寫入（這是本 Phase 的停止點）。
- 回傳 `True` 表示這次是新建；`create_only` 撞鍵回 `False`；`create_only=False` 期間被改過丟 `CoordinationError`。

`put_meta` 在 `_put_item` 回 `False` 時丟 `CoordinationError("metadata already exists or changed since read: ...")`。
`CoordinationError` **不是** `TransientError`，呼叫端不得自動重試（00A §4.1）。

**`update_meta` 是 revision compare-and-swap。**
- 空 `changes` → `PermanentError("update_meta needs at least one change: ...")`，不送出請求。
- `changes` 含保留屬性 → `PermanentError("reserved attributes are not updatable: [...]")`，不送出請求。
- 每個欄位名都經 `ExpressionAttributeNames` 的 `#fN` 佔位，因為 `name`／`status`／`type` 都是 DynamoDB 保留字。
- `#revision = :next` 與業務欄位在**同一個 `SET`**，所以版本與內容一定一起生效或一起失敗。
- `ConditionExpression="#revision = :expected"`；失敗 → `CoordinationError(f"stale revision for {pk}: expected ...")`。
- 回傳 `expected_revision + 1`。

**`revision_of` 是 `expected_revision` 的唯一取值來源。** `get_meta` 會濾掉 `_revision`，領域模型身上沒有它；
item 不存在時 `revision_of` 丟 `CoordinationError(f"metadata not found: {pk}")`，**不回 0、不回 `None`**。

**boto3 型別。** 公開簽名寫 `table: object`（00A §6.3），內部存 `self._table: Any`——boto3 的 resource 物件
沒有穩定的靜態型別，用 `Any` 才能在 mypy strict 下呼叫 `put_item`／`get_item`／`update_item`，
同時讓呼叫端的型別提示維持 00A 的樣子。**全檔沒有 `# type: ignore`、沒有 `ignore_errors`。**

   Phase 08／10 的實作者會發現這三個成員已存在。建議 controller 在派 P08／P10 時提醒「確認已存在並直接消費／擴充，

3. **`put_meta_item` 的 `create_only=False` 語意是我推導的。** 我讓它與 `put_meta` 共用同一條路徑
   （讀 `_revision` → 加一 → 條件覆寫），這是 00A §3.6「不重設 `_revision`」的唯一合理延伸，
   但 00A 沒有逐字寫明這個分支。Phase 10／11 若有不同需求，改的是這個分支，不是 `put_meta_item` 的簽名。
4. **`_revision` 沒有上限保護。** `update_meta` 每次加一，long-running 的 item 理論上會一直長；
