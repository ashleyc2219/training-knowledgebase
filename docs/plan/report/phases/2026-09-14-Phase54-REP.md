## 1. 實作內容與邏輯（逐檔說明）

### 1.1 `src/training_kb/analytics/reopen.py`（新增）

| 名稱 | 說明 |
|---|---|
| `reopen_window(published_at, days=14) -> tuple[datetime, datetime]` | **全 repo 唯一**定義十四天窗口的地方。naive datetime 直接 `ValueError`（沒有偏移量就無從換算，猜成 UTC 會讓窗口靜靜平移）；回 `(p, p + days)`，成員資格由呼叫端用 `start <= ts < end` 表達。 |
| `ReopenStats(count, reopen_users, viewers, rate)` | `frozen=True` 的四欄 dataclass。`count` 是**不同 Ticket ID 數**（筆數，不是比例）、`reopen_users` 是分子、`viewers` 是分母、`rate` 在 `viewers == 0` 時是 `None`。 |
| `reopen_stats(views, tickets, *, cluster_id, published_at) -> ReopenStats` | 四道過濾（窗口內的 View → 同 cluster → 窗口內的 Ticket → author 在分母內且**最早**的 view 嚴格早於開票）＋兩種去重（Ticket ID 與 author）。 |

邏輯的三個關鍵，都是「不這樣寫就會靜靜算錯」的地方：

1. **`timedelta(days=…)` 只出現在 `reopen_window`。** O4 核定若改成右端包含，只要改這一處與
   `test_reopen_metrics.py` 的兩個端點測試。`grep -rn "timedelta(days=" src/ infra/` 的結果只有
   `operations.py:400`（lease TTL 7 天）、`pipelines/ticket.py:173`（recurring 的「當日加前十三日」，
   `anchor - timedelta(days=offset) for offset in range(days)`，**另一個**十四天）與本檔。
2. **分母只認 `TutorialView`。** 簽名沒有 `feedback` 參數，而且有一個測試用
   `inspect.signature` 把四個參數名釘死——這就是「用 Feedback 代 View」那個停止點。
3. **零分母回 `None` 而不是 `0.0`。** `rate = len(users) / viewers if viewers else None`。
   回 `0.0` 會讓 Phase 55 誤判「rate 嚴格下降」而把 candidate 規則轉 active。

### 1.2 `src/training_kb/analytics/rules_metrics.py`（新增）

| 名稱 | 說明 |
|---|---|
| `RULE_STATUS_KEYS` | `("candidate", "active", "retired")`，取自 Phase 03 的 `RuleStatus`，**不抄字面值**。 |
| `rule_counts(rules) -> dict[str, int]` | `dict.fromkeys(RULE_STATUS_KEYS, 0)` 起頭，所以空輸入也有三個鍵。缺鍵會讓畫面把「這個狀態沒有規則」讀成「沒有這種狀態」。 |
| `applied_count(versions, rule_id) -> int` | `len({item.version_id for item in versions if rule_id in item.rules_applied})`。唯一權威是 `VERSION.rules_applied`（D17）；與 `Repository.list_versions_applying_rule`（「從 DB 查」的同一條規則）**並存，不互相取代**。 |
| `bedrock_call_count(trace, *, operation_id=None) -> int` | 直接轉呼 `CallTrace.count`。**不自建第二份計數器**：Phase 15 已保證每次真實 request（含丟例外的）恰有一筆 trace，所以 retry 的第二次、Map 的每個 item、Rote 的 `tool_use` 與 embedding 都已經在裡面。 |

### 1.3 `src/training_kb/analytics/version.py`（新增）

- `VersionMetrics(version_id, published_at, average, sample_size, negative_ids, reopen)`，`frozen=True`。
  `average` 是**未四捨五入**的 float（門檻比較吃它）、`None` 代表「尚無評分」而不是 0 分；
  `sample_size` 是**有評分**的筆數（與 Phase 44 的 `n` 同一套分母，D-44）。
- `version_metrics(version_id, *, repository, approved, project_id)` 是本 Phase **唯一**讀 Repository
  的函式。`published_at is None`（未發布）或 `Tutorial.cluster_id is None`（沒有固定同題對應）時回
  `NO_REOPEN = ReopenStats(0, 0, 0, None)`：**不憑空造窗口、不拋例外**——這兩種是資料狀態不是錯誤。
  版本不存在才是 `PermanentError`。
- `metrics_action(event, *, repository, approved, project_id)` 回 `{"action": "metrics", "results": [...]}`，
  形狀與 Phase 55 的 `validate_rules_action` 一致。`version_ids` 為空丟 `PermanentError`，
  **不**預設成「全部版本」。

評分那三個值全部來自 Phase 53 的子模組路徑
（`from training_kb.analytics.ratings import average_rating, format_average, negative_feedback_ids`）；
`analytics/__init__.py` 依 Phase 53 的裁決維持 docstring-only，本 Phase 沒有碰它。

### 1.4 `src/training_kb/handlers/analytics.py`（新增）

`training-kb-analytics` 的 Lambda 入口（D-56）。三個重點：

1. **分派在接線之前。** `handler` 先看 `action`，只有 `"metrics"` 才呼叫 `_wiring()`；
   其他一律 `raise PermanentError`。所以單元測試跑這條路徑不需要 AWS 憑證
   （雲端實測 duration **3.38 ms**，見 §4.3，證明真的沒有建任何 boto3 資源）。
2. **接線照 `ingress._wiring`／`_build_wiring` 的既有範式**：模組層 `_WIRING` 快取、
   `boto3.resource(..., region_name=settings.aws_region)`、另備 `_reset_wiring()` 給測試。
3. **`_approved_categories()` 用延後解析**（見 §5 問題 1）。

`handler` 不 try／except：`PermanentError` 原樣往外丟，呼叫端才看得到失敗原因。

## 5. 遇到的問題與解法

1. **Phase 43 的 `approved_categories` 還不存在，但這支 Lambda 要真的部署。**
   Phase 文件 (b)7 只說「單元測試不受影響」，但 controller 要求部署後 invoke——模組層
   `from training_kb.ingress import approved_categories` 會讓整支 `handlers/analytics.py`
   連 import 都失敗（單元測試與雲端一起掛）。
   **解法（本計畫選擇）：** `_approved_categories(repository)` 用 `importlib.import_module`
   ＋ `getattr(..., None)` 在 `_wiring()` 裡延後解析，取不到就回 `frozenset()`。
   Phase 43 一落地就自動取到真的那一份，不需要任何人回來改這裡。退回值刻意**不**抄一份
   `DEFAULT_FEEDBACK_CATEGORIES`（會製造第二個權威），代價是在 Phase 43 落地前
   `negative_feedback_ids` 只認 `rating <= 2` 那一半——這是看得出來的降級，不是靜默錯誤。

2. **Task 1 的實作一次寫太多，Task 2 拿不到紅燈。** 見 §3 Task 2 的誠實記錄：
   把多寫的部分移除、`--amend` 修正 Task 1 的 commit（未 push），重跑紅燈後才寫實作。

3. **同波次把 `_grant_data` 的簽名改掉了。** 本 Phase commit `d6f54d9` 當下的簽名是
   `_grant_data(function, table, bucket)`，稍後變成
   `_grant_data(..., *, prefixes, actions, with_index)`（webhook 的權限收斂那一批）。
   **解法：** 不動他們的程式，只在自己的區段補 `ANALYTICS_PREFIXES`／`ANALYTICS_DDB_ACTIONS`
   並改自己那一行（commit `c455d26`），順便把分析入口的權限講清楚（§1.5）。

4. **部署需要 `TKB_GITHUB_WEBHOOK_SECRET`，但它只存在於 Phase 41 的 scratchpad。**
   自己生一個新的會**換掉**已部署 webhook 的 secret，讓 Phase 41 的 Function URL 證據失效。
   **解法：** 從已部署的 `training-kb-webhook` 用
   `get-function-configuration --query 'Environment.Variables.TKB_GITHUB_WEBHOOK_SECRET'`
   把原值讀回 scratchpad 再填進部署 shell。secret 不進 repo、不進報告、不進 log。

5. **`cdk deploy` 會連帶部署共用 stack 檔裡別人未提交的修改。** 這無法避免（CDK 讀工作樹）。
   部署前後 `pytest`／`ruff`／`mypy` 都是綠的、`describe-stacks` 也是 `UPDATE_COMPLETE`，
   所以部署的是一份一致的樹；在此記錄讓 controller 知道。
