### 1.1 `pipelines/ticket.py` §3 Recurring 判定

| 產出 | 內容 |
|---|---|
| `RECURRING_DAYS = 14` | 窗口長度。`Thresholds` 刻意沒有對應欄位（00A §5.4），這是全套唯一一份 `14`；不自創 `Thresholds.recurring_days`（D-35）。 |
| `RECURRING_MIN_TICKETS = Thresholds().recurring_tickets` | `5` 的別名，模組內沒有第二份字面值。 |
| `recurring_window(anchor: date, days: int = RECURRING_DAYS) -> frozenset[date]` | 回 anchor 當日與前 `days - 1` 個 UTC **日期**組成的集合。 |
| `is_recurring(ticket: Ticket, *, repository: Repository) -> bool` | 同群、窗口內、依 `Ticket.id` 去重後是否 `>= 5`。 |

實作邏輯：

- **窗口是日期集合、不是時間區間**（設計 §7.3、F11）。`frozenset(anchor - timedelta(days=offset)
  for offset in range(days))` 產出恰 14 個日期，所以 `2026-08-31T00:00:00Z` 在窗口內、
  `2026-08-30T23:59:59Z` 在窗口外，而同一 UTC 日不管幾點都落在同一桶。用 `now - 14 days`
  會讓同一批輸入在不同時刻重跑得到不同答案。
- `days < 1` 丟 `PermanentError`：空窗口會讓任何群都算不出 recurring 而**安靜地**跳過命名，
  屬於呼叫端的錯，不是資料問題。
- `is_recurring` 的固定順序：`cluster_id` 為空 → `PermanentError`（Phase 38 還沒跑完，
  是流程順序錯，不是「不算 recurring」）→ `anchor = utc_date(ticket.ts)`（`Ticket.ts` 在
  Phase 04 已是 `datetime`，不套 `parse_iso`）→ `list_tickets(ticket.project_id)` 只留同群且
  日期落在窗口內的 → 依 `Ticket.id` 去重 → 把 anchor 自己補進集合（Phase 41 的
  `assign_cluster` 只判斷不寫入，掃描不一定看得到它）→ 比 `RECURRING_MIN_TICKETS`。
- 同一天內的多筆各算一筆：日期只拿來**過濾**，不拿來去重。

### 1.2 `pipelines/ticket.py` §4 Knowledge Gap 命名

| 產出 | 內容 |
|---|---|
| `_meta_rows(repository, entity) -> list[DynamoItem]`（私有） | `scan_entity(entity)` 之後再濾一次 `str(row["SK"]) == META`。 |
| `known_features(repository) -> tuple[Feature, ...]` | `FEATURE` 的 META item → `item_to_model` → 依 `feature_id` 升序。 |
| `_validated_naming(payload, validate) -> dict[str, object]`（私有） | `gap` 去頭尾非空 ＋ **包裝** Phase 18 的 `gap_naming_validator`。 |
| `name_gap(cluster_id, *, repository, writer, operation_id, operations) -> dict[str, object]` | 兩道守衛 ＋ 一次模型呼叫 ＋ 物件去重。 |

實作邏輯（`name_gap` 的固定順序）：

1. `ref = operation_ref(operation_id, "gap-naming")`——Phase 10 的 key 組字函式，不自己拼字串。
2. `known_features(...)` → `gap_naming_validator(known_feature_ids=...)`。
3. **先 `get_object(ref)`**：去重的判準是**物件本身**而不是 operation 紀錄的 ref 清單。先寫物件、
   再記 ref，中間失敗時紀錄裡沒有 ref 但物件已存在；只看 `operations.load` 會再叫一次模型，
   而且 `put_object(if_none_match=True)` 還會撞 `ObjectAlreadyExists`。先讀物件同時蓋掉兩個洞；
   讀回後仍重跑 `_validated_naming`，並**補記** `record_model_output`（§6 流程圖與 §9 表格要求的
   「ref 照補」；Phase 文件 Task 3 Step 3 的片段漏了這行，已一併修正）。
4. `scan_entity("TICKET")` 濾 `SK == META` → `item_to_model` → 依 `Ticket.id` 升序 → 濾同群，
   群總數 `< RECURRING_MIN_TICKETS` 就 `PermanentError`，**擋在模型呼叫之前**。這是「必要條件」
   守衛：任何 14 天窗口都不可能從不到五筆的群裡湊出五筆，所以不足五一定是呼叫端漏做
   `is_recurring`，不會誤擋已判定 recurring 的群；精確窗口判斷仍只由 `is_recurring` 負責。
5. `prompt_name_gap(texts, [one.feature_id for one in features])` →
   `writer.generate_json(system, user, GapNaming, operation_id=..., node="name_gap")` **一次**。
6. `_validated_naming`：`gap` 空白 → `ContentError("gap_empty: gap")`；`feature_id` 不存在 →
   Phase 18 丟 `ContentError("feature_id_not_found: feature_id")`（**不改寫成 `null`、不補建 Feature**）；
   `feature_id` 是 `null` → 合法業務結果，保留 gap 交 Phase 40。
7. `put_object(ref, body, "application/json", if_none_match=True)` → `record_model_output` → 回 `dict`。

`GapNaming` 是 Phase 17 的 **JSON schema 字典**，不是 pydantic 類別，所以回傳型別是
`dict[str, object]`，呼叫端用 `naming["feature_id"]` 取值（00A D-02）。全檔沒有
`GapNaming.model_validate` / `model_dump_json`。任何路徑都不建立 Feature 或 Tutorial、
不改 `Ticket.feature_ids`、不寫 `ASKS_ABOUT` 邊（那是 P40 的 D-52）。

## 5. 遇到的問題與解法

1. **`generate_json` vs `generate_validated_json`。** 00A §6.5 的通用列寫「P39–P51 呼叫端一律只呼叫
   `generate_validated_json` 一次」，但 00A §6.9 的 **P39 專屬列**寫「`generate_json` 在整個節點只
   呼叫一次」，Phase 文件 §6／§8 又明文要求不存在的 `feature_id` 丟 `ContentError`、本 Phase
   「不重試、不第二次呼叫模型」。走 `generate_validated_json` 會多送一次修正請求、把失敗改成
   `PermanentError`，`pytest.raises(ContentError)` 會直接紅燈。**裁決：Phase 專屬契約優先**，
   直接 `generate_json` 一次 ＋ `_validated_naming`。副作用是 `GapNaming` 實際上不走 correction，
   與 `writing/validators.py` 模組註解表格的「correction：是」不一致——列在第 9 節請主導者裁決。
2. **`fake_writer` 名稱衝突。** Phase 文件 Task 3 描述的替身用 `self.reply`，與
   `tests/unit/conftest.py` 既有的 `RecordingWriter`（`replies` 佇列）形狀不同。若在測試模組裡
   另造同名替身會遮蔽全域 fixture，多一份維護成本。**改用既有 `RecordingWriter`**：它已經把
   `(system, user, schema, node)` 都記進 `calls`；佇列只排一個回應，第二次呼叫會因佇列空掉而失敗，
   「只呼叫一次」的斷言反而更強。Phase 文件已同步修正。
3. **`fake_repo` 兩種形狀。** `is_recurring` 要 `list_tickets`（P38 conftest 的 `fake_repo` 剛好有）；
   `name_gap` 要 `scan_entity`／`get_object`／`put_object`，conftest 那份完全沒有，而 00A §3.2 只准
   P39 動兩個測試檔、不准改 P38 的 conftest。**解法**：`test_ticket_recurring.py` 沿用 conftest 的
   `fake_repo`；`test_ticket_name_gap.py` 在模組層級定義同名 fixture 刻意遮蔽它（pytest 的標準行為，
   作用範圍只有該檔），並在模組 docstring 寫清楚為什麼。
4. **關係邊會被 `scan_entity` 掃到。** `entity` 等於起點 PK 的前綴，所以 P40 之後的
   `TICKET#<id>` → `ASKS_ABOUT#FEATURE#<id>` 邊與 TICKET 本體同前綴。P08 的 `meta_only=True`
   已擋一次，本 Phase 沿用 P27 的做法自己再濾一次 `SK == META`；測試的假 `scan_entity`
   **刻意忽略 `meta_only`**，把邊一起回傳，才驗得到本 Phase 這一層。
5. **`ruff check src tests infra` 一度紅燈。** `tests/unit/test_ingress_acceptance.py:126` E501
   與 `training_kb.ingress` 的 `Wiring` ImportError，都是同一個 checkout 裡 Phase 31／32 agent
   進行中的修改（`git log` 最後一筆是 `1054465 feat(ingress): 固定事件與執行名稱`）。依 COMMON.md
   「別人的失敗用 `--ignore` 並記錄，不去修」處理；另外有一次 ruff 掃到兩個瞬間錯誤、重跑即消失，
   是併行寫檔的競態，不是本 Phase 的問題。我的四個檔案連跑三次都 `All checks passed!`。

- **`name_gap` 回的是 `dict`，不是模型**（00A D-02）。鍵恰好兩個：`naming["gap"]`（非空字串）
