### 1.3 `src/training_kb/publishing.py` 的 `# ---- Phase 59 ----` 區段

新增 `_string_tuple`、`_resume_targets`、`resume_publish` 三個名稱，既有程式一行未改
（除了切點 3、4 各一行呼叫）。

```text
resume_publish(operation_id, *, operations, repository, publisher, now) -> PublishResult
  |
  +-- _resume_targets：待補清單怎麼算（兩種輸入互補，00A §6.7）
  |     多篇  operations/<op>/pending-promote.json     <- Publisher._record_pending_promote
  |     單篇  ledger 的 OPS#<op>.version_id + public_site_keys(...)
  |     兩個都沒有 -> CoordinationError（這筆 operation 還沒走到交易，沒東西可補）
  |
  +-- 逐篇 get_version；不存在 -> CoordinationError
  |
  +-- publisher.prepare(...)          <- **硬性順序：先 prepare**
  |
  +-- 有任何一篇 published_at is None -> publisher.commit(...)   # 切點 1、2、3、5
  |
  +-- 全部已發布 -> promote_site_objects(...)                     # 切點 4
        |
        +-- 實際補出的 key != 待補清單 -> CoordinationError（兩份真相分岔了）
        +-- 重建教學索引 + 站台索引，回 PublishResult(published=version_ids)
```

**為什麼一定要先 `prepare`**（00A §6.7、上一批 REP §8 第 9 項）：切點 4 之前留下的 staging
是交易**前**渲染的，那時 `published_at` 還是 `None`，頁面帶著 `UNPUBLISHED_MARKER`
（`data-published="false"`）；直接 promote 會被 `_put_public_object` 的 runtime 守門擋下並丟
`PublishError`——擋得好，但那代表**復原失敗**而不是成功。重跑 `prepare` 時表裡的
`published_at` 已經有值，重新渲染出來的 staging 才是 `data-published="true"`。
真實 AWS 上驗過：復原後的 `v2.html` HTTP 200 且**不含**未發布標記（recovery 報告 §3）。

**本計畫選擇：補完版本頁與 diff 副本之後接著重建兩層索引。** 00A 第 1230 列說
`resume_publish` 要「把中斷的發布接著做完」，而 `_publish_site` 的第 4、5 步就是索引；
只補版本頁會讓公開站永遠沒有連到新版的路徑（§2 的不變量說注入後索引不得有 v2 連結，
復原就必須把它補回去）。索引是可重建投影（`if_none_match=False`），不影響
「補出的 key 清單 == 待補清單」這條斷言。

`resume_publish` **不**呼叫 `Publisher.commit`（已發布時 `inspect` 會擋下）、**不**刪除既有
公開物件、**不**重新 `allocate_version`。

## 5. 遇到的問題與解法

1. **`InjectedFault` 在雲端證不出 Retry。** P41 §9 第 3 點已警告。依 controller 裁決把它降級成
   `TransientError` 的相容別名，注入一律丟 `TransientError` 本身；00A 的名稱不變。P41 留下的
   `test_injected_fault_is_a_transient_error`（斷言 `__name__ == "InjectedFault"`）改寫成新契約
   ——那條測試原本就是風險備忘，檔案 owner 是 P59（00A §3.3）。
2. **`aws` 測試把共用的 `site/index.html` 蓋掉了。** 第一次跑 `aws` marker 測試時，seed 會寫
   `site/index.html`（模擬「上一次發布」），結果把 P57 發布的站台索引覆寫成只列 `p59-` 教學。
   發現後：(a) 用 P57 報告記載的原文還原，ETag 回到 `"f13d0a9936e0515b7ffe48962f64eae4"`
   （289 bytes）逐字相同；(b) 在 `aws_world` fixture 與演練腳本都加上「開始前存下原 bytes、
   結束時逐字寫回」。**這是本 Phase 對真實環境造成又修復的唯一一次副作用，照實記錄。**
3. **`TKB_FAULT` 沒有「批次內第 j 篇」的切點。** 五個切點是 00A 的固定清單。要重現 Phase 12 的
   `a3_after_first_site_before_second` 只能讓第 2 篇的 promote 失敗，所以沿用 P25 在 moto 用過
   的技法 monkeypatch `Publisher._promote`（產品程式不動），並在 recovery 報告寫明注入方式。
4. **`resume_publish` 只補版本頁會留下半完成的復原。** 補完之後接著重建教學索引與站台索引，
   理由見 §1.3。
5. **模型呼叫數在切點 5 的期望值。** 切點 5 在模型段之前，重送時模型是第一次跑（＋1）；
   切點 1／2／3 在模型段之後，重送必須是 0。測試分開斷言並寫進 docstring。
6. **mypy strict 涵蓋 `infra/`。** `check_asl.py` 與 `resume_publish` 都補了完整註記；
   `pending-promote.json` 的欄位改用 `_string_tuple` 驗形狀，避免整段 `# type: ignore`。
