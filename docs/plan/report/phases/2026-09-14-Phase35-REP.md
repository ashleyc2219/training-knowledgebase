# Phase 35 報告：PROC 成功失敗與退役生命週期

## 1. 實作內容（含實作邏輯）

在 `src/training_kb/rote.py` 的**第 4 段**（`# --- 4. PROC 生命週期（Phase 35 追加）---`）
追加一個常數、一個私有守門函式與四個公開函式，1–3 段完全沒有重排、沒有改既有簽名。

| 名稱 | 形狀 | 邏輯 |
|---|---|---|
| `PROC_MAX_CONSECUTIVE_FAIL` | `= 3` | 連敗上限（D20）。與 P34 的 `PROC_MIN_SUCCESS`（重放門檻）同值但不同義，所以是兩個常數名（00A §5.4），程式裡不再出現第三個 `3`。 |
| `_reject_retired` | `(proc) -> None` | `status == RETIRED` 就丟 `PermanentError`，訊息含「人工」。 |
| `on_new_success` | `(proc, operation_id, operations, now) -> ProvenWorkflow` | `success_count + 1`、`last_used = now`。 |
| `on_replay_success` | `(proc, now) -> ProvenWorkflow` | `fail_count = 0`、`last_used = now`。 |
| `on_replay_failure` | `(proc, now) -> ProvenWorkflow` | `fail_count + 1`；加完 `>= 3` 時 `status = RETIRED`。**不動 `last_used`**。 |
| `proc_changes` | `(proc) -> dict[str, DynamoValue]` | 只序列化四個會變的欄位：`success_count`／`fail_count`／`status.value`／`to_iso(last_used)`。 |

四個關鍵的實作決定：

1. **「算不算新樣本」不由呼叫次數決定**：`on_new_success` 先 `_reject_retired`，再問
   Phase 10 的 `operations.record_proc_sample(operation_id, proc.signature)`。回 `False`
   就**原樣回傳同一個物件**，不是回一個計數相同的新物件——同一個 operation 重送十次，
   `success_count` 與 `last_used` 都停在第一次（決策 F05、Rule 8）。
2. **`fail_count` 是連續失敗，不是歷史總和**（D20）：只有 `on_replay_success` 歸零。
   `on_new_success` **刻意不清** `fail_count`——被 fallback Agent 救回的那一次重放仍然是
   一次重放失敗（設計 §7.2 只授權重放成功歸零，對應 P37 的 `agent_after_replay_failure`）。
3. **`on_replay_failure` 的 `now` 是刻意不用的參數**：三個轉移函式維持同一種形狀（00A §6.8
   逐字簽名），但失敗時更新 `last_used` 會讓連敗中的 PROC 在 P34 的平手排序（`-last_used`）
   排到最前面，違反 F04 的「最近一次**成功**使用」。這一點寫進 docstring，避免之後被
   「順手補上 now」。
4. **狀態只有兩態、門檻是計數**：`status` 永遠是 `active`／`retired`，「還不能重放」是
   `success_count < PROC_MIN_SUCCESS`；可重放與否一律問 P34 的 `replayable(proc)`，
   本 Phase 沒有再寫一份條件。

持久化不在純函式裡：呼叫端的固定順序是 `revision_of(pk)` → 純函式算 →
`update_meta(pk, proc_changes(updated), expected_revision=...)`，`CoordinationError`
由上層重讀重算。整合測試把這個順序收在 `save()` 一個 helper 裡示範給 P37 抄。

`rote.py` 的 import 區新增三行（`datetime`、`training_kb.clock.to_iso`、
`training_kb.operations.OperationCoordinator`，並把 `repository` 那行擴成
`DynamoValue, Repository`）。`operations` → `repository` → `rote` 沒有形成循環：
`operations.py` 不 import `rote`，而 `rote.py` 早就經 `pipelines/common.py` 間接載入
`repository`，pytest 與 mypy 都確認過。

## 5. 遇到的問題與解法

1. **Phase 文件 Task 3 的掃描測試用相對路徑 `Path("src/training_kb")`**：CWD 不是 repo 根目錄時
   `rglob` 掃到空清單，`offenders == []` 會**靜默通過**——Rule 31 的證據就消失了。改成
   `REPO_ROOT = Path(__file__).resolve().parents[2]`，與 repo 既有 18 處掃描測試（
   `test_keys.py`、`test_o6_stable_keys.py` 等）同一個寫法；`str(path.relative_to(REPO_ROOT))`
   讓失敗訊息維持 `src/training_kb/xxx.py` 的原樣。已修文件（第 6 節第 2 點）。
2. **`repository.get_proc(SIG)` 回 `ProvenWorkflow | None`**：文件片段直接把它接進
   `on_replay_failure(...)`，item 不見時會變成 `AttributeError: 'NoneType' object has no
   attribute 'status'`，讀不出真正原因。改成 `reload(repository)` helper（內含
   `assert stored is not None`），與 Phase 34 對 `pick_layer2` 補 `assert picked is not None`
   同一個理由與同一個前例。斷言內容與覆蓋範圍不變。已修文件（第 6 節第 2 點）。
3. **同 checkout 其他 agent 的檔案暫時失敗**：`uv run pytest tests -q -W error` 有一個
   `FAILED tests/unit/pipelines/test_ticket_create_v1.py::test_rerun_with_the_same_operation_id_reuses_version_and_tutorial`
   （`PermanentError: 群 c12 不是 CREATE，不能建立第一版`，來自 `src/training_kb/pipelines/ticket.py:534`）。
   那是 Phase 40 agent 進行中的檔案（最後一次相關 commit `4b0d343 feat(ticket): 判斷 CREATE 與 KEEP`），
   依 COMMON.md「別人的檔案暫時失敗用 `--ignore` 並記錄，不去修」處理，未碰
   `pipelines/`。排除後 622 passed、零 warning。
4. **`operations` import 會不會造成循環**：`rote.py` 新增 `from training_kb.operations import
   OperationCoordinator`。先確認 `operations.py` 不 import `rote`（它只 import `errors`／
   `clock`／`keys`／`repository`），而 `rote.py` 本來就透過 `pipelines/common.py` 間接載入
   `repository`，所以沒有新增相依方向。pytest 與 mypy 都通過。
5. **`on_replay_failure(now)` 是未使用參數，會不會被 ruff 擋**：專案的 `select = ["E","F","I","UP"]`

   而不是 inline 註解，讓它跟著 API 文件一起被讀到。

   ConditionalCheckFailed 行為要等 P10／P11 的 O2 證據，**不得**據此宣稱計數永不分岔。
2. **Rule 8 的端到端那一段不在本 Phase**：「validate 通過**而且** Step Functions 成功啟動才算
   完整成功」這個前置條件由 P37 的 `commit_success` 落地（`tests/integration/test_rote_commit.py`）。
   本 Phase 只保證「呼叫 `on_new_success` 時計數會正確前進」，無法保證呼叫時機正確。
3. **`on_new_success` 的 no-op 回傳是同一個物件**：`record_proc_sample` 回 `False` 時直接
   `return proc`。這是刻意的（讓 P37 能用 `is` 省掉一次 `update_meta`），但如果之後有人改成
   `proc.model_copy()` 就會失去這個性質；目前沒有測試鎖定 identity，只鎖定欄位值。
4. **`record_proc_sample` 併發下的第三種訊號**：00A §6.4 與 P10 review 提到併發時 CAS 失敗會是
   `CoordinationError` 而不是 `False`，兩種訊號都代表「別人已算過」。本 Phase 的
   `on_new_success` **不吞** `CoordinationError`（純函式不做重試），P37 的呼叫端要自己決定
   把它當成「不加分」還是重試——這一點 Phase 35 文件與 00A 都沒有明寫，留給 P37 裁決。
5. **`fail_count` 的「連續」語意只在 rote 內成立**：DynamoDB item 上存的是一個數字，
   沒有任何欄位記錄「上一次成功是什麼時候」。如果之後有人繞過這三個函式直接
   `update_meta({"fail_count": ...})`，D20 的語意就會被破壞；`test_only_rote_touches_proc_items`
   只擋 `proc_pk(`／`PROC#` 出現在 `rote.py` 以外的模組，擋不了「透過 P37 傳進來的 pk」。
