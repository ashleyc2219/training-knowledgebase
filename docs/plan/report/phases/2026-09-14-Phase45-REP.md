### 1.1 `src/training_kb/pipelines/feedback.py`（Edit，新增 `# ---- Phase 45（owner）----` 區段）

把 Phase 44 選出的 `WeakTarget` 交給模型診斷，再由**程式**決定結果能不能進 REFINE。交付四個名稱：

| 名稱 | 說明 |
|---|---|
| `DIAGNOSE_NODE = "diagnose_weak"` | 寫進 Phase 15 `CallTrace` 的節點名；`generate_json(node=...)` 一律傳它。 |
| `DiagnosisResult`（frozen dataclass） | `version_id`／`step_indexes`／`reasons`／`feedback_ids`。`step_indexes` 與 `reasons` 的鍵裝的都是步驟 **`number`（從 1 起）**，不是 0-based index（D-55，欄位旁逐字註明）。 |
| `diagnose_weak(target, *, repo, writer, operation_id)` | 唯一入口。 |
| `_validated_items(reply, valid)`（module-private） | schema 之後的業務驗證。 |

`diagnose_weak` 的順序固定，整段**只讀不寫**（沒有 `put_meta`／`put_object`，不碰 `OperationCoordinator`）：

1. `repo.get_steps(target.version_id)` 取本版步驟，再依 `number` 升序（`Repository` 已排序，這裡再排一次是為了不依賴替身的行為）。
2. `valid = frozenset(步驟 number)`，這是「編號存不存在」的唯一依據。
3. `wanted = tuple(sorted(set(target.feedback_ids)))`——證據集合去重後升序，所以同一份輸入重送兩次會得到**逐欄相同**的結果。
4. `repo.list_feedback_of_version(target.version_id)` 只留 `id in wanted` 的那幾筆，依 ID 升序。別版、別類的回饋在這一步就被擋掉，不會進 prompt。
5. `prompt_diagnose_weak(...)` 產生 `(system, user)`。
6. **`writer.generate_json(...)` 在整個函式只出現一次**（F45：每次真實 attempt 都由 `CallTrace` 計入），schema 直接傳 `WeakDiagnosis` 這個 **dict**、拿回 `dict`（D-02），全檔沒有 `model_validate`／`model_dump`。
7. `_validated_items` 做業務驗證後組成 `DiagnosisResult`。

`_validated_items` 的四道檢查（設計 §7.6「schema 通過仍要業務驗證」）：

1. `isinstance(number, bool)` **先擋**——`bool` 是 `int` 的子類，`True in frozenset({1})` 會成立，只比對「編號在不在」擋不掉它；再擋非 `int`。
2. `number not in valid` → 丟棄該 item（模型指到不存在的步驟時**不改整篇**，設計 §14.1）。
3. `reason.strip()` 為空 → 丟棄該 item。
4. 同 `number` 重複：原因相同就去重；**原因不同丟 `ContentError`**（本計畫選擇；任選第一筆或最後一筆會讓重送結果不穩定）。

全部被丟掉就回 `step_indexes == ()`，也就是 `NO_STEP`——那是**合法業務結果**，由 Phase 46 記錄、不配版號。本節點**不**走 `generate_validated_json`：D-11／00A §6.5 沒有把它列為修正迴圈節點，`ContentError` 直接往外丟給 ASL 的 Catch。

## 5. 遇到的問題與解法

1. **`WeakTarget` 尚未落地（同波次 W1 的 P44 正在寫同一支檔）。** 我先用唯讀 `Protocol` 標註 `target`，等 P44 的 `WeakTarget` 在工作樹出現後，立刻改回 00A §6.9 的 `target: WeakTarget` 並刪掉 Protocol（測試的 `weak_target` fixture 也改用真的 `WeakTarget`）。最終程式碼與 00A 逐字一致。
2. **共用檔的 import 區**。`pipelines/feedback.py` 原本沒有任何 import；P44／P47 也同時在加。為了不讓 ruff 的 isort（`I001`）紅燈，我把需要的名稱**併進既有的 import 行**（`collections.abc`、`typing`）而不是另起一行重複的 `from ... import`，其餘一行一個新增。沒有重排、沒有重新格式化、沒有改別人的函式；兩支共用檔都**沒有**跑 `ruff format`。
3. **整套 pytest 在併行波次下會拍到別人的半成品。** 第一次整套執行時遇到兩個**別的 Phase 進行中的測試檔**收集失敗，依 R3.5 用 `--ignore` 排除：
   - `tests/unit/test_release_safety_net.py`（`cannot import name 'needs_safety_net'`）
   - `tests/unit/pipelines/test_ticket_flow.py`（`cannot import name 'task_name'`）

   排除後的結果是 `3 failed, 1029 passed, 23 skipped, 11 xfailed, 8 errors in 340.49s`。逐一回查：
   - 8 個 `tests/integration/test_batch_publish_cutpoints.py` 的 error 來自 `src/training_kb/site.py:159` 新加的 `PermanentError: prepare-meeting@v2 缺少 supersedes`（別的 Phase 進行中的行為改動）。
   - 3 個 `tests/unit/test_site_pages.py` 的 failure **單獨重跑就是 17 passed**，是整套跑了 5 分 40 秒期間別的 agent 正在改 `site.py` 造成的拍照不一致。
   
   兩者都不是 Phase 45 造成的：本 Phase 只動 `feedback.py`／`prompts.py` 的自有區段與一個新測試檔，沒有任何 site／release 相依。

   收尾時（別的 Phase 陸續 commit 之後）再跑一次**完整**的 `uv run pytest tests -q -W error`，
   兩個收集失敗都已消失，結果是 `1 failed, 1105 passed, 23 skipped, 11 xfailed, 8 errors`：
   - 8 個 error 仍是 `tests/integration/test_batch_publish_cutpoints.py`，原因一樣是
     `src/training_kb/site.py:159` 的 `PermanentError: prepare-meeting@v2 缺少 supersedes`。
   - 1 個 failure 是 `tests/integration/test_release_hits_consistency.py::test_safety_net_prompt_holds_one_version_and_escapes_untrusted_text`
     （別的 Phase 新加的檔），**單獨重跑是綠的**。
   
   本 Phase 的 `tests/unit/test_feedback_diagnosis.py` 在整套與單獨兩種跑法都是 10 passed。
4. **`bool` 是 `int` 的子類**。`{"number": True}` 會通過 `True in frozenset({1})`，所以 `_validated_items` 第一道就是 `isinstance(number, bool)`。測試用 parametrize 把它釘住。
