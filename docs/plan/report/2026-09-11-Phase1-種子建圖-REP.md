## 1. 實作邏輯

### 這個 phase 解決什麼

把 Bitext 的歷史票單從 JSON 變成三層可查的狀態：**關聯資料（hotdata／SQLite）＋ 知識圖譜（HydraDB）＋ 語意記憶（Cognee）**。
沒有這一步，Phase 2 的 CREATE 沒有「同一個 UserProblem 已經 3 張票」可算，Phase 3 的 deflect 沒有可命中的 UserProblem，指標分母全是 0。

同時這也是五層 stack 裡 **Memory 建構（Cognee）／Memory 儲存（HydraDB）／Live 分析（hotdata）** 三層第一次真的在做事的地方——評審會問「這三個是不是只是擺著」，這個 phase 就是答案。

### 怎麼切

| 切法 | 內容 |
|---|---|
| `app/ingest/seed.py` | 唯一的匯入入口：`seed(db, cognee, hydra, rows)`，一次把一列 Bitext row 寫進三層 |
| `app/memory/hydradb_client.py` | 圖譜層：節點／邊 upsert ＋ 四個具名 Cypher 模板 |
| `app/memory/cognee_client.py` | 語意層：`remember` / `recall` 兩支 REST |
| `app/analytics/hotdata_client.py` | 把 Phase 0 的初版補成真的能跑（三段式表名、CLI load、唯讀保護） |

### 關鍵設計決定與理由

| 決定 | 理由 |
|---|---|
| **圖譜／語意層失敗只 WARN，不擋資料層** | demo 當天最大的風險是外部服務掛掉。Ticket 一定要進得了 DB，Tutorial 才生得出來；圖譜掉了頂多少一張圖，不能整條 pipeline 倒 |
| Feature／UserProblem 走 **get-or-create** | `建構知識圖譜.feature` 明確要求「同一 topic 重用同一列」「同名 Feature 重用同一列」 |
| 冪等鍵用 **content + created_at** | 對齊輪詢 Release 的同一條規則（相同 content + created_at 不重複），全專案只有一種冪等概念 |
| `cypher()` 只吃 **4 個具名模板**，不是真 parser | hackathon 簡化。寫一個 OpenCypher parser 是兩天的事，而 demo 只需要 4 個固定查詢（`ping`／`affected_by_release`／`tickets_by_feature`／`published_tutorial_for_problem`） |
| 邊型別 **五種白名單**、label **8 種白名單**，違反就 `OperationFailed` | `CLAUDE.md` 已定死五種邊（`asks_about`, `explains`, `refers_to`, `changes`, `supersedes`）。白名單讓「圖譜被寫髒」在寫入當下就爆，而不是 demo 時查不到 |
| `HotdataClient.execute()` **明確擋掉** | hotdata query 是唯讀的。與其讓呼叫端拿到看不懂的錯，不如在 client 層就講清楚「寫入請走 `load_rows`」 |
| hotdata「declared but has no data」當**空結果**而非錯誤 | 剛建表還沒 load 資料時 CLI 會回這句。當錯誤處理會讓第一次跑必炸 |

## 5. 遇到的問題與解法

| 問題 | 原因 | 怎麼解 |
|---|---|---|
| `sql.py` 的 `RECURRING_TOPICS` 在 hotdata 上炸掉 | `GROUP BY` 只列了 `t.user_problem_id`，但 SELECT 帶了 `up.topic`；SQLite 寬容、hotdata 嚴格 | 改成 `GROUP BY t.user_problem_id, up.topic`（整合時已修） |
| hotdata 查詢說表不存在 | hotdata 要三段式表名 `catalog.schema.table` | `run_sql` 自動把裸表名補成 `support.public.<table>` |
| 剛建好的表查詢回錯誤 | CLI 對空表回「declared but has no data」 | 在 client 層把這句當成空結果回 `[]` |
| `hotdata databases tables add -d` 傳 database 名稱失敗 | `-d` 只吃 database **id**，不吃名稱 | 改用 `--database support` 長參數 |
| hotdata JSON 不是 list | 回傳形狀是 `{columns, rows, row_count, ...}` | 在 `run_sql` 裡把 columns × rows zip 成 `list[dict]` |
| 想用 `execute()` 寫入 hotdata 失敗 | hotdata query 通道唯讀 | `execute()` 改成明確 raise，寫入一律走 `load_rows()` → `hotdata databases load` |
| HydraDB 沒有憑證 | 連線字串還沒拿到 | `HYDRADB_URI` 有值才走 HTTP；沒值就用本機 `.state/graph.json`，`_post()` 先留 `NotImplementedError` |
| Cognee 上傳一直 400 | `/api/v1/remember` 要 multipart，不是 JSON body | 改用 httpx `files=`，dataset 固定 `support_tutorials` |

## 8. 與計畫的偏差／hackathon 簡化

| 偏差 | 說明 |
|---|---|
| **`cypher()` 不是真的 OpenCypher** | 只認 4 個具名模板字串，收到別的就拒絕。真 parser 不在八小時的預算內 |
| **HydraDB 走本機檔案** | 憑證未到位，`.state/graph.json` 當替身。介面已抽好，憑證到位只要補 `_post()` |
| 圖譜／語意層失敗只 WARN | 計畫沒明講失敗策略；選了「資料層優先」的降級，理由見 §1 |

| 沒做圖譜的刪除／重建 | 重置一律靠 `scripts/reset_demo.py` 砍 `.state/` |
| 整合測試沒進 CI | 沒有 CI。`-m integration` 靠人手動跑，沒 env 就 skip |

## 9. 追記（2026-09-11 稍晚）：HydraDB Cloud 已接上

- 使用者提供 HydraDB Cloud 憑證（`HYDRADB_URI=https://api.hydradb.com`、`HYDRADB_APIKEY`）。查官方 OpenAPI（https://docs.hydradb.com/api-reference/v2/openapi.json ）確認 **v2 REST 沒有 Cypher 端點**，只有 `/databases`、`/context/ingest`、`/context/relations`、`/context/{id}/subgraph`、`/query`。
- 接法（write-through）：本機 `.state/graph.json` 永遠寫，五種邊的多跳查詢在本機算（決定性、可測）；`HYDRADB_URI` 有值時每個節點／邊同步 `POST /context/ingest`（type=memory、database `support_tutorials`、collection `graph`、upsert=true），HydraDB 自己抽實體與關係並跨 session 保存；`recall()` 走 `POST /query`（graph_context=true）、`relations()` 走 `GET /context/relations`。HydraDB 失敗只記 `last_error`，不擋資料層。
- 已建 database `support_tutorials`（`POST /databases`，infra ready）；種子重跑後 12 節點／6 邊全部鏡射（`mirrored=18`）。
- 測試：`tests/unit/test_hydradb_http.py` 6 個（httpx MockTransport：header、form 欄位、失敗不外拋、recall／relations 端點、無 URI 不打網路）；`tests/integration/test_hydradb_live.py` 2 個（database 就緒；節點＋邊 ingest 進入終態，實跑 95 秒因為索引是非同步）。`tests/unit/conftest.py` 把 `HYDRADB_URI` 等清空，單元測試不碰外部服務。
- Streamlit 底部新增「記憶層：HydraDB 圖譜 ＋ Cognee」展開區：本機索引數、HydraDB memory rows、抽出的關係表、recall 輸入框。
- 簡化：ingest 一筆一 call（種子 18 次）、不等索引完成；relations 抽取內容由 HydraDB 決定，不在規格驗收內。
