## 3. 這一批的 controller 裁決（全部 agent 都要遵守）

- **R1 真實 AWS 這一批要接。** 上一批把所有真實 AWS 延後到 P41；這一批的 P41／P48／P52／P57／P59／P60 **要真的部署與執行**並保存證據（execution ARN、`describe-execution`、`get-execution-history`、CloudWatch、HTTP 回應）。做不到的部分（Bedrock）標 BLOCKED 並附實際錯誤原文，不填猜測值、不假裝通過。
- **R2 Lambda 打包。** `lambda_.Code.from_asset("src")` 只會帶原始碼，**不含 `pydantic`／`jsonschema`**（pydantic-core 是編譯套件）。P41 要做一個可重現的相依 layer 或 bundling（Docker 可用），並把做法寫進 Phase 41 文件與報告。P42／P48／P52／P54 沿用同一支 layer／bundling，不各自再做一套。
- **R3 同一波次可能有人跟你改同一支檔**（`pipelines/feedback.py`、`pipelines/release.py`、`writing/prompts.py`、`writing/schemas.py`、`infra/training_kb_stack.py`、`ingress.py`）。規則：
  1. 既有檔案**只用 Edit，不用 Write**（Write 會蓋掉別人的修改）；動手前先重讀要改的那一段。
  2. 新增的函式放在你自己的區段（以 `# ---- Phase NN ----` 註解分隔），**不重排、不重格式化、不改名別人的程式**；`ruff format` 只能跑在你自己**新建**的檔案上；共用檔與既有檔**不跑** `ruff format`（它會改別人的行，gate 也不看它）。
  3. `git add` **只加自己的檔案路徑**（不 `git add -A`／`git add .`）。共用檔裡若含別人的未提交修改，照樣提交，不要 `git stash`、`git checkout --`、`git reset`、`git restore`。
  4. `git commit` 撞到 `index.lock` 就等幾秒再試。**絕不 `git commit --amend`、絕不 `git reset`（任何模式）、絕不 `git rebase`**——同一時間有別人在提交，amend／reset 會把別人的 commit 從分支上輾掉（2026-09-14 22:49 已發生一次：P54 的 amend＋reset 讓 P46 的 4d8d3c4 掉出歷史）。要補東西就再開一個 commit。
  5. 跑整套測試時若紅燈來自**別的 Phase 進行中的測試檔**，用 `--ignore=<那個檔>` 排除並在報告寫明，**不要去修別人的測試**；紅燈若來自你改的共用檔，就是你的責任。
  6. 不修改別的 Phase 的測試檔；`tests/unit/conftest.py` 只有 P55 可以動、`tests/conftest.py` 只加 fixture 不改既有的。
- **R4 controller 已預建空殼**：`src/training_kb/pipelines/feedback.py`、`src/training_kb/pipelines/release.py`（只有 docstring）。「建立」這兩支檔的 Phase 直接往裡面 Edit。
- **R5 Phase 文件裡的程式碼片段是示意，00A 的名稱與簽名是契約。** 兩者衝突、或與既有程式衝突時：以 00A ＋ 既有程式為準，並在 Phase 文件加一行「**現況核對（2026-09-14）：…**」說明差異；不要為了讓文件的片段能跑而改壞既有程式。
