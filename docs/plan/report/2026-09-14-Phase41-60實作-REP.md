|---|---|---|
| **R1** | 真實 AWS 這一批要接：P41／P48／P52／P57／P59／P60 要真的部署與執行並保存證據（execution ARN、`describe-execution`、`get-execution-history`、CloudWatch、HTTP 回應）。做不到的標 BLOCKED 並附錯誤原文。 | 前兩批把所有真實 AWS 延後到 P41；再不接，「應用程式完成」就只剩假資料綠燈。 |

## 5. 遇到的問題與解法

### 5.1 兩次 git 事故（併行提交）

**第一次（W2，21:47–21:49）。** 一個 agent 用了 `git commit --amend` 之後又 `git reset`，把自己 amend 出來的 commit 和 **P46 的 `4d8d3c4`** 一起從分支上輾掉。工作目錄的內容始終完好，所以復原方式是**單純重新提交工作目錄**（`1f4af65`），沒有 `reset`、沒有 force。同一次事故也把 **P51 的 `prompt_release_rewrite`** 從歷史上抹掉，那段內容只存在於工作目錄，所以依 R3.3（「共用檔裡若含別人的未提交修改，照樣提交」）一併補回，commit message 寫明。controller 事後逐檔核對：**沒有工作內容遺失**。

**第二次。** 另一個 agent 想更新自己報告裡的測試數字，用了 `--amend`；那幾秒之間別人已經先提交，HEAD 因此不是自己的 commit，**amend 改到的是 P42 的 `e5ef9c6`**，把它重寫成 `5c1fb97`。核對 `git diff e5ef9c6 5c1fb97 --stat`：唯一差異是報告多出的 3 行，其餘逐字相同。

**解法與代價。** COMMON.md R3.4 立刻改成「**絕不 `git commit --amend`、絕不 `git reset`（任何模式）、絕不 `git rebase`**」，並通知所有進行中的 agent；要補東西就再開一個 commit。代價是歷史上有幾個「補回」與「修正」的 commit，以及兩個 Phase 報告裡的 SHA 與實際 SHA 有出入（各自報告已註明）。**這是整批最值得記住的一課：多個寫入者共用一個 checkout 時，任何會改寫歷史的指令都是全域操作，不是自己的操作。**

### 5.2 模型 rate limit 打斷了兩個 agent

2026-09-15 01:1x（PDT）撞到 opus 的 session limit（429），P56（正在寫文件）與 P59 的 reviewer 同時被殺掉。P56 已經落地的三個 commit 沒有受影響，用 `SendMessage` 續跑即可；P59 的 reviewer 重派一個。代價是大約一個半小時的牆鐘時間。**教訓：長跑的 agent 要讓每個 Task 自己 commit，被殺掉時才不用重做。**

### 5.3 P57 的 site index 被 P59 的演練覆寫

P59 第一次跑真實 AWS 演練時，寫了共用的 `site/index.html`（站台索引是全站唯一一份，任何一次發布都會重建它），把 P57 留下的內容蓋掉。發現後**還原成 byte-identical 的原內容**，並在演練的 fixture 裡加了守門，之後的演練不再碰共用索引。**教訓：把「真實資源上的共用單例」列出來（站台索引、`CONFIG#`、active 規則），演練腳本要明確避開它們。**

### 5.4 `ErrorEquals` 比的是類別名字串，不是繼承（P41）→ D-85

Phase 59 的設計是 `InjectedFault(TransientError)`，想法是「注入的失敗會走完 Retry 再進 Catch」。P41 在真實 AWS 上一試才發現：**Step Functions 的 `ErrorEquals` 比對的是 Lambda runtime 回報的類別名字串，沒有繼承關係**——丟 `InjectedFault` 時 `ErrorEquals: ["TransientError"]` 一次都比不中，Retry **靜靜地完全不執行**。這是最危險的一種錯：沒有錯誤訊息、沒有警告，只是「重試沒有發生」。解法是把 `InjectedFault` 降成 `TransientError` 的**相容別名**，注入一律丟 `TransientError` 本身。**推廣規則：任何想被 `ErrorEquals` 攔到的錯誤，類別名必須和 ASL 裡寫的字串逐字相同。**

### 5.5 失敗細節在 `lambdaFunctionFailedEventDetails`（P41）→ D-86

用 `get-execution-history` 找失敗原因時，直覺會去找 `taskFailedEventDetails`，結果永遠是空的，看起來像「失敗但沒有錯誤資訊」。原因是我們用**直接函式 ARN**（`"Resource": "<function arn>"`）而不是 `arn:aws:states:::lambda:invoke` 信封，所以根本不會產生 `TaskFailed` 事件；事件型別是 `LambdaFunctionFailed`，細節欄位叫 `lambdaFunctionFailedEventDetails`。

### 5.6 `pipeline_task_handler` 差一點把每個 Task 都跑成整條 pipeline（W0-G4）→ D-89

00A §7 的圖畫成 `pipeline_task_handler -> run_sequence(pipeline, payload, tasks, deps)`。照字面實作的話，七個 Task state 會把整條 pipeline 跑七遍（七倍的模型呼叫、七倍的寫入）。正確的關係是：雲端**一次只跑一個 Task**（`event["pipeline"]` 選 pipeline、`event["task"]` 選函式），`run_sequence` 只留給本機把整條序列跑完。圖已在這次 doc sync 改掉。

### 5.7 雲端的失敗從來沒有進過紀錄簿（最終 review A／B／C 共同發現）→ D-89 後半

`run_sequence` 會在例外時先 `operations.fail(...)` 再 re-raise，但雲端走的是逐 Task 的 handler，那條路徑**完全沒有**這段。結果是：ASL 顯示 `FAILED`，紀錄簿上那筆 operation 卻永遠停在 `started`。三份最終 review 各自獨立發現這件事。解法是在 `pipeline_task_handler` 修一次（三條 pipeline 共用），並確認 `operations._change` 沒有轉移守門，所以「先記 failed、重試後 complete」仍然成立。

### 5.8 moto 與真實 AWS 的差異

前兩批全部跑在 moto 上，這一批是第一次和真實 AWS 對照。實際碰到的差異：

- **Lambda 打包**：`from_asset("src")` 只帶原始碼。`pydantic-core` 是編譯套件，必須用 `--python-platform x86_64-manylinux2014 --only-binary=:all:` 打進 layer；打成本機平台的 wheel 會在 Lambda 上 import 失敗（而且 `MARKERS` 的存在檢查看不出平台不對）。
- **`s3:ListBucket`**：真實 S3 沒有這個權限時，讀不存在的 key 回 **403 而不是 404**，`get_object -> None` 就不成立。moto 一直回 404，所以這件事只有在真實 AWS 上才會爆。
- **S3 website endpoint 只有 HTTP**：P09 設的 `enforce_ssl=True` 會產生一條 Deny policy，把整個公開站擋掉。P57 明確改成 `False`，私有前綴改靠 IAM 與 block public access 保護。
- **`enforce_ssl` 的 Deny 會被誤判成「公開」**：寫 `check_public` 時要只看 `Effect: "Allow"` 的陳述。
- **GSI 落後**：`by_target` 是最終一致的，剛寫進去的邊可能查不到；`find_release_hits` 因此必須用基表核對（P50 的既有設計在真實 AWS 上成立）。
- **`sts:GetCallerIdentity` 不需要權限**：原本補了一條 `Resource: "*"` 的 Allow，`check_iam` 抓到之後查了 AWS 文件，確認是純粹的擴權，直接移除。

### 5.9 「全部已發布」和「半發布」長得一模一樣（最終 review A 的 Critical）→ D-94

`task_commit_batch` 在「每一版都已經有 `published_at`」時會跳過交易，直接回報整批成功。但 `Publisher._after_transaction` 是**先**切 `published_at`、**後**寫 `site/`，所以切點 `a2`／`a3`（半發布）的狀態正好也是「全部已發布」——redrive 或同日手動重跑會回報成功，而公開頁其實不存在。解法是讓那個分支同時檢查「公開物件齊全」與「本次 operation 的 `pending-promote.json` 存在」。這一條之所以危險，是因為**它讓一個已知的 O3 缺口變成靜默的成功**。

### 5.10 孤兒版本：失敗一次之後，每次重跑都回報成功（最終 review A）→ D-95

`_guard` 只看「版本完整嗎」不看「發布了嗎」。Prepare／Inspect／Commit 任一步失敗後，後續每次執行都短路成「沒有新證據 → 空的 `prepared_version_ids` → Succeeded」，那個版本永遠不會上線。解法是「完整但未發布」要放回 `prepared` 重新發布。

### 5.11 診斷先付錢再判斷要不要做（最終 review A）→ D-96

REFINE 的順序是「先 `diagnose_weak`（一次模型呼叫）→ 再由 `_guard` 決定要不要跳過」，重送時每個 target 都白付一次；更糟的是重試出來的 `step_indexes` 可能和已存的改寫回覆對不上，`_apply_rewrite` 會**永遠**丟 `ContentError`。解法是先查子 operation、再決定要不要呼叫模型，並把診斷一起持久化。

### 5.12 `demo/` 裡藏著兩條會寫正式資料的路徑（最終 review C）→ D-103

`demo/scripts/cluster_demo_tickets.py` 的 docstring 只承諾「輸出本機 JSON」，實際上會對 `load_settings()` 解析出的表寫 20 筆工單；`demo/cli.py` 的 `seed` 子命令會用 `create_only=False` 覆寫 `TUTORIAL#prepare-meeting`、`RULE#R-007`、`RULE#R-012`、`FEATURE#Prepare`。今天沒有出事，**只是因為 O7 還沒核定所以沒人跑**。解法是：明示旗標（`--write`／`--apply`）、執行前印出解析到的 table 與 bucket、`TKB_ENV=prod` 一律拒絕，並補上拒絕行為的測試。

### 5.13 `TKB_ENV` 在兩個地方比法不同（最終 review C）→ D-106

`faults.active_fault` 做 `.strip().lower()` 之後比 `prod`；`pipelines/common.py` 的 `maybe_fail_task` 用完全相等。所以 `TKB_ENV=" PROD "` 在一邊是正式環境、另一邊不是——**注入開關在正式環境有機會生效**。解法是抽出 `faults.is_production(env)` 當唯一實作。

### 5.14 `check_secrets` 不掃 `docs/`，而機器產物全落在 `docs/plan/report/`（最終 review C）→ D-107

排除 `docs/` 的理由是誤報多（文件裡會出現看起來像賦值的字串），但 `docs/plan/report/**` 正是所有自動產生的報告、掃描紀錄與證據索引的落點。解法是「高精度樣式（AKIA／`gh?_`／PRIVATE KEY）照掃 `docs/`，只有容易誤報的 `SECRET_ASSIGNMENT` 規則在那裡豁免」。reviewer 手動 grep 過，**目前沒有真的外洩**。

### 5.15 O3 在真實 AWS 上又輸了一次（P59）

前一批在 moto 上重現過切點 5 的 partial；這一批在**真實** DynamoDB 與 S3 上又重現了一次：多篇整批在第 2 篇 promote 之前中斷，兩篇的 `current_version` 都已經切到 v2，但公開站上 A 是 200、B 是 404。`resume_publish` 可以把兩篇都補完（補完之後兩篇都 200），**但補償是補救不是通過**。gate 維持 FAIL、F49 未放寬、沒有加 CloudFront 或任何未授權服務。

### 5.16 多篇整批在「交易之前」中斷時沒有 resume 輸入（P59）→ D-97 ②

那個時間點還沒有 `pending-promote.json`、operation 也還沒 `record_version`，所以 `resume_publish` 只能丟 `CoordinationError`。這是**已知邊界不是缺陷**：正確的復原是上游帶同一組 `version_ids` 重跑（同 operation 拿到同版號，O2 保證）。

### 5.17 `verify_recipe` 綠燈不等於 O7 通過（P56）

種子的 schema 檢查與八個目標數字的重算都 PASS，20 筆工單也用真實 Titan embedding 分過群。但 `demo/seed/approvals/` 缺三份核定檔（`R007-B1`、`R012-B1`、`R012-B2`），`o7_ready` 是 `False`。**程式重算成功與維護者核定是兩個不同條件**，這一點在 00A §4.2 與 00 總覽都寫得很清楚，P56 也照辦了。

### 5.18 `validate_rules` 的退役條件可能永遠不觸發（最終 review B）→ 00A §6.10

「連續兩個不重疊且未改善的完整批次才 retired」需要看到那條規則的**完整決定性歷史**，但 Lambda 的一次 invoke 只帶得到這次事件裡的批次。如果呼叫端一次只送一批，退役條件本來永遠不會成立——**而且不會有任何警告**。解法是在呼叫 `next_status` 之前先把已存的 `RuleEvaluation` 讀回來合併。
