## 1. 這套文件是什麼

`docs/design/training-kb.md`（以下都稱「設計文件」）描述了一個叫 **Training Knowledge Base** 的系統要長什麼樣子。它有 1245 行，寫的是「設計決定」，不是「動手步驟」。

這套 26 份文件把那份設計切成 25 個可以照做的階段（Phase 01–Phase 25），加上你現在看的這份總覽。每一份文件都是一段 3–8 小時的工作，每個 Task 都附**完整可貼上的測試碼與實作碼**（不會出現「略」或「自行補上」），結尾有一張**完成檢查清單**，你自己勾完才算做完。

重要的前提（設計文件第 4 節已寫明）：**這個 repo 現在沒有任何程式碼、沒有 `pyproject.toml`、沒有測試、也沒有建立任何 AWS 資源。** 所以 Phase 01 是真的從空的資料夾開始。這套文件也**不會**保證 AWS 一定免費、模型一定叫得到、或某段程式「已經測過」；它只告訴你：做完之後，你要用哪一個指令、看到什麼輸出，才能說它可以動。

## 2. 怎麼用這套文件

### 2.1 一次只做一份，做完勾完檢查清單再做下一份

```text
打開 NN 文件 -> 讀 §1 §2 §3（要做什麼、在哪裡、前置齊不齊）-> 讀 §4 §5（名詞與設計理由）
             -> 照 §6 的 Task 1、Task 2 … 依序做，每個 Task 都 commit
             -> 回到 §7 完成檢查清單，一條一條手動驗證並打勾 -> 全部打勾才打開 NN+1
```

不要跳號：Phase 07 的程式會 `import` Phase 03 做好的東西，跳號會讓你在 `ModuleNotFoundError` 裡打轉。卡住時先看該份文件的「§8 常見錯誤與排除」，那裡列了至少四個「症狀 → 原因 → 解法」。

### 2.2 TDD：先寫測試，再寫程式

TDD 是 **Test-Driven Development（測試驅動開發）** 的縮寫。用一句白話講：**先寫一段「檢查答案的程式」，再寫「產生答案的程式」。**

這聽起來反直覺，但有三個很實際的好處：（1）**你被迫先想清楚介面**——要寫 `assert parse_version_id("a@v2") == ("a", 2)`，就必須先決定這個函式叫什麼、吃什麼、吐什麼；（2）**你知道測試是真的有在測**——先看到它失敗，才分得出「它真的有檢查」還是「它根本沒執行到」；（3）**改壞了會馬上知道**——之後 Phase 16 改動 Phase 07 的東西時，跑一次全部測試就知道有沒有弄壞舊功能。

每個 Task 都是固定的五個步驟：

```text
  步驟 1 寫測試            步驟 2 跑測試看它失敗      步驟 3 寫最少的程式
  描述「正確答案長什麼樣」 -> 紅燈：ModuleNotFound  -> 剛好夠讓測試過
          ^                   或 AttributeError        不多寫下階段的功能
          |                 （沒看到紅燈就往下做，          |
          |                   是最常見的錯誤）              v
          |                                        步驟 4 再跑一次 -> 綠燈
          +--------- 下一個 Task <--- 步驟 5 commit <-------+
```

「紅燈 → 綠燈 → commit」是一個循環。一個 Task 做完就是一個循環，通常只有 10–40 分鐘。

### 2.3 BDD 與 Gherkin Rule：驗收的依據

BDD 是 **Behaviour-Driven Development（行為驅動開發）**。它跟 TDD 的差別是：TDD 的測試在講「這個函式的輸入輸出」，BDD 的描述在講「使用者做了 X，系統應該發生 Y」。

這個 repo 用 **Gherkin** 這種格式把行為寫在 `docs/spec/features/*.feature` 裡，共 13 份檔案、147 條 `Rule`。例如：

```gherkin
  Rule: Feedback 的 rating 只能為 1 到 5 的整數
```

這些 `Rule` 是**驗收契約**：程式做完之後，必須能說明每一條 Rule 由哪一段程式落實。設計文件第 20 節已經把 147 條 Rule 全部列出來，並指定每條由哪個模組負責。

所以每份 Phase 文件都有「§10 對照：設計章節與 Rule 編號」這一節，把屬於該階段的 Rule 原文抄一次，並指到落實它的 Task。**你不需要學會寫 Gherkin，也不需要安裝 Cucumber**；這套文件只用 pytest，Gherkin Rule 在這裡的角色是「驗收清單」而不是「要執行的測試」。

有些 Rule 在 `.feature` 檔裡標了 `@Missing`，代表規格本身還缺範例資料。設計文件第 15 節規定：**不可以為了讓它看起來完整就自己捏造 fixture**，也不可以刪掉那條 Rule。

## 3. 產品在做什麼

一句話：**把「一直有人來問同一個問題」變成教學文章，再用讀者的回饋把文章改好，並在產品改版時只改受影響的那一步。**

設計文件第 3 節把它畫成兩條循環：

```text
循環一：問題 -> 教學 -> 回饋 -> 更好的教學
  重複工單 --> 教學缺口 --> 新教學 --> 回饋與瀏覽 --> 改善教學
                                          |
                                          +--> 寫作規則 --> 後續教學也採用

循環二：產品改版 -> 只改受影響的步驟
  產品改版 --> 找到引用該功能的「目前已發布步驟」--> 只改命中步驟
                                          |
                                          +--> 功能被移除時，整篇教學退役
```

用生活化的例子講：

> 你經營一間小店的線上服務。這一週有 20 個人來信問「會前摘要在哪裡開啟？」——問法都不一樣，但問的是同一件事。
>
> **循環一**：系統發現這 20 封信講的是同一個主題（分群），而且 14 天內超過 5 筆（recurring，代表不是偶發），就判斷「這裡缺一篇教學」，於是寫出〈準備會議〉v1 並上架。讀者看完之後打分數、留言「第三步沒有說按鈕在哪一頁」。累積到一定數量，系統就把第三步改寫成 v2，同時把「點 UI 的步驟要寫出頁面與按鈕位置」這件事記成一條**寫作規則**。等到證明這條規則真的讓評分變高、重開票變少，它才會被啟用，之後寫別篇教學也會自動套用。
>
> **循環二**：工程師把「Meeting Summary」這個功能改名叫「Prepare」，送出一個 PR。系統沿著「哪些步驟引用了這個功能」的關係，找到〈準備會議〉目前上架版本的第 3 步，**只改那一步**，第 1、2、4 步一個字都不動，然後出 v3。其他兩篇沒有引用這個功能的教學完全不動。

設計文件第 3 節列了四個「看得見的驗收結果」——這也是整個專案做完的定義，見 §12。**不做的事**（設計文件第 3 節明列）：完整 LMS、教學影片、企業認證、Teams／Microsoft Graph、多租戶、複雜 dashboard、multi-agent、MCP server、瀏覽器自動操作、fine-tuning；Neptune、OpenSearch、Athena 也不在範圍內。

## 6. 名詞總表

第一次看到不懂的字就回來這裡查。程式識別字、指令與服務名稱一律保留英文。

### 6.1 產品名詞（設計文件第 1 節）

| 名詞 | 白話解釋 |
|---|---|
| Tutorial | 一篇教學的「身分」，例如〈準備會議〉。它自己不含文字，只記著目前上架的是哪一版。 |
| TutorialVersion | 一篇教學的某一版，例如 `prepare-meeting@v2`。教學文字是存在版本上的。 |
| TutorialStep | 某一版裡的一個操作步驟，例如「第 3 步：點右上角的 Prepare」。 |
| Feature | 產品的一個功能，例如「Prepare」。**不是** Gherkin 檔案裡的 `Feature` 關鍵字。 |
| Release／publish | Release 是一次產品改版事件（改名／改行為／移除），例如 PR #42；publish 是把某個教學版本上架。兩者不同。 |
| Step／Task | Step 是教學裡的操作步驟；Task 是 Step Functions 流程裡的一個工作節點。 |
| Ticket | 一筆使用者問題（GitHub Issue、Discord 訊息、email）。 |
| Feedback | 讀者對某一版教學的評分／類別／留言。 |
| TutorialView | 一次「某人在某時間看過某一版」的瀏覽紀錄，用來當重開票率的分母。 |
| AuthoringRule | 寫作規則，例如「點 UI 的步驟要寫出頁面與按鈕位置」。有 candidate／active／retired 三種狀態。 |
| Rote／ProvenWorkflow（PROC） | Rote 是接入層的三層處理策略（精確比對 → 相似比對 → 交給 Agent）；PROC 保存已驗證的工具呼叫順序，同形狀的事件下次可以直接重放，不必再問模型。 |
| Knowledge Gap／cluster_id | 教學缺口：一群重複工單問的是同一件事但還沒有教學。用分群編號 `cluster_id`（例 `c12`）表達。 |
| recurring | 「反覆發生」：同一群在當日加前 13 個 UTC 日期內至少 5 筆。 |
| CREATE／KEEP／UPDATE／REFINE／RETIRE | 五種動作：建新教學／不動只記原因／因改版出新版／因回饋出新版／整篇退役。 |
| candidate／active／retired | 規則的三種狀態：待驗證／可以拿來寫作／已停用。 |
| 弱教學 | 平均評分 < 3.5、回饋數夠（正式 ≥10、Demo ≥8）、同一核定問題類別 ≥5，三者同時成立。 |
| 負面回饋 | rating ≤ 2 **或** category 屬核定問題類別的回饋；同一筆同時命中只算一次。 |
| 重開票率 | 看過某版教學、之後又在 14 天窗口內就同一題開票的人數，除以該窗口內看過的不同人數。 |
| 核定問題類別 | 初始為「找不到按鈕」「缺少資訊」；不在表上的歸「待分類」，待分類不算負面。 |
| operation_id | 一次邏輯操作的固定編號（例 `ingest:ticket:t_881`）。重送時靠它找回原本的結果與版號。 |
| backfill／safety_net | backfill 是事後補回漏掉的 Feature 引用邊（只補漏、不替換）；safety_net 是改版流程的補漏：關係反查為零時改用步驟文字搜尋，再請 Claude 確認。 |
| slug | 教學的英文短代號，例 `prepare-meeting`；用在 ID 與 S3 路徑裡。 |

### 6.2 AWS 服務

| 名詞 | 白話解釋 |
|---|---|
| AWS／Region／IAM | Amazon 的雲端平台；Region 是機房地區（例 `us-east-1`），資源屬於某一區、跨區不共用；IAM 決定「誰可以對哪個資源做什麼」。 |
| DynamoDB | AWS 的資料庫，像一本超大的字典：給它鍵，它給你值。不用寫 SQL。本案十種實體全放同一張表 `training_kb`。 |
| PK／SK／GSI | PK 是分割鍵（決定資料放哪台機器）、SK 是排序鍵（同一 PK 底下可有多筆並依 SK 排序）；GSI 是「第二本索引」，本案只有一個 `by_target`，用來反查「誰指向我」。 |
| 一致讀取／交易／條件寫入 | 一致讀取＝讀到的一定是最新值（基表可以、GSI 不行）；交易＝一組寫入全成功或全不發生；條件寫入＝條件成立才寫，本案用它做去重與搶鎖。 |
| S3／bucket | AWS 的檔案倉庫，用「key」（像路徑的字串）存取物件；bucket 是容器，名稱全球唯一。教學全文、diff、操作紀錄都放這裡。 |
| S3 website endpoint | 把 bucket 當成靜態網站對外提供。**只有 HTTP、沒有 HTTPS**（設計文件第 13 節）。 |
| Lambda／Layer | 「跑一段程式就結束」的雲端執行環境，不用自己管伺服器；Layer 是把依賴套件打包成一包給它用。 |
| Function URL | 給 Lambda 一個公開網址。本案的 GitHub webhook 入口用它，驗簽由程式自己做。 |
| Step Functions | 流程編排服務：把一連串 Lambda 依圖上的順序、分支、重試規則跑完。本案用 Standard 型。 |
| ASL／Retry／Catch | ASL 是用 JSON 描述流程的語言；Retry 設定失敗時重試幾次，Catch 設定最後失敗轉去哪個節點。 |
| StartExecution | 啟動一次執行的 API。同名且執行中時有冪等行為，但**不能當成永久去重**。 |
| EventBridge Scheduler | 排程器。本案用 `cron(30 0 * * ? *)` 每天 UTC 00:30 啟動回饋檢視流程。 |
| Bedrock／bedrock-runtime | AWS 的生成式 AI 服務，用同一套 API 呼叫不同廠商的模型；`bedrock-runtime` 是真正送出推論請求的 client 名稱。 |
| Titan Embeddings | Amazon 的向量模型（`amazon.titan-embed-text-v2:0`），把文字轉成 1024 個數字。用 `invoke_model` 呼叫。 |
| Claude／inference profile | Anthropic 的語言模型，本案用來寫教學、分類留言、判斷衝突，用 `converse` 呼叫；inference profile 是跨區呼叫時用的另一種模型識別方式，實際用哪個由 Phase 04 確認。 |
| toolConfig | `converse` API 裡「告訴模型有哪些工具可以呼叫」的設定。Rote 第三層用它。 |
| CDK／stack／CloudFormation | 用 Python 寫程式建立 AWS 資源（取代手點網頁）；stack 是部署單位，本案兩個；CloudFormation 是底下實際執行建立與刪除的服務。 |
| AWS CLI／boto3 | 在終端機操作 AWS 的命令列工具（`aws configure` 設定金鑰與 Region）；boto3 是 Python SDK，程式裡所有 AWS 操作都透過它。 |

### 6.3 開發工具與測試

| 名詞 | 白話解釋 |
|---|---|
| uv／`.venv/` | 很快的 Python 專案與套件管理工具（`uv init`、`uv add`、`uv run`）；它會把套件裝在專案自己的 `.venv/` 裡，不污染系統 Python。 |

| pytest／assert | Python 的測試框架，`uv run pytest` 會自動找 `tests/` 底下 `test_*.py` 裡的 `test_*` 函式；`assert x == 1` 代表「不成立就讓測試失敗」。 |
| fixture／marker／conftest.py | fixture 是測試前置資料工廠（`@pytest.fixture`）；marker 是標籤（例 `@pytest.mark.aws`）；conftest.py 是 pytest 自動載入的設定檔，放共用 fixture 與收集規則。 |
| moto | 在本機「假裝」自己是 AWS 的套件。用 `from moto import mock_aws` 之後，boto3 的呼叫會被攔下來在記憶體裡處理，不花錢也不連網。 |
| ruff | 很快的 Python 檢查器與排版器。`ruff check` 抓問題，`ruff format` 排版。 |
| pydantic／BaseModel／ValidationError | 資料驗證套件（本案用 **v2**）：用型別註記描述資料長相，繼承 `BaseModel` 就得到驗證、`model_validate()`、`model_dump()`；驗證失敗丟 `ValidationError`。 |
| StrEnum／dataclass | StrEnum 是 Python 3.11+ 內建的列舉，成員同時也是字串；dataclass 是「只裝資料、不做驗證」的類別寫法，本案的 `Settings`、`Thresholds` 用它。 |
| commit | 把一組改動存進 Git 的一個版本點。訊息格式見 §7。 |
| `.env`／`.gitignore` | `.env` 放本機祕密設定（金鑰、實際 bucket 名稱），**絕對不能進 Git**；`.gitignore` 是告訴 Git「這些檔案不要管」的清單。 |
| Node.js | JavaScript 的執行環境。本案只因為 **CDK CLI 是 Node 寫的**才需要它。 |
| Snyk／Streamlit | Snyk 掃描依賴套件漏洞（Phase 25 用）；Streamlit 用 Python 幾行就做出網頁介面（Phase 23 的本機控制台用）。 |

### 6.4 演算法與資料格式

| 名詞 | 白話解釋 |
|---|---|
| embedding | 把一段文字變成一串數字（本案 1024 個），意思相近的文字數字也相近。 |
| cosine（餘弦相似度）／centroid（群中心） | cosine 比較兩串數字「方向」有多接近，在 -1 到 1 之間，越接近 1 越像（本案門檻 0.85）；centroid 是一群向量的平均，代表這群的中心點。 |
| Jaccard | 比較兩個集合有多像：交集大小 ÷ 聯集大小。本案門檻 0.8。 |
| SHA-1／SHA-256 | 雜湊函式：把任意輸入變成固定長度的指紋。相同輸入永遠得到相同指紋。 |
| HMAC／固定時間比較 | 帶密鑰的雜湊；GitHub 用 HMAC-SHA256 對送出的內容簽名，我們用同一把密鑰重算並比對，比對時用 `hmac.compare_digest`，不論哪個字元不同都花一樣的時間，避免被猜出密鑰。 |
| webhook | 別的系統在發生事情時「主動打你的網址」通知你。本案接 GitHub 的 Issue 與 PR 事件。 |
| JSONPath | 指向 JSON 裡某個位置的字串，例 `$.issue.title`。本案只自己實作 `$.a.b`、`$.a[0].b` 這個子集，不支援運算式。 |
| unified diff | 常見的差異格式（`+` 新增、`-` 刪除）。本案用 Python 內建 `difflib.unified_diff`。 |
| UTC／tz-aware／ISO 8601 | 本案所有時間一律用世界協調時間 UTC、帶時區（`datetime.now(timezone.utc)`），存成 `2026-08-01T00:00:00Z` 這種 ISO 8601 字串。 |
| 冪等（idempotent） | 同一個操作做一次跟做很多次結果一樣。本案靠 operation_id 與條件寫入達成。 |
| 裸 ID | 不帶類型前綴的識別碼，例 `prepare-meeting@v2`、`R-007`。存在模型欄位裡的一律是裸 ID。 |

## 9. 介面契約總表

### 9.1 怎麼讀這張表

「產出」的階段**必須照這個名稱與參數實作**，「使用」的階段**必須用一模一樣的名稱呼叫**，不可以自己改名。若某階段需要新增表上沒有的函式，命名要跟同檔案風格一致，並寫在那份文件的「介面 → 產出」欄裡。簽名裡 `|` 代表「或」（`str | None` 是「字串或沒有」）。

### 9.2 各模組介面

**`errors.py`／`clock.py`／`config.py`**（產出 Phase 01；使用：之後全部階段）

| 簽名 | 一句白話 |
|---|---|
| `TransientError` / `PermanentError`（Exception） | 可重試（網路、限流、逾時）／不可重試（資料非法、業務驗證失敗）；ASL 的 Retry 只重試前者 |
| `IngressError(PermanentError).__init__(message, fields: list[str])` | 接入驗證失敗，`fields` 是不合法欄位名，對應規格的「操作失敗」 |
| `ContentError(PermanentError)` | 教學內容驗證失敗（五段不齊、步驟引用不對） |
| `now_utc()` / `to_iso(dt)` / `parse_iso(s)` / `utc_date(dt)` | 取現在（UTC 帶時區）／轉成 `2026-08-01T00:00:00Z`／轉回時間（`Z` 與 `+00:00` 都接受）／取 UTC 日期 |
| `@dataclass Thresholds` | 所有門檻數字集中一處（0.85、0.8、3、14、5、3.5、10、8…） |
| `@dataclass Settings` | 執行環境設定（Region、表名、bucket、模型 ID、逾時、token 上限、`thresholds`） |
| `load_settings(env=None) -> Settings` | 從 `TKB_*` 環境變數建出 `Settings`；缺必填值丟 `PermanentError` 並列出缺哪些 |

**`models.py`／`keys.py`**（產出 Phase 02；使用：Phase 03 起全部）

| 簽名 | 一句白話 |
|---|---|
| 七個 StrEnum：`TicketSource`、`ReleaseSource`、`ReleaseKind`、`StepType`、`TutorialStatus`、`RuleStatus`、`ProcStatus` | 把合法值寫死，打錯字會被擋下來 |
| `APPROVED_CATEGORIES_DEFAULT` / `PENDING_CATEGORY` | 核定問題類別的初始清單，以及「待分類」這個字串 |
| 十個實體：`Ticket`、`Release`、`Feedback`、`TutorialView`、`Feature`、`Tutorial`、`TutorialVersion`、`TutorialStep`、`AuthoringRule`、`ProvenWorkflow`（含 `ProcStep`） | 十種資料的形狀，欄位名照 ERM；邏輯關聯一律存裸 ID |
| `StepDraft` / `TutorialContent` | 模型寫出來的「五段內容」的形狀 |

### 12.3 三件不可以宣稱的事

設計文件第 12.3、15、17.3 節明文禁止：（1）把「評分變高、重開票變少」說成**已證明因果**，那只是觀察結果；（2）把預先跑好的結果說成本次現場成功，備援畫面必須寫「預先執行結果」；（3）宣稱「一定免費」或「secrets scan 通過」，除非真的跑了 Snyk Secrets 並保留版本與範圍。
