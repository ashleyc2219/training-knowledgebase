# Training Knowledge Base 60 Phase 實作總覽

> **給執行這份計畫的人或 agent：** 逐一執行 Phase 01→60；每個 Phase 都要先寫會失敗的測試，再做剛好讓它通過的最小實作。可使用 `superpowers:subagent-driven-development` 或 `superpowers:executing-plans` 這類逐項流程工具，但不得跳過前置 gate（gate 是「必須有真實證據才能通過的關卡」，見下面的名詞小抄）。

**Goal：** 把 [Training Knowledge Base 設計](../../design/training-kb.md) 拆成 60 個可以依序實作、測試、審查與停止的 Phase。

**Architecture：** 單一 Python 專案透過三條固定的 Standard Step Functions workflow（AWS 的流程編排服務），使用一張 DynamoDB 表 `training_kb`、唯一一個 `by_target` GSI 與一個 S3 bucket。Rote（接入層的重放機制）只處理接入程序；Writing（唯一呼叫 Bedrock 模型的模組）只處理文字工作；Analytics（唯一能把規則狀態寫成 active／retired 的模組）只處理指標與規則驗證。這一段出現的英文名詞都在下面「名詞小抄」有一句白話。

**Tech Stack：** Python 3.12、uv、pytest、ruff、mypy、AWS CDK、Lambda、Step Functions Standard、DynamoDB、S3、EventBridge Scheduler、Amazon Bedrock。

### TDD 的紅燈與綠燈（白話版）

每個 Task 都是同一組五個動作。「紅燈」「綠燈」只是「測試失敗」「測試通過」的俗稱：

```text
1 先寫測試：用程式描述「做完以後應該看到什麼」
        |
        v
2 跑測試 --> 紅燈（測試失敗）。這是預期的，因為實作還沒寫
        |    正常的紅燈訊息長得像 cannot import name 'xxx' 或 AttributeError
        |    代表測試真的有去找那個東西，只是它還不存在
        v
3 寫剛好讓這個測試通過的最少程式，不要順手多寫別的功能
        |
        v
4 再跑一次 --> 綠燈（測試通過）。到這裡這一步才算做完
        |
        v
5 git commit，然後做下一個 Task
```

兩個常見誤解要先講清楚：

- **紅燈必須因為「正確的理由」失敗。** 如果錯誤訊息是打錯字、縮排錯誤或 `SyntaxError`，那是測試本身壞了，不是預期的紅燈；先把測試修好再繼續。
- **綠燈不等於功能正確。** 綠燈只代表「這條測試描述的行為成立」。每個 Phase 文件的「驗收矩陣」與「人工驗收」才是真正的完成條件；牽涉 AWS、瀏覽器或維護者核定的項目，還要有真實證據（見下面的 gate 說明）。

### 指令規則

所有 Python 指令一律用 `uv run` 開頭，複製貼上就能跑：

```bash
uv run pytest tests/unit/test_xxx.py -q        # 跑單一測試檔
uv run pytest tests/unit/test_xxx.py::test_name -q   # 跑單一測試函式
uv run ruff check src tests                    # 風格檢查
uv run mypy src                                # 型別檢查
```

不要用裸 `pytest`、`python -m pytest` 或 `.venv/bin/python -m pytest`：那些會用到不同的環境，錯誤訊息會和文件對不上。**唯一不加 `uv run` 的是 `cdk` 指令**（`cdk synth`／`cdk deploy`），因為它是 Node.js 套件。

| TDD／紅燈／綠燈 | 先寫會失敗的測試再寫程式；紅燈＝測試如預期失敗，綠燈＝測試通過。 |
| uv | Python 的套件與環境管理工具；本專案所有 Python 指令都用 `uv run` 開頭。 |
| Tutorial／TutorialVersion | 一篇教學的身分（用英文短名 slug 當識別，例如 `prepare-meeting`）／它的某一個版本（`prepare-meeting@v2`）。 |
| Feature（功能） | 產品的一個功能，例如「準備會議」；不是 Gherkin 規格檔裡的 `Feature:` 關鍵字。 |
| Ticket（工單）／Release（改版事件） | 使用者回報的一則問題／產品改版的一筆紀錄（改名、變更、移除）。Release 和「發布教學」的 publish 是兩回事。 |
| CREATE／KEEP／UPDATE／REFINE／RETIRE | 對教學的五種動作：依缺口新建、維持原狀、因產品改版只改命中步驟、因低分回饋只改命中步驟、因功能移除而退役。 |
| Rote | 接入層的三層處理：先找完全一樣的舊處理程序、再找相似的，都沒有才叫模型。目的是少呼叫模型。 |
| PROC／ProvenWorkflow | Rote 記住的「已驗證可重複使用的接入處理步驟順序」。 |
| pipeline | 一條固定的處理流程。本專案只有三條：`ticket-analysis`、`release-update`、`feedback-review`。 |
| Step Functions／ASL | AWS 的流程編排服務（Standard 模式會保留完整執行歷史）／它的流程定義 JSON（Amazon States Language）。 |
| DynamoDB／GSI | AWS 的 key-value 資料庫（本專案只有一張表 `training_kb`）／它的第二種查法（本專案只有 `by_target`，而且剛寫進去的資料可能還查不到）。 |
| S3 | AWS 的檔案儲存。`site/` 前綴是公開的，其餘一律私有。 |
| Bedrock／Titan／Claude | AWS 的模型服務入口／把文字轉成 1024 個數字的 embedding 模型／產生文字的模型。 |
| embedding／cosine | 把文字轉成一串數字以便比較語意／兩串數字方向有多接近（1 是完全同向）。 |
| Jaccard | 兩個集合「交集除以聯集」的比例，用來比較兩組欄位名有多像。 |
| recurring／knowledge gap | 同一群工單在 UTC 當日與前 13 日累積到至少 5 筆／這些工單指出的「缺少的教學主題」。 |
| candidate／active／retired（寫作規則） | 剛提出還沒驗證的規則／驗證有效、可拿來寫作的規則／驗證無效已停用但保留歷史的規則。 |
| backfill | 事後補上當初漏寫的關係邊；只補缺的，不動已經存在的。 |
| BLOCKED | 因為外部條件（沒帳號、沒權限、模型不可用）做不下去，必須留下報告並停止，不填猜測值。 |
| CDK／Lambda／IAM／EventBridge Scheduler | 用 Python 描述 AWS 資源的工具／AWS 的無伺服器函式／AWS 的權限系統／AWS 的排程服務（本專案每天 UTC 00:30 觸發一次回饋檢視）。 |
| operation（操作）／ledger（紀錄簿） | 一次可追溯、可重送而不重複的處理單位／記下每個 operation 狀態的那張表。 |
| canonical（正規形式） | 同一件事只有一種標準寫法；例如同一個事件不論重送幾次，都算出同一個 `operation_id`。 |
| FIFO | 先進先出，也就是「事件一定照送達順序處理」。O2 沒有 PASS 之前不得宣稱做得到。 |
| lease（租約） | 同時只讓一個執行者處理某個範圍的暫時標記。拿到 lease 不等於拿到接受順序，TTL 到期也不保證準時解鎖。 |
| spike（探路程式） | 為了回答一個技術問題而寫的最小一次性程式，不是產品程式，用完就丟。 |
| fixture | 測試用的固定資料，例如一份真實的 GitHub webhook JSON。 |
| HMAC | 用共享密鑰對「原始 bytes」算出的簽章，用來確認 webhook 真的來自 GitHub。 |
| STABLE_KEYS／結構簽名 | 某個來源可以拿來算簽名的欄位名清單／由它算出的 16 字元指紋（只看欄位結構，不含 ID、時間或標題等事件值）。 |
| normalize（正規化）／fallback（回退） | 把各種來源的原始事件轉成本專案的固定欄位／前面的捷徑沒命中時，退回去叫模型做。 |
| JSONPath | 指向 JSON 某個欄位的路徑。本專案只允許「欄位名」與「陣列 index」兩種，不允許任意運算式。 |
| successor（後繼教學）／alias（別名） | 教學退役後要把讀者導去的那一篇／Feature 改名後保留下來的舊名稱。 |
| Safety Net（補漏） | 反查不到步驟、或遇到重大改名時，額外用步驟文字相似度提出候選再請模型逐一確認的補救路徑。 |
| renderer／widget | 把資料轉成 HTML 的程式／教學頁上讓讀者填評分的那個小元件（只在瀏覽器本機產生檔案，不送出）。 |
| evidence（證據）／green | 可以被別人重新查證的實際紀錄（截圖、執行歷史、報告檔）／檢查項目標成「通過」。沒有實際跑過的項目一律不得標 green。 |
| Snyk | 第三方安全掃描服務。依賴掃描與金鑰掃描是兩種不同能力，只跑了前者不能說金鑰檢查通過。 |
| partial（部分可見） | 多篇一起發布時出現「A 已經是新版、B 還是舊版」這種對外可見的中間狀態；本專案不允許。 |

## Global Constraints

- 本目錄是**實作計畫**，不是應用程式、AWS 部署、瀏覽器驗收或產品核定證據。
- 唯一主來源是 [docs/design/training-kb.md](../../design/training-kb.md)；舊文件衝突時依該文件 §2 裁決。
- 模型固定為十個邏輯實體，包含 `TUTORIAL_VIEW`；十實體映到一張表，不是十張資料表。
- 資料層固定為一張 `training_kb`、唯一 `by_target` GSI 與 S3；不得自行增加 Neptune、OpenSearch、CloudFront、公開讀取 API、第四條教學 pipeline 或人工發布審核佇列。
- O1–O7（設計 §18 的七個待確認事項）都仍待實作階段的決策、整合驗證或維護者核定；計畫文字與假資料測試的綠燈都不能關閉它們。
- O2、O3、O6 是前期阻擋 gate。未通過時，依各 Phase 的停止條件保留可追溯 FAIL，不把限制改寫掉。
- O3 必須同時處理 DynamoDB、S3 公開切換與多篇原子發布的失敗切點；目前設計沒有宣稱已有可行解。
- Phase 24 只做最小頁面 renderer；完整 feedback widget 與下載流程留到 Phase 57。
- Phase 55 只用自含、明示為非核定的 fixture 驗證程式邏輯；Phase 56 才建立並等待維護者核定 O7 種子。
- 所有測試命令從 Phase 01 起統一使用 `uv run pytest`；不得混用裸 `pytest`、`python -m pytest` 或 `.venv/bin/python -m pytest`。Lint 與型別檢查同樣是 `uv run ruff check`、`uv run mypy`；唯一不加 `uv run` 的是 `cdk` 指令。
- 跨 Phase 的名稱、簽名、檔案路徑與 AWS 資源名稱一律以 [00A 共用契約與名詞](00A-共用契約與名詞.md) 第 3 節為準。最容易寫錯的三項：Step Functions 流程定義檔固定放 `infra/stepfunctions/<pipeline>/v<n>.json`；Lambda 只有 `training-kb-webhook`、`training-kb-import`、`training-kb-pipeline-task`、`training-kb-analytics` 四支；state machine 只有 `training-kb-ticket-analysis`、`training-kb-release-update`、`training-kb-feedback-review` 三條。Phase 文件與 00A 不一致時，改 Phase 文件。

## 先看懂整條路

```text
Batch B｜Writing、版本、發布與圖譜

                                                              v

Batch C｜Pipeline、接入、Rote、Ticket、Feedback
P29 -> P30 -> P31 -> P32 -> P33 -> P34 -> P35 -> P36
                                                       |
                                                       v
                   P37 -> P38 -> P39 -> P40 -> P41 -> P42 -> P43 -> P44

P45 -> P46 -> P47 -> P48 -> P49 -> P50 -> P51 -> P52
```

跨 Batch 的主要阻擋關係如下。**左邊的 gate 沒有真實證據，右邊整條路徑就不能開始。** 這張圖只說明依賴，不代表任何 gate 已經通過。

```text
P54   O4 邊界 ---> P55 規則驗證 ---> P56 O7 種子核定 ---> P58/P60 Demo 與最終證據
```

## 如何開始一個 Phase

1. 從本頁找到下一個 Phase；確認所有前置 Phase 的「完成清單」都勾完，且擋在前面的 gate 都有真實證據。
2. 先讀 [00A 共用契約與名詞](00A-共用契約與名詞.md) 中這個 Phase 的 owner 與消費名稱，再讀 [00B 需求覆蓋對照](00B-需求覆蓋對照.md) 第 2 節裡 primary Phase 欄寫著這個編號的那幾列。若一列都沒有（驗收型與打地基型 Phase 常見），就以本頁的「單一交付物」為範圍。
3. 只建立該 Phase「預計新增／修改」所列的檔案。那些路徑是未來目標；本計畫沒有宣稱它們現在存在。
4. 按 checkbox 做 TDD：寫測試 → 跑紅燈 → 最小實作 → 跑綠燈 → 提交（五個動作的白話說明在上面「TDD 的紅燈與綠燈」）。
5. Phase 01 建立環境後，測試命令固定為：

   ```bash
   uv run pytest <該 Phase 指定的測試路徑> -q
   ```

6. 遇到 gate FAIL 就停止依賴路徑，保留報告與重現指令；不得用改需求、加未授權服務，或放寬設計決策 F49（多篇一起發布時只要一篇失敗就整批不發布）來取得綠燈。
7. 把該 Phase 文件最後的「完成清單」逐條核對並勾完，才進下一個 Phase。

## 如何判定一個 Phase 完成

```text
文件 checkbox 全勾
        |
        v
指定測試真的執行且結果符合？ -- 否 --> 尚未完成
        |
```
