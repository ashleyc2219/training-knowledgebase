# 00A：共用契約與名詞

> 這份文件是 60 個 Phase 的**共用字典與契約總表**：跨 Phase 不可任意改名的介面、欄位、檔案路徑、S3 key、錯誤類別與 gate 語彙，全部集中在這裡。實作某個 Phase 前先查這裡確認名稱；審閱 Phase 文件時以這裡為唯一準則，兩邊不一致就改 Phase 文件，不改 00A。[00 總覽](00-總覽.md) 負責「做什麼、依什麼順序、在哪裡停」；[00B 需求覆蓋對照](00B-需求覆蓋對照.md) 負責「哪一條 Rule 由哪個 Phase 負責、用什麼斷言證明」；00A 只負責「叫什麼名字、長什麼樣子」。

---

## 1. 怎麼使用這份文件（新手）

這份文件不是教學，是查詢表。建議這樣用：

1. **開始一個 Phase 前**：在[第 6 節](#6-介面-owner-總表)找出這個 Phase 的 owner 名稱與它要消費的名稱，抄下確切簽名。Phase 文件的「固定介面」如果和第 6 節不同，**以第 6 節為準**，並到[第 8 節](#8-已知不一致與裁決清單給審閱者)確認是不是已知不一致。
2. **看不懂某個詞**：查[第 2 節名詞總表](#2-名詞總表)，每個詞都有一句白話與第一次出現的 Phase。
3. **要建立檔案**：查[第 3.2 節路徑總表](#32-目錄與檔案路徑總表)。表上寫 owner 的那個 Phase 才負責建立，其他 Phase 只能修改。
4. **要寫 item 或 S3 物件**：先讀[第 3.4 節](#34-s3-key-與-asl-檔案佈局)與[第 3.6 節](#36-嚴格模型規則與保留屬性)，這兩節有最容易踩的雷。
5. **要填模型欄位或流程 state**：實體與草稿模型的欄位查[第 5 節](#5-資料模型固定欄位)；三條 pipeline 的 Task 名稱、ASL state 名稱與可放進 state 的欄位查[第 7 節](#7-三條-pipeline-的-state-與-task-契約)。
6. **遇到失敗或不確定**：查[第 4 節](#4-錯誤與-gate-語彙)。哪個錯誤該丟、誰負責接、gate 沒過時該寫什麼句子，都在那裡。
7. **審閱 Phase 文件**：逐條跑[第 8 節](#8-已知不一致與裁決清單給審閱者)，「要修改的文件與位置」就是工作清單。

三個原則：**不得自行改名**（名稱由 owner Phase 決定）；**衝突時較早的 Phase 是 owner**（第 8 節有明文裁決的以裁決為準）；**不得把待確認寫成已完成**（O1–O7 只能由真實證據改變，文件文字與 mock 綠燈都不算）。

## 3. 全套共用約定

### 3.1 語言與指令

| 項目 | 固定寫法 | 說明 |
|---|---|---|
| 文件語言 | 繁體中文、台灣用語 | 程式識別字、指令、AWS 服務名維持英文。 |
| Python 版本 | Python 3.12 | 由 Phase 01 的 `pyproject.toml` 鎖定。 |
| 測試指令 | `uv run pytest <路徑> -q` | 不得用裸 `pytest`、`python -m pytest` 或 `.venv/bin/python -m pytest`。 |
| Lint／型別 | `uv run ruff check <路徑>`、`uv run mypy <路徑>` | 一律經 `uv run`。 |
| CDK CLI | `cdk synth`、`cdk deploy`、`cdk bootstrap`（**不加** `uv run`） | `cdk` 是 Node.js 套件，用 `npm install -g aws-cdk@2` 或 `npx aws-cdk@2`；只有 `cdk.json` 內部寫 `{"app": "uv run python -m infra.app"}`。 |
| 真實 AWS 測試 | 放 `tests/integration/`，標 `@pytest.mark.aws`，用 `uv run pytest ... -m aws` | **全套只有這一種機制**（D-41、D-64）：marker 由 P01 在 `pyproject.toml` 的 `[tool.pytest.ini_options] markers` 註冊，P01 建立的 `tests/conftest.py` 在環境變數 `TKB_RUN_AWS_INTEGRATION=1` 沒設時自動 skip 標了 `aws` 的測試，所以平常跑測試**不需要** `-m "not aws"`；P59 只負責貼標籤。 |
| 真實 Bedrock 測試 | 同上一列，**沒有第二種開關** | Bedrock 也算「需要真實帳號」，一樣是 `@pytest.mark.aws` + `TKB_RUN_AWS_INTEGRATION=1`；不得另外發明 Bedrock 專用的環境變數開關（D-41）。 |
| commit 訊息 | `feat(<scope>): <中文主旨>` | scope 用模組名，例如 `content`、`ingress`、`analytics`。 |

### 3.3 命名規則

- **裸 ID 與前綴 PK 分開。** 模型與流程只傳裸 ID（`Prepare`、`prepare-meeting@v2`、`R-007`、`t_881`）；只有 `keys.py` 可以加前綴。已帶前綴的字串再傳進 PK builder 一律拒絕。
- **entity 前綴清單**（item 的 `entity` 屬性值 = PK 前綴）：業務實體 `TUTORIAL`、`VERSION`、`STEP`、`FEATURE`、`TICKET`、`RELEASE`、`FEEDBACK`、`VIEW`、`RULE`、`PROC`；非業務實體 `OPS`、`CONFIG`、`SEQ`、`LEASE`。後四者不進 `Entity` union、不需要模型。
- **步驟編號一律叫 `number`**：`StepDraft.number`、`TutorialStep.number`、`StepHit.number`、`StepRewrite.steps[].number`、`StepConfirmation.confirmed_step_numbers`、`WeakDiagnosis.items[].number`。唯一例外是 `DiagnosisResult.step_indexes` 與 `RefinePlan.changed_indexes` 兩個既有欄位名保留（P46、P48 已消費），但它們裝的就是 `number` 的值。
- **StrEnum 成員大寫、值小寫**：`StepType.CLICK_UI = "click_ui"`、`TicketSource.GITHUB_ISSUE = "github_issue"`，其餘同法；程式可用 `StepType("click_ui")` 或直接字串比較。
- **`operation_id` 格式**：`operation_id_for(kind, canonical_id)` 固定回 `op-<kind>-<canonical_id>`，`<kind>` 是 `OperationKind` 的字面值，例如 `op-ticket-t_881`、`op-release-r_42`、`op-feedback-f_12`、`op-feedback-review-demo-2026-09-13`（feedback-review 的 canonical id 是 `f"{project_id}-{UTC 日期}"`，中間用 `-` 不用 `#`，見 §7 與 D-61）。`execution_name(operation_id)` 必須符合 `[A-Za-z0-9_-]{1,80}`；超長時以固定 UTF-8 SHA-256 截取並保留 kind 前綴。各 Phase 測試裡的 `op-1`、`op-17`、`op-gap-c12` 只是測試字串，正式路徑一律經 `operation_id_for` 產生。
- **正規化之前還沒有正式 operation**：webhook 收件到 `accept_*` 之間會先呼叫模型（Rote 的 Agent 回退），這段的 `CallTrace` 用臨時 ID `op-ingress-<來源投遞識別碼>`（GitHub 就是 `X-GitHub-Delivery` 的值），不經 `operation_id_for`、也不會寫成 `OPS#` item；正規化成功後才換成正式的 `op-<kind>-<canonical_id>`（P33、P37）。
- **`scan_entity` 掃得到邊**：`entity` 屬性值等於 PK 前綴，所以 `RULE#…` 的 `APPLIED_TO#` 邊、`TICKET#…` 的 `ASKS_ABOUT#` 邊、`FEEDBACK#…` 的 `REFERS_TO#` 邊、`VERSION#…` 的 `SUPERSEDES#` 邊都會跟著本體一起被掃出來。`scan_entity` 因此預設 `meta_only=True`，只回 `SK == META` 的 item；唯一要傳 `meta_only=False` 的是 `get_steps`，因為 **STEP 沒有 `META` item**（它的 SK 就是 `REFERENCES#<FEATURE PK>`）。簽名見 §6.3。
- **版本 ID**：`make_version_id(slug, number)` → `<slug>@v<n>`；`parse_version_id` 是它的反函式。永久失敗允許版號缺口，不得用 `v1..vN` 推算連號。
- **Feature PK 後綴固定**：`FEATURE#<建立時名稱>`，改名只動 `name` 與 `aliases`，不遷移 PK。
- **關係邊只有五種名稱**（設計 §9.2；邊的形狀固定是 `PK=起點`、`SK=<關係>#<終點 PK>`、`target=<終點 PK>`）：

  | 關係 | 起點 → 終點 | 誰寫 | 用途 |
  |---|---|---|---|
  | `REFERENCES` | STEP → FEATURE | P23 | 功能反查引用步驟；這也是 STEP 唯一的 SK，**STEP 沒有 `META` item**。 |
  | `SUPERSEDES` | VERSION → VERSION | P23 | 版本往前追溯。 |
  | `APPLIED_TO` | RULE → VERSION | P23（寫）、P28（重建／刪除） | 規則套用到哪些版本；`VERSION.rules_applied` 是權威，這條邊可重建。 |
  | `ASKS_ABOUT` | TICKET → FEATURE | P40（本文件 D-52 指派） | 工單指向功能，最多一條。目前 P05 宣告、P08／P27 讀取，但**還沒有任何 Phase 文件寫入**，P40 要補。 |
  | `REFERS_TO` | FEEDBACK → VERSION | P42 | 版本反查回饋。 |

  這五個名稱在 `keys.py` 以 `RELATIONS = frozenset({"REFERENCES", "SUPERSEDES", "APPLIED_TO", "ASKS_ABOUT", "REFERS_TO"})`（P05）集中宣告；不得自行新增 `HAS_VERSION`、`VIEWED`、`SUCCESSOR` 或 User／Project 邊。`Tutorial.successor` 存在 metadata item，View 靠欄位掃描而不建邊。
- **版本 `reason` 只有三種格式**（寫進 `TutorialVersion.reason`，測試要逐字比對）：`gap:<cluster_id>`（P40 的 CREATE）、`release:<release_id>`（P51 的 UPDATE、P26 被 Release 觸發的退役）、`feedback:<n> 則 <category>`（P46 的 REFINE，`<n>` 是去重後的證據筆數）。`reason` 屬於私有欄位，公開頁不顯示。

  site/index.html                                   站台索引         P24

- 上表最後一欄是**第一個寫出這個物件的 Phase**，不是 key helper 的 owner。三個組出公開 key 的 helper `site_key(version_id)`／`tutorial_index_key(slug)`／`site_index_key()` 依 D-54 全部由 **P24** 定名並放在 `training_kb.publishing`，P25、P26、P57 只消費；只有公開 diff 的 `site_diff_key(version_id)` 歸 P57。任何 Phase 都不得自己用 `PUBLIC_SITE_PREFIX` 接字串拼出這四個 key。
- `site_key(version_id) -> str` 回**不含** `site/` 前綴的相對 key（`tutorials/prepare-meeting/v2.html`）；公開物件 = `PUBLIC_SITE_PREFIX + site_key(...)`，私有 staging = `operations/<operation_id>/site/<site_key>`。
- `PRIVATE_TUTORIAL_PREFIX = "tutorials/"`、`PUBLIC_SITE_PREFIX = "site/"`、`SITE_PREFIX = "site/"`（P57 的別名，值必須相同）。
- P09 的 `PRIVATE_PREFIXES = ("tutorials/", "operations/", "stepfunctions/", "demo/previews/")` 只是測試核對清單；公開範圍由 bucket policy 的 `site/*` 決定。
- **ASL 檔案**：本地定義檔一律 `infra/stepfunctions/<pipeline>/v<n>.json`；部署前用 `put_object(..., if_none_match=True)` 把同一份 bytes 存成 S3 快照 `stepfunctions/<pipeline>/v<n>.json`。`infra/asl/<name>.asl.json` 這種寫法作廢。

`handlers/` 這個套件**只放這三支非 pipeline 的 Lambda 入口**（webhook、import、analytics）；三條 pipeline 的 `ticket_analysis_handler`／`feedback_review_handler`／`release_update_handler` 仍留在對應的 `pipelines/*.py`（D-25），它們在雲端是被共用的 `pipeline_task_handler` 分派到的，不各自部署成 Lambda。

環境變數一律 `TKB_` 前綴，`load_settings` 只讀這個前綴：`TKB_TABLE_NAME`→`table_name`（預設 `training_kb`）、`TKB_CONTENT_BUCKET`→`content_bucket`（預設 `training-kb-content`）、`TKB_AWS_REGION`→`aws_region`、`TKB_BEDROCK_REGION`→`bedrock_region`（缺值沿用 `aws_region`）、`TKB_GENERATION_MODEL_ID`→`generation_model_id`（O5 未通過不得填猜測值）、`TKB_EMBEDDING_MODEL_ID`→`embedding_model_id`（預設 `amazon.titan-embed-text-v2:0`）、`TKB_PROJECT_ID`→`project_id`（預設 `demo`）。非 `Settings` 欄位的執行期開關（`load_settings` 不讀它們，程式各自 `os.environ` 取用）：`TKB_FAULT`、`TKB_ENV`（P59 的故障注入）、`TKB_RUN_AWS_INTEGRATION`（真實 AWS 測試的唯一開關，見 §3.1）、`TKB_GITHUB_WEBHOOK_SECRET`（P30 `load_secret` 讀的 webhook 共享密鑰；**不是** `Settings` 欄位、不得寫進 `.env` 以外的地方，P60 的 `check_secrets` 核對表要列它）。

**時間一律 UTC ISO 8601，而且只到整秒**：`now_utc()` 回 `datetime.now(UTC).replace(microsecond=0)`（**去掉微秒**）；`to_iso(dt)` 只輸出 `2026-08-03T10:00:00Z` 這個形狀，遇到 `dt.microsecond != 0` 直接丟 `PermanentError`（明確拒絕，不靜默截斷）；naive datetime 一律拒絕。這樣 `view_pk`（P05 用三元組算 SHA-256）與操作紀錄（P10）的時間字串才只有一種形狀，重送才算得到同一個鍵。業務函式把 `now` 當參數傳，不在深層程式讀系統時鐘。

### 3.6 嚴格模型規則與保留屬性

```text
DynamoDB item 的屬性 = 模型欄位 + RESERVED_ATTRS，沒有第三類
  RESERVED_ATTRS = {"PK", "SK", "target", "entity", "_revision"}
        |
        v
get_meta(pk, Model) --> 去掉 RESERVED_ATTRS --> Model.model_validate(payload)
        |                                              |
        |                                     多一個欄位就 ValidationError
        v
item_to_model(item, Model) --> 同一套過濾，給 query_pk / scan_entity 的 raw item 用
```

- 十實體模型是 strict：**不接受模型以外的屬性**。不得為了方便在 item 上加 `step_count`、`retired_at`、`retired_reason` 這類欄位；需要保存的執行資訊一律寫進 operation 紀錄或私有 S3。
- `_revision` 是樂觀鎖版本號（樂觀鎖＝寫的時候附上「我讀到的版本」，別人先改過就寫不進去），由 `put_meta`／`update_meta` 維護、`get_meta` 濾掉。取值一律用 `Repository.revision_of(pk) -> int`。**唯一例外**：手上已經有整筆 raw item 時（例如剛用 `query_pk`／`get_meta_item` 讀回來），可以直接用同一次讀到的 `_revision` 當 `expected_revision`，不必再讀一次；語意與 `revision_of` 完全相同，只是少一次 read。
- 對 `query_pk`／`scan_entity`／`list_edges` 回來的 raw item **一律用 `item_to_model`**，不可直接 `Model.model_validate(item)`。
- `entity` 屬性值等於 PK 前綴（`parse_pk(pk)[0]`），`scan_entity("STEP")` 就是靠它篩選；屬性名固定就是 `entity` 這五個字母，不得自行加後綴或改名。
- **`entity` 相同的邊也會被掃到**：邊 item 的 PK 是起點，所以 `scan_entity("RULE")` 會一起撈到 `APPLIED_TO#` 邊。`scan_entity` 因此預設 `meta_only=True`（只回 `SK == META`），六個 `list_*` 靠這個預設自動過濾；**STEP 沒有 `META` item**（本體就是 `REFERENCES#` 邊），所以 `get_steps` 必須傳 `meta_only=False`。
- **模型欄位可以由鍵導出時，允許不落成 item 屬性**：例如 STEP 邊只存 `type` 與 `text` 兩個屬性，`tutorial_version` 與 `number` 由 PK（`parse_step_pk`）還原、`feature_id` 由 `target` 還原。這不算「少寫欄位」，是避免同一份資訊有兩份會不一致的副本；反過來「模型沒有的屬性」仍然絕對禁止。
- `OPS#`、`CONFIG#`、`SEQ#`、`LEASE#` 不走模型，用 `put_meta_item`／`get_meta_item` 這對原語讀寫。

### 3.7 Retry／Catch 參數

```text
一次 Task 的失敗路徑（設計 §14.2、§14.3）

Lambda 丟 TransientError -> ASL Retry: 等 1 秒 -> 等 2 秒 -> 仍失敗
Lambda 丟 PermanentError -> 不重試
                                 |
                                 v
                    Catch: States.ALL -> PipelineFailed (Fail state)
                                 |
                                 v
                    OperationCoordinator.fail(..., retryable=?)
```

- 每個 Task state 固定帶**兩個 retrier**（D-53），順序與內容逐字如下，兩條參數相同（等 1 秒、最多再試 2 次、每次等待時間乘 2）：

  ```text
  "Retry": [
    {"ErrorEquals": ["TransientError"],
     "IntervalSeconds": 1, "MaxAttempts": 2, "BackoffRate": 2},
    {"ErrorEquals": ["Lambda.ServiceException", "Lambda.AWSLambdaException",
                     "Lambda.SdkClientException", "Lambda.TooManyRequestsException"],
     "IntervalSeconds": 1, "MaxAttempts": 2, "BackoffRate": 2}
  ],
  "Catch": [{"ErrorEquals": ["States.ALL"], "ResultPath": "$.failure", "Next": "PipelineFailed"}],
  "TimeoutSeconds": 120
  ```

- **第一條**是我們自己的 `TransientError`：Python Lambda 沒接住的例外，Step Functions 看到的 `errorType` 就是類別名（**這件事由 P41 用 `get-execution-history` 實證**，實證前不得宣稱 Retry 一定命中）。**第二條**是 AWS SDK 端的 Lambda 服務錯誤（服務忙、節流、連線斷），它們不會變成 `TransientError`，少了這條就完全不重試。不要寫成 `TrainingKB.TransientError`（自訂錯誤名不加前綴）。
- `RETRY`（兩條 retrier 的 tuple）與 `CATCH` 由 P29 的 `pipelines/asl.py` 產出，P41／P48／P52 一律 `from training_kb.pipelines.asl import RETRY, CATCH, task_state`，**不各自寫一份**；`assert_safe_asl` 逐字檢查前兩條 retrier 相同，且沒有任何 retrier 涵蓋 `States.ALL`。
- `PermanentError` 刻意不進 `ErrorEquals`：資料確定不合法時直接進 Catch。
- **只有一層管理重試**：Lambda 內不自行 retry、SDK 不疊 retry，避免次數相乘。
- Choice state **沒有** Retry／Catch 是正確的，但必須有 `Default` 分支。
- Lambda Task 一律用**直接函式 ARN**（`"Resource": "<function arn>"`），不用 `arn:aws:states:::lambda:invoke` 信封。事件封套因此寫在 `Parameters` 裡（`{"pipeline": ..., "task": ..., "state.$": "$"}`），**沒有** `Payload` 外層；task result 就是函式輸出。

其餘執行參數固定取自設計 §14.3，是**建議起點**而不是已核定門檻，O5 實測後才可調整：

| 項目 | 固定值 | 誰使用 |
|---|---|---|
| 判斷類模型 | `max_tokens` 512、`temperature` 0.1 | P17、P18、P39、P43、P45、P47、P50、P55 |
| 教學寫作模型 | `max_tokens` 2048、`temperature` 0.1；截斷即驗證失敗、不發布 | P17、P40、P46、P51 |
| Bedrock 連線／等待 | 連線 2 秒、等待回應 30 秒 | P15 的 Bedrock adapter |
| Lambda／Task 時限 | 一般 Lambda 90 秒；ASL Task `"TimeoutSeconds": 120`（常數 `TASK_TIMEOUT_SECONDS`，P29 產出） | P41、P48、P52 |
| 公開 webhook | 整個 handler 8 秒；優先於上面兩列 | P30 |
| 每日 Review | UTC 00:30（`cron(30 0 * * ? *)`） | P48 |

Titan 是 embedding API，**不接受** `max_tokens`／`temperature`（見 §6.5）。

## 4. 錯誤與 gate 語彙

### 4.1 錯誤類別

```python
class TransientError(Exception): ...
class PermanentError(Exception): ...
class IngressError(PermanentError):
    message: str; fields: tuple[str, ...]
class ContentError(PermanentError): ...
class CoordinationError(Exception): ...
class PublishError(Exception): ...
class ObjectAlreadyExists(PermanentError): ...
```

| 類別 | 意思 | 誰拋 | 誰接 |
|---|---|---|---|
| `TransientError` | 暫時性服務故障，重送有機會成功。 | `Repository`（S3 409、DynamoDB 取消）、`Writer`（SDK 暫時錯誤）、`Publisher`（交易非條件式取消） | ASL Task 的 `Retry`；`run_sequence` 不自行重試。 |
| `PermanentError` | 確定不合法或確定不會成功，重送沒有意義。 | 幾乎所有模組 | ASL 的 `Catch` → `PipelineFailed`；`OperationCoordinator.fail(retryable=False)`。 |
| `IngressError` | 接入資料缺欄位或值不合法；`fields` 是**不合法欄位名的 tuple**。 | `validate_ticket`／`validate_release`（P31）、`validate_feedback`／`validate_view`（P42）、`assert_accepts_feedback`（P26，教學已退役時 `fields=("tutorial_version",)`） | webhook handler 回失敗；固定匯入回 `ImportResult(status="rejected")`。P42 一律呼叫 P26 的 `assert_accepts_feedback`，不自己再寫一次 retired 判斷。 |
| `ContentError` | 內容不合規：段落缺失、步驟編號不連續、每步不是恰一個 Feature、未命中步驟被改動。**資料一致性問題也算**（找不到該篇教學、`current_version` 指到別篇的版本、版本全文讀不回來）。 | `validate_content`、`parse_markdown`、`assert_unchanged`、業務 validator | 建版流程中止，不產生版本。它是 `PermanentError` 子類，行為與 `PermanentError` 完全相同，只是訊息更好讀。 |
| `CoordinationError` | 操作紀錄或樂觀鎖不一致：找不到 operation、狀態轉移不合法、同 operation 取到不同版號、`create_only` 撞鍵、`_revision` 過期。 | `OperationCoordinator`（含 `next_sequence` 的 CAS 重試超過 8 次）、`allocate_version`、`Repository.put_meta`（`create_only=True` 撞鍵）／`update_meta`（`expected_revision` 過期）／`revision_of`（item 不存在） | 停止該路徑並保留可追溯紀錄；屬於 O2 範圍。**它不是 `TransientError`**，呼叫端不得自動重試——要重來必須重新讀取現況再決定。 |
| `PublishError` | 發布前提不成立或中途失敗：版本不完整、`current_version` 已被改、staging 與 S3 bytes 不同。 | `Publisher.prepare`／`inspect`／`commit`、`promote_site_objects` | 呼叫端停止本批發布；`site/` 不得留下新檔；屬於 O3 範圍。 |
| `ObjectAlreadyExists` | `put_object(..., if_none_match=True)` 遇到同 key 已存在（S3 412）。 | `Repository.put_object` | `put_private_artifact` 用**型別**判斷是否為同操作重送，不靠訊息字串。 |

`InjectedFault`（P59）繼承 `TransientError`，所以注入的失敗會走完 Retry 再進 Catch，把整條失敗路徑走一次。

- `ProvenWorkflow.domain`／`adapter` 是**本計畫選擇**（對應 O2／D19：來源脈絡需要持久化）。P33 的「adapter 保存在 PROC 範圍欄位」、P34 的同 domain+adapter 比較、P08 的 `list_procs(domain, adapter)` 都依賴它們。
- `AuthoringRule.applies_when` 型別是 `StepType`（單一等值條件）。模型輸出 schema `RuleProposal.applies_when` 是**字串**（`"click_ui"`／`"input"`／`"read"`），P47 驗證後轉成 `StepType` 才存入；P19 的篩選寫成 `rule.applies_when == step_type`。不得用 `"step.type == click_ui"` 字串或 `{"step.type": "click_ui"}` dict。
- `AuthoringRule` **沒有** `validated_at` 欄位；最近驗證時間存私有 S3 `operations/rules/validated_at.json`，只有 P55 寫。
- **可為 `None` 的欄位在模型層一律給預設值 `None`**（`Release.source_event_id`／`old_name`／`new_name`、`Feedback.category`／`comment`／`rating`／`ts`）。這不代表它們可有可無：「必填但值可以是 null」由**入口** `validate_release`／`validate_feedback` 檢查「這個 key 有沒有出現在 payload 裡」，模型層只管型別。兩層分工固定是「模型寬、入口嚴」。
- **模型層三條額外限制**（本計畫選擇，P04 用 pydantic validator 實作，D-66）：
  1. `AuthoringRule.evidence` 至少 5 個**不同**的 Feedback ID（少於 5 或有重複就 `ValidationError`）。P47、P55、P56 的 fixture 與種子都要給滿五個，`propose_candidate` 的前置檢查只是為了先丟出好讀的 `ContentError`，不是唯一防線。
  2. `Feedback` 至少要有 `rating`／`category`／`comment` 其中一項（`carries_signal`）；三個都是 `None` 的回饋沒有任何訊號，直接拒絕。
  3. `Feedback.rating` 在模型層就拒絕 `bool`（`True` 在 Python 裡是 `1`，會被誤當評分）與 1..5 以外的值（`rating_is_strict_int`）。
- `Feedback.rating` 在模型是 `int | None`（歷史匯入可能缺評分），**固定匯入入口比模型嚴格**：`validate_feedback` 要求 1..5 的嚴格整數並排除 `bool`。`rating is None` 的回饋不進平均的分子也不進分母（本計畫選擇）。
- `Feedback.ts` 可為 `None`，缺值記匯入時間並明講「非使用者實際提交時間」；`TutorialView.ts` 必填。`Ticket.feature_ids` 最多一個元素。關聯欄位一律存裸 ID。

- `record_version` 是 **write-once**：同一個 `operation_id` 再寫**同一個** `version_id` 是 no-op，寫**不同**的 `version_id` 丟 `CoordinationError`。這是 O2「同 operation 重送取得同版號」的機制本體，`allocate_version`（P20）靠它擋住分叉（P10 review 提出，P11 實作，commit `4897a6c`）。
- `OperationStatus` 的 `normalized`／`started` 在 P10／P11 是**保留值**：目前沒有任何公開方法會寫入它們（`accept` 寫 `accepted`、`complete` 寫 `done`、`fail` 寫 `failed`），要不要推進由接受路徑的 owner **P32** 裁決（2026-09-14 controller 裁決）。
- 儲存鍵 `OPS#<operation_id>`、`SEQ#<scope>`、`LEASE#<scope>`，SK 一律 `META`；大型內容放 `operations/<operation_id>/<name>.json`，紀錄只存 ref。
- **三個協調方法都是 `OperationCoordinator` 的方法**（P11 加在 P10 的 class 上，不是模組函式，也不新增 `Repository` 原語）：
  - `next_sequence(scope)` 用 **compare-and-swap** 實作——`get_meta_item` 讀目前值，`update_meta(..., expected_revision=剛讀到的 `_revision`)` 寫回加一；被別人搶先就重讀再試，上限由常數 **`SEQUENCE_ATTEMPTS = 8`**（P11）控制，超過丟 `CoordinationError`，**不無限重試**。取號 scope 固定 `SEQ#PROJECT#<project_id>`。
  - `acquire_lease`／`release_lease` 的 scope 固定 `LEASE#TUTORIAL#<slug>`（呼叫端傳 `TUTORIAL#<slug>`，`LEASE#` 由 P11 自己補）。**租約只是「同時只有一個人在做」的暫時標記，不是接受順序，TTL 也不保證準時解鎖**。
  - `OperationRecord.accept_seq` 才是接受順序，是**專案層級**的單調遞增序號（同一個 `project_id` 共用一條號），由 `accept` 第一次寫入時取號；`duplicate` 不重新取號。
- O3 切點名稱有兩套，**刻意不統一**（一套是 gate spike 的觀察點，一套是故障注入點），對照表見 §6.11。
- **續跑分支**：`accept` 回 `duplicate` 但目標物件其實不存在時，呼叫端要補寫，避免「OPS 已寫、item 未寫」的丟資料視窗（P42）。
- gate 工具：P11 的 `O2Case`、`O2CaseResult`、`run_o2_case(case, *, table, region)`、`o2_verdict`、`render_o2_report(results, *, run_id, table, region)`（腳本 `infra/scripts/o2_report.py`）；P12 的 `O3CutPoint`、`PublicView`、`CutPointResult`、`observe(slugs, *, table, bucket)`、`is_partial(views, *, expected)`、`run_cut_point`、`o3_verdict`、`render_o3_report(results, *, run_id, table, bucket, region)`（腳本 `infra/scripts/o3_report.py`，**不開 `tests/spikes/` 目錄**）。

- **state 只放 ID、S3 ref 與小型判斷結果**，不放工單全文、教學全文、Release evidence 原文、回饋留言或向量陣列（設計 §14.3）。需要全文時由 Task 自己用 ref 讀。
- **ASL input 有兩種形狀**：
  - `ticket-analysis` 與 `release-update` 由 `PipelineStarter.start` 啟動，input 固定只含 `operation_id`、`project_id`、`input_ref`。
  - `feedback-review` 是**例外（D-61）**：它由 EventBridge Scheduler（每天 UTC 00:30）或 Demo 的 `trigger-review` 手動觸發，**不經 `PipelineStarter`**。input 逐字只有 `{"mode": "formal"}` 或 `{"mode": "demo"}`；`project_id` 可選，缺值用 `Settings.project_id`；**不帶任何「排程時間」欄位**（早期草稿寫過的那個欄位已作廢，時間一律 `deps.now()`）。`operation_id` 不由呼叫端給，由 `ListTargets` 呼叫 P48 的 `review_operation_id(state, deps)` 產生：`operation_id_for("feedback-review", f"{project_id}-{UTC 日期}")`，例如 `op-feedback-review-demo-2026-09-13`。canonical id 用 `-` 串接（不用 `#`），才不會超長而走 `execution_name` 的 SHA-256 截取；Demo 的 execution name 也用同一個 `operation_id` 算出來。
- **一個 operation 只能對應一篇教學的一個版本**（`OperationRecord.version_id` 是單值）。因此凡是「一次改很多篇」的流程，一律先建 **per-slug 子 operation**，再各自 `allocate_version`（D-59）：
  - REFINE（P46／P48）：每個 `WeakTarget` 先用 `refine_operation_id(version_id, category, ids)` → `operation_id_for("feedback", 證據指紋)` `accept` 一個子 operation。跨日同一組證據會撞到同一筆 `OPS#`，這正是 F23 要的去重。
  - Release UPDATE（P51／P52）：每篇用 `operation_id_for("release-update", f"{release_id}--{slug}")` 先 `accept` 再 `allocate_version`。
  - 父 operation（`op-feedback-review-…`／`op-release-…`）只負責整批的追溯與 `input_ref`／`result_ref`，本身**不**持有 `version_id`。
- `training-kb-import` 同時處理 Feedback／View 的固定匯入，**那條路徑只寫 DynamoDB 與 S3，不啟動任何 pipeline**（設計 §5：Feedback／View 走固定保存路徑，不經 Rote 也不建版本）。
- 每個 Task 的 `Retry`／`Catch` 見 §3.7；Choice state 沒有 Retry／Catch，但必須有 `Default`。
- `UpdateAliases` 排在 `PublishBatch` 之後（設計 §7.4：寫下一版、diff、reason，完成後才更新 aliases）；`kind=changed` 時它原樣回傳 state。
- 本地 ASL 檔 `infra/stepfunctions/<pipeline>/v1.json`；部署前先把同一份 bytes 用 `put_object(..., if_none_match=True)` 存成 S3 快照 `stepfunctions/<pipeline>/v1.json`。
- `Catch` 之後不得產生新版本；失敗一律經 `OperationCoordinator.fail(...)` 留下可追溯紀錄。
