# 00B：需求覆蓋對照

> 這份文件把十三份 `.feature` 的 **147 條 Rule** 逐條對到 60 份 Phase 文件：每條 Rule 有且只有一個 **primary Phase**（唯一負責寫出直接 assertion 的 Phase），其餘牽涉到它的 Phase 一律列為「其他相關 Phase」。新手的用法是：拿到一個 Phase 編號，先在第 2 節搜尋這個編號出現在哪幾列的 primary 欄，那就是你這個 Phase 一定要寫出可執行斷言的需求；出現在「其他相關」欄的，你只要不破壞它、必要時引用即可，不需要重複寫 assertion。審閱者的用法是：從第 3 節開始看，先確認沒有 Rule 無人認領、沒有兩份文件同時宣稱 primary、沒有引用錯的 Rule 原文。

與另外兩份總表的分工：[00 總覽](00-總覽.md) 決定「做什麼、依什麼順序做、何時可以停」；[00A 共用契約與名詞](00A-共用契約與名詞.md) 決定「跨 Phase 的名稱、簽名與欄位歸誰所有」；本文件只決定「每條需求由誰證明、用什麼證明」。三者衝突時，Rule 原文以 [功能規格目錄](../../spec/features/) 為準，責任模組以 [Training KB 設計 §20](../../design/training-kb.md) 為準，Phase 範圍以 [00 總覽](00-總覽.md) 的「單一交付物」為準。

本文件只是對照表。表格裡的測試檔路徑原本是**實作時預計建立**的目標；「有對應」只代表「有一個 Phase 負責寫出這條 Rule 的直接 assertion」，不代表該 assertion 已經執行或通過。O1–O7 的狀態一律以 [00 總覽](00-總覽.md) 的 gate 表與 [00A 第 4.2 節](00A-共用契約與名詞.md) 為準，本文件不宣稱任何 gate 已通過。

## 2. 逐條對照

欄位說明：**Rule #** 是該 feature 檔內的編號（不是全域編號）；**Rule 原文**逐字照 `.feature` 原檔；**primary Phase** 只有一個；**其他相關 Phase** 只寫編號；**可觀察 assertion** 指出哪個測試檔、哪個測試函式或哪個可見結果證明它，一律寫成一句具體的話，不寫「見該 Phase」；**狀態**原本有 `有對應` 與 `待補：primary 為 Phase NN` 兩種；三條待補的 Rule 都已在對應文件補上 Task（見第 3.1 節），所以現在 147 條全部是 `有對應`。再提醒一次：`有對應` 只代表「有一份 Phase 文件負責寫出這條 Rule 的直接 assertion」，不代表該 assertion 已經執行或通過。

「Rule 原文逐字」有一個排版例外：三條原文帶角括號佔位符的 Rule（`RUN` Rule 10、`VER` Rule 5 與 Rule 7，含 `<pipeline>`、`<slug>`、`<n>`）把路徑用行內程式碼包起來。不包的話 Markdown 會把 `<slug>` 當成 HTML 標籤吃掉，畫面上會變成 `tutorials//v.md`；反引號內的字元與 `.feature` 原檔逐字相同。
