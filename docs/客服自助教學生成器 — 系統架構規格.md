客服自助教學生成器 — 系統架構規格
專案代號：Self-Improving Support Tutorial Generator 黑客松：Data and AI Hackathon: From Memory to Muscle Memory（Compound Agents 主題） 核心價值主張：客服系統隨著處理的票單越多，越懂得自動生成教學文章攔截重複問題，讓自動解決率（deflection rate）隨時間持續上升。

> **現行設計（2026-09-11）：** 產品是**單一 Agent** 的客服教學生成器，不是 MCP、也不是 platform。左餵票、中寫教學、下看曲線。真人只填「這張票怎麼解」，沒有教學人員清單；LLM 收成 Tutorial 五欄後直接發布。Deflect = 已有教學才回連結（擋票發生在下一張票）。轉真人 = 還沒教學；同類解完 ≥ 3 才 CREATE v1。畫面與一句話架構見 `docs/design/architecture.md`；完整 design 見 `docs/design/showme.md`。下列正文是 Clarify 前的產品主軸來源，其中人工審核佇列、必須操作產品 UI、Slack 入庫、先備圖譜邊、教學影片、SLA 監測已被 Clarify 推翻，以 `docs/spec/` 為準。

二、各層職責
🧩 Cognee.ai — 記憶建構層
輸入：歷史已解決的客服票單（顧客問題＋客服解決步驟）、產品文件/API 說明、Slack Q&A。

處理：透過 ECL pipeline（Extract, Cognify, Load）把雜亂文字拆解成「顧客」「問題類型」「解決步驟」「產品功能」等實體，並標出彼此關係（例如「這個問題的解法，前提是要先懂某功能」）。

輸出：結構化知識圖譜（問題—解法—先備知識的關係網）。

判斷依據：每一篇教學文章都要能連回它所引用的具體產品功能節點，這是後續「版本更新偵測」能運作的基礎。

🗄️ HydraDB — 記憶儲存層
負責：把 Cognee 建出的知識圖譜持久存放，並存放每篇已生成教學的內容版本、教學與問題類型的對應關係、以及回饋成效紀錄。

查詢型態：多跳查詢（Cypher），例如「這個新問題的先備知識，有沒有現成教學可以連結」「哪些教學文章引用了某個剛更新的功能」。

關鍵角色：整個系統「記憶不會重置、跨 session 持續累積」的核心，也是 self-learning 中「知識覆蓋範圍自動擴張」的落點。

⚡ hotdata.dev — 即時查詢層
負責兩件事：

即時業務分析：查詢目前哪一類問題票量暴增、哪些問題完全沒有對應教學、SLA 快超時的類別是什麼，並計算 deflection rate（自動解決率）這條核心 demo 曲線。
事件監測（輪詢機制）：對「票單表」和「模擬 changelog 表」做定期輪詢查詢（WHERE created_at > 上次檢查時間）。新票單進入 Ticket；新 changelog 列寫入 Release（processed_at 為空），之後才由「依 Release Note 更新 Tutorial」做 UPDATE / RETIRE。不需要另外架 webhook，直接用 hotdata.dev 的即席查詢把產品變更定期更新到資料庫。
🚀 RocketRide.ai — 動作／協調層
負責三件事：

實際操作產品介面或呼叫 API 把問題解決一遍，確保後續生成的教學步驟是「真的驗證過」，不是憑空想像。
呼叫 LLM 生成教學文章草稿（發布前先進入審核佇列）。
當新票單匹配到已有教學的問題類型時，自動回覆顧客教學連結，不升級給真人客服；若無匹配，正常轉真人處理。
決策依據：讀取 HydraDB 的歷史記憶 ＋ hotdata.dev 的即時狀況，決定下一步動作。

🔁 Modiqo.ai (Rote) — 肌肉記憶／可靠性層
負責：捕捉 RocketRide 第一次成功處理某類問題的完整步驟序列（API 呼叫、順序、參數），固化成確定性、可重放的流程。

重放邏輯：下次遇到同類型問題，直接重放已驗證的步驟，不用讓 LLM 重新推理——這是系統從「每次都要想」進化到「直接套用答案」的關鍵，也是 self-learning 最直接、最好量化展示的部分（見下方「重放解決率」指標）。

額外用途：捕捉到的步驟序列可以重播＋錄影，一魚兩吃變成教學影片素材（stretch goal）。

🛡️ Snyk — 資安層（非核心資料迴圈，但影響總分）
負責：掃描團隊自己寫的自動化程式碼與後端服務，確保沒有安全漏洞。與功能迴圈無關，但漏洞會直接扣分，建議整個開發過程中隨時掃描，不要留到最後才做。

三、資料策略
歷史種子資料：優先使用公開資料集（如 Bitext Customer Support Dataset、Kaggle Customer Support Ticket Dataset 等），挑 3–5 個主打類別，每類抓 2–3 筆餵給 Cognee 提前建圖。

即時 demo 資料流：同一批公開資料集裡，同類別剩下的資料先扣住不用，demo 現場依序餵入，刻意安排同類別重複出現，保證 deflection rate 曲線會如預期上升，而不是隨機賭運氣。

補強原則：只有在某類別筆數不足或「解決方案」欄位太簡略時，才用 LLM 針對該類別「模仿既有真實資料的語氣格式」局部補寫或擴寫，而不是整批重新生成，避免跟真實資料風格脫節。

四、Self-Learning 的三個具體落點
重放解決率上升（Modiqo/Rote）：靠重放而非重新推理解決的票單比例，隨處理過的類型增加而上升。這是最推薦的 demo 主軸指標。
知識圖譜覆蓋範圍擴張（Cognee/HydraDB）：圖譜節點數/關係數隨時間增加，代表系統「懂」的問題空間自動變大。
教學品質的結果回饋修正：追蹤顧客看完教學後是否又開新票單，作為教學是否有效的訊號，觸發重新生成或標記人工審核——這是最能展現「判斷力真的變好」而不只是「資料變多」的部分。
提醒：單純把資料存進 HydraDB 不算學習，那只是記憶；學習必須能在某個可觀察指標上隨時間產生看得見的變化。

五、Demo 主軸建議
8 小時 demo 現場流程：先用歷史種子資料離線建好圖 → 依序餵入預先安排好的「模擬即時票單」，前幾筆同類別問題轉真人處理並生成新教學 → 同類別後續票單自動命中攔截 → 現場展示 deflection rate 曲線上升＋重放解決率上升＋（如有時間）一筆模擬 changelog 觸發教學自動更新的畫面。
