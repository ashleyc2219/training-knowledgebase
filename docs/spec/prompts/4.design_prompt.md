# Design：從已釐清規格產生客服自助教學生成器的 canonical design

## 任務

你是一位資深工程師。請依 formulation、discovery、clarify 三個階段的輸出，建立 **客服自助教學生成器（Self-Improving Support Tutorial Generator）** 的 canonical design。

本專案是 Data and AI Hackathon（2026-09-11，AWS Builder Loft，8 小時）的參賽作品。產品主軸是 **客服 deflection**：顧客票單（Ticket）聚成問題類型（UserProblem）→ 產生 Tutorial → 同類新票自動回覆教學連結 → 評分與再開票驅動 REFINE；Release Note 驅動 UPDATE / RETIRE；成功攔截流程由 Workflow（Rote）重放。Tutorial 生命週期 **CREATE / UPDATE / REFINE / KEEP / RETIRE** 是內核。

Self-learning 的定義是 *past outcomes change future system behavior*，不是 fine-tuning。Demo 要看得見 deflection rate、重放解決率、圖譜覆蓋隨時間變化。

本階段只做設計文件，**不實作 production code、不產生 implementation plans、不改規格**。唯一允許寫入的輸出是：

`docs/design/tutorial-generator.md`

請使用繁體中文與台灣常用技術用語。Repo root：`AWS-Hackathon/`（本檔所在 repo）。路徑一律用相對 repo root 的寫法，不要寫其他 repo（例如 `hackathonQoder/`、`18652FSE/`）的絕對路徑。

## 1. 任務模式與完成條件

模式：spec-first + hackathon-scoped application design。

完成條件：

1. 完整盤點第 2 節指定來源，而不是只讀檔名或 `design-draft.md` 標題。
2. 分清楚 **hackathon / 產品約束**（不可違反）、**clarified decision**（已定案）、**design decision**（本文件所做的選擇）與 **open question**（尚未定案）四種來源層級，每一項設計都要能被歸類。
3. 對互相衝突的敘述做單一、可追溯的裁決。`design-draft.md` 與產品架構規格草稿早於 clarify；被 clarify 推翻的敘述以 clarify 與現行 `erm.dbml` / `.feature` 為準。
4. 產生可直接用來拆 8 小時實作切片與撰寫驗收測試的設計文件。
5. 不把規劃中的目錄、ASCII 圖、`docs/design/architecture.md` 草圖或文件敘述誤寫成已實作。目前 repo **幾乎只有 docs**，沒有 entry point、依賴或測試。
6. 不引入 MVP 以外的能力。MVP 只保證一條可 demo 的學習迴圈：種子建圖 → 餵票 → 無教學則 escalated／達門檻 CREATE → 同類新票 deflected → Rote 重放 → Feedback／Release 觸發 REFINE 或 UPDATE／RETIRE → 三條學習指標上升。

Hackathon 原則：能 demo「同類票從轉真人變成自動攔截、曲線上升」就好。怪輸入、完整列舉、正式站、多租戶、人工審核佇列，能不做就不做。不要為尚未發生的正式產品、教學影片、複雜 dashboard 做架構。

## 4. 強制設計決策

除非上述來源有更新且有明確證據，design 必須保持下列決策不變。

### 4.1 Hackathon / 產品約束（違反即超出 MVP）

- **形態：** 單一 Agent 的客服 deflection 教學生成器。不是 MCP server、不是 multi-agent platform、不是客服總機。
- **五層都要真的在做事**（評審會查，不可只 import 一次）：

  | 層 | 工具 | 本專案負責 |
  |---|---|---|
  | Memory 建構 | Cognee（ECL） | Tickets / Release Notes / Tutorial / Feedback → 實體與關係（`asks_about`, `explains`, `refers_to`, `changes`, `supersedes`） |
  | Memory 儲存 | HydraDB（OpenCypher） | 跨 session 的知識圖譜與 Tutorial 版本；多跳查詢「哪些 Tutorial 受這次 Release 影響」 |
  | Live 分析 | hotdata.dev（SQL） | `AVG(rating)`、feedback_count、ticket counts、版本間效果比較；輪詢新票／changelog |
  | Motion / 協調 | RocketRide | 單一 Agent 的三條 pipeline：Ticket Analysis / Release Note Update / Periodic Feedback Review；以及自動回覆顧客 |
  | Muscle memory | Modiqo Rote | 第一次成功的攔截流程之後直接重放 |
  | 安全 | Snyk | 掃描依賴與原始碼；不把 key 寫進 repo |

- **領域資料：** Bitext Customer Support 公開資料集。主打 UserProblem topic = `cancel_order` / `track_refund` / `change_shipping_address`。貫穿 Tutorial：`tutorials/cancel-order.md`，Step 3 `Click "Cancel Order"` → Release Note 更名 → `Click "Cancel Purchase"`。顧客範例：`alice@example.com` / `bob@example.com`。
- **Tutorial 建立即 published**（保留 `status`：draft / published / retired）。不做人工審核佇列。
- **回饋雙訊號：** 顯性 `Feedback`（rating / category / comment）＋隱性再開票（`Ticket.reopened_from_ticket_id`）。再開票不寫進 rating，本輪不直接觸發 REFINE。
- **Release Note 只驅動 UPDATE / RETIRE**；CREATE 只由分析 Ticket 決定。輪詢 changelog 入庫與處理是兩個 Feature。
- **Rote 只重放攔截流程**（匹配 UserProblem → 取 published Tutorial → 回覆 → 更新 Ticket），以 UserProblem 為鍵。不重放「解票步驟」、不產教學影片。
- **Bitext 沒有可操作產品：** 建立 Tutorial **不需**先實際操作產品或 API。教學來源是已解決票的 `resolution_steps`。
- **範圍外（不做）：** 人工審核佇列、SLA／票量暴增監測、Slack 輸入、Customer 表、先備知識圖譜邊、教學影片、複雜 dashboard、多服務／K8s／message queue。
- **狀態與儲存：** 9 表是邏輯模型。跨 session 記憶在 HydraDB；即時聚合與輪詢在 hotdata。不要另發明第 10 張業務表。
- **秘密：** `.env` 的 `ROCKETRIDE_URI` / `ROCKETRIDE_APIKEY` 只給 dev；deploy 只能用 `ROCKETRIDE_DEPLOY_*`。design 階段不安裝套件、不 deploy、不啟動服務。

### 4.2 規劃中的系統切分（不可先發明另一套）

design 依此切模組邊界，**目錄尚未存在**，不要改成 microservices：

```text
AWS-Hackathon/
├── docs/spec/                      規格與本 prompt
├── docs/design/tutorial-generator.md   本階段唯一輸出
├── tutorials/                      產出的教學檔（如 cancel-order.md）；尚未存在
└── （實作目錄由 design 第 5 節定義，須對應五層，不得拆多服務）
```

資料流（單向為主，學習結果寫回）：

```text
種子／新票／Release／Feedback
        → Cognee 建圖
        → HydraDB 持久化圖譜與 Tutorial 版本
        → hotdata 輪詢與算指標
        → RocketRide 決策（CREATE / UPDATE / REFINE / KEEP / RETIRE / deflect / escalate）
        → 成功攔截由 Rote 捕捉；下次重放
        → 新學習寫回 HydraDB／ERM 對應欄位
```

### 4.3 已釐清的規格決策（clarify 定案，不得推翻）

撰寫時以各檔「解決記錄」與 `決策總表.md` 為準；下列是 2026-09-11 已 resolved 的摘要，若與檔案衝突以檔案為準。

**訊號 → 動作（門檻已定案，寫程式直接用）**

| 訊號 | 決定 |
|---|---|
| 新票（`status = open`）：其 `user_problem_id` 已有 `status = published` 的 Tutorial | deflected（回覆 `current_version`；第一次成功即捕捉 Workflow，之後 `replay_count` +1） |
| 新票：無 UserProblem／無 published Tutorial／同顧客同問題再開票 | escalated（再開票另設 `reopened_from_ticket_id`） |
| 分析 Ticket（只看 escalated / resolved）：同 `user_problem_id` ≥ 3 張且無 published Tutorial | CREATE（Tutorial v1 即 published；TutorialVersion 五欄必填） |
| 輪詢 changelog（`created_at` > 上次檢查）：新列寫入 `Release`，`processed_at` 為空 | 入庫（相同 content + created_at 不重複；本步不 UPDATE / RETIRE） |
| Release Note：`ReleaseFeatureChange` 命中 `Tutorial.feature_id`，renamed / changed | UPDATE（新版本、`Feature.name` 改新名、`processed_at`） |
| 同上，deprecated / removed | RETIRE（`status = retired`、`is_obsolete`） |
| 定期 Feedback Review（只算 `current_version`）：avg < 3.5 且 ≥ 3 筆且同 `feedback_category` ≥ 2 筆 | REFINE（新版本＋`reason`）；否則 KEEP；`is_possibly_outdated = true` 本輪 KEEP |
| 學習指標 | deflection rate = deflected/(deflected+escalated)；重放解決率 = Σreplay_count/deflected；圖譜覆蓋 = 有 published Tutorial 的 UserProblem / 全部 UserProblem |

**資料與生命週期**

- 9 表：Ticket, UserProblem, Feature, Tutorial, TutorialVersion, Feedback, Release, ReleaseFeatureChange, Workflow。不建 Customer、ProductDocument。
- Tutorial 版本是快照：內容五欄只在 `TutorialVersion`；`supersedes_version` 只指同篇上一版；`Tutorial` 只存身分、`status`、`current_version`、旗標與 `last_action`。
- Feedback 參照 `TutorialVersion`。Ticket **沒有** `analyzed` 狀態。
- `UserProblem.topic` 全域唯一；Tutorial 1:1 UserProblem；Workflow 1:1 UserProblem。
- `is_obsolete = true` ⇒ `is_possibly_outdated = false`、`status = retired`、`last_action = RETIRE`。
- `status = published` ⇒ `current_version` 有值。`last_action = CREATE` ⇒ `current_version = v1`。
- REFINE 與 UPDATE 同時命中同一篇：先 UPDATE，REFINE 等下一輪。
- 失敗一律規格語意 `Then 操作失敗`；design 需指出由哪一層回傳失敗，不得發明規格沒有的錯誤碼 excelsheet。

**Demo 常數**

- 資料集：`bitext/Bitext-customer-support-llm-chatbot-training-dataset`（`instruction` / `category` / `intent` / `response`）
- Feature 名稱：`Cancel Order`、`Track Refund`、`Change Shipping Address`
- Feedback 貫穿：v1 avg 2.9 → v2 avg 4.4（Step 3 被抱怨）

### 4.4 預設 design decision（非 clarify 定案，可重新論證）

以下可在設計文件中改採其他做法，但**必須標示為 design decision 並附理由**，不得默默改。

- 單一 RocketRide Agent，三條 pipeline（Ticket Analysis / Release Note Update / Periodic Feedback Review）加上「輪詢新票 → 自動回覆」即時路徑。理由：對齊產品架構規格與 Clarify，8 小時內可 demo。
- Demo UI 用一個簡單頁面（`docs/design/architecture.md` 草圖是 Streamlit：左餵票、中看教學、下看曲線）。UI **只觸發、只展示**，不在 UI 裡決定 CREATE／擋票。可改框架，但不得做成複雜 dashboard。
- 邏輯 9 表：圖譜關係與 Tutorial 版本在 HydraDB；聚合／輪詢 SQL 在 hotdata。不要為了「方便」再加業務表。
- LLM 只負責把 `resolution_steps` 收成 TutorialVersion 五欄（title / problem / prerequisites / steps / expected_outcome）。聚集 topic 在 demo 用 Bitext `intent` 標籤，規格不驗演算法。
- 節點參數以 `.rocketride/schema/` 為準（相關節點示例：`db_hydradb`、`tool_cognee`、`agent_rocketride`、`llm_bedrock`、`llm_anthropic`、`db_postgres`、`webhook`）。沒有對應 schema 就不要發明 node。
- 定期 Review／輪詢週期不規定，demo 手動觸發即可。

### 4.5 open questions 的處理原則

Clarify 尚未 resolved、且作用中規格也還沒寫死的項目，才是 open question。撰寫當下請重掃 `.clarify/data/` 與 `.clarify/features/`（未搬進 `resolved/` 者）。截至 2026-09-11，overview 為 **0 題待處理**。

處理方式：

- 必須在設計文件標示為 **open question**，並說明影響哪個模組；
- 可提出 hackathon 最省選項與傾向，但**不得寫成已確認決策**；
- 不得自行修改 `.feature`、`erm.dbml` 或 `.clarify/` 來「補上」規格。
- 實作細節（CLI 旗標、Streamlit widget 名稱、檔案目錄微調）是 design decision，不是規格 open question。

因此本階段不得以「規格還有未決」為由迴避**已定案範圍**的設計。已定案的 11 個 Feature、訊號門檻、生命週期、三條指標必須寫完。

## 5. 必做分析

在寫 design 前完成下列內部分析，最終文件只呈現結論與證據。

### 5.1 Spec-to-Design 對照

逐條比對 `docs/spec/features/*.feature` 的 `Rule:` 與設計中的實作位置，標示每條由哪一層負責（Cognee / HydraDB / hotdata / RocketRide pipeline / Rote / Demo UI）。**不得有規則無人負責。**

規則數以實際檔案為準：撰寫時自行統計 `Rule:` 數量，不要沿用任何舊數字。

### 5.2 現況 vs 目標盤點

逐項比較 repo 現況與目標：

- 不存在（需從零建立）
- 僅有規格／草稿
- 規劃中且本 design 要定義清楚的模組邊界
- 非本階段產出（implementation plan 屬 `docs/plan/`，本階段不寫）

### 5.3 約束衝突稽核

至少檢查設計是否在任何一處：

- 做成 ShowMe／MCP overlay／Playwright 教人點頁面；
- 做成 multi-agent 或第二個 controller process；
- 引入人工審核佇列、SLA 監測、Slack 入庫、Customer 表、先備圖譜邊、教學影片；
- 讓 Release Note 觸發 CREATE；
- 讓 Rote 重放「解票步驟」而非攔截流程；
- 要求建立 Tutorial 前必須操作真實產品 UI；
- 把 Session 做成與本產品無關的 MCP 狀態機；
- 把 Copilot / Meeting Preparation 範例寫回 Bitext 領域；
- 沿用已被 clarify 推翻的草稿敘述（見下表）。

**草稿已被推翻、design 不得再寫回去：**

| 草稿舊敘述 | 現行裁決 |
|---|---|
| 產品是 Copilot IT／Champion 知識庫 | 客服 deflection 教學生成器；主詞是顧客 |
| Tutorial 先入審核佇列再發布 | 建立即 published；不建審核功能 |
| 必須實際操作產品／API 才准生成教學 | 不需；來源是 `resolution_steps` |
| Slack Q&A 納入建圖 | 不納入 |
| 先備知識做成圖譜邊 | `prerequisites` 自由文字 |
| Release Note 也可觸發 CREATE | Release 只 UPDATE / RETIRE |
| Rote 重放解票步驟或錄教學影片 | 只重放攔截流程 |
| 監測票量暴增／SLA | 不進作用中規格 |
| 建 Customer 表 | 只用 `Ticket.customer_ref` |
| Example 用 Meeting Preparation | 改 Bitext `cancel_order` 等 |

### 5.4 相依順序分析

建立 8 小時可 demo 的交付切片 DAG。每一片結束後應能手動驗證（例如：先能匯入種子票建 UserProblem，再能餵一張同類票 escalated，再能第三張 CREATE 並 published，再能第四張 deflected，再能 Rote 重放，再能 Release 改 Step 3）。不要先做 stretch。

## 6. Output Structure

將結果寫入 `docs/design/tutorial-generator.md`，至少包含：

1. 文件目的與狀態
2. Source of Truth 與衝突裁決
3. 產品範圍：Goals / Non-Goals（明列不做：審核佇列、SLA 監測、Slack、Customer 表、先備邊、教學影片、複雜 dashboard、ShowMe／MCP）
4. 現況基線（repo 實際只有哪些檔）
5. 目標架構與相依方向（Cognee / HydraDB / hotdata / RocketRide / Rote / Snyk；單向資料流＋寫回）
6. 端到端流程：建圖 → 輪詢新票 → 自動回覆／升級 → 分析 → CREATE → Feedback Review → Release 入庫與 UPDATE／RETIRE → 重放 → 算指標
7. 三條 RocketRide pipeline 與即時路徑的契約（觸發、讀哪些表／圖、寫哪些欄、成功／失敗）
8. Tutorial 生命週期狀態機（CREATE / UPDATE / REFINE / KEEP / RETIRE；draft / published / retired）
9. 資料模型對應（`erm.dbml` 9 表 → HydraDB 節點／關係與 hotdata SQL；不發明第 10 表）
10. 圖譜關係（`asks_about`, `explains`, `refers_to`, `changes`, `supersedes`）與多跳查詢「哪些 Tutorial 受這次 Release 影響」
11. Demo 資料策略（Bitext 種子 vs 現場餵票；三個主打 topic）
12. 學習指標（三條公式、分子分母、由 hotdata 計算）
13. Demo UI 邊界（只觸發／展示；決策在 Agent）
14. 錯誤與異常語意（對齊 `Then 操作失敗`；open 的錯誤碼不得假裝已定）
15. 測試策略（如何用十一份 `.feature` 驗收；不要發明例子當需求）
16. 交付切片與相依順序（對齊約 8 小時）
17. Demo 當日風險（帳號、CLI、Bedrock／RocketRide 連線、Snyk 掃描時機）— 與規格 open question 分開
18. 假設、限制與 open questions（沒有新的就寫「無新發現」；未 resolved 的 clarify 項要列）
19. 實際讀取的 source inventory

## 7. Design Quality Rules

- 具體定義資料流、負責模組、輸入、輸出、不變條件與失敗行為。
- **不使用「適當處理」「之後補上」「視情況」等不可驗證的描述。**
- 不新增規格未提及的產品能力。
- 明確區分 hackathon 約束、clarified decision、design decision 與 open question，並標示來源。
- 清楚標示假設與限制；不要把假設寫成已確認事實。
- 每個設計決策用一兩句話解釋「為什麼」——這是 8 小時 hackathon，選最簡單能 demo 學習迴圈的。
- 偏好最簡單且完全滿足現行規格的做法；不做投機性抽象、設定與間接層。
- 不公開 private chain-of-thought；只記錄證據、精簡 rationale 與決策。

---

## 8. 禁止事項

- 不修改 production code（目前也還沒有）、`.feature`、`erm.dbml`、`.clarify/` 或 `design-draft.md`。
- 不建立 implementation plan 或工作分解清單以外的「假進度」。交付切片只寫在 design 第 16 節，不是另開 `docs/plan/`。
- 不安裝 dependency、不執行 `uv` / `npm install`、不啟動 Cognee／HydraDB／hotdata／RocketRide、不 deploy。
- 不建議 chrome-devtools-mcp、ShowMe overlay、sidecar、第二個 agent、K8s。
- 不把五層做成「只寫進架構圖、沒有對應 Feature」。
- 不把 §草稿 的 Copilot／審核佇列／操作產品 UI／Slack 當成現行架構。
- 不聲稱尚未存在的模組、函式或測試已完成。
- 不因外部工具不可用就捏造查證結果。
- 不把 ShowMe 四工具、`wait_for_user`、Chat Room、JWT、socket.io 等複製殘留寫進本文件。
- 不在文件中寫入 `.env` 的真實金鑰。

## 9. Self-review Gate

寫完後自行檢查並直接修正：

1. **Placeholder**：不得有未解釋的 TBD/TODO。
2. **約束合規**：逐條對照第 4.1 與 4.2 節。
3. **規則覆蓋**：每個 `Rule:` 都有負責層（自行統計條數）。
4. **現況/目標分離**：沒有把規劃目錄寫成已存在。
5. **決策層級**：clarified decision 沒有被改寫；4.4 若沿用或改用都有標示。
6. **Open questions**：沒有把已定案重寫成未定；新歧義依 4.5 標示，未擅自改規格。
7. **Draft 脫鉤**：5.3 表格中的舊敘述沒有回流。
8. **可驗證性**：每個關鍵不變條件都有驗收方向。
9. **簡單性**：每段設計能用一兩句話對評審解釋「這一層在迴圈裡做什麼」。
10. **來源純淨**：沒有 ShowMe、Qoder overlay、`hackathonQoder`、`18652FSE`、Copilot Meeting 範例。
11. **五層負荷**：Cognee / HydraDB / hotdata / RocketRide / Rote（以及 Snyk）都有對應的、會重複發生的工作，不是一次性 import。
