# Design：從已釐清規格產生 Training Knowledge Base 的 canonical design

## 任務

你是一位資深工程師。請依 formulation、discovery、clarify 三個階段的輸出，建立 **自我優化 Training Knowledge Base** 的 canonical design。

本專案是 Data and AI Hackathon 的參賽作品。產品主軸是替 indie builder **持續產生、更新、優化使用者教學**，並用真實結果衡量有沒有教會人。Self-learning 的定義是 *past outcomes change future system behavior*，不是 fine-tuning。

兩條必須能 demo 的 loop：

1. Ticket → Knowledge Gap → Tutorial → Feedback／重開票 → REFINE + Authoring Rule → 下一篇寫得更好
2. Release → 圖譜反查受影響步驟 → 只改那一步 → UPDATE 或 RETIRE

Tutorial 生命週期 **CREATE / UPDATE / REFINE / KEEP / RETIRE** 是內核。CREATE 只由 Ticket Analysis 決定；Release 只驅動 UPDATE／RETIRE。

本階段只做設計文件，**不實作 production code、不產生 implementation plans、不改規格**。唯一允許寫入的輸出是：

`docs/design/training-kb.md`

請使用繁體中文與台灣常用技術用語。Repo root：`AWS-Hackathon/`（本檔所在 repo）。路徑一律用相對 repo root 的寫法。

## 1. 任務模式與完成條件

模式：spec-first + hackathon-scoped application design。

完成條件：

1. 完整盤點第 2 節指定來源，而不是只讀檔名或舊 design 標題。
2. 分清楚 **hackathon / 產品約束**（不可違反）、**clarified decision**（已定案）、**design decision**（本文件所做的選擇）與 **open question**（規格未寫死）四種來源層級，每一項設計都要能被歸類。
3. 對互相衝突的敘述做單一、可追溯的裁決。草稿與舊 design 早於 clarify；被 clarify 推翻的敘述以 clarify 與現行 `erm.dbml` / `.feature` 為準。**不要默默選邊**；衝突必須寫進 design 的衝突裁決節。
4. 產生可直接用來拆實作切片與撰寫驗收測試的設計文件。
5. 不把規劃中的目錄、ASCII 圖、舊 design 或文件敘述誤寫成已實作。目前 repo **幾乎只有 docs**，沒有 entry point、依賴或測試。
6. 不引入 MVP 以外的能力。MVP 只保證兩條 loop 可 demo，以及規則轉移（Tutorial A 的教訓變成可驗證的 Authoring Rule）。

Hackathon 原則：能 demo「缺口變成教學、弱教學被改寫、改版只動受影響步驟、規則可轉移」就好。怪輸入、完整列舉、正式站、多租戶、人工審核佇列，能不做就不做。不要為尚未發生的企業 Copilot 版或複雜 dashboard 做架構。

## 4. 強制設計決策

除非上述來源有更新且有明確證據，design 必須保持下列決策不變。

### 4.1 Hackathon / 產品約束（違反即超出 MVP）

- **形態：** 單一協調流程的 Training Knowledge Base。Agent 自由度只在接入層選 adapter。核心三條 pipeline 是預定義 Step Functions，不是 multi-agent platform，也不是 MCP server。
- **執行環境（草稿對照，clarify 未改平台）：**

  | 職責 | AWS 對應 | 本專案負責 |
  |---|---|---|
  | 抽實體／關係、寫作、確認 | Bedrock（官方文件核對模型） | Ticket／Release／Feedback 正規化之後的分析與改寫 |
  | 語意向量 | Titan Text Embeddings V2（1024 維，存在 `Ticket.embedding`） | 分群、safety_net、alias 未命中時的 Feature 搜尋 |
  | 持久化 | DynamoDB 單表 + GSI `by_target` + S3 教學全文／diff | 十個邏輯實體與邊；**不是**十張 SQL 表 |
  | 編排 | Step Functions × 3 + EventBridge 每日 Periodic Feedback Review | Ticket Analysis／Release Note Update／Feedback Review |
  | 接入 | 一個已驗簽 GitHub webhook（Lambda Function URL）；其餘手動上傳 | Discord／email／changelog／Feedback 不開放未驗證公開入口 |
  | 程序性記憶 | DynamoDB `PROC#`（Rote 三層：簽名 → Jaccard → Agent） | 只學 Ticket／Release；Feedback 不進 PROC |
  | 安全 | Snyk 掃依賴與 secrets | 不把 key 寫進 repo |

- **領域：** MVP 單一專案。Demo 腳本以草稿 §16 的 prepare-meeting／PR #42 為敘事骨架，但**數字與門檻以 clarify 為準**（例如正式弱教學 n≥10，Demo 隔離 n≥8；recurring 同類 5 筆；cosine 0.85）。
- **發布：** `published_at` 空＝未發布；publish 成功才寫入非空 `published_at` 並切換 `current_version`。**不是**建立即 published。不做版本狀態機，也不做人工審核佇列。
- **回饋：** 顯性 Feedback（rating 1..5、可空 category／comment）＋瀏覽事件 `TUTORIAL_VIEW`＋同題重開票。同一穩定使用者 ID 貫穿 `Ticket.author`、`Feedback.user`、`TUTORIAL_VIEW.user`。
- **Release 只驅動 UPDATE／RETIRE**；CREATE 只由分析 Ticket 決定。對不到 Feature 則保留 gap，不建 Tutorial，不新建 Feature。
- **Rote 只學接入正規化流程**（Ticket／Release）。不重放「解票步驟」、不產教學影片、不重放 Feedback。
- **範圍外（不做）：** 完整 LMS、影片、Teams／Microsoft Graph、企業認證、複雜 dashboard、多 persona、fine-tuning、multi-agent 協作、瀏覽器合成使用者、多租戶、人工審核佇列、未驗證公開 webhook、第十一個業務實體。
- **秘密：** design 階段不安裝套件、不 deploy、不啟動服務、不寫真實金鑰。

### 4.2 規劃中的系統切分（不可先發明另一套）

design 依此切模組邊界，**目錄尚未存在**，不要改成 microservices：

```text
AWS-Hackathon/
├── docs/spec/                         規格與本 prompt
├── docs/design/training-kb.md         本階段唯一輸出
└── （實作目錄由 design 定義，須對應接入／Rote／Step Functions／DynamoDB＋S3／Analytics／Demo，不得拆多服務）
```

資料流（單向為主，學習結果寫回）：

```text
GitHub webhook 或手動上傳
        → Rote 三層（簽名／Jaccard／Agent）正規化
        → Ticket Analysis ／ Release Note Update ／ 固定保存 Feedback
        → DynamoDB 單表 + S3 內容
        → EventBridge 每日 Feedback Review
        → CREATE / UPDATE / REFINE / KEEP / RETIRE / 提出規則
        → publish 成功才切 current_version
        → Analytics 聚合評分、重開票、規則成效、Bedrock 呼叫數
```

### 4.3 已釐清的規格決策（clarify 定案，不得推翻）

撰寫時以各檔「解決記錄」與作用中 `erm.dbml`／`.feature` 為準。下列是 2026-09-13 已 resolved 的摘要；若與檔案衝突以檔案為準。不要把摘要寫成比解決記錄更權威。

**資料（十實體）**

| 決策 | 內容 |
|---|---|
| 實體 | `TUTORIAL`、`TUTORIAL_VERSION`、`TUTORIAL_STEP`、`FEATURE`、`TICKET`、`RELEASE`、`FEEDBACK`、`TUTORIAL_VIEW`、`AUTHORING_RULE`、`PROVEN_WORKFLOW`。不建 User、UserProblem、Customer、Project。 |
| 識別 | MVP 單一專案。邏輯關聯用裸 ID；`VERSION#` 等前綴只在 DynamoDB 邊與查詢。 |
| Ticket | 對 0 或 1 個 Feature。接入必填 `id, source, text, author, ts, project_id`。向量只存 `embedding`（1024 維），不持久化 `embedding_ref`。 |
| Step | 每步恰好 1 個 Feature。 |
| Feature | 第一次 PK 不再變；改名只改 `name`／`aliases`。同一專案 alias 必須唯一，也不可與其他 Feature 的 name 撞名。 |
| 版本 | `published_at` 空＝未發布。同一邏輯變更重試重用原版號。`reason`：`gap:<cluster_id>`／`release:<id>`／`feedback:<n> 則 <category>`。 |
| 同題 | 首版 `gap:<cluster_id>` 寫入 `Tutorial.cluster_id`，之後不變。 |
| 後繼 | `Tutorial.successor` 可空裸 slug；資料狀態只用 `retired`；`obsolete` 是顯示文字。 |
| 回饋 | `user` 必填。只有評分仍有效。每個新 `Feedback.id` 計一筆；同一提交重送不另計。核定類別：找不到按鈕、缺少資訊；未知→待分類。 |
| 規則 | `rules_applied` 是套用關係權威。`derived_from` 恰好一個裸 `version_id`。`evidence` 只存 Feedback ID 清單。MVP `applies_when` 僅單一 `step.type` ∈ {click_ui, input, read}。 |
| PROC | 同寄件者＝來源網域＋adapter 類型。`fail_count` 連續失敗，成功歸零，達 3 退役。`success_count` 每次完整成功 +1；重放須 `active` 且 ≥3。 |
| 瀏覽 | `TUTORIAL_VIEW` 必填 `tutorial_version`、`user`、`ts`。PK 格式未指定，不假設 `VIEW#`。 |

**訊號 → 動作（門檻已定案）**

| 訊號 | 決定 |
|---|---|
| Ticket 分群 | 與群中心 cosine ≥ 0.85 取最高；否則開新群。UTC 當日＋前 13 日、同群 ≥5 才 recurring。 |
| recurring 且對到 Feature、尚無有效教學 | CREATE。`active` 即使未首次發布也算已有教學；`retired` 不算。對不到 Feature：保留 gap，不建 Tutorial，不新建 Feature。 |
| Release 多 Feature | 拆子 Release，共用 `source_event_id`，子 `id` 仍須全域唯一。 |
| 改版命中 | 只改目前已發布且為 `current_version` 的步驟。alias 失敗的 renamed 才是重大改名並跑 safety_net；反查為零仍獨立觸發。未確認→記錄未命中、KEEP、不建新版。向量確認 Feature 須 cosine ≥ 0.85。 |
| 弱教學 | 只看已發布 `current_version` 的全部有效回饋。平均 < 3.5 **且** 正式 n≥10（Demo 隔離 n≥8）**且** 同一 category ≥5。 |
| REFINE | 只重寫診斷命中步驟。完成後記已處理證據；無新有效證據不再 REFINE。無有效步驟→記「無可改步驟」，不建新版。 |
| 提出規則 | 不必先過弱教學門檻；同一 TutorialVersion 同類 ≥5 即可。正式寫作只讀 `active`。 |
| 升 active | 套用組平均評分嚴格提高 **且** 重開票率嚴格下降。對照＝同篇套用前已發布版。只在完整核定種子驗證批次後改狀態。 |
| 退役規則 | 連續兩個不重疊核定種子批次未達 F30 才退役。衝突：模型出結構化判定，Analytics 把該 **candidate** 退役，不自動覆蓋 active。curation 只建相近群組供人看，不自動合併。 |
| 發布 | S3 靜態 docs 站＋feedback widget。內容與關聯不齊不可 publish。publish 成功才切 `current_version`。同篇 Release／Feedback 依接受順序串行。 |
| Catch／Agent 失敗 | 整次失敗、不發布；不寫入合法物件或成功 PROC。來源依既定契約重試。 |
| 重開票率 | 分母＝窗口內可識別瀏覽；分子須瀏覽早於同群開票。零分母顯示 N/A，不得當改善。Demo 7→2 是筆數。無評分顯示尚無評分，驗證不用該版平均。跨版評分：每版平均再等權。 |

**Demo 與驗收**

- Demo 指標由**完整 seeded 回饋／瀏覽／Ticket**算出；2.9、4.4、7、2 必須能重現。7 與 2 仍是重開票筆數。
- Tutorial B 規則開關對照是隔離 Demo，不寫入正式教學與統計。
- 缺少原始 Example 時，可用**明示合成且經確認**的驗收資料；不得描述為原始觀測。不得為了補例而改規格契約。
- 失敗一律規格語意 `Then 操作失敗`；design 指出由哪一層回傳失敗，不得發明規格沒有的 HTTP 狀態或錯誤碼表。

### 4.4 預設 design decision（非 clarify 定案，可重新論證）

以下可在設計文件中改採其他做法，但**必須標示為 design decision 並附理由**，不得默默改。

- 三條 Step Functions（Ticket Analysis／Release Note Update／Periodic Feedback Review）加一個驗簽 GitHub webhook 與手動上傳入口。理由：對齊草稿與 F08，8 小時可 demo。
- Analytics 用 Lambda 對 DynamoDB 聚合，不另開 warehouse。理由：草稿已把 hotdata 對成這條路徑。
- Demo UI 只觸發與展示（餵事件、看教學、看曲線）。決策在 pipeline，不在 UI。
- 定期 Review 的 EventBridge 排程可在 demo 改手動觸發；契約仍是「每日只看已發布 current_version」。
- 節點／模型／免費方案配額以官方文件為準；沒查到就標 needs confirmation，不捏造。
- `TUTORIAL_VIEW` 的 PK／SK 由 design 選定並標為 design decision（規格故意不假設 `VIEW#`）。

### 4.5 open questions 的處理原則

Clarify 佇列在 2026-09-13 已為 **0 題待處理**（84 已歸檔）。不要把 `@Missing` Example 或 `#TODO` 重新開成產品問題。

仍可標為 open question 的只有：

- 作用中規格**明確說未定義**、且會改變模組邊界、安全、成本或使用者可見行為的項目（例如 metadata item 的 SK、瀏覽事件 PK 格式、Retry 次數）；
- 官方文件查不到、會影響選型的平台限制。

處理方式：

- 必須在設計文件標示為 **open question**，並說明影響哪個模組；
- 可提出 hackathon 最省選項與傾向，但**不得寫成已確認規格決策**；
- 不得自行修改 `.feature`、`erm.dbml` 或 `.clarify/` 來「補上」規格。
- 實作細節（CLI 旗標、畫面 widget 名稱、CDK 資源名）是 design decision，不是規格 open question。

因此本階段不得以「規格還有未決」為由迴避**已定案範圍**的設計。已定案的 13 個 Feature、門檻、生命週期、指標必須寫完。

## 5. 必做分析

在寫 design 前完成下列內部分析，最終文件只呈現結論與證據。

### 5.1 Spec-to-Design 對照

逐條比對 `docs/spec/features/*.feature` 的 `Rule:` 與設計中的實作位置，標示每條由哪一層負責（Ingress／Rote／Step Functions／DynamoDB＋S3／Bedrock／Analytics／Demo UI）。**不得有規則無人負責。**

規則數以實際檔案為準：撰寫時自行統計 `Rule:` 數量，不要沿用任何舊數字。

### 5.2 現況 vs 目標盤點

逐項比較 repo 現況與目標：

- 不存在（需從零建立）
- 僅有規格／草稿
- 規劃中且本 design 要定義清楚的模組邊界
- 非本階段產出（implementation plan 屬後續，本階段不寫）

### 5.3 約束衝突稽核

至少檢查設計是否在任何一處：

- 做成 ShowMe／MCP overlay／Playwright 教人點頁面；
- 做成 multi-agent 或第二個 controller process；
- 引入人工審核佇列、企業 Graph、教學影片、第十一個業務實體；
- 讓 Release Note 觸發 CREATE；
- 讓 Rote 重放「解票步驟」或學習 Feedback；
- 把建立版本當成已發布（漏掉 `published_at`／publish）；
- 刪除或忽略 `TUTORIAL_VIEW`，或把重開票改回「種子對照即可」；
- 把 HydraDB／hotdata／RocketRide／Bitext／UserProblem 寫回作用中架構；
- 沿用已被 clarify 推翻的草稿敘述（見下表）。

**舊稿已被推翻、design 不得再寫回去：**

| 舊敘述 | 現行裁決 |
|---|---|
| 產品是客服 deflection／Bitext／UserProblem | Training Knowledge Base；無 UserProblem 實體 |
| 9 表；邏輯模型在 HydraDB／hotdata | 10 個邏輯實體；DynamoDB 單表＋GSI＋S3 |
| 建立即 published；status = draft／published | `published_at` 空＝未發布；publish 成功才切 `current_version` |
| 無瀏覽事件、暫不算重開票率 | `TUTORIAL_VIEW`；穩定使用者 ID；先瀏覽再開票 |
| Feedback 進 PROC／啟動 Step Functions | 固定保存即成功；不進 PROC |
| 多來源公開 webhook | MVP 一個已驗簽 GitHub webhook；其餘手動上傳 |
| 弱教學 n≥3 或 Demo 8 冒充正式 10 | 正式 n≥10，Demo 隔離 n≥8；同類 category ≥5 |
| 升 active 只需評分 | 評分嚴格提高 **且** 重開票率嚴格下降 |
| 九實體不可加第十 | 第十個是 `TUTORIAL_VIEW`，不是 User |
| Example 用 Meeting Preparation 當規格契約 | Demo 敘事可沿用草稿腳本，門檻與欄位以 clarify 為準 |

### 5.4 相依順序分析

建立可 demo 的交付切片 DAG。每一片結束後應能手動驗證（例如：先能驗簽接入一則 GitHub 事件，再能分群並在對到 Feature 時 CREATE 未發布版，再能 publish 後切 `current_version`，再能記瀏覽與回饋，再能 Release 只改一步，再能提出 candidate 而不改正式寫作）。不要先做 stretch。

## 7. Design Quality Rules

- 具體定義資料流、負責模組、輸入、輸出、不變條件與失敗行為。
- **不使用「適當處理」「之後補上」「視情況」等不可驗證的描述。**
- 不新增規格未提及的產品能力。
- 明確區分 hackathon 約束、clarified decision、design decision 與 open question，並標示來源。
- 清楚標示假設與限制；不要把假設寫成已確認事實。
- 每個設計決策用一兩句話解釋「為什麼」——選最簡單能 demo 兩條 loop 與規則轉移的。
- 偏好最簡單且完全滿足現行規格的做法；不做投機性抽象。
- 不公開 private chain-of-thought；只記錄證據、精簡 rationale 與決策。

## 8. 禁止事項

- 不修改 production code、`.feature`、`erm.dbml`、`.clarify/` 或 `docs/spec/draft/`。
- 不建立 implementation plan 或另開 `docs/plan/` 假進度。交付切片只寫在 design 第 16 節。
- 不安裝 dependency、不啟動 AWS 服務、不 deploy。
- 不建議 chrome-devtools-mcp、ShowMe overlay、sidecar、第二個 agent、K8s。
- 不把五層做成「只寫進架構圖、沒有對應 Feature」。
- 不把舊客服 deflection／HydraDB／hotdata／RocketRide／Bitext／九表當成現行架構。
- 不刪 `TUTORIAL_VIEW`，不把 D23／D24 寫回 C。
- 不聲稱尚未存在的模組、函式或測試已完成。
- 不因外部工具不可用就捏造查證結果。
- 不在文件中寫入真實金鑰。

## 9. Self-review Gate

寫完後自行檢查並直接修正：

1. **Placeholder**：不得有未解釋的 TBD/TODO。
2. **約束合規**：逐條對照第 4.1 與 4.2 節。
3. **規則覆蓋**：每個 `Rule:` 都有負責層（自行統計條數）。
4. **現況/目標分離**：沒有把規劃目錄寫成已存在。
5. **決策層級**：clarified decision 沒有被改寫；4.4 若沿用或改用都有標示。
6. **Open questions**：沒有把已定案重寫成未定；新歧義依 4.5 標示，未擅自改規格。
7. **Draft 脫鉤**：5.3 表格中的舊敘述沒有回流。
8. **可驗證性**：每個關鍵不變條件都有驗收方向。
9. **簡單性**：每段設計能用一兩句話對評審解釋「這一層在迴圈裡做什麼」。
10. **來源純淨**：沒有 ShowMe、Bitext UserProblem、HydraDB／hotdata／RocketRide 當作用中儲存、九表、建立即 published。
11. **十實體**：`TUTORIAL_VIEW` 仍在；物理儲存仍是單表＋GSI＋S3。
12. **平台查證**：Bedrock／DynamoDB／Step Functions 的用法有官方來源或標 needs confirmation。

## 10. 最終回覆格式
